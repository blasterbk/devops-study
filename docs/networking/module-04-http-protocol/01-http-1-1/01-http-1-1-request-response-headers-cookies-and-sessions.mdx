# Chapter 1 — HTTP/1.1: Request-Response Lifecycle, Headers, Cookies & Sessions

> **Goal:** Master the semantics, formatting, and operational mechanics of HTTP/1.1 (RFC 2616 & RFC 7230–7235). Understand the textual request-response wire format, status code classes, core headers, persistent TCP connections (`Connection: keep-alive`), statelessness, and state management via HTTP cookies and sessions.
>
> By the end of this chapter, you will understand:
> 1. The plain-text structure of HTTP/1.1 requests (Method, URI, Version, Headers, Body) and responses
> 2. HTTP Status Code ranges ($1xx, 2xx, 3xx, 4xx, 5xx$) and correct semantic usage
> 3. Core HTTP headers: Content-Type, Content-Length, Host, Transfer-Encoding: chunked, and Cache-Control
> 4. Persistent connections (`Keep-Alive`) vs non-persistent HTTP/1.0 connections and Pipelining
> 5. Statelessness vs State Management: `Set-Cookie` flags (`HttpOnly`, `Secure`, `SameSite`), Session IDs, and JWTs
> 6. CLI exploration using `curl`, `openssl s_client`, and `socat`

## Real-Life Analogy

Think of HTTP/1.1 communication as **a formal written order slip system at a restaurant**:

- **The Request (Order Slip):**
  - You hand the waiter a slip: *"GET /lunch/burger HTTP/1.1, Host: restaurant.com, Accept: application/json"*.
- **The Response (Tray & Receipt):**
  - The kitchen sends back a tray with a slip: *"HTTP/1.1 200 OK, Content-Type: application/json, Content-Length: 450"*, followed by the food payload.
- **Statelessness & Cookies (The Customer Loyalty Card):**
  - The waiter has zero memory of previous customers. To remember you, the waiter clips a numbered stamp to your receipt: *"Set-Cookie: user_session=xyz987"*. Next time you order, you hand that stamp back, allowing the kitchen to look up your open tab (**Session State**).

### 1. HTTP/1.1 Wire Format

```http
GET /index.html HTTP/1.1\r\n
Host: www.example.com\r\n
User-Agent: Mozilla/5.0\r\n
Accept: text/html,application/xhtml+xml\r\n

\r\n
```

### 3. Cookie Security Attributes

```http
Set-Cookie: session_id=s9x2m48b1; Secure; HttpOnly; SameSite=Strict; Path=/; Max-Age=3600
```

- **`Secure`:** Instructs browser to transmit cookie exclusively over encrypted HTTPS connections.
- **`HttpOnly`:** Prevents client-side JavaScript (`document.cookie`) from reading the cookie, mitigating Cross-Site Scripting (XSS) session theft.
- **`SameSite=Strict / Lax`:** Restricts cookie transmission on cross-site requests, mitigating Cross-Site Request Forgery (CSRF).

## Hands-On Lab: Raw HTTP/1.1 Inspection via CLI

```bash
# Step 1: Send a raw HTTP/1.1 request with headers using cURL verbose mode
curl -v -H "Accept: application/json" https://httpbin.org/get

# Step 2: Test persistent keep-alive by sending multiple requests over one socket
curl -iv --keepalive-time 60 https://httpbin.org/get https://httpbin.org/headers

# Step 3: Inspect HTTP response headers and cookies
curl -I https://httpbin.org/cookies/set?user_session=active_token_123

# Step 4: Perform a manual raw HTTP/1.1 GET query using OpenSSL over TLS
echo -e "GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n" | openssl s_client -connect example.com:443 -quiet
```

## Common Interview Questions

**Q1: What is the purpose of the `Host` header in HTTP/1.1 and why was it made mandatory?**

In HTTP/1.0, the `Host` header did not exist. When web hosting providers began running multiple distinct domain names (Virtual Hosts) on a single public IP address, the web server could not determine which domain's website the client wanted to load. HTTP/1.1 made the `Host` header mandatory so the web server (e.g. NGINX `server_name`) routes the request to the correct VirtualHost configuration.

**Q2: What is the difference between `Transfer-Encoding: chunked` and `Content-Length`?**

`Content-Length` specifies the exact byte size of the payload body in advance. When a server streams dynamically generated content (e.g., database exports or large LLM tokens) whose total size is unknown upfront, it uses `Transfer-Encoding: chunked`. The payload is transmitted in a series of hex-encoded byte-length chunks followed by a zero-length chunk (`0\r\n\r\n`) to terminate the stream without closing the TCP connection.

**Q3: What is the difference between HTTP Status 401 Unauthorized and 403 Forbidden?**

- **401 Unauthorized:** Actually means **Unauthenticated**. The client has not provided credentials (or provided invalid credentials) and must authenticate via `Authorization` header.
- **403 Forbidden:** The client is authenticated and their identity is known, but they do not have sufficient RBAC permissions to access the requested resource. Retrying with identical credentials will always fail.

**Q4: What is Head-of-Line (HoL) blocking in HTTP/1.1 and how did HTTP/1.1 Pipelining attempt to fix it?**

In HTTP/1.1, multiple requests sharing a single persistent TCP connection must be processed and returned sequentially in strict FIFO order. If Request 1 requires a slow 5-second database query, Requests 2 and 3 are blocked behind it (**HTTP Head-of-Line blocking**). HTTP/1.1 Pipelining allowed clients to send multiple requests without waiting for responses, but servers were still forced to respond in exact arrival order, leading to widespread bugs and abandonment in browsers.

**Q5: How does HTTP caching work with `ETag` and `If-None-Match`?**

When a server sends a resource, it includes an `ETag` (a hash of the content, e.g. `ETag: "68ab2-12"`). On subsequent requests, the browser sends `If-None-Match: "68ab2-12"`. If the server verifies the resource has not changed, it returns **304 Not Modified** with zero payload body, saving bandwidth and accelerating page loads.
