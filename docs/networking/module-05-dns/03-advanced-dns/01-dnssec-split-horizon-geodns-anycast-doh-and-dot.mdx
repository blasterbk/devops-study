# Chapter 3 — Advanced DNS: DNSSEC, Split-Horizon, GeoDNS, Anycast, DoH & DoT

> **Goal:** Master modern enterprise and security architectures in DNS. Understand how DNSSEC provides cryptographic authenticity and data integrity via the Root-to-Leaf Chain of Trust, how Split-Horizon DNS isolates internal corporate assets from the public internet, how GeoDNS and Anycast optimize global user routing, and how encrypted DNS protocols (DoH, DoT) safeguard user privacy.
>
> By the end of this chapter, you will understand:
> 1. DNSSEC mechanics: Resource Record Signature (`RRSIG`), DNS Public Key (`DNSKEY`), Delegation Signer (`DS`), and Next Secure (`NSEC3`)
> 2. The cryptographic Chain of Trust from the ICANN Root zone (`.`) down to domain records
> 3. Split-Horizon (Split-Brain) DNS architectures for multi-cloud and internal VPC networks
> 4. GeoDNS and Latency-Based Routing using EDNS Client Subnet (ECS / RFC 7871)
> 5. BGP Anycast DNS: how a single IP address powers global sub-millisecond resolvers
> 6. Encrypted DNS: DNS-over-HTTPS (DoH / RFC 8484) on port 443 vs DNS-over-TLS (DoT / RFC 7858) on port 853

## Real-Life Analogy

Think of Advanced DNS as **upgrading from an unsealed paper postcard to a cryptographic biometric embassy courier network**:

- **Legacy DNS (Unsealed Postcard):**
  - Anyone on the postal route (ISP, rogue Wi-Fi router) can read what address you are asking for (**Zero Privacy**) or erase the return address with pencil and write their own phishing IP (**DNS Spoofing / Poisoning**).
- **DNSSEC (Wax Seal & Embassy Certificate Chain):**
  - The answer arrives with a cryptographic wax seal stamped by the King (**ICANN Root**), certifying the Ambassador's signature (**TLD**), certifying the local Mayor (**Authoritative NS**). You can mathematically prove nobody altered the address.
- **DoH / DoT (Armored Diplomatic Pouch):**
  - The entire query travels inside an encrypted bulletproof briefcase (**TLS 1.3**). Intermediate ISPs and Wi-Fi eavesdroppers cannot even see what domain name you are looking up.

### 2. Split-Horizon (Split-Brain) DNS

Split-Horizon DNS serves different DNS answers depending on the **source IP of the client**:
- **Internal Query (from VPC `10.0.0.0/16`):** Resolves `db.internal.corp` $\to$ `10.0.4.50` (Private IP).
- **External Query (from Public Internet):** Resolves `db.internal.corp` $\to$ `NXDOMAIN` or points to an external WAF/DMZ.

## Hands-On Lab: Validating DNSSEC & Querying DoH Endpoints

```bash
# Step 1: Query DNSSEC records (DNSKEY + RRSIG + DS) using dig
dig +dnssec +multiline cloudflare.com A

# Step 2: Verify the Authenticated Data (ad) flag in the DNS header
dig @1.1.1.1 +dnssec isc.org | grep -i "flags:"

# Step 3: Perform an encrypted DNS-over-HTTPS (DoH) query using curl
curl -H 'accept: application/dns-json' 'https://cloudflare-dns.com/dns-query?name=google.com&type=A'

# Step 4: Perform a DNS-over-TLS (DoT) query over port 853 using kdig (if available)
kdig -d @1.1.1.1 +tls-ca +tls-host=cloudflare-dns.com example.com 2>/dev/null || echo "kdig or drill can test DoT on port 853"
```

## Common Interview Questions

**Q1: What problem does DNSSEC solve, and does it encrypt DNS queries?**

DNSSEC provides **Data Origin Authentication** and **Data Integrity**; it guarantees that a DNS response truly came from the authoritative nameserver and was not tampered with in transit (preventing DNS cache poisoning). **DNSSEC does NOT provide encryption or privacy**; queries and answers remain plain text on the wire. Privacy requires **DoH** or **DoT**.

**Q2: What is the purpose of the KSK (Key Signing Key) vs ZSK (Zone Signing Key) in DNSSEC?**

- **ZSK (Zone Signing Key):** Used frequently to sign the zone's daily resource records (`RRSIG`). It has a shorter key length for fast performance and is rotated frequently (e.g. monthly).
- **KSK (Key Signing Key):** Used exclusively to sign the `DNSKEY` record containing the ZSK. The KSK's hash is stored in the parent zone's `DS` record. Separating them allows rotating the ZSK without updating the parent zone registry.

**Q3: How does GeoDNS utilize EDNS Client Subnet (ECS / RFC 7871)?**

Normally, an authoritative nameserver only sees the IP of the recursive resolver (e.g., Google `8.8.8.8`). If a user in Paris uses a public resolver in New York, the authoritative server would mistakenly return a US server IP. With **EDNS Client Subnet (ECS)**, the resolver forwards the client's first 24 bits (e.g. `Client: 194.50.12.0/24`), allowing GeoDNS to return the closest European IP.

**Q4: What is Zone Walking and how does NSEC3 prevent it?**

With legacy `NSEC` records, a query for a nonexistent domain returns the next alphabetically sorted record in the zone (e.g. *"Nothing exists between `admin` and `billing`"*). An attacker could issue repeated queries to map every hidden record in the corporate zone (**Zone Walking**). **NSEC3 (RFC 5155)** hashes the domain names with salt (`NSEC3 1 0 10 abcd...`), preventing attackers from discovering secret records.

**Q5: Why do network administrators prefer DoT over DoH in corporate enterprise environments?**

DoT operates on a dedicated port (**TCP 853**). Enterprise network security appliances can easily monitor, enforce, or block port 853 to ensure all corporate workstations use internal corporate DNS resolvers (for DLP and malware blocking). DoH multiplexes inside standard **HTTPS port 443**, making it virtually impossible for firewalls to distinguish encrypted DNS queries from normal web traffic without breaking TLS inspection.
