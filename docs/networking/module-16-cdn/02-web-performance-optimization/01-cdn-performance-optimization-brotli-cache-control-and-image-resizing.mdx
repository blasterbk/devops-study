### 1. Compression Algorithms: Gzip vs Brotli

```text

 │ Algorithm            │ Compression Ratio        │ CPU Decompression Speed  │ Best File Type                         │
 │──────────────────────┼──────────────────────────┼──────────────────────────┼────────────────────────────────────────┤
 │ **Gzip (deflate)**   │ Baseline ($1\times$)     │ Ultra-Fast               │ Universal legacy support (All clients) │

```

### 2. The `immutable` Directive for Cache Busting

Modern web frameworks (React, Vite, Next.js) append content hashes to build assets (e.g. `main.8f9b2c.js`). Because the filename changes whenever the code changes:

```http
Cache-Control: public, max-age=31536000, immutable
```

- **`max-age=31536000` (1 Year):** Instructs browser to cache file for 1 year.
- **`immutable`:** Informs the browser that the file contents **will never change**. The browser will **never send conditional 304 revalidation requests (`If-None-Match`)** even when the user clicks the browser Refresh button, delivering 0ms instant page loads.

## Common Interview Questions

**Q1: Why is Brotli significantly more effective than Gzip for text assets (HTML, CSS, JS)?**

Brotli utilizes a **pre-built static dictionary of over 13,000 common words, phrases, and HTML/CSS snippets** (such as `<html>`, `<div>`, `function()`, `background-color`, `https://`) embedded directly into the decompression library. When compressing web assets, Brotli replaces these entire words with tiny 1-byte dictionary references, achieving **20%–30% smaller file sizes than Gzip** with near-identical decompression speed.

**Q2: What is the `stale-if-error` Cache-Control directive and how does it protect website uptime?**

`stale-if-error=86400` instructs the CDN edge that if the origin server crashes, throws HTTP 500/502/503 errors, or suffers a database outage, the CDN should **continue serving the existing cached version for up to 24 hours** rather than displaying an error page to users. This guarantees high availability during transient backend failures.

**Q3: How does HTTP 103 Early Hints accelerate page rendering?**

In standard web requests, after the browser sends `GET /`, it sits completely idle for 200–500ms waiting for the origin server to query databases and generate the HTML. With **103 Early Hints**, the server immediately sends an informational 103 response containing `Link: </app.css>; rel=preload` headers within 5ms. The browser begins downloading critical CSS, fonts, and scripts **in parallel while the server is still rendering the HTML**, eliminating the network idle time and cutting Largest Contentful Paint (LCP) by up to 50%.

**Q4: What is the difference between client-side image resizing and Edge Image Optimization?**

- **Client-Side:** The server transmits a heavy 5MB (4000x3000) image. The mobile phone downloads 5MB over cellular data and uses CSS (`width: 300px`) to shrink it in browser memory (wasting bandwidth and draining battery).
- **Edge Optimization:** The CDN dynamically resizes the image to exactly 300x225, transcodes it to AVIF/WebP, strips EXIF metadata, and delivers a tiny 15KB file, reducing bandwidth by $99\%$.

**Q5: Why should you never set `Cache-Control: immutable` on an un-versioned file (like `/index.html`)?**

`immutable` informs the browser to never check with the server for updates under any circumstances until the TTL expires. If you set `immutable` on `/index.html` with a 1-year `max-age`, any user who visits your site will be stuck on that version for a year, even if you deploy critical bug fixes or new features! **Immutable must only be used on hashed assets (`app.v123.js`)**, while `/index.html` should use `Cache-Control: no-cache`.
