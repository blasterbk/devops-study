# Chapter 1 — CDN Architecture: Edge POPs, Origin Shielding & Tiered Cache Hierarchies

> **Goal:** Master the global architecture and caching topology of modern Content Delivery Networks (CDNs: Cloudflare, Fastly, CloudFront, Akamai). Understand how BGP Anycast terminates TCP and TLS connections within 2ms of the end-user, tiered caching hierarchies (L1 Edge $\to$ L2 Regional Core), Origin Shielding to protect centralized backend databases from cache stamps, and cache invalidation mechanics (Purge by URL, Tag, and Prefix).
>
> By the end of this chapter, you will understand:
> 1. The CDN value proposition: Latency reduction, bandwidth cost savings, and origin infrastructure offload (90%+ cache hit ratio)
> 2. Edge Points of Presence (POPs): BGP Anycast edge routing vs Unicast DNS Geo-routing
> 3. Tiered Cache Hierarchy: Edge Cache $\to$ Regional Cache $\to$ Origin Shield $\to$ Origin Server
> 4. Dynamic vs Static caching rules and Cache Key normalization (URI, Query Strings, Headers)
> 5. Cache Invalidation: Soft Purge vs Hard Purge, Surrogate-Keys / Cache-Tags
> 6. CLI diagnostic workflows with `curl` to analyze CDN cache headers (`CF-Cache-Status`, `X-Cache`)

## Real-Life Analogy

Think of a global CDN as **a worldwide network of local neighborhood convenience store branches for a master central bakery**:

- **Without a CDN (Traveling to Paris for Every Croissant):**
  - If a customer in Tokyo or Sydney wants a croissant (**Web page / Image**), they must fly across the globe to the central Paris bakery (**Origin Server**). The round-trip flight takes 20 hours (**250ms latency**), and the Paris bakery gets crushed with millions of international tourists (**Server Overload Crash**).
- **With a CDN (Local Neighborhood Corner Stores):**
  - The bakery deploys 300 refrigerated corner stores in Tokyo, Sydney, London, and New York (**Edge POPs**).
  - When the first Tokyo customer orders, the Tokyo store fetches one fresh batch from Paris, stores it in its display case (**Edge Cache**), and serves all subsequent 50,000 Tokyo customers in **5 seconds (2ms latency)**.
- **Origin Shield (The Regional Central Warehouse):**
  - A giant Tokyo regional warehouse sits between the local convenience stores and the Paris bakery. If 10 local Tokyo stores all run out of croissants simultaneously, they query the Tokyo Regional Warehouse (**Origin Shield**) instead of hammering the Paris bakery all at once.

## Deep Technical Content

### 1. The CDN Cache Response Headers

```text
 ┌──────────────────────┬────────────────────────────────────────────────────────────────────────┐
 │ Header Value         │ Operational Meaning & CDN State                                        │
 │──────────────────────┼────────────────────────────────────────────────────────────────────────┤
 │ **`HIT`**            │ Asset was served directly from the local Edge POP memory/disk cache.   │
 │ **`MISS`**           │ Asset was not present in cache; fetched from origin and stored in cache.│
 │ **`EXPIRED`**        │ Asset was present but TTL expired; revalidated with origin via `ETag`. │
 │ **`STALE`**          │ Asset TTL expired, but served stale due to `stale-while-revalidate`.   │
 │ **`BYPASS` / `DYNAMIC`| Request bypassed cache due to cookies/auth or custom rule (e.g. POST).│
 └──────────────────────┴────────────────────────────────────────────────────────────────────────┘
```

### 2. Request Coalescing (Collapsing Forward Requests)

If 5,000 users simultaneously request a viral video file that is not yet in cache:
- **Without Request Coalescing:** The Edge POP sends 5,000 duplicate backend requests to the Origin Server, crashing the database.
- **With Request Coalescing (Origin Shield):** The Edge POP holds 4,999 user requests in a waiting queue and sends **exactly 1 request** to the origin. When the payload returns, the edge broadcasts the single response to all 5,000 waiting users and saves it to cache.

## Common Interview Questions

**Q1: What is an Origin Shield in CDN architecture and why is it necessary?**

An Origin Shield is an intermediate, centralized caching tier (L2 cache) placed between hundreds of globally distributed Edge POPs and your origin datacenter. If 300 global Edge POPs experience a cache miss for a newly published asset simultaneously, all 300 POPs would hammer the origin at once (**Cache Stampede**). With an Origin Shield, all 300 POPs query the Shield; the Shield fetches the asset **exactly once** from the origin and distributes it to the edge POPs, reducing origin traffic by up to $99\%$.

**Q2: What is the difference between Purge by URL, Purge by Prefix, and Purge by Cache-Tag (Surrogate-Key)?**

- **Purge by URL:** Invalidates a single specific URL (e.g. `/images/banner.jpg`). Fast, but requires issuing thousands of API calls for bulk updates.
- **Purge by Prefix:** Invalidates an entire folder path (e.g. `/assets/v2/*`).
- **Purge by Cache-Tag / Surrogate-Key (Industry Best Practice):** During origin response, the server adds `Surrogate-Key: product_42 category_shoes`. When product 42 is updated, the server sends a single purge API call for tag `product_42`, instantly invalidating product pages, search result snippets, and recommendation widgets across the entire global CDN in $<150$ milliseconds.

**Q3: How does BGP Anycast enable sub-millisecond CDN routing compared to GeoDNS?**

- **GeoDNS:** Relies on DNS resolvers to estimate client geography and return a regional IP. If the user's recursive resolver is far away (e.g. public DNS resolver in another state), GeoDNS directs the client to the wrong datacenter. Furthermore, DNS TTL caching prevents instant failover during outages.
- **BGP Anycast:** The exact same IP address is announced from all 300+ global Edge POPs. The global Internet BGP routing fabric automatically forwards packets to the topologically closest physical POP. If a POP goes offline, BGP withdraws the route, triggering instant failover in seconds.

**Q4: What is the "Cache Key" in a CDN and why is Cache Key Normalization important?**

The Cache Key is the unique hash identifier used to store and retrieve an object from memory (Default: `Scheme + Hostname + Path + QueryString`). If users request `/item?color=red&size=L` and `/item?size=L&color=red`, standard CDNs treat them as two different cache keys (wasting cache memory). **Cache Key Normalization** reorders query parameters alphabetically, strips unnecessary tracking cookies (e.g. `utm_source`), and normalizes case to maximize the Cache Hit Ratio.

**Q5: What is the difference between a "Hard Purge" and a "Soft Purge" on modern CDNs (like Fastly or Cloudflare)?**

- **Hard Purge:** Immediately deletes the cached asset from edge memory. The next user request suffers a cache miss and must wait for a full origin round-trip.
- **Soft Purge (Stale Revalidation):** Marks the asset as expired (stale) in memory rather than deleting it. The CDN immediately serves the stale asset to the next user with zero latency while asynchronously triggering a background fetch to the origin to update the cache.
