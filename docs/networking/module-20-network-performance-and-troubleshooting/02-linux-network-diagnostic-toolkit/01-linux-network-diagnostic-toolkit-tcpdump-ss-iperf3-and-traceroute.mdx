# Chapter 2 — Linux Network Diagnostic Toolkit: tcpdump, ss, iperf3, traceroute & ethtool

> **Goal:** Master the battle-tested command-line diagnostic toolkit used by Senior Site Reliability Engineers (SRE) and Network Engineers to diagnose production outages, packet drops, TCP resets, connection leaks, and bandwidth bottlenecks. Master `tcpdump` with Berkeley Packet Filters (BPF), `ss` socket diagnostics, `iperf3` bandwidth and jitter benchmarking, Layer 4 `traceroute` / `mtr`, `ethtool` NIC ring buffer tuning, and `conntrack` debugging.
>
> By the end of this chapter, you will understand:
> 1. Packet Capturing with `tcpdump`: capture filters, packet truncation (`-s0`), ring buffer rotation (`-W -C`), and writing to `.pcap`
> 2. Deep Socket Diagnostics with `ss`: socket buffer queues (`Send-Q`, `Recv-Q`), TCP states, and timer inspection (`ss -tiepm`)
> 3. Active Bandwidth & Latency Benchmarking with `iperf3`: TCP window sizing, multi-stream parallel tests (`-P`), and UDP jitter/loss testing
> 4. Hop-by-Hop Path Diagnostics: ICMP vs UDP vs TCP SYN `traceroute`, `tcptraceroute`, and interactive `mtr`
> 5. Physical & Virtual Interface Diagnostics: `ethtool` ring buffers (`-g / -G`), pause frames, and hardware offloading (`-k / -K`)
> 6. Kernel Conntrack Diagnostics: `conntrack -L`, table overflows, and sysctl tuning

Think of the Linux network diagnostic toolkit as **a master mechanic's diagnostic instrument set for high-performance sports cars**:

- **`tcpdump` (The 10,000 FPS High-Speed Camera):**
  - Filming every micro-detail of the car's fuel injectors and pistons in real time (**Raw packet capture byte-by-byte**).
- **`ss` (The Cockpit Instrument Dashboard):**
  - Instantly checks the status of all open valves and tanks: *"Valve #443 has 500 liters of fuel waiting in the input queue (**`Recv-Q` is full; application thread is hanging!**)"*.
- **`iperf3` (The Engine Dynamometer / Dyno Test):**
  - Pushes the engine to 100% full throttle to mathematically measure horsepower and fuel flow (**Raw line-rate bandwidth & packet loss**).
- **`ethtool` (The Tire Pressure & Shock Absorber Gauge):**
  - Checks if the tires are slipping on the pavement (**Physical NIC ring buffer overflows and hardware CRC errors**).

## Deep Technical Content

### 1. Master `tcpdump` Power Commands

```bash
# 1. Capture full packets (-s0), no DNS lookup (-nn), save to rotating 100MB PCAP files
sudo tcpdump -i eth0 -nn -s0 -C 100 -W 5 -w /tmp/capture.pcap

# 2. Capture only TCP SYN, FIN, or RST packets (diagnose connection drops)
sudo tcpdump -i any -nn "tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0"

# 3. Capture HTTP GET and POST requests in ASCII (-A)
sudo tcpdump -i any -nn -A -s0 "tcp port 80 and (((ip[2:2] - ((ip[0]&0xf)<<2)) - ((tcp[12]&0xf0)>>2)) != 0)"

# 4. Capture DNS queries and responses on Port 53
sudo tcpdump -i any -nn "udp port 53"
```

### 2. Deep Socket Diagnostics with `ss` (Socket Statistics)

```bash
# 1. List all listening TCP sockets with process names and port numbers
ss -tlpn

# 2. Inspect internal TCP connection socket memory buffers and RTT timers
ss -tiepm 'sport = :443'
```

- **`Recv-Q` on a Listening Socket:** The number of completed TCP connections waiting in the kernel accept queue for the user-space application to call `accept()`. If `Recv-Q > 0`, **the application is overloaded or deadlocked!**
- **`Send-Q` on an Established Socket:** The number of bytes queued in the kernel transmit buffer waiting for TCP ACK from the remote peer. If `Send-Q` is large and stays high, **the network path is experiencing heavy packet loss or the remote peer is stalled**.

## Common Interview Questions

**Q1: What is the difference between `Recv-Q` and `Send-Q` in `ss` for a LISTENING socket vs an ESTABLISHED socket?**

- **Listening Socket:**
  - `Recv-Q`: Number of connections currently waiting in the kernel's `accept()` backlog queue.
  - `Send-Q`: Maximum allowed backlog queue size (`backlog` parameter in `listen(fd, backlog)`).
  - *If `Recv-Q > Send-Q`, the application is dropping incoming connections!*
- **Established Socket:**
  - `Recv-Q`: Number of bytes received by the OS kernel but not yet read by the application via `read()` / `recv()`.
  - `Send-Q`: Number of bytes written by the application via `write()` / `send()` that are queued in kernel memory waiting for TCP ACK acknowledgment from the remote peer.

**Q2: Why does a standard ICMP `traceroute` often show `* * * Request timed out` on intermediate hops even when the target is fully reachable?**

Many enterprise core backbone routers and firewalls are explicitly configured to **drop incoming ICMP Echo and ICMP Time-Exceeded generation** to protect their control plane CPUs from denial-of-service attacks. The router still forwards data packets normally at line rate in hardware, but refuses to generate the ICMP response to your traceroute probe. Using **TCP SYN Traceroute (`traceroute -T -p 443`)** bypasses ICMP filters.

**Q3: How do you identify whether network packet drops are happening in hardware NIC buffers or in the OS kernel?**

1. **Hardware NIC Buffer Drops:** Query `ethtool -S eth0`. Look for `rx_dropped`, `rx_missed_errors`, or `rx_fifo_errors`. This indicates the physical NIC DMA ring buffer (`rx-ring`) is full before the kernel could process the packets (fix: increase ring buffer with `ethtool -G eth0 rx 4096`).
2. **OS Kernel Queue Drops:** Query `cat /proc/net/dev` and `/proc/net/softnet_stat`. Look for `drop_total` and `netdev_budget` overruns. This indicates Linux kernel CPU SoftIRQ cores are overloaded (fix: enable RPS/RFS or increase `net.core.netdev_max_backlog`).

**Q4: How does `tcpdump` capture packets without significantly affecting host CPU performance?**

`tcpdump` compiles the filter expression (e.g. `tcp port 443`) into an in-kernel **Berkeley Packet Filter (cBPF / eBPF) program**. The kernel evaluates the filter directly in kernel space on the raw packet buffer; only packets that match the filter are copied into the user-space `libpcap` buffer, discarding 99% of irrelevant traffic with near-zero memory copy overhead.

**Q5: What happens when the Linux `conntrack` table fills up, and what is the diagnostic fix?**

When active connections exceed `/proc/sys/net/netfilter/nf_conntrack_max`, the Linux kernel logs `"nf_conntrack: table full, dropping packet"` in `dmesg` and **drops all subsequent incoming new connections**.
- **Diagnostics:** Query current count: `cat /proc/sys/net/netfilter/nf_conntrack_count` vs limit `nf_conntrack_max`.
- **Fix:** Increase limit dynamically via `sysctl -w net.netfilter.nf_conntrack_max=1048576`, reduce timeouts (`nf_conntrack_tcp_timeout_established=86400`), or bypass conntrack on high-throughput ports using `iptables -t raw -A PREROUTING -p tcp --dport 80 -j NOTRACK`.
