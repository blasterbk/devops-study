## Deep Technical Content

### Incident Runbook 1: Path MTU Discovery (PMTUD) Black Hole

#### Symptoms:
- Ping works fine (`ping host`).
- SSH connection opens and authenticates, but typing `ls -la /usr/bin` or running `cat large_file.txt` hangs the terminal indefinitely.
- HTTPS `curl` connects (TLS handshake completes), but the HTTP response body download never finishes.

#### Root Cause:
Intermediate router has a lower MTU (e.g. 1420 over VPN/VXLAN). A firewall on the path drops incoming **ICMP Type 3 Code 4 (Fragmentation Needed)** error packets. The client never learns to shrink its TCP Maximum Segment Size (MSS).

#### Diagnostic & Remediation Steps:
```bash
# Step 1: Prove PMTUD Black Hole by pinging with Don't Fragment (DF) bit set
ping -M do -s 1472 198.51.100.20 # If fails, shrink packet size until it succeeds
ping -M do -s 1372 198.51.100.20 # If succeeds: MTU is exactly 1372 + 28 = 1400 bytes!

# Step 2: Emergency Immediate Fix: Apply TCP MSS Clamping on the Linux Router / Firewall
sudo iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
```

### Incident Runbook 2: Linux Ephemeral Port Exhaustion (`TIME_WAIT` Pileup)

#### Symptoms:
- Client application (e.g., Python / Node.js backend calling microservices) crashes with:
  `cURL error: Failed to connect to host: Cannot assign requested address (errno 99)`.

#### Root Cause:
Application opens a brand-new TCP connection for every single HTTP request (no HTTP keep-alive connection pooling). Sockets transition into `TIME_WAIT` for 60 seconds (`2 * MSL`). All 28,000 ephemeral ports (`32768-60999`) are consumed.

#### Diagnostic & Remediation Steps:
```bash
# Step 1: Count active sockets by state using ss
ss -tan | awk '{print $1}' | sort | uniq -c

# Step 2: Expand local ephemeral port range
sudo sysctl -w net.ipv4.ip_local_port_range="10240 65535"

# Step 3: Enable TCP TIME_WAIT socket reuse for outgoing connections
sudo sysctl -w net.ipv4.tcp_tw_reuse=1

# Step 4: Permanent Application Fix: Configure HTTP Keep-Alive / Persistent Connection Pooling!
```

## Common Interview Questions

**Q1: How do you systematically troubleshoot a production incident where "Service A cannot talk to Service B in Kubernetes"?**

Follow the 7-Layer bottom-up diagnostic workflow:
1. **Layer 3 (IP Reachability):** Run `kubectl exec` from Pod A: `ping <Pod_B_IP>`. Verify Pod B IP is valid.
2. **Layer 4 (Port & TCP):** Run `nc -zv -w 2 <Pod_B_IP> 8080`. If it hangs, inspect **Kubernetes NetworkPolicies** and security groups blocking ingress/egress.
3. **Service Discovery / DNS (CoreDNS):** Run `dig service-b.default.svc.cluster.local`. Verify CoreDNS returns the correct ClusterIP.
4. **Service Endpoints:** Check `kubectl get endpoints service-b` to verify backend Pods are healthy and passing Readiness Probes.
5. **Layer 7 (HTTP):** Run `curl -v http://service-b:8080/healthz` to inspect HTTP status codes and TLS handshake logs.

**Q2: What is an Asymmetric Routing loop and why does it break stateful firewalls?**

Asymmetric routing occurs when an outbound packet follows Path A (Router 1 $\to$ Firewall 1 $\to$ Server), but the return response packet follows Path B (Server $\to$ Router 2 $\to$ Firewall 2 $\to$ Client). Because Firewall 2 never saw the initial TCP SYN packet on Path A, its stateful connection tracking table (`conntrack`) has no record of the session. Firewall 2 assumes the returning `SYN-ACK` or `ACK` packet is an illegal out-of-state attack and **immediately drops the connection**.

**Q3: How does BGP Route Flap Damping protect global Internet routing stability?**

When a flaky physical fiber link causes a router to repeatedly announce and withdraw a BGP prefix every few seconds (**Route Flapping**), thousands of core Internet routers are forced to recompute their routing tables (SPF / BGP decision algorithms), driving router CPU usage to 100%. **BGP Route Flap Damping** assigns a penalty score to flapping routes. If penalties exceed a threshold, the router **suppresses (damps) the route entirely for a cooldown period (e.g. 30 minutes)**, insulating the global Internet from the oscillating link.

**Q4: What causes the `TCP Reset (RST)` packet to be sent by a Linux host?**

1. **Port Closed:** A packet arrived for a TCP port where no process is listening (`ECONNREFUSED`).
2. **Accept Queue Overflow:** The listening application's backlog queue is full (`Recv-Q > Send-Q`) and `tcp_abort_on_overflow=1` is set.
3. **Connection Aborted in TIME_WAIT:** A packet arrived with an unexpected TCP sequence number for a closed/closing socket.
4. **Firewall / Security Group REJECT:** A firewall rule explicitly executed `-j REJECT --reject-with tcp-reset`.

**Q5: What is the post-mortem Blameless Root Cause Analysis (RCA) framework for a major network outage?**

A proper blameless post-mortem documents:
1. **Summary:** Brief description of user impact, duration, and business revenue loss.
2. **Timeline:** Exact UTC timestamps from initial trigger, automated alert firing, responder triage, root cause identification, to final mitigation.
3. **Root Cause:** Deep technical analysis of the underlying failure mechanism (not human error, but systemic flaws).
4. **What Went Well / What Went Poorly:** Evaluation of monitoring, runbooks, and alerting thresholds.
5. **Action Items:** Prioritized preventative tasks with assigned owners (e.g. adding automated canary validation, adding automated MSS clamping, tuning conntrack limits).
