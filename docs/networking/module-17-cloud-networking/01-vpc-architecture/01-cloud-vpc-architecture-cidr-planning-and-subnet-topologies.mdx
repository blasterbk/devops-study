# Chapter 1 — Cloud VPC Architecture: CIDR Planning, Subnet Tiers & Multi-AZ High Availability

> **Goal:** Master the fundamental architecture of cloud networking: the **Virtual Private Cloud (VPC / VNet)**. Understand enterprise CIDR block partitioning strategies across multi-region and multi-account cloud environments (AWS, GCP, Azure), the 3-Tier Subnet architecture (Public Ingress, Private Application, Isolated Database), Multi-Availability Zone (Multi-AZ) fault domains, and Route Table routing logic.

> By the end of this chapter, you will understand:
> 1. VPC fundamental primitives: Logical software-defined network boundary inside multi-tenant hyperscalers
> 2. Strategic CIDR allocation: Avoiding IP overlaps, reserving capacity for Kubernetes Pod CIDRs, and VPC sizing (/16 to /28)

## Real-Life Analogy

Think of a Cloud VPC as **a private, gated enterprise corporate campus inside a master city**:

- **The VPC Boundary (The Campus Outer Perimeter):**
  - A secure, fenced-off territory (`10.0.0.0/16`) dedicated exclusively to your company inside the cloud provider's physical infrastructure.
- **Availability Zones (Independent Physical Buildings):**
  - AZ-a, AZ-b, and AZ-c are three completely separate physical buildings with independent power generators, cooling, and water supplies. If Building A loses power in a storm, Buildings B and C operate uninterrupted (**Multi-AZ Resilience**).
- **The 3 Subnet Tiers (Security Zones inside each building):**
  - **Tier 1 (Public Lobby):** Accessible to visitors; houses receptionists and load balancers (**Public Subnet with Internet Gateway**).
  - **Tier 2 (Employee Offices):** Access to internal tools and microservices; cannot be accessed directly from the street (**Private Application Subnet**).
  - **Tier 3 (Underground Bank Vault):** Houses customer financial databases; zero internet access, strictly isolated (**Isolated Data Subnet**).

## Deep Technical Content

### 1. Cloud Provider Reserved IP Addresses per Subnet

In a standard on-premises network, only 2 IP addresses are reserved per subnet (Network ID and Broadcast ID). **AWS reserves 5 IP addresses in every subnet**:

```text
 ┌─────────────┬──────────────────────────────────────────────────────────────────────────────┐
 │ IP Offset   │ AWS Reserved Function                                                        │
 │─────────────┼──────────────────────────────────────────────────────────────────────────────┤
 │ **`.0`**    │ Network Address (e.g. `10.0.1.0`)                                            │
 │ **`.1`**    │ VPC Router / Default Gateway Address (e.g. `10.0.1.1`)                       │
 │ **`.2`**    │ Amazon Provided DNS (AmazonRoute53 / CoreDNS resolver) (e.g. `10.0.1.2`)     │
 │ **`.3`**    │ Reserved by AWS for future operational expansion                             │
 │ **`.255`**  │ Network Broadcast Address (AWS VPC does not support broadcast; reserved)     │
 └─────────────┴──────────────────────────────────────────────────────────────────────────────┘
```

*(In a `/24` subnet with 256 total addresses, exactly $256 - 5 = 251$ addresses are usable).*

## Common Interview Questions

**Q1: What are the 5 reserved IP addresses in an AWS VPC subnet, and why are they not usable by EC2 instances?**

In every AWS subnet (e.g. `10.0.1.0/24`), AWS reserves:
1. `10.0.1.0`: Network Address.
2. `10.0.1.1`: VPC Router / Default Gateway.
3. `10.0.1.2`: Amazon DNS Resolver (Route 53 resolver for internal VPC name resolution).
4. `10.0.1.3`: Reserved by AWS for future use.
5. `10.0.1.255`: Network Broadcast Address (broadcast is not supported in VPC software-defined networks).
Therefore, a `/28` subnet (16 IPs) has only $16 - 5 = 11$ usable host IPs.

**Q2: What is the difference between a Security Group (SG) and a Network Access Control List (NACL)?**

- **Security Group (Stateful):** Attached directly to the virtual network interface (ENI). It is **stateful** (if inbound traffic is allowed on port 443, response traffic is automatically allowed outbound, regardless of outbound rules). Evaluates allow rules only (cannot create deny rules).
- **NACL (Stateless):** Attached at the **subnet boundary**. It is **stateless** (return traffic must be explicitly allowed in the outbound rules using ephemeral ports `1024-65535`). Supports both ALLOW and DENY rules in a numbered priority sequence.

**Q3: Why should an enterprise deploy one NAT Gateway per Availability Zone instead of a single shared NAT Gateway?**

1. **High Availability / Fault Tolerance:** If AZ-a suffers a catastrophic physical power failure and the single NAT Gateway was in AZ-a, all private EC2 instances in AZ-b and AZ-c lose all outbound internet connectivity.
2. **Cross-AZ Data Transfer Costs:** Traffic crossing from AZ-b to a NAT Gateway in AZ-a incurs expensive cross-AZ network bandwidth charges ($0.01/GB each way).
3. **Bandwidth Scalability:** Each NAT Gateway scales up to 45 Gbps; multi-AZ NAT Gateways scale aggregate VPC egress throughput linearly.

**Q4: How does a VPC Software-Defined Network (SDN) handle Layer 2 broadcast and multicast traffic?**

Hyperscale cloud VPCs (AWS Nitro, GCP Andromeda, Azure Virtual Network) do **not** emulate physical Ethernet switches. They operate purely at **Layer 3 (IP-routed)** using proprietary overlay encapsulation (like Geneve or customized VXLAN). **Layer 2 Broadcasts (like standard ARP) and Multicast are dropped at the virtual hypervisor boundary**. ARP is answered synthetically by the cloud SDN controller.

**Q5: What is the recommended strategy to prevent IP address exhaustion when planning Kubernetes (EKS / AKS) clusters in a VPC?**

In AWS VPC CNI, every Kubernetes Pod is assigned a native, real IP from the VPC subnet. If an EKS cluster runs 500 pods on a `/24` subnet (251 IPs), the subnet exhausts within minutes, preventing new pods and nodes from launching. Strategies to mitigate this:
1. **Secondary CIDR Blocks:** Attach non-routable secondary CIDR blocks (e.g. `100.64.0.0/16` CGNAT space) to the VPC dedicated exclusively to Pods.
2. **Prefix Delegation:** Assign `/28` IP prefixes (16 IPs) to ENIs rather than individual secondary IPs, reducing EC2 API throttling.
