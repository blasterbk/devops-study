# Chapter 2 — Cloud Connectivity: Internet Gateways, NAT, Transit Gateways & VPC Peering

> **Goal:** Master interconnectivity architectures across multi-account, multi-region cloud networks. Understand the operational mechanics of Internet Gateways (IGW), Managed NAT Gateways, the non-transitive routing limitation of VPC Peering, scalable Hub-and-Spoke networks using **AWS Transit Gateway (TGW) / Azure Virtual WAN / GCP Network Connectivity Center**, and private service consumption using **AWS PrivateLink / VPC Endpoints**.
>
> By the end of this chapter, you will understand:
> 1. Internet Gateways (IGW): 1:1 Static 1-to-1 NAT scaling without physical bottlenecks
> 2. Managed NAT Gateways: Port Address Translation (PAT) for egress-only private subnet connectivity
> 3. VPC Peering: Line-rate inter-VPC routing and why peering is strictly **Non-Transitive** ($A \leftrightarrow B$ and $B \leftrightarrow C$ does NOT equal $A \leftrightarrow C$)
> 4. AWS Transit Gateway (TGW): Centralized Layer 3 routing hub connecting thousands of VPCs and VPNs
> 5. Transit Gateway Route Tables, route domain segmentation (Prod vs Non-Prod vs Shared Services), and Appliance Mode (Egress inspection firewalls)
> 6. AWS PrivateLink (VPC Interface Endpoints): securely accessing SaaS services and AWS APIs without internet gateways

## Real-Life Analogy

Think of multi-VPC connectivity as **transportation links between sovereign international cities**:

- **Internet Gateway (The International Airport):**
  - Allows international tourists with valid passports (**Public IP / Elastic IP**) to land directly in the city center.
- **NAT Gateway (The City Passport-Controlled Exit Gate):**
  - Allows internal residents (**Private Subnet VMs**) to leave the city to buy goods on the outside world, but prevents outsiders from entering through this one-way gate.
- **VPC Peering (A Private Tunnel Between 2 Cities):**
  - A direct underground highway between City A and City B. It's fast and free of tolls, but if you have 100 cities, you must dig $4,950$ separate tunnels (**$N(N-1)/2$ full mesh explosion**). Furthermore, City A cannot drive through City B to reach City C (**Non-transitive**).
- **Transit Gateway (The Central High-Speed Train Grand Central Station):**
  - Every city builds 1 single railway spur to Grand Central Station. Grand Central handles all routing, security inspections, and traffic switching between all 1,000 cities effortlessly!

### 2. AWS PrivateLink (Interface VPC Endpoints)

Traditionally, when an EC2 instance in a private subnet needed to access an AWS API (like S3, DynamoDB, SQS, or a vendor SaaS API), traffic had to route through an expensive **NAT Gateway $\to$ Public Internet $\to$ AWS Public Endpoint**.
- **AWS PrivateLink:** Injects an **Elastic Network Interface (ENI)** with a private IP (`10.0.1.50`) directly into your private subnet.
- Traffic travels over the Amazon internal optical backbone with **zero public internet traversal, zero NAT Gateway data processing fees**, and strict IAM / VPC Endpoint Policy authorization.

## Common Interview Questions

**Q1: What does "VPC Peering is strictly Non-Transitive" mean, and what is a concrete example?**

Non-transitive means traffic cannot hop through an intermediate VPC to reach a third network. If **VPC A is peered with VPC B**, and **VPC B is peered with VPC C**, an EC2 instance in **VPC A cannot send packets to VPC C through VPC B**. To enable connectivity, you must either create a direct peering link between VPC A and VPC C, or deploy an **AWS Transit Gateway (TGW)**.

**Q2: What is the "Appliance Mode" in an AWS Transit Gateway and why is it essential for Next-Gen Firewalls?**

In a centralized security inspection VPC with dual Palo Alto / Fortinet firewall appliances across AZ-a and AZ-b, standard ECMP hashing on Transit Gateway might route the request packet to the firewall in AZ-a, but route the return response packet to the firewall in AZ-b. Because firewalls are stateful, Firewall B drops the response as invalid. Enabling **TGW Appliance Mode** guarantees that for a given bidirectional network flow, **both the forward and return traffic are pinned to the exact same Availability Zone and firewall appliance**.

**Q3: What is the difference between a Gateway VPC Endpoint and an Interface VPC Endpoint (PrivateLink)?**

- **Gateway VPC Endpoint (Free):** Implemented as a route table target in the VPC. Only supports **AWS S3** and **DynamoDB**. Does not work across VPC Peering, Direct Connect, or Transit Gateways.
- **Interface VPC Endpoint / PrivateLink (Paid):** Injects a physical private ENI (IP address) into your subnet. Supports **hundreds of AWS services, third-party SaaS (Datadog, Snowflake), and custom internal microservices**, and is fully reachable across Direct Connect and Transit Gateways.

**Q4: How do Transit Gateway Route Tables enforce network segmentation (e.g. isolating Prod from Dev)?**

A Transit Gateway supports **multiple independent route tables**. To isolate environments:
1. Create a `Prod_Route_Table` and a `Dev_Route_Table`.
2. Associate Prod VPCs with `Prod_Route_Table` and Dev VPCs with `Dev_Route_Table`.
3. In `Dev_Route_Table`, only propagate routes to the `Shared_Services_VPC` and the `Internet_Egress_VPC`, omitting any routes to Prod VPCs.
Traffic between Prod and Dev is completely blocked at the Layer 3 routing plane with zero firewall rules needed.

**Q5: What is Cloud WAN (AWS Cloud WAN / Azure Virtual WAN)?**

While Transit Gateway operates inside a single AWS Region, **AWS Cloud WAN** allows enterprises to build a unified global wide area network across multiple AWS regions and on-premises branch offices using a centralized **Global Network policy document** (managing multi-region core network peering, routing, and segmentation automatically).
