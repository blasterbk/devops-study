# Chapter 3 — Linux Firewall Frontends: UFW, firewalld Zones & Rich Rules

> **Goal:** Master higher-level user-space firewall management daemons across modern Linux distributions: **UFW (Uncomplicated Firewall)** on Debian/Ubuntu and **`firewalld`** on RHEL, CentOS, Rocky Linux, and Fedora. Understand firewalld's dynamic zone architecture (`public`, `internal`, `dmz`, `trusted`), rich language rules, direct interface bindings, and the difference between Runtime and Permanent state management.
>
> By the end of this chapter, you will understand:
> 1. The abstraction hierarchy: User Frontends (`ufw` / `firewall-cmd`) $\to$ Kernel Backend (`nftables` / `iptables`)
> 2. UFW management: default incoming/outgoing policies, application profiles (`/etc/ufw/applications.d`), and rate limiting
> 3. `firewalld` Zones: assigning network interfaces and source CIDR subnets to discrete trust zones
> 4. `firewalld` Rich Rules: complex multi-criteria matching (IP + Port + Log + Rate Limit)
> 5. Runtime vs Permanent configuration synchronization (`firewall-cmd --runtime-to-permanent`)
> 6. CLI diagnostic workflows and rule verification

## Real-Life Analogy

Think of UFW and `firewalld` as **user-friendly software touchscreens mounted on top of a complex industrial security control system**:

- **The Underlying Engine (`iptables` / `nftables`):**
  - The massive basement electrical wiring and high-voltage physical circuit breakers (**Netfilter bytecode**). Complex, dangerous to wire by hand, and one wrong move cuts power to the entire building.
- **UFW (The Simple Home Security Keypad):**
  - A clean 3-button keypad on the wall: *"Arm Home Mode"*, *"Allow Guest on Door 22"* (`ufw allow ssh`). Simple, safe, and prevents administrator lockout.
- **`firewalld` (Enterprise Corporate Security Zones):**
  - An interactive building management console divided into **Zones**:
    - **Lobby Zone (`public`):** Strictest rules for visitors.
    - **Employee Lounge (`internal`):** Open access to intranet printers and internal APIs.
    - **Data Center Vault (`trusted`):** Full unhindered access for certified network admins.

### 1. UFW vs firewalld Comparison

```text
 ┌──────────────────────┬──────────────────────────────────────────┬──────────────────────────────────────────┐
 │ Feature              │ UFW (Uncomplicated Firewall)             │ firewalld                                │
 │──────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────┤
 │ **Primary Distros**  │ Ubuntu, Debian                           │ RHEL, Rocky Linux, AlmaLinux, Fedora     │
 │ **Core Philosophy**  │ Minimalist, single-table simplification  │ Multi-zone enterprise segmentation       │

 │ **Zone Support**     │ No (Global policy only)                  │ Yes (9 built-in zones + custom zones)    │
 │ **Direct Rules**     │ Raw iptables hooks in `before.rules`     │ Rich Rules & Direct Netfilter pass-through│

```

### 2. `firewalld` Built-In Zone Hierarchy

```text
 ┌──────────────┬────────────────────────────────────────────────────────────────────────┐
 │ Zone Name    │ Default Trust Level & Behavior                                         │
 │──────────────┼────────────────────────────────────────────────────────────────────────┤
```

## Hands-On Lab: Managing Firewalls with UFW and firewall-cmd

```bash
# ==========================================================
# UFW (Ubuntu / Debian) Master Commands
# ==========================================================
# Step 1: Check UFW status
sudo ufw status verbose

# Step 2: Set default policies: deny incoming, allow outgoing
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Step 3: Allow SSH with rate-limiting and allow HTTPS
sudo ufw limit 22/tcp comment "Rate-limited SSH"
sudo ufw allow 443/tcp comment "Production HTTPS"

# Step 4: Allow specific subnet access to private MySQL database
sudo ufw allow from 10.0.4.0/24 to any port 3306 proto tcp

# ==========================================================
# firewalld (RHEL / CentOS) Master Commands
# ==========================================================
# Step 5: Query active zones and assigned interfaces
sudo firewall-cmd --get-active-zones 2>/dev/null || echo "firewalld not on this host"

# Step 6: Add permanent service and reload dynamically
# sudo firewall-cmd --permanent --zone=public --add-service=https
# sudo firewall-cmd --reload
```

## Common Interview Questions

**Q1: What is the critical difference between `firewall-cmd --permanent` and runtime configuration in `firewalld`?**

- **Runtime Configuration (Default without `--permanent`):** Applies the rule to the running kernel **immediately without reloading**, but the rule is **lost upon server reboot** or firewall restart.
- **Permanent Configuration (`--permanent`):** Writes the rule to persistent XML configuration files on disk (`/etc/firewalld/zones/`), but **does not take effect in the running kernel** until you execute `firewall-cmd --reload`.
- **Best Practice:** Use `firewall-cmd --runtime-to-permanent` to save tested runtime rules to disk permanently.

**Q2: What is a `firewalld` Rich Rule and when is it required?**

Standard `firewalld` commands only allow opening a port or service to the entire zone. A **Rich Rule** allows complex multi-variable conditions: matching a specific Source Subnet, Port, Protocol, Action, Log prefix, and Rate Limit in a single statement (e.g., `firewall-cmd --add-rich-rule='rule family="ipv4" source address="192.168.1.0/24" service name="ssh" limit value="5/m" log prefix="SSH_ACCESS" accept'`).

**Q3: How does UFW prevent system administrators from accidentally locking themselves out of remote servers?**

When an administrator runs `ufw enable` over an active SSH session, UFW inspects the current active shell connection. If port 22 is not explicitly allowed, UFW prompts an interactive confirmation warning: `"Command may disrupt existing ssh connections. Proceed with operation (y|n)?"`, allowing the administrator to abort and add `ufw allow ssh` before enabling.

**Q4: How do Docker and Kubernetes interact with UFW and why can Docker bypass UFW rules?**

Docker automatically injects its own iptables rules directly into the **`PREROUTING` and `DOCKER` chains** of the `nat` and `filter` tables. Because Docker's chains are evaluated **before** UFW's `ufw-user-input` chain, published Docker container ports (e.g. `docker run -p 8080:80`) become publicly accessible on the internet, completely bypassing UFW block rules! Mitigating this requires configuring Docker daemon with `{"iptables": false}` or routing through reverse proxies.

**Q5: What is the purpose of the `firewalld` Direct Interface?**

The Direct Interface (`firewall-cmd --direct ...`) allows advanced administrators to inject raw `iptables`, `ip6tables`, or `ebtables` syntax directly into the running table chains without being constrained by firewalld's zone abstractions.
