# Chapter 1 — iptables Architecture: Netfilter Hooks, Tables, Chains & Connection Tracking

> **Goal:** Master the internal packet-filtering architecture of Linux `iptables` and the underlying `Netfilter` kernel framework. Understand the exact packet traversal flow across all 5 Netfilter hooks (`PREROUTING`, `INPUT`, `FORWARD`, `OUTPUT`, `POSTROUTING`), the priority hierarchy of the 5 tables (`raw`, `mangle`, `nat`, `filter`, `security`), stateful connection tracking (`conntrack`), and iptables targets (`ACCEPT`, `DROP`, `REJECT`, `SNAT`, `DNAT`, `MASQUERADE`).
>
> By the end of this chapter, you will understand:
> 1. The Linux Netfilter kernel architecture and packet inspection lifecycle
> 2. The 5 standard iptables Tables: `raw` (bypass conntrack), `mangle` (header alteration), `nat` (address translation), `filter` (default packet filtering), and `security` (SELinux MAC)
> 3. The 5 standard Chains: `PREROUTING`, `INPUT`, `FORWARD`, `OUTPUT`, and `POSTROUTING`
> 4. Stateful inspection with `conntrack`: `NEW`, `ESTABLISHED`, `RELATED`, `INVALID`, and `UNTRACKED`
> 5. Custom user-defined chains and `kube-proxy` iptables rules generation (`KUBE-SERVICES`, `KUBE-NODEPORTS`)
> 6. CLI rule manipulation, packet statistics, and debugging with `iptables -vL -n -t nat`

## Real-Life Analogy

Think of Netfilter and iptables as **an international airport security, customs, and immigration clearance checkpoint**:

- **PREROUTING (Arrival Gate Inspection):**
  - Right as your plane lands, officers inspect your passport to see if you have a connecting flight (**DNAT / Port forwarding decision**).
- **INPUT (Immigration & Customs for Entering the City):**
  - If your final destination is local, you pass through immigration (**`filter` INPUT chain**). Authorized passengers enter; suspicious individuals are turned away (**`DROP` / `REJECT`**).
- **FORWARD (International Transit Lounge):**
  - If you are transferring to a different country, you walk through the secure transit hallway without entering the local city (**`filter` FORWARD chain**).
- **POSTROUTING (Final Departure Exit Stamp):**
  - Right before your outgoing flight takes off, the agent stamps your boarding pass with the airline's official group flight code (**SNAT / MASQUERADE**).

## Deep Technical Content

### 1. The 5 iptables Tables & Priority Hierarchy

```text
 ┌──────────────┬──────────────────┬──────────────────────────────────────────┬────────────────────────────────────────────────────────┐
 │ Table        │ Priority Order   │ Valid Chains                             │ Purpose & Functionality                                │
 │──────────────┼──────────────────┼──────────────────────────────────────────┼────────────────────────────────────────────────────────┤
 │ **`raw`**    │ 1 (Highest)      │ `PREROUTING`, `OUTPUT`                   │ Exempts packets from connection tracking (`NOTRACK`)   │
 │ **`mangle`** │ 2                │ All 5 Chains                             │ Alters packet headers (TOS, DSCP, TTL, MARK)           │
 │ **`nat`**    │ 3                │ `PREROUTING`, `INPUT`, `OUTPUT`, `POST`  │ Address translation: DNAT (ingress), SNAT/MASQ (egress)│
 │ **`filter`** │ 4 (Default)      │ `INPUT`, `FORWARD`, `OUTPUT`             │ Core packet filtering: `ACCEPT`, `DROP`, `REJECT`      │
 │ **`security`**│ 5 (Lowest)      │ `INPUT`, `FORWARD`, `OUTPUT`             │ Mandatory Access Control (SELinux security marks)      │
 └──────────────┴──────────────────┴──────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### 2. Connection Tracking (`conntrack`) States

```text
 ┌──────────────────┬─────────────────────────────────────────────────────────────────────────────────────────┐
 │ State            │ Description & Operational Meaning                                                       │
 │──────────────────┼─────────────────────────────────────────────────────────────────────────────────────────┤
 │ **`NEW`**        │ Packet initiates a new connection (e.g. TCP SYN packet received).                       │
 │ **`ESTABLISHED`**│ Packet belongs to an existing, bidirectional connection that has seen traffic in both dir│
 │ **`RELATED`**    │ Packet opens a new connection related to an existing one (e.g. FTP data channel, ICMP)  │
 │ **`INVALID`**    │ Packet cannot be identified (corrupt headers, out-of-window TCP sequences). DROP these! │
 │ **`UNTRACKED`**  │ Packet matched a `NOTRACK` target rule in the `raw` table; ignored by conntrack.       │
 └──────────────────┴─────────────────────────────────────────────────────────────────────────────────────────┘
```

## Hands-On Lab: iptables Hardening & Rule Management

```bash
# Step 1: List all active rules in the default filter table with packet counters
sudo iptables -L -n -v --line-numbers

# Step 2: List all NAT rules (DNAT, SNAT, MASQUERADE)
sudo iptables -t nat -L -n -v

# Step 3: Allow established/related traffic and loopback, then drop invalid packets
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -A INPUT -m conntrack --ctstate INVALID -j DROP

# Step 4: Allow incoming SSH (port 22) rate-limited to 10 connections/min to prevent brute-force
sudo iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW -m limit --limit 10/min --limit-burst 5 -j ACCEPT

# Step 5: Save iptables rules on Debian/Ubuntu systems
# sudo iptables-save > /etc/iptables/rules.v4
```

## Common Interview Questions

**Q1: What is the difference between the `DROP` target and the `REJECT` target in iptables?**

- **`DROP`:** Silently discards the packet with **zero feedback to the sender**. The sender's socket hangs until its TCP timeout expires. Preferred for public-facing edge firewalls to waste an attacker's port scanning time.
- **`REJECT`:** Discards the packet and explicitly sends an active error response back to the sender: an **ICMP Port Unreachable** (for UDP) or a **TCP RST packet** (for TCP). The client application disconnects immediately without hanging.

**Q2: What causes `kube-proxy` iptables mode to suffer from severe CPU degradation in clusters with $>5,000$ Services?**

iptables evaluates rules sequentially in an **$O(N)$ linear list**. In large Kubernetes clusters with 5,000 Services and 50,000 Pods, `kube-proxy` generates over 100,000 iptables rules. Every single packet traversing the node must evaluate thousands of sequential rules, driving CPU usage high. Furthermore, updating a single pod requires writing the entire 100,000-rule table atomically to kernel memory, causing kernel lock contention. This led to **IPVS Mode** ($O(1)$ hash tables) and **eBPF (Cilium)**.

**Q3: How does Destination NAT (DNAT) differ from Source NAT (SNAT), and on which chains do they run?**

- **DNAT (Destination NAT):** Rewrites the destination IP of incoming packets (e.g. exposing internal private service `10.0.0.50` to public internet requests on `203.0.113.1`). It runs exclusively in the **`PREROUTING`** and **`OUTPUT`** chains.
- **SNAT (Source NAT):** Rewrites the source IP of outgoing packets (e.g. allowing internal private subnet hosts to access the public Internet via the router's public IP). It runs exclusively in the **`POSTROUTING`** chain.

**Q4: What is the purpose of the `raw` table and when should a network engineer use `NOTRACK`?**

The `raw` table is evaluated before connection tracking. Under massive high-volume traffic (such as a 10-Gigabit DNS resolver or high-throughput HTTP benchmark), the kernel's `conntrack` table can reach its maximum limit (`/proc/sys/net/netfilter/nf_conntrack_max`), dropping packets with `"table full, dropping packet"`. Adding a rule in the `raw` table (`iptables -t raw -A PREROUTING -p udp --dport 53 -j NOTRACK`) bypasses conntrack entirely, allowing ultra-high packet rates with zero memory state.

**Q5: How does the `conntrack` subsystem handle ICMP error messages related to a TCP connection?**

When a router sends an ICMP Type 3 Code 4 (Fragmentation Needed) or ICMP Type 11 (Time Exceeded) packet back to a host, the payload of the ICMP packet includes the original IP and TCP headers. The `conntrack` subsystem inspects inside the ICMP payload, matches it to the existing active TCP session, and marks the incoming ICMP packet with state **`RELATED`**, allowing stateful firewalls to accept essential error diagnostics automatically.
