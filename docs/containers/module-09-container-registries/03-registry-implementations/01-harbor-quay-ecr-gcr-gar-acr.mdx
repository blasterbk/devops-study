# Chapter 1 — Enterprise Registries: Harbor, Quay, ECR, GAR & ACR

> **Goal:** Master the enterprise features, cloud integrations, and architectural differences of leading container registries — analyzing open-source powerhouses **Harbor (CNCF Graduated)** and **Project Quay**, and managed hyperscaler cloud services: **AWS Elastic Container Registry (ECR)**, **Google Artifact Registry (GAR)**, and **Azure Container Registry (ACR)**.
>
> By the end of this chapter, you will understand:
> 1. Why Harbor is the de facto open-source private registry standard for Kubernetes platforms
> 2. How Harbor integrates RBAC, automated vulnerability scanning (Trivy), and image signing (Cosign)
> 3. How cloud-native registries (AWS ECR, GAR, ACR) integrate with cloud IAM and private VNets
> 4. How to author automated Image Retention Lifecycle Policies to eliminate storage sprawl
> 5. The architectural differences between single-format Docker registries and multi-artifact stores
> 6. How to authenticate and push images to enterprise registries across on-prem and cloud

## Real-Life Analogy

Think of enterprise container registries as **different tier security vaults for storing high-value corporate intellectual property**:

- **1. CNCF Harbor (The Private High-Security Custom Corporate Vault):**
  - Built inside your own company headquarters (**On-Premises or Private Kubernetes**).
  - You own the keys, the security guards (**Trivy vulnerability scanner**), the passport verification desk (**OIDC/LDAP integration**), and the automated courier trucks (**Cross-datacenter replication**).
- **2. AWS ECR / Google GAR / Azure ACR (The Managed Cloud Bank Safety Deposit Boxes):**
  - Fully managed, zero-maintenance vault facilities operated by AWS, Google, or Microsoft.
  - You don't manage hard drives, database backups, or server patching (**Serverless & 99.99% SLA**).
  - Entry is strictly authenticated using your existing corporate cloud identity badge (**AWS IAM Roles, Google Workload Identity, Azure Managed Identity**).

## 1. CNCF Harbor: The Gold Standard for Kubernetes

Harbor is the most popular open-source enterprise registry in the world:
- **Robot Accounts**: Dedicated service credentials with fine-grained push/pull permissions for CI/CD pipelines.
- **Tag Immutability Rules**: Prevents developers from overwriting existing tags (e.g. `v1.0.0`), guaranteeing reproducible deployments.
- **Automated Retention Policies**: Automatically prunes old untagged images or tags older than 30 days while preserving production releases.

## Automated Image Retention Policy Example

In AWS ECR, preventing storage bill explosions requires a **Lifecycle Policy** (`policy.json`):

```json
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Keep only the last 30 tagged production images",
      "selection": {
        "tagStatus": "tagged",
        "tagPrefixList": ["v", "release-"],
        "countType": "imageCountMoreThan",
        "countNumber": 30
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 2,
      "description": "Expire untagged images older than 7 days",
      "selection": {
        "tagStatus": "untagged",
        "countType": "sinceImagePushed",
        "countUnit": "days",
        "countNumber": 7
      },
      "action": { "type": "expire" }
    }
  ]
}
```

## Common Interview Questions

**Q1: Why is CNCF Harbor widely preferred for on-premises and private cloud Kubernetes environments?**

Harbor provides an end-to-end **enterprise governance platform** out of the box: (1) **Integrated Vulnerability Scanning**: Automatically triggers Trivy scans on every push and blocks deployments if CVEs exceed a defined severity threshold; (2) **Tag Immutability**: Enforces policies preventing the modification or overwriting of production release tags; (3) **Multi-Tenancy & RBAC**: Projects isolate teams with granular permissions integrated with enterprise OIDC/LDAP identity providers; (4) **Replication Engine**: Automatically syncs images bidirectionally across hybrid clouds and edge Kubernetes clusters.

**Q2: How does authentication differ between self-hosted registries and managed cloud registries like AWS ECR?**

- **Self-Hosted (Harbor/Quay)**: Uses traditional username/password, long-lived Robot Account tokens, or OIDC Bearer tokens. Kubernetes nodes store these credentials in a `kubernetes.io/dockerconfigjson` Secret referenced by `imagePullSecrets`.
- **Managed Cloud (AWS ECR)**: Eliminates static passwords. Kubernetes nodes authenticate using **IAM Instance Profiles or IRSA (IAM Roles for Service Accounts)**. The ECR credential helper automatically fetches short-lived (12-hour) auth tokens directly from the AWS STS API, eliminating credential rotation overhead.

**Q3: What is "Tag Immutability", and why is it a mandatory security practice?**

Tag Immutability is a registry policy that **forbids pushing an image with a tag that already exists** in the repository. If an image `my-app:v1.2.0` is already published, subsequent pushes to `v1.2.0` are rejected with HTTP 409 Conflict. This prevents two critical hazards: (1) **Supply Chain Tampering**: An attacker overwriting a trusted tag with malicious code; (2) **Deployment Non-Determinism**: Different nodes in a Kubernetes cluster pulling different versions of the "same" tag during a rollout.

**Q4: What is Google Artifact Registry (GAR), and how does it improve upon legacy Google Container Registry (GCR)?**

Legacy GCR was strictly an OCI/Docker container image registry backed by Google Cloud Storage buckets. **Artifact Registry (GAR)** is Google's modern universal package manager. It supports **OCI images, Helm charts, Java Maven/Gradle packages, Node.js NPM modules, Python Wheels, and Debian/RPM OS packages** in a single interface with regional and multi-regional storage, granular IAM per repository, and native Google Cloud Workload Identity federation.

**Q5: How do Image Retention / Lifecycle Policies prevent cloud storage cost overruns?**

In active CI/CD environments where every Git commit triggers an image build, registries accumulate thousands of orphaned untagged images and old build artifacts, consuming terabytes of object storage. **Lifecycle Policies** automate cleanup by rules such as: (1) Expiring untagged images older than 7 days; (2) Retaining only the last $N$ tagged versions of development branches (`feat-*`); (3) Retaining production release tags indefinitely.
