## Why `/var/run/docker.sock` Mounts Are Catastrophic

Mounting the Docker UNIX socket inside a container gives the container **the exact same privileges as the root Docker daemon**:

```bash
# How an attacker escapes from an unprivileged container to host root in 2 seconds:
# 1. Attacker is inside an unprivileged container with /var/run/docker.sock mounted.
# 2. Attacker runs:
docker -H unix:///var/run/docker.sock run -it --privileged --net=host --pid=host \
  -v /:/host-root alpine chroot /host-root /bin/bash

# 💥 The attacker is now ROOT on the physical Linux host node!
```

## SRE Runbook: Detecting and Cleaning Orphaned Namespace Leaks

```bash
# STEP 1: Scan for namespaces with 0 active processes holding references
sudo lsns -t net | awk '$3 == 0 {print $0}'

# STEP 2: Check for forgotten network namespace bind mounts in /var/run/netns/
sudo ip netns list

# STEP 3: Find any process holding an open file descriptor to a namespace
# sudo lsof | grep -E "ns/net|ns/mnt|ns/pid"

# STEP 4: Delete the leaked persistent network namespace
# sudo ip netns del <leaked-namespace-name>
```

```bash
# Step 1: Create a persistent namespace
```

## Common Interview Questions

**Q1: What is an orphaned namespace leak in Linux, and what operational problems does it cause?**

An orphaned namespace leak occurs when a container process terminates, but its Linux namespace (typically a **Network Namespace**) is **not freed from kernel memory**. This happens if a host process holds an open file descriptor to `/proc/[pid]/ns/net` or if a CNI plugin fails to unmount a persistent bind mount in `/var/run/netns/`. Over time, leaked namespaces consume kernel memory structs (`struct net`), retain virtual ethernet interfaces (`veth`), lock assigned IP addresses in CNI IPAM pools, and eventually exhaust the node's maximum network device limits.

**Q2: Why is mounting `/var/run/docker.sock` inside a CI/CD container considered a critical security vulnerability?**

The Docker daemon socket (`/var/run/docker.sock`) is a root-privileged UNIX socket API. If a container mounts this socket, any process inside that container can issue commands directly to the host's Docker daemon. An attacker can instruct the daemon to launch a new privileged container with `-v /:/host-root`, chroot into the host's root filesystem, add backdoor SSH keys, modify `/etc/shadow`, and gain **unrestricted root control over the physical host server**.

**Q3: What makes running a container with `--privileged` dangerous?**

Running a container with `--privileged`: (1) Disables Seccomp syscall filtering; (2) Disables AppArmor / SELinux mandatory access controls; (3) Grants all 40+ Linux kernel capabilities (including `CAP_SYS_ADMIN` and `CAP_SYS_MODULE`); (4) Maps all physical host hardware device nodes (`/dev/sda`, `/dev/mem`, `/dev/kmsg`) directly into the container. An attacker inside a privileged container can simply mount the host disk (`mount /dev/sda1 /mnt`) and read or alter all host operating system files.

**Q4: How can an attacker exploit `--pid=host` combined with `CAP_SYS_PTRACE` to escape a container?**

When a container shares the host's PID namespace (`--pid=host`), it can see all host processes, including `systemd` (PID 1) and host SSH daemons. If the container also possesses the **`CAP_SYS_PTRACE`** capability (or runs as root), an attacker can use the `ptrace(2)` system call to attach to a running host root process, inject malicious shellcode or a reverse shell payload directly into that process's memory space, and execute arbitrary code with host root privileges.

**Q5: How do Kubernetes Pod Security Standards (PSS) prevent container breakout attacks?**

Kubernetes Pod Security Standards define three policy tiers: **Privileged**, **Baseline**, and **Restricted**. When a namespace enforces the **`restricted`** profile via Pod Security Admission (PSA):
1. It forbids `privileged: true`.
2. It forbids host namespace sharing (`hostPID: true`, `hostNetwork: true`, `hostIPC: true`).
3. It forbids dangerous capabilities and mandates dropping `ALL` capabilities except `NET_BIND_SERVICE`.
4. It forbids running as root (`runAsNonRoot: true`) and restricts hostPath volume mounts.
