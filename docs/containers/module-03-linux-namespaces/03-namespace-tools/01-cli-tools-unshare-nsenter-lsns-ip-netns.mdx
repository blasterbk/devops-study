# Chapter 1 — Namespace CLI Tools: unshare, nsenter, lsns & ip-netns

> **Goal:** Master the essential systems administration, SRE debugging, and low-level CLI toolkit for managing and inspecting Linux Namespaces — mastering **`unshare`** for ad-hoc process isolation, **`nsenter`** for attaching host debugging utilities to distroless/scratch containers, **`lsns`** for auditing system-wide namespace trees, and **`ip netns`** for persistent software-defined networking.
>
> By the end of this chapter, you will understand:
> 1. The operational roles of the 4 primary Linux namespace CLI utilities
> 2. How `unshare` creates isolated execution sandboxes directly from shell scripts
> 3. How `nsenter` enters container namespaces to run `tcpdump` on containers lacking shells
> 4. How `lsns` discovers orphaned, leaked, or active namespaces across all host processes
> 5. How `ip netns` coordinates virtual network namespace topologies
> 6. How to author production diagnostic one-liners to debug live container incidents

## 1. `nsenter`: Debugging Distroless & Scratch Containers

Modern security best practices build **Distroless or Scratch container images** containing *zero* shell binaries (`/bin/sh`), zero package managers, and zero debugging tools (`curl`, `netstat`, `tcpdump`).

### The SRE Problem:
When an application inside a distroless container has a network bug, `docker exec -it <container> sh` **fails immediately** with:
`OCI runtime exec failed: exec: "/bin/sh": executable file not found in $PATH`.

### The `nsenter` Solution:
Run the host's native `tcpdump` or `curl` directly inside the container's network namespace:
```bash
# 1. Find the container's host PID
CONTAINER_PID=$(docker inspect <container-name> --format '{{.State.Pid}}')

# 2. Enter the container's Network Namespace using the HOST's tcpdump binary!
sudo nsenter -t $CONTAINER_PID --net tcpdump -i eth0 -n -vv port 8080
```

## Hands-On Lab: Capturing Traffic from an Isolated Container

```bash
# Step 1: Launch a background NGINX container
docker run -d --name debug-target -p 8085:80 nginx:alpine

# Step 2: Extract its real Linux Host PID
TARGET_PID=$(docker inspect debug-target --format '{{.State.Pid}}')
echo "Target Container Host PID: $TARGET_PID"

# Step 3: Inspect all namespaces owned by this container PID using lsns
sudo lsns -p $TARGET_PID

# Step 4: Use nsenter to inspect the container's IP configuration from host
sudo nsenter -t $TARGET_PID --net ip addr show dev eth0

# Step 5: Clean up
docker rm -f debug-target
```

## Common Interview Questions

**Q1: How do you troubleshoot a network issue inside a Distroless or Scratch container that contains no shell or utilities?**

Use **`nsenter` (Namespace Enter)** from the host operating system. Because Distroless containers lack `/bin/sh` and diagnostic binaries (`curl`, `tcpdump`, `ss`), `docker exec` will fail. By discovering the container's host PID (`docker inspect <name> --format '{{.State.Pid}}'`), an SRE can execute `sudo nsenter -t <PID> --net <host-command>`. The command executes using the **host's binary and libraries**, but operates directly **inside the container's isolated network namespace**.

**Q2: What is the purpose of the `--fork` and `--mount-proc` flags in `unshare`?**

- **`--fork`**: Required when creating a new **PID Namespace (`-p`)**. In Linux, the calling process cannot change its own PID namespace; only child processes spawned after the syscall enter the new namespace. `--fork` tells `unshare` to fork a child process into the new PID namespace.
- **`--mount-proc`**: Automatically mounts a new, private `/proc` filesystem inside the new Mount and PID namespace. Without this, tools like `ps` will continue reading the host's `/proc`, incorrectly displaying all host processes!

**Q3: How does `lsns` discover namespaces on a Linux host?**

`lsns` reads the **`/proc` filesystem**. It scans every running process directory (`/proc/[pid]/ns/`), reads the magic symlinks for each namespace type (`mnt`, `net`, `pid`, `uts`, `ipc`, `user`, `cgroup`, `time`), and extracts their inode numbers. It groups processes that share the same namespace inode, calculates process counts (`NPROCS`), and displays the namespace hierarchy.

**Q4: What is the difference between `ip netns exec <name> <cmd>` and `nsenter --net=/var/run/netns/<name> <cmd>`?**

They are functionally equivalent under the hood:
- **`ip netns exec`**: A specialized utility provided by the `iproute2` package that looks up persistent network namespaces in the default directory `/var/run/netns/` and invokes `setns(CLONE_NEWNET)`.
- **`nsenter --net`**: A general-purpose utility from `util-linux` that can attach to network namespaces specified either by **file path** (`--net=/path/to/ns`) or by **process ID** (`-t <PID> --net`), offering greater flexibility for container troubleshooting.

**Q5: Can `nsenter` be used to enter a container's Mount namespace? What are the risks?**

**Yes** (`nsenter -t <PID> -m`). Entering a container's Mount namespace changes the calling shell's view of the filesystem to the container's rootfs. **The Risk**: If the container has an insecure or corrupted rootfs, executing commands inside its mount namespace may load untrusted shared libraries or execute malicious binaries. For security-critical debugging, SREs prefer entering only the Network (`--net`) and IPC (`--ipc`) namespaces while retaining the host's trusted Mount namespace.
