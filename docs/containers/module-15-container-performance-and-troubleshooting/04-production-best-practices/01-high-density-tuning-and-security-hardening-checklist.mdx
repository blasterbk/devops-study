## High-Density Linux Kernel Sysctl Tuning

Save to `/etc/sysctl.d/99-kubernetes-containers.conf`:

```ini
# Prevent inotify file watcher exhaustion across hundreds of pods:
fs.inotify.max_user_watches = 1048576
fs.inotify.max_user_instances = 8192

# Expand global system-wide file descriptor limit:
fs.file-max = 2097152

# Increase TCP connection listen backlog for high-traffic microservices:
net.core.somaxconn = 32768

# Expand ephemeral port range to prevent TCP port exhaustion:
net.ipv4.ip_local_port_range = 1024 65535

# Increase maximum memory map areas for Elasticsearch / PostgreSQL / Kafka:
vm.max_map_count = 262144

# Disable IPv4 route caching and enable IP forwarding for CNI bridges:
net.ipv4.ip_forward = 1
```

```bash
# Apply sysctl settings immediately without rebooting:
sudo sysctl --system
```

## Complete Hardened Production Kubernetes Manifest

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: production-microservice
  labels:
    app.kubernetes.io/name: microservice
spec:
  replicas: 3
  selector:
    matchLabels:
      app: microservice
  template:
    metadata:
      labels:
        app: microservice
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
        fsGroup: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: app
        image: gcr.io/distroless/static-debian12:nonroot
        securityContext:
          readOnlyRootFilesystem: true
          allowPrivilegeEscalation: false
          capabilities:
            drop:
            - ALL
        resources:
          requests:
            cpu: "250m"
            memory: "256Mi"
            ephemeral-storage: "50Mi"
          limits:
            memory: "512Mi"
            ephemeral-storage: "100Mi"
        volumeMounts:
        - name: tmp-volume
          mountPath: /tmp
      volumes:
      - name: tmp-volume
        emptyDir:
          medium: Memory
          sizeLimit: 64Mi
```

## Common Interview Questions

**Q1: Why is `fs.inotify.max_user_watches` a critical sysctl parameter for high-density container nodes?**

In Linux, the `inotify` subsystem allows processes to monitor filesystem directory changes (used heavily by Node.js, Python hot-reloaders, fluentd, Prometheus config-reloader sidecars, and IDE sync tools). The default kernel limit is typically only 8,192 watches. When a node runs 150+ pods, all pods share the same host kernel inotify watch table. Once the limit is exceeded, pods fail to start or throw **`ENOSPC: System limit for number of file watchers reached`**. Setting `fs.inotify.max_user_watches = 1048576` prevents file-watcher exhaustion.

**Q2: Why is `SystemdCgroup = true` mandatory in modern containerd configurations?**

On Linux distributions using `systemd` as the init system, `systemd` expects to be the **single source of truth for the cgroup hierarchy**. If containerd is configured with the `cgroupfs` driver instead of `systemd`, two competing software entities manage the cgroup tree simultaneously: Kubelet/containerd creates direct cgroup paths while `systemd` periodically sweeps and reorganizes slices. This creates race conditions, ghost cgroups, resource leakages, and sudden node instability under high load.

**Q3: How does `readOnlyRootFilesystem: true` neutralize malware and zero-day exploits?**

When `readOnlyRootFilesystem: true` is configured, the container runtime mounts the container's rootfs as read-only. If an attacker exploits a remote code execution (RCE) vulnerability in the application (like Log4j or SQL injection), they cannot: (1) Download malicious binaries via `curl`/`wget`; (2) Drop rootkits or cryptominers into `/tmp` or `/app`; (3) Overwrite application binaries or shared libraries. Any disk write triggers an immediate `Read-only file system` kernel error.

**Q4: Why should temporary scratch directories be mounted on `emptyDir` with `medium: Memory`?**

Applications with read-only root filesystems often require a writable directory for temporary pid files or session caches (e.g. `/tmp`). By mounting an `emptyDir` backed by `medium: Memory` (a `tmpfs` RAM-disk) with an explicit `sizeLimit` (e.g. `64Mi`), temporary file writes execute at **lightning RAM speeds** with zero disk I/O wear. Furthermore, the `sizeLimit` prevents runaway logs from exhausting physical host disk storage.

**Q5: What are the key architectural steps to achieve 99.999% reliability across a multi-tenant container fleet?**

1. **Host-Level**: Enforce cgroups v2, optimize sysctls (`somaxconn`, `file-max`, `inotify`), and dedicate fast NVMe drives for container storage.
2. **Runtime-Level**: Standardize on containerd with `SystemdCgroup = true` and configure automated image GC thresholds (85% high / 80% low).
3. **Pod-Level**: Enforce the 10-Point Security Checklist (Non-root, read-only rootfs, drop capabilities, Seccomp `RuntimeDefault`, resource requests/limits).
4. **Continuous Runtime Defense**: Deploy eBPF behavioral threat detection (Falco) and static image vulnerability gates in CI/CD.
