## 1. Package Cache Mounts (`--mount=type=cache`)

Normally, package manager directories (`/root/.npm`, `/root/.cache/pip`, `/root/go/pkg/mod`) are either discarded between builds or baked into the image, creating bloated 1GB layers. **Cache Mounts keep package caches persistent on the host across builds while excluding them from the final image**:

```dockerfile
# Go Compiler Cache Mount (Compiles 10x faster!)
RUN --mount=type=cache,target=/root/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -v -o /bin/server .

# Python Pip Cache Mount
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

# Node.js NPM Cache Mount
RUN --mount=type=cache,target=/root/.npm \
    npm ci
```

## 2. Zero-Leak Secret Mounts (`--mount=type=secret`)

> [!WARNING]
> **Never use `ARG` or `ENV` for Secrets!** Passing API tokens via `ARG` bakes the secret permanently into the image's metadata and layer history, where anyone running `docker history` can extract it!

### The Secure BuildKit Solution:
```dockerfile
# Dockerfile: Mounts secret temporarily in RAM during execution
RUN --mount=type=secret,id=github_token \
    GITHUB_TOKEN=$(cat /run/secrets/github_token) \
    curl -H "Authorization: token $GITHUB_TOKEN" https://api.github.com/data
```

```bash
# Build Command: Passes secret from local host file or environment variable
docker buildx build --secret id=github_token,src=./token.txt .
# Or directly from host environment:
docker buildx build --secret id=github_token,env=GITHUB_TOKEN .
```

## 3. SSH Agent Forwarding (`--mount=type=ssh`)

```dockerfile
# Clone private GitHub / GitLab enterprise repositories securely
RUN --mount=type=ssh \
    mkdir -p -m 0600 ~/.ssh && ssh-keyscan github.com >> ~/.ssh/known_hosts && \
    git clone git@github.com:my-org/private-repo.git /src
```

```bash
# Build Command: Forwards host's active ssh-agent session
eval $(ssh-agent) && ssh-add ~/.ssh/id_ed25519
docker buildx build --ssh default .
```

## 4. Hermetic Air-Gapped Compilations (`--network=none`)

To guarantee security and build reproducibility, enforce that compilation steps **cannot connect to the internet**:

```dockerfile
# Step 1: Download dependencies (Network enabled)
RUN go mod download

# Step 2: Compile binary with ZERO network access (Guarantees no rogue downloads!)
RUN --network=none go build -o /app/server .
```

## Hands-On Lab: Multi-Mount Production Dockerfile

```dockerfile
# Syntax directive unlocking BuildKit advanced features
# syntax=docker/dockerfile:1.4

# Stage 1: Secure Builder Stage
FROM golang:1.22-alpine AS builder
WORKDIR /src

# Copy dependency manifests
COPY go.mod go.sum ./

# Download dependencies with cache mount
RUN --mount=type=cache,target=/root/go/pkg/mod \
    go mod download

COPY . .

# Compile binary with cache mounts, secret injection, and zero network
RUN --mount=type=cache,target=/root/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    --mount=type=secret,id=enterprise_key \
    --network=none \
    CGO_ENABLED=0 go build -ldflags="-s -w" -o /bin/app .

# Stage 2: Clean Distroless Production Image
FROM gcr.io/distroless/static-debian12
COPY --from=builder /bin/app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]
```

## Common Interview Questions

**Q1: Why is passing API keys or passwords via `ARG` a major security vulnerability, and how does `--mount=type=secret` solve it?**

When a secret is passed via `ARG` (e.g. `ARG API_KEY`), the value is permanently recorded in the **image configuration JSON, layer diffs, and `docker history` metadata**. Anyone with pull access to the image can run `docker history --no-trunc <image>` and extract the plaintext secret. **`--mount=type=secret`** mounts the secret as a **temporary in-memory `tmpfs` file (`/run/secrets/<id>`)** accessible only to that specific `RUN` command. It is never committed to intermediate layer tarballs, never written to disk, and leaves zero trace in the final image.

**Q2: How do Cache Mounts (`--mount=type=cache`) accelerate container builds without bloating image size?**

Normally, package manager directories (`/root/.cache/pip`, `/root/go/pkg/mod`) create multi-hundred-megabyte layers inside the image if left uncleaned. With **`--mount=type=cache,target=/root/.cache`**, BuildKit mounts a **persistent cache directory from the host builder storage into the container during step execution**. Package managers write downloaded archives directly into this cache mount. When the step completes, the mount is detached, leaving the container layer **completely free of cached tarballs while preserving the cache for future builds**.

**Q3: What are Cache Sharing Modes in BuildKit cache mounts (`sharing=shared`, `private`, `locked`)?**

When multiple concurrent build stages or parallel jobs access the same cache mount target:
- **`sharing=shared` (Default)**: Multiple concurrent processes can read and write to the cache mount simultaneously.
- **`sharing=private`**: Creates a dedicated private copy of the cache mount for this step; changes are not merged back.
- **`sharing=locked`**: Locks the cache mount, forcing other concurrent build steps to wait until this step finishes to prevent race conditions or database corruptions (mandatory for package managers with file locks like `apt-get` or `dpkg`).

**Q4: How does SSH Agent Forwarding (`--mount=type=ssh`) work in BuildKit?**

SSH Forwarding mounts the host machine's **active UNIX domain socket for `ssh-agent`** into the build container at `/run/buildkit/ssh_agent.sock`. When a command like `git clone git@github.com:...` runs inside the container, Git forwards the cryptographic challenge over the socket to the host's `ssh-agent`. The host signs the challenge and returns the signature. The private key **never leaves the host machine's memory and is never copied into the container filesystem**.

**Q5: What is a Hermetic Build, and how is it enforced with `--network=none`?**

A Hermetic Build is a build process that is **100% self-contained, deterministic, and isolated from external internet state**. Specifying **`RUN --network=none`** completely unshares the container's network namespace during that step (leaving only the loopback `lo` interface). This guarantees that the compilation step uses only files explicitly provided in the source tree, preventing build failures due to external network outages or supply chain dependency injection attacks.
