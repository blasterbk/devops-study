## Mounting Virtual Filesystems in `runc`

Before executing the user application, `runc` mounts critical kernel pseudo-filesystems inside the container's isolated mount namespace:

1. **`/proc` (procfs)**: Must be mounted freshly inside the container's PID namespace (`mount -t proc proc /proc`). This ensures commands like `ps` show only container processes (PID 1, 2) rather than host processes.
2. **`/sys` (sysfs)**: Mounted strictly as **Read-Only (`ro`)** to prevent containers from modifying host hardware and kernel parameters.
3. **`/dev` (devtmpfs / tmpfs)**: Populated with minimal safe pseudo-devices (`/dev/null`, `/dev/zero`, `/dev/random`, `/dev/urandom`, `/dev/pts`). Dangerous device nodes like physical disk blocks (`/dev/sda`) are strictly excluded!

---

## Capability Dropping & Bounding Sets

Linux splits traditional root privileges into 40+ granular **Capabilities**:
- `CAP_SYS_ADMIN`: The god-mode capability (mount filesystems, load BPF, configure cgroups).
- `CAP_SYS_RAWIO`: Direct access to physical hardware memory.
- `CAP_NET_RAW`: Ability to forge raw IP packets and sniff network interfaces.

When `runc` boots a non-privileged container, it **drops dangerous capabilities from the Bounding Set** before calling `execve()`. Even if the application process runs as `UID 0 (root)`, it is stripped of `CAP_SYS_ADMIN`, preventing host compromises!

## Common Interview Questions

**Q1: What is the difference between `pivot_root(2)` and `chroot(2)` in container runtime security?**

`chroot(2)` only changes the root path resolution pointer for the current process; the old host root filesystem remains mounted in the underlying filesystem tree. A root process inside a `chroot` can easily break out (e.g. by opening a file descriptor to a directory outside the jail, calling `chroot()` on a child directory, and calling `fchdir()` on the open descriptor). `pivot_root(2)` moves the entire **VFS root mount point** of the mount namespace to the new `rootfs` and allows the runtime to unmount and detach the old host root (`umount2(old_root, MNT_DETACH)`), making the host operating system **completely unreachable and unescapable**.

**Q2: Why must `/proc` be re-mounted inside a container's Mount namespace?**

The `/proc` filesystem is a kernel interface exposing process table telemetry, CPU info, and kernel parameters. If a container creates a new PID Namespace (`CLONE_NEWPID`) but fails to re-mount a fresh `/proc` filesystem, utilities like `ps`, `top`, and `kill` will continue reading the host's `/proc` mount. The container will see all 500+ host processes instead of its own isolated processes. Re-mounting `procfs` (`mount -t proc proc /proc`) inside the new PID and Mount namespaces forces the kernel to populate `/proc` **exclusively with processes belonging to that specific PID namespace**.

**Q3: What are the contents of a standard OCI Runtime Bundle?**

An OCI Runtime Bundle has an exact two-part directory structure defined by the OCI Runtime Specification:
1. **`config.json`**: The declarative configuration file specifying the process arguments, environment variables, Linux namespace array, cgroup resource limits, capability bounding sets, and mount points.
2. **`rootfs/` directory**: The unpacked root filesystem containing all application binaries, libraries, and files that will become the container's root directory (`/`).

**Q4: How does capability dropping protect a Linux host from a container running as root (`UID 0`)?**

In Linux, root privileges are divided into distinct POSIX capabilities (`CAP_*`). When `runc` launches a container, it reads the `capabilities` section of `config.json` and invokes `capset(2)` to **drop dangerous capabilities** (such as `CAP_SYS_ADMIN`, `CAP_SYS_MODULE`, `CAP_SYS_RAWIO`, and `CAP_MKNOD`) from the process's Bounding and Permitted sets. Even if a process runs as `UID 0`, without `CAP_SYS_MODULE` it cannot load malicious kernel rootkits, and without `CAP_SYS_ADMIN` it cannot mount host disks, neutralizing major breakout vectors.

**Q5: What is the role of `umount2(old_root, MNT_DETACH)` during the container startup sequence?**

After `pivot_root` swaps the host root to a temporary location (e.g. `/rootfs/.old_root`), the old host filesystem is still technically mounted in memory at that sub-directory. To seal the container sandbox, `runc` invokes `umount2("/.old_root", MNT_DETACH)` (lazy unmount) followed by `rmdir("/.old_root")`. This **completely unlinks and detaches the host operating system from the container's mount namespace**, ensuring zero residual references to the host filesystem remain.
