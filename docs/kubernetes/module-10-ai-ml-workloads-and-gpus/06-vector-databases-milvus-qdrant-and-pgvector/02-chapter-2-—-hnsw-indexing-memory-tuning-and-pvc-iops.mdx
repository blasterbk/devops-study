  - **`efSearch` (The Number of Scouting Cars):** When searching, you send 64 scout cars down different streets (**`efSearch: 64`**). If 1 car hits traffic, the other 63 cars guarantee you find the absolute best coffee shop (**99.9% Recall Accuracy**).

## The Production RAM Sizing Formula for Vector Databases

Before deploying vector databases on Kubernetes, platform teams calculate exact RAM requirements:

$$\text{RAM}_{\text{Total}} = \Big[ N \times \Big( (\text{Dimensions} \times 4\text{ Bytes}) + (M \times 8\text{ Bytes}) \Big) \times 1.25 \Big] + \text{OS Overhead}$$

### Real-World Example: 50 Million OpenAI 1536-Dimensional Vectors ($M = 32$):
1. **Raw Vector Data**: $50,000,000 \times (1536 \times 4\text{ bytes}) = 307.2\text{ GB}$
2. **HNSW Graph Links**: $50,000,000 \times (32 \times 8\text{ bytes}) = 12.8\text{ GB}$
3. **Subtotal**: $320\text{ GB}$
4. **With 25% JVM/Go Safety Buffer**: $320\text{ GB} \times 1.25 = \mathbf{400\text{ GB RAM}}$

Vector databases write continuous streaming data to Write-Ahead Logs (WAL). Provision low-latency NVMe storage:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-nvme-vector-storage
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
parameters:
  type: gp3
  iops: "16000"                         # 16,000 Provisioned IOPS for rapid WAL flush!
  throughput: "1000"                   # 1,000 MB/s throughput for background compaction
  encrypted: "true"
```

## Common Interview Questions

**Q1: How does Hierarchical Navigable Small World (HNSW) achieve $O(\log N)$ search complexity?**

HNSW is a multi-layer graph data structure based on the concept of **Skip Lists**. The top layers contain sparse graphs with long-distance links between distant vector clusters, enabling rapid long-range geometric hops across the vector space. As the search algorithm navigates closer to the query vector, it drops down to lower, denser graph layers to perform local neighborhood exploration. This hierarchical navigation reduces the search space from an exhaustive linear scan ($O(N)$) to logarithmic time ($O(\log N)$).

**Q2: What is the impact of tuning the `M` parameter in an HNSW index?**

`M` defines the **maximum number of bi-directional connection edges (neighbors) assigned to each vector node in the graph** (typically 16 to 64). Increasing `M`:
- **Pros**: Creates a denser graph, significantly improving search recall accuracy ($\ge 99\%$) for high-dimensional or noisy datasets.
- **Cons**: Increases memory consumption linearly (each link requires 8 bytes of RAM) and increases index construction time.

**Q3: How does `efSearch` allow tuning latency vs accuracy at query runtime?**

`efSearch` (or `ef`) controls the size of the dynamic candidate priority list maintained during a live search traversal. Unlike `M` and `efConstruction` (which are fixed at index creation time), **`efSearch` can be adjusted dynamically on every single API request**. A lower `efSearch` (e.g. `32`) returns results in 1ms with 95% accuracy; a higher `efSearch` (e.g. `256`) explores more graph paths, achieving 99.9% accuracy at the cost of 4ms search latency.

**Q4: How does Product Quantization (PQ) differ from Scalar Quantization (SQ8)?**

- **Scalar Quantization (SQ8)**: Compresses each 32-bit floating-point number independently into an 8-bit integer ($0..255$), achieving a fixed **4x memory reduction** with high mathematical fidelity.
- **Product Quantization (PQ)**: Splits a 1536-dimensional vector into smaller sub-vectors (e.g. 192 sub-vectors of 8 dimensions), runs k-means clustering on each sub-space, and replaces the sub-vectors with cluster centroid IDs. PQ can achieve massive **8x to 16x memory reductions**, but introduces higher loss in search recall.

**Q5: Why is high disk IOPS critical for vector databases even when vector search runs entirely in RAM?**

While active vector searches execute in RAM, vector databases must continuously handle **Write-Ahead Logging (WAL) and segment compaction on disk**. High write rates (streaming 10,000 inserts/second) require high sequential write throughput. Furthermore, background compaction processes merge small vector segment files into large immutable segments. If the underlying disk has low IOPS (e.g. standard HDD or throttled cloud disks), disk I/O bottlenecks will stall the streaming ingestion queue and cause API timeouts.
