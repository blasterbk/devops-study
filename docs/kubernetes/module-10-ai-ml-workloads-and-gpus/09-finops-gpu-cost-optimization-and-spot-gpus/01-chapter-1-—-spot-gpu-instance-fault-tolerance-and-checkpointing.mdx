## 1. Automated PyTorch `SIGTERM` Checkpoint Handler

Embed this graceful termination handler inside your Python AI training script:

```python
import signal
import sys
import torch
import boto3

s3_client = boto3.client('s3')
interrupted = False

def handle_sigterm(signum, frame):
    global interrupted
    print("🚨 [ALERT] Received SIGTERM (Spot Interruption Warning)! Flushing checkpoint to S3...")
    interrupted = True

# Register the OS SIGTERM signal handler
signal.signal(signal.SIGTERM, handle_sigterm)

def train_loop(model, optimizer, epoch, dataloader):
    for step, batch in enumerate(dataloader):
        # Normal training step...
        loss = train_step(model, batch)
        
        # Check if Spot Interruption signal was received
        if interrupted:
            checkpoint = {
                'epoch': epoch,
                'step': step,
                'model_state_dict': model.state_dict(),
                'optimizer_state_dict': optimizer.state_dict(),
            }
            torch.save(checkpoint, "/tmp/emergency_checkpoint.pt")
            s3_client.upload_file("/tmp/emergency_checkpoint.pt", "ai-checkpoints", f"checkpoint-step-{step}.pt")
            print(" Checkpoint uploaded to S3 successfully. Exiting cleanly.")
            sys.exit(0)
```

## 2. Production Spot GPU Kubernetes Pod Specification

Configure `terminationGracePeriodSeconds` to match the cloud provider's 2-minute notice:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: spot-llama-trainer
  namespace: ai-training
spec:
  # 1. 120-Second Termination Grace Period (Matches AWS 2-minute warning!)
  terminationGracePeriodSeconds: 120
  
  # 2. Tolerations and Node Selectors targeting Spot GPU pools
  nodeSelector:
    karpenter.sh/capacity-type: spot
    nvidia.com/gpu.product: NVIDIA-H100-SXM5-80GB
  tolerations:
    - key: "nvidia.com/gpu"
      operator: "Exists"
      effect: "NoSchedule"
    - key: "spot"
      operator: "Equal"
      value: "true"
      effect: "NoSchedule"
      
  containers:
  - name: trainer
    image: nvcr.io/nvidia/pytorch:24.04-py3
    command: ["python", "train_with_checkpoint.py"]
    resources:
      limits:
        nvidia.com/gpu: 8
        memory: "256Gi"
        cpu: "64"
```

## Common Interview Questions

**Q1: How much money can an enterprise save by running AI/ML workloads on Spot GPU instances?**

Running AI training workloads on Spot (AWS) or Preemptible (GCP) GPU instances provides **60% to 75% cost reductions** compared to on-demand pricing. For an 8x NVIDIA H100 node, on-demand costs approximately **\$32.77/hour (\$23,500/month)**, whereas Spot pricing averages **\$9.83/hour (\$7,000/month)**. For an enterprise operating a fleet of 20 GPU nodes, this represents over **\$3.9 million in annual infrastructure savings**.

**Q2: What happens when a cloud provider reclaims a Spot GPU instance, and how is it detected?**

When cloud capacity is needed by on-demand customers, the cloud provider issues a **2-Minute Termination Warning** via cloud metadata APIs (e.g. AWS EC2 metadata `http://169.254.169.254/latest/meta-data/spot/instance-action` or EventBridge). Tools like **AWS Node Termination Handler (NTH)** or **Karpenter** intercept this event instantly, mark the Kubernetes node as `Cordoned` (preventing new pods), and send a `SIGTERM` signal to all running pods with a `120-second` grace period.

**Q3: How does PyTorch handle distributed training resumption after a Spot node is interrupted?**

Using **TorchElastic (`torchrun`)**:
1. When a Spot worker node is terminated, the remaining worker processes detect the lost TCP connection.
2. `torchrun` halts the current training epoch.
3. Once the cluster autoscaler (Karpenter) provisions a replacement Spot GPU node, `torchrun` performs an automated **Rendezvous** handshake over etcd or c10d.
4. All worker processes synchronize and reload the latest saved model weights and Adam optimizer states from S3, resuming training with zero human intervention.

**Q4: Why should the Ray Head Node always run on an On-Demand instance while Worker Nodes run on Spot?**

The **Ray Head Node** runs the Global Control Store (GCS), the API server, the Raylet scheduler, and the active task lineage graph. If the Head Node is terminated, the entire distributed Ray session dies, and all active worker state is permanently lost. Running the lightweight Head Node on an inexpensive **On-Demand CPU instance (\$0.15/hour)** guarantees control-plane permanence, while placing the expensive **GPU Worker nodes on Spot (\$9.00/hour)** provides massive cost savings with complete fault tolerance.

**Q5: What is the risk of setting `terminationGracePeriodSeconds` to less than 120 seconds on a Spot GPU training pod?**

Saving large LLM model checkpoints (e.g. a 70B parameter model in FP16 is 140GB) requires streaming gigabytes of tensor data to Amazon S3. If `terminationGracePeriodSeconds` is set to the default of `30 seconds`, Kubernetes will forcefully send a `SIGKILL` after 30 seconds while the S3 upload is only partially complete, **corrupting the checkpoint file and wasting the previous hours of training progress**. Setting `terminationGracePeriodSeconds: 120` gives the pod the full 2-minute cloud warning window to complete the upload safely.
