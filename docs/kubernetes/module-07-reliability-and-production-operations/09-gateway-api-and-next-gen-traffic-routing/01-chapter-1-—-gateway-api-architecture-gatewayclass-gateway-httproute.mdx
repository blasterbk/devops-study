# Chapter 1 — Gateway API Architecture: GatewayClass, Gateway & HTTPRoute

> **Goal:** Master the next-generation service networking standard in Kubernetes with the **Gateway API** (`gateway.networking.k8s.io`) — understanding why Gateway API supersedes the legacy Ingress specification, analyzing the **Role-Oriented Persona Architecture** separating Infrastructure Providers (`GatewayClass`), Cluster Operators (`Gateway`), and Application Developers (`HTTPRoute`), eliminating proprietary annotation sprawl with strongly typed YAML schemas, and routing traffic with multi-vendor portable conformance (Envoy Gateway, Cilium, Istio).
>
> By the end of this chapter, you will understand:
> 1. The architectural limitations of the legacy Ingress API that led to Gateway API
> 2. The 3 Role-Oriented Personas: Infrastructure Provider, Cluster Operator, and App Developer
> 3. The declarative schema and lifecycle of `GatewayClass`, `Gateway`, and `HTTPRoute`
> 4. How typed API fields replace unstructured Ingress annotations (URL rewrites, headers, filters)
> 5. How `parentRefs` bind application routes to shared infrastructure gateways
> 6. How to verify Gateway status conditions and listener readiness

## Real-Life Analogy

Think of the Gateway API as **the modern commercial airport runway, terminal gate, and airline flight assignment system**:

- **The Monolithic Ingress Problem (One Single Paper Form for Everyone):** In the past, the Ingress API tried to make one person write down the concrete runway specifications, the security checkpoint rules, and the gate boarding announcements on a single sheet of paper. To make it work, everyone scribbled hundreds of conflicting, vendor-specific sticky notes all over the margins (**Proprietary Annotations Sprawl**).
- **The Role-Oriented Solution (Gateway API Personas):**
  - **1. The Airport Architect (Infrastructure Provider - `GatewayClass`):** Installs the high-speed radar and concrete runways (**Envoy Gateway, Cilium, Istio Controller**).
  - **2. The Airport Terminal Manager (Cluster Operator - `Gateway`):** Provisions Terminal 1, manages the main security checkpoint, assigns power plugs, and binds official TLS certificates (**`Gateway` on Port 443**).
  - **3. The Airline Flight Dispatcher (Application Developer - `HTTPRoute`):** Delta Airlines or United Airlines (**The Payments Team or Search Team**) simply declares: *"Our flight arrives at Gate 4B; route passengers matching `/v1/orders` to our airplane (**`HTTPRoute` binding to `parentRefs`**)."* Delta cannot accidentally change the airport's runway lights or steal United's gate!

## Complete Production Gateway API Manifests

### 1. `Gateway` Manifest (Managed by Platform Team in `infra` namespace):
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: external-https-gateway
  namespace: gateway-infra
spec:
  gatewayClassName: envoy-gateway      # Binds to cluster GatewayClass
  listeners:
  - name: https-prod
    protocol: HTTPS
    port: 443
    hostname: "api.company.com"
    tls:
      mode: Terminate
      certificateRefs:
      - name: company-wildcard-tls
    allowedRoutes:
      namespaces:
        from: All                      # Allows cross-namespace HTTPRoute attachments!
```

---

### 2. `HTTPRoute` Manifest (Managed by Application Team in `production` namespace):
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: payment-api-route
  namespace: production
spec:
  # 1. Attaches route to the central Gateway in gateway-infra!
  parentRefs:
  - name: external-https-gateway
    namespace: gateway-infra

  hostnames:
  - "api.company.com"

  rules:
  # Rule A: Orders API with Native URL Rewrite Filter!
  - matches:
    - path:
        type: PathPrefix
        value: /v1/orders
    filters:
    - type: URLRewrite
      urlRewrite:
        path:
          type: ReplacePrefixMatch
          replacePrefixMatch: /api/orders
    backendRefs:
    - name: order-service
      port: 8080

  # Rule B: Authentication Service with Exact Match
  - matches:
    - path:
        type: Exact
        value: /v1/auth
    backendRefs:
    - name: auth-service
      port: 8080
```

## Common Interview Questions

**Q1: Why was the Gateway API created to replace the Kubernetes Ingress API?**

The Ingress API suffered from three fundamental design flaws: (1) **Lack of Role Separation**: A single `Ingress` manifest mixed infrastructure concerns (TLS certs, IP addresses) with application concerns (path routing), preventing self-service in multi-tenant environments; (2) **Annotation Sprawl**: Ingress lacked typed fields for basic features like URL rewriting, rate limiting, and header injection, forcing vendors to invent thousands of incompatible proprietary annotations; and (3) **Limited Protocols**: Ingress supported only HTTP/1 and HTTP/2, with no native support for gRPC, TCP, UDP, or TLS pass-through.

**Q2: What are the three primary personas in the Gateway API, and what resources do they own?**

1. **Infrastructure Provider** (owns `GatewayClass`): Configures the underlying ingress controller implementation (e.g. Envoy Gateway, Cilium, Istio).
2. **Cluster Operator / Platform SRE** (owns `Gateway`): Provisions network entry points, configures listening ports (80, 443), attaches TLS certificates, and declares which namespaces are allowed to attach routes.
3. **Application Developer** (owns `HTTPRoute`, `GRPCRoute`): Authors path matching, header routing, URL rewrites, and traffic splitting rules, attaching their route to the shared `Gateway` via `parentRefs`.

**Q3: How does the Gateway API eliminate vendor-specific annotations?**

Gateway API replaces annotations with **strongly typed, standardized API fields and Filters** inside the core specification. Common capabilities—such as `URLRewrite`, `RequestHeaderModifier`, `ResponseHeaderModifier`, `RequestRedirect`, and `RequestMirror`—are first-class schema elements defined in `spec.rules[].filters`. A Gateway API manifest works identically across Envoy Gateway, Cilium, Istio, and Traefik without changing a single line of YAML.

**Q4: How does an `HTTPRoute` in namespace A attach to a `Gateway` in namespace B?**

The `HTTPRoute` declares a `spec.parentRefs` block specifying the name and namespace of the target Gateway (e.g. `name: shared-gateway`, `namespace: gateway-infra`). For the attachment to succeed, the `Gateway`'s listener must explicitly permit cross-namespace attachments via `allowedRoutes.namespaces.from: All` (or `from: Selector`).

**Q5: What status reporting capabilities does Gateway API provide compared to Ingress?**

The Ingress API provides almost zero status visibility. Gateway API provides rich, bidirectional **Condition Reporting** on all objects (`Programmed: True`, `Accepted: True`, `ResolvedRefs: True`, `Conflicted: False`). If an `HTTPRoute` contains an invalid backend service reference or an invalid certificate name, the controller updates the route's `.status.conditions` array with detailed error explanations instantly.
