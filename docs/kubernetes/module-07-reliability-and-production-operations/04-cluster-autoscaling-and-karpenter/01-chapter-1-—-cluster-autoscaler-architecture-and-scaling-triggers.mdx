# Chapter 1 — Cluster Autoscaler Architecture & Scaling Triggers

> **Goal:** Master the internal control loops and scaling mechanics of the **Kubernetes Cluster Autoscaler (CA)** — understanding why CA scales nodes strictly based on **Pending Pods with scheduling failures** rather than CPU/memory utilization thresholds, dissecting simulated scheduling against cloud Auto Scaling Groups (ASGs), mastering scale-down evaluation rules and timers, and overcoming common scale-down blockers using `safe-to-evict` annotations.
>
> By the end of this chapter, you will understand:
> 1. Why Cluster Autoscaler evaluates Pending Pods rather than metric metrics
> 2. How the CA control loop simulates scheduling against cloud node groups
> 3. The 4-step scale-down evaluation algorithm (`scale-down-utilization-threshold: 0.5`)
> 4. The 5 conditions that permanently block a worker node from scaling down
> 5. How to use the `cluster-autoscaler.kubernetes.io/safe-to-evict` annotation
> 6. How to deploy and tune the Cluster Autoscaler for multi-AZ high availability

## Real-Life Analogy

Think of the Cluster Autoscaler as **a hotel manager who orders new hotel rooms built only when guests with reservations are standing in the lobby unable to find an empty bed**:

- **The Metric Misconception (The Thermometer Trap):** If the hotel lobby feels crowded (**High CPU Utilization**), the manager does **not** call the construction company. If guests are already in their rooms watching TV, the hotel is simply doing its job.
- **The True Scaling Trigger (The Guest with Nowhere to Sleep - Pending Pod):** When a guest walks into the lobby with a confirmed booking (**A Pod with `resources.requests`**), but every single bed in the building is occupied (**`FailedScheduling: Insufficient cpu/memory`**), the guest must wait in the lobby (**Pod in `Pending` state**).
- **The Construction Order (Simulated ASG Expansion):** The manager checks their catalog of room blueprints (**Cloud Auto Scaling Groups - ASGs**): *"Blueprint B fits this family of 4."* The manager calls the construction contractor (**Cloud Provider API**) to add 1 room (**ASG Desired Capacity $+1$**).
- **The Checkout & Consolidation (Scale-Down Logic):** If a 100-room wing of the hotel is 80% empty for more than 10 minutes (**`scale-down-unneeded-time: 10m`**), the manager asks the remaining 5 guests to move into the main building and shuts down the wing (**Node Termination**).
- **The "Do Not Disturb" Sign (`safe-to-evict: false`):** If a guest in Room 302 has delicate scientific equipment plugged into the wall (**A batch job that cannot restart**), they hang a "Do Not Disturb" sign on the door. The manager will **never** shut down that hotel wing as long as that guest is inside!

## Why Cluster Autoscaler Does NOT Scale on CPU/Memory Metrics

```text
 ┌────────────────────────────────────────────────────────────────────────────────────────────────────┐
 │ The Fundamental Autoscaling Separation in Kubernetes:                                              │
 ├────────────────────────────────────────────────────────────────────────────────────────────────────┤
 │ 1. Horizontal Pod Autoscaler (HPA): Scales Pods based on METRICS (CPU %, Memory %, Requests/sec).  │
 │ 2. Cluster Autoscaler (CA): Scales Nodes based on SCHEDULING CAPACITY (Pending Pods).              │
 ├────────────────────────────────────────────────────────────────────────────────────────────────────┤
 │ Why CA ignores CPU usage:                                                                          │
 │ If a cluster has 10 nodes at 95% CPU, but zero Pods are Pending, the cluster is operating at peak │
 │ efficiency! Adding nodes would waste cloud money. Nodes are only added when Pods CANNOT schedule!  │
 └────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

## Scale-Down Evaluation Algorithm

Cluster Autoscaler continuously checks if worker nodes can be removed to eliminate idle waste:

$$\text{Node Utilization} = \max\left( \frac{\sum \text{Pod CPU Requests}}{\text{Node Allocatable CPU}}, \frac{\sum \text{Pod Memory Requests}}{\text{Node Allocatable Memory}} \right)$$

```text
 Scale-Down Execution Sequence:
 1. A node's utilization drops below `scale-down-utilization-threshold` (Default: 0.5 / 50%).
 2. CA runs a simulation to verify that ALL pods on the node can fit onto OTHER existing nodes.
 3. The node remains underutilized continuously for `--scale-down-unneeded-time` (Default: 10m).
 4. CA marks the node unschedulable (Cordon), drains the pods, and terminates the cloud VM.
```

## The 5 Scale-Down Blockers

A node will **never** be scaled down if any of these 5 conditions are met:

```text
 ┌──────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
 │ Blocker Condition    │ Root Cause & How to Resolve                                                 │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **1. Naked Pods**    │ Pods created directly without a Controller (Deployment, StatefulSet, Job).  │
 │                      │ Evicting a naked pod destroys it permanently. CA refuses to delete it!      │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **2. Local Storage** │ Pods using local `emptyDir` or `hostPath` volumes (Data loss risk).         │
 │                      │ Resolve: Set `cluster-autoscaler.kubernetes.io/safe-to-evict: "true"`.      │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **3. Explicit Safe-**│ Pod has annotation: `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"`│
 │ **to-Evict: False**  │ Used to protect mission-critical long-running batch/ML jobs from eviction.  │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **4. PDB Violation** │ Evicting the pod would violate its `PodDisruptionBudget` `minAvailable`.   │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **5. No Destination**│ No other node in the cluster has sufficient unreserved capacity to host pods│
 └──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## Complete Production Cluster Autoscaler Deployment Manifest

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cluster-autoscaler
  namespace: kube-system
  labels:
    app: cluster-autoscaler
spec:
  replicas: 2                          # HA Active-Passive (Uses Leader Election!)
  selector:
    matchLabels:
      app: cluster-autoscaler
  template:
    metadata:
      labels:
        app: cluster-autoscaler
    spec:
      serviceAccountName: cluster-autoscaler
      priorityClassName: system-cluster-critical
      containers:
      - name: cluster-autoscaler
        image: registry.k8s.io/autoscaling/cluster-autoscaler:v1.30.0
        command:
        - ./cluster-autoscaler
        - --v=4
        - --stderrthreshold=info
        - --cloud-provider=aws
        - --skip-nodes-with-local-storage=false
        - --expander=least-waste        # Chooses node group with least idle waste!
        - --node-group-auto-discovery=asg:tag=k8s.io/cluster-autoscaler/enabled,k8s.io/cluster-autoscaler/production-cluster
        - --balance-similar-node-groups=true # Balances nodes evenly across Availability Zones!
        - --scale-down-enabled=true
        - --scale-down-utilization-threshold=0.5
        - --scale-down-unneeded-time=10m
        - --scale-down-delay-after-add=10m
        - --max-node-provision-time=15m
        resources:
          requests:
            cpu: 100m
            memory: 300Mi
          limits:
            cpu: 500m
            memory: 1Gi
```

## Hands-On Lab: Observing Cluster Autoscaler Status

```bash
# Step 1: Query Cluster Autoscaler status ConfigMap in kube-system
kubectl get configmap cluster-autoscaler-status -n kube-system -o yaml 2>/dev/null || echo "Cluster Autoscaler active / simulated"

# Step 2: Annotate a pod to prevent node scale-down
kubectl annotate pod my-critical-pod cluster-autoscaler.kubernetes.io/safe-to-evict="false" --overwrite 2>/dev/null || true

# Step 3: Trigger a simulated scale-up by creating an oversized Pending Pod
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: oversized-pending-pod
spec:
  restartPolicy: Never
  containers:
  - name: sleeper
    image: alpine:latest
    command: ["sleep", "3600"]
    resources:
      requests:
        cpu: "999"                     # Impossible capacity triggers FailedScheduling!
EOF

# Step 4: Verify Pod is in Pending state
kubectl get pod oversized-pending-pod

# Step 5: Clean up lab
kubectl delete pod oversized-pending-pod
```

## Common Interview Questions

**Q1: Why does the Kubernetes Cluster Autoscaler scale on Pending Pods rather than node CPU or memory utilization?**

Node CPU and memory metrics fluctuate rapidly. High CPU usage does not necessarily mean the cluster needs more nodes—it indicates that existing hardware is being utilized efficiently. The Cluster Autoscaler is specifically designed to solve **unschedulable workload bottlenecks**: it scales up when and only when the `kube-scheduler` marks a Pod as `Pending` due to `FailedScheduling` (insufficient allocatable CPU, memory, or port capacity), ensuring cloud spend occurs only when workloads genuinely cannot run.

**Q2: How does the Cluster Autoscaler simulate scheduling before making a cloud API call?**

When Pending Pods are detected, the Cluster Autoscaler inspects its registered cloud node group templates (ASGs/MIGs). It runs an in-memory simulation of the Kubernetes scheduler's filtering and scoring algorithms against a virtual node created from the ASG template. If the simulation proves that the Pending Pods will successfully bind to that node template (matching taints, affinities, and resource requests), CA makes the cloud API call to increment the group's desired capacity.

**Q3: What is the purpose of the `--expander` flag in Cluster Autoscaler?**

When multiple node groups can satisfy a pending pod's requirements, the **Expander** determines which node group to scale:
- `random`: Picks a matching node group at random.
- `most-pods`: Selects the node group that can schedule the highest number of pending pods.
- `least-waste`: Selects the node group that will have the smallest percentage of unallocated idle CPU/RAM after scheduling.
- `price`: (GCP/AWS) Chooses the node group with the lowest financial cost.
- `priority`: Uses a declarative ConfigMap to prioritize specific node groups (e.g. Spot instances before On-Demand).

**Q4: What causes a worker node to be blocked from scaling down even if its utilization is at 10%?**

Common scale-down blockers include:
1. **Naked Pods**: Pods created without a controller (Deployment/StatefulSet) that would be permanently lost upon eviction.
2. **Local Storage**: Pods using `emptyDir` or `hostPath` without the `safe-to-evict: "true"` annotation.
3. **PDB Constraints**: Evicting pods would violate an active `PodDisruptionBudget`.
4. **`safe-to-evict: "false"`**: An explicit annotation preventing automated eviction.
5. **No Capacity Elsewhere**: Other nodes in the cluster cannot accommodate the evicted pods.

**Q5: How does the `--balance-similar-node-groups=true` flag protect multi-AZ high availability?**

In cloud environments with multi-AZ clusters (e.g. `us-east-1a`, `us-east-1b`, `us-east-1c`), scaling down randomly could terminate all nodes in `us-east-1a`, leaving workloads unbalanced across zones. Setting `--balance-similar-node-groups=true` forces the Autoscaler to maintain an identical node count across all matching regional node groups, ensuring consistent multi-AZ failure domain distribution.
