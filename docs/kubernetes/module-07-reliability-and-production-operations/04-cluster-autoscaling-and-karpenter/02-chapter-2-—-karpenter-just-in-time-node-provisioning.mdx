# Chapter 2 — Karpenter Just-In-Time Node Provisioning

> **Goal:** Master next-generation, high-performance node autoscaling in Kubernetes using **CNCF Karpenter** — understanding how Karpenter bypasses legacy cloud Auto Scaling Groups to provision right-sized instances directly via cloud fleet APIs in under 45 seconds, configuring declarative **`NodePool`** and **`EC2NodeClass`** Custom Resources, mastering multi-architecture (ARM64 vs AMD64) and Spot diversification, and automating zero-waste node consolidation (`WhenUnderutilized`).
>
> By the end of this chapter, you will understand:
> 1. The architectural advantages of Karpenter over the legacy Cluster Autoscaler
> 2. How Karpenter provisions bare VM instances in $<45$ seconds directly via cloud APIs
> 3. The declarative schema of `NodePool` (workload policy) and `EC2NodeClass` (infrastructure spec)
> 4. How Karpenter dynamically selects the cheapest instance type matching pod resource constraints
> 5. How automated Node Consolidation (`WhenUnderutilized`) continuously eliminates idle waste
> 6. How to manage automated 30-day security AMI rotation using `expireAfter`

## Real-Life Analogy

Think of Karpenter vs Cluster Autoscaler as **ordering a bespoke custom-tailored suit delivered by an on-demand drone in 30 minutes versus buying pre-made suits from a department store catalog with a 2-week shipping delay**:

- **The Legacy Cluster Autoscaler (The Rigid Department Store Catalog):** You must pre-configure 10 rigid, static store aisles (**10 AWS Auto Scaling Groups - ASGs**): one ASG for 4-core AMD, one for 8-core Intel, one for GPUs. If a pod needs 5 cores, CA orders an entire 8-core ASG box (**Wasted Idle Capacity**), and AWS takes 5 minutes to spin up the ASG template.
- **Karpenter (The AI Tailor with 3D Printing Drones):** Karpenter doesn't use pre-configured aisles or ASGs. When 5 pods arrive with odd CPU and RAM requests, Karpenter's mathematical bin-packing solver instantly scans all 500 EC2 instance types available in the cloud datacenter (**`c6g.xlarge`, `m5.large`, `r6i.2xlarge`**), selects the **single cheapest instance that fits all 5 pods perfectly**, and launches the VM directly via cloud APIs in **under 45 seconds**.
- **The Continuous Clothes Tailor (Node Consolidation - `WhenUnderutilized`):** When 3 of those pods finish their work, Karpenter notices that the remaining 2 pods can fit on a tiny \$0.04/hr instance. It orders the tiny instance, migrates the 2 pods seamlessly, and terminates the expensive node immediately.

## Declarative Architecture: `NodePool` & `EC2NodeClass`

Karpenter separates workload requirements (`NodePool`) from cloud-specific infrastructure definitions (`EC2NodeClass`):

### 1. `EC2NodeClass` (Infrastructure Configuration):
```yaml
apiVersion: karpenter.k8s.aws/v1beta1
kind: EC2NodeClass
metadata:
  name: default-ec2-infra
spec:
  amiFamily: AL2                      # Amazon Linux 2 (or Bottlerocket, Ubuntu)
  role: "KarpenterNodeRole-production"
  subnetSelectorTerms:
    - tags:
        karpenter.sh/discovery: "production-cluster"
  securityGroupSelectorTerms:
    - tags:
        karpenter.sh/discovery: "production-cluster"
  blockDeviceMappings:
    - deviceName: /dev/xvda
      ebs:
        volumeSize: 50Gi
        volumeType: gp3
        encrypted: true
```

---

### 2. `NodePool` (Workload & Lifecycle Policy):
```yaml
apiVersion: karpenter.sh/v1beta1
kind: NodePool
metadata:
  name: default-workload-pool
spec:
  template:
    spec:
      nodeClassRef:
        name: default-ec2-infra

      # 1. Instance Constraints & Diversification
      requirements:
        - key: "karpenter.sh/capacity-type"
          operator: In
          values: ["spot", "on-demand"] # Prefers Spot; falls back to On-Demand
        - key: "kubernetes.io/arch"
          operator: In
          values: ["arm64", "amd64"]    # Supports both Graviton ARM & Intel/AMD!
        - key: "karpenter.k8s.aws/instance-category"
          operator: In
          values: ["c", "m", "r"]       # Compute, General, and Memory optimized
        - key: "karpenter.k8s.aws/instance-generation"
          operator: Gt
          values: ["4"]                 # Modern generations only (5, 6, 7)

  # 2. Automated Disruption & Consolidation Policies
  disruption:
    consolidationPolicy: WhenUnderutilized # Merges and downsizes underutilized nodes!
    consolidateAfter: 30s
    expireAfter: 720h                   # Automated 30-day AMI security patching rotation!

  # 3. Resource Spending Ceilings
  limits:
    cpu: "1000"                        # Maximum cluster CPU capacity managed by this pool
    memory: "4000Gi"
```

## Automated Node Consolidation (`WhenUnderutilized`)

Karpenter continuously audits the cost efficiency of all worker nodes in the cluster:

```text

 │ How Consolidation Eliminates Cloud Waste:                                                          │
 ├────────────────────────────────────────────────────────────────────────────────────────────────────┤
 │ 1. Empty Node Deletion: If a node has zero pods (or only DaemonSets), Karpenter terminates it     │
 │    after `consolidateAfter: 30s`.                                                                  │
 │ 2. Multi-Node Merge: If Node A ($0.20/hr) and Node B ($0.20/hr) are both at 30% utilization,       │

 │ 3. Single Node Downsizing: If an m5.2xlarge node is running pods that can fit on an m5.large,      │

```

## Common Interview Questions

**Q1: How does Karpenter provision nodes so much faster than the legacy Cluster Autoscaler?**

The legacy Cluster Autoscaler relies on Cloud Provider **Auto Scaling Groups (ASGs)**. CA must make an API call to the ASG, the ASG invokes EC2, the instance boots, executes user-data scripts, joins the cluster, and registers with the API server (taking 3 to 7 minutes). Karpenter is **group-less**: it bypasses ASGs completely, directly invoking the cloud fleet API (`ec2:CreateFleet`) with custom launch templates. It parallelizes node bootstrapping, bringing fully ready nodes online in **under 45 seconds**.

**Q2: What is the separation of responsibilities between `NodePool` and `EC2NodeClass` in Karpenter?**

- **`NodePool`**: Defines **workload scheduling rules and lifecycle policies** (e.g. CPU/RAM limits, allowed instance families `c`, `m`, `r`, Spot vs On-Demand preference, consolidation triggers `WhenUnderutilized`, and node expiration `expireAfter`).
- **`EC2NodeClass`**: Defines **cloud-specific infrastructure and security configurations** (e.g. AWS subnet selectors, security groups, AMI family, EBS root disk volume encryption, and IAM instance roles).

**Q3: How does Karpenter's `WhenUnderutilized` consolidation policy work?**

When `consolidationPolicy: WhenUnderutilized` is configured, Karpenter continuously runs bin-packing simulations against active nodes. If it identifies that a group of underutilized nodes can be consolidated onto a single cheaper instance, or that a large node can be replaced by a smaller instance, Karpenter: (1) Provisions the cheaper replacement node; (2) Cordon and drains the old nodes respecting PDBs; and (3) Terminates the old instances once workloads are running smoothly, eliminating idle capacity waste automatically.

**Q4: How does Karpenter achieve high availability with Spot instances?**

Karpenter leverages **Spot Diversification**: instead of restricting a node group to a single instance type (e.g. `m5.large`), Karpenter's `requirements` block allows selecting across hundreds of instance types and generations (`c5`, `c6g`, `m5`, `m6g`, `r5`). When requesting capacity, Karpenter uses the AWS `price-capacity-optimized` allocation strategy to select Spot pools with the lowest risk of interruption, while automatically falling back to On-Demand if Spot capacity is unavailable in a specific AZ.

**Q5: What is the purpose of the `expireAfter` setting in Karpenter NodePools?**

`expireAfter` (e.g. `expireAfter: 720h` / 30 days) defines the maximum lifespan of a worker node. When a node reaches its expiration deadline, Karpenter marks it for replacement, provisions a fresh node with the latest OS security patches and updated AMI, migrates workloads gracefully, and terminates the old node. This enforces **automated, immutable OS patching** across the entire cluster without manual maintenance windows.
