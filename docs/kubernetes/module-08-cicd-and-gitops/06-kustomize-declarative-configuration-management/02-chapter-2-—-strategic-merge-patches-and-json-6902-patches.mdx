## Real-Life Analogy

Think of Strategic Merge Patches vs JSON 6902 Patches as **two different surgical techniques used to modify a complex machine blueprint**:

- **The Strategic Merge Patch (The Context-Aware Mechanical Surgeon):** You hand the mechanic a mini-blueprint that says: *"Find the container named `api-worker` and increase its memory to 4GiB."* The mechanic understands the internal structure of Kubernetes objects (**Schema-Aware**). They find `api-worker` in the container list by its name (**`patchMergeKey: name`**) and update only that specific container without touching any other sidecars.
- **The JSON 6902 Patch (The Precision Microscopic Scalpel - RFC 6902):** A strict, mathematical, coordinate-based surgical cut:
  - Step 1: Walk to line coordinates `/spec/template/spec/containers/0/args/2`.
  - Step 2: **`op: replace`** $\to$ Change the string to `--log-level=debug`.
  - Step 3: **`op: add`** $\to$ Insert a new environment variable at index `3`.
- **The Trade-Off:** Strategic Merge Patches are human-readable, robust, and intuitive. JSON 6902 patches provide absolute mathematical control when modifying unnamed lists or deleting specific array indices that lack merge keys.

## Strategic Merge Patching (SMP) Mechanics

Strategic Merge Patching is Kubernetes' default patching format. It uses the API's OpenAPI schema to determine how lists are merged using the **`patchMergeKey`** (e.g. `name` for container arrays):

```yaml
# overlays/production/patch-resources.yaml (SMP Format)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  replicas: 10                         # Directly overrides scalar replica count
  template:
    spec:
      containers:
      # Matches existing container by name: "payment-api" and merges fields!
      - name: payment-api
        resources:
          requests:
            cpu: 500m
            memory: 1Gi
          limits:
            cpu: 2000m
            memory: 4Gi
      # Merges a brand-new logging sidecar into the existing container list!
      - name: vector-log-agent
        image: timberio/vector:0.35.0-alpine
```

### Deleting Elements with SMP Directives:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
spec:
  template:
    spec:
      containers:
      # Permanently deletes a debug sidecar present in the base manifest!
      - name: debug-sidecar
        $patch: delete
```

## RFC 6902 JSON Patching Mechanics

When patching unnamed arrays (such as container command arguments or toleration lists), use **RFC 6902 JSON Patches**:

```yaml
# overlays/production/patch-json6902.yaml
- op: replace
  path: /spec/template/spec/containers/0/args/1
  value: "--enable-clustering=true"

- op: add
  path: /spec/template/spec/nodeSelector
  value:
    topology.kubernetes.io/zone: "us-east-1a"

- op: remove
  path: /spec/template/spec/containers/0/env/2
```

The 6 RFC 6902 Operations:

```text
 ┌──────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
 │ Operation (`op`)     │ Meaning & Syntax Example                                                    │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`add`**            │ Inserts a new field or appends an element to an array.                      │
 │                      │ `{ op: "add", path: "/spec/replicas", value: 5 }`                           │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`remove`**         │ Deletes the targeted field or array index.                                  │
 │                      │ `{ op: "remove", path: "/spec/template/spec/tolerations/0" }`               │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`replace`**        │ Replaces an existing value with a new value.                                │
 │                      │ `{ op: "replace", path: "/spec/template/spec/dnsPolicy", value: "Cluster" }`│
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`move`**           │ Moves a value from one path to another within the document.                 │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`copy`**           │ Copies a value from one path to another.                                    │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`test`**           │ Verifies that a target path equals a specific value before applying patch.  │
 └──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## Modern `patches` Syntax in `kustomization.yaml`

Modern Kustomize consolidates all patching into the top-level **`patches`** block, supporting both inline and external files:

```yaml
# overlays/production/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - ../../base

patches:
  # 1. External Strategic Merge Patch File
  - path: patch-resources.yaml

  # 2. Targeted Inline Strategic Merge Patch
  - target:
      group: apps
      version: v1
      kind: Deployment
      name: payment-api
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 10

  # 3. Targeted Inline JSON 6902 Patch
  - target:
      kind: Service
      name: payment-service
    patch: |-
      - op: replace
        path: /spec/type
        value: LoadBalancer
```

## Hands-On Lab: Testing Strategic Merge vs JSON Patches

```bash
# Step 1: Create lab directory structure
mkdir -p /tmp/patch-lab/base /tmp/patch-lab/prod

# Step 2: Create base deployment with an argument list
cat <<EOF > /tmp/patch-lab/base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-server
spec:
  replicas: 1
  template:
    spec:
      containers:
      - name: nginx
        image: nginx:alpine
        args: ["-g", "daemon off;"]
EOF

cat <<EOF > /tmp/patch-lab/base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
EOF

# Step 3: Create production overlay with an inline JSON 6902 patch
cat <<EOF > /tmp/patch-lab/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
patches:
  - target:
      kind: Deployment
      name: web-server
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 5
      - op: add
        path: /spec/template/spec/containers/0/resources
        value:
          limits:
            memory: "512Mi"
EOF

# Step 4: Render and verify the patched output!
kubectl kustomize /tmp/patch-lab/prod

# Step 5: Clean up lab
rm -rf /tmp/patch-lab
```

## Common Interview Questions

**Q1: What is the fundamental difference between a Strategic Merge Patch (SMP) and an RFC 6902 JSON Patch in Kustomize?**

- **Strategic Merge Patch (SMP)**: A Kubernetes-specific, **schema-aware** patching format. It uses standard YAML structures and leverages the API server's OpenAPI schema to merge lists using keys (e.g. matching containers by `name` rather than index).
- **RFC 6902 JSON Patch**: A standard, **schema-agnostic** operations format (`op: add`, `remove`, `replace`). It operates on exact path pointers and array indices (e.g. `/spec/containers/0/args/1`), providing surgical control when modifying unnamed arrays or deleting specific keys.

**Q2: How does `patchMergeKey` work in Strategic Merge Patching?**

When Kubernetes merges a list (such as `spec.containers`), it checks the schema's `patchMergeKey` (which for containers is defined as `name`). Instead of replacing the entire container array, Kustomize matches existing containers by their `name` value, merging the new fields (e.g. `resources`, `image`) into the existing container and preserving all other containers in the list.

**Q3: How do you delete a specific container or environment variable using Strategic Merge Patching?**

To delete an item from a list using SMP, add the **`$patch: delete`** directive to the target element:
```yaml
containers:
- name: unwanted-sidecar
  $patch: delete
```
When Kustomize builds the manifest, it locates `unwanted-sidecar` and purges it entirely from the rendered output.

**Q4: When must you use an RFC 6902 JSON Patch instead of a Strategic Merge Patch?**

You must use an RFC 6902 JSON patch when: (1) Patching lists of primitive scalar types (like container `args: ["-a", "-b"]` or `command`) which lack a `patchMergeKey`; (2) Deleting an element from an array that does not support SMP directives; or (3) Executing conditional patches using the `test` operation.

**Q5: What is the `test` operation in an RFC 6902 JSON Patch, and why is it useful?**

The `test` operation verifies that a specific path contains an expected value before applying subsequent mutations:
`{ op: "test", path: "/spec/replicas", value: 1 }`.
If the live or base value does not equal `1`, Kustomize fails the build immediately. This acts as a safety guardrail, preventing patches from applying if the underlying base architecture has unexpectedly drifted.
