# Chapter 2 — Application & AppProject CRDs

> **Goal:** Master the declarative configuration and multi-tenant governance of Argo CD using **`Application`** and **`AppProject`** Custom Resource Definitions (CRDs) — understanding how `Application` orchestrates declarative source-to-destination bindings, tuning advanced sync options (`ServerSideApply`, `selfHeal`, `PruneLast`), ordering multi-tiered deployments using **Sync Waves** (`sync-wave`) and **Resource Hooks** (`PreSync`, `PostSync`), and establishing multi-tenant project guardrails using `AppProject` resource whitelists.
>
> By the end of this chapter, you will understand:
> 1. The complete declarative schema of the `Application` CRD
> 2. How `AppProject` isolates tenants by restricting source repos, clusters, and namespaces
> 3. How to prevent unauthorized cluster-scoped resource creation using `clusterResourceBlacklist`
> 4. How Sync Waves order resource deployments (Database Migrations $\to$ Backend $\to$ Ingress)
> 5. How Resource Hooks execute schema migrations and automated smoke tests
> 6. How the **App-of-Apps** pattern bootstraps entire Kubernetes cluster fleets from a single root manifest

## Real-Life Analogy

Think of `Application` and `AppProject` as **a high-tech automated skyscraper construction contract and the city zoning code**:

- **The Construction Project Contract (`Application` CRD):** A detailed contract that says: *"Take the architectural blueprints located in Cabinet 4 of the Architect's Office (**`source.repoURL` + `path`**), and construct this exact building on Plot 14 in the Downtown District (**`destination.server` + `namespace`**). If someone vandalizes the building, repair it immediately (**`selfHeal: true`**)."*
- **The Phased Construction Schedule (Sync Waves - `sync-wave`):** You cannot install the roof before pouring the concrete foundation. The contract specifies:
  - Wave 0: Excavate dirt and lay water pipes (**Namespaces & Secrets**).
  - Wave 1: Pour concrete foundation (**Database Schema Migrations - `PreSync` Hook**).
  - Wave 2: Build the walls and rooms (**Microservice Deployments**).
  - Wave 3: Turn on the neon entrance sign (**Ingress & DNS**).
- **The City Zoning Board Guardrails (`AppProject` CRD):** The city zoning board issues a strict construction permit to the junior residential contractor (**The Frontend Dev Team**): *"You are permitted to build 2-story houses in Residential District A (**Namespace Whitelist**), but you are STRICTLY FORBIDDEN from building nuclear reactors or public bridges (**ClusterResourceBlacklist: No ClusterRoles or StorageClasses**)."*

## Complete Production `AppProject` Multi-Tenancy Manifest

The `AppProject` resource establishes hard security boundaries for specific development teams:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payment-team-project
  namespace: argocd
spec:
  description: "Governance boundary for Payment Engineering Team"

  # 1. Allowed Source Git Repositories
  sourceRepos:
  - "https://github.com/enterprise-org/payment-gitops-*.git"

  # 2. Allowed Target Destination Clusters & Namespaces
  destinations:
  - namespace: "payment-prod"
    server: "https://kubernetes.default.svc"
  - namespace: "payment-staging"
    server: "https://kubernetes.default.svc"

  # 3. Security Guardrail: Block Dangerous Cluster-Scoped Resources!
  clusterResourceBlacklist:
  - group: ""
    kind: Node
  - group: "rbac.authorization.k8s.io"
    kind: ClusterRole
  - group: "rbac.authorization.k8s.io"
    kind: ClusterRoleBinding
  - group: "apiextensions.k8s.io"
    kind: CustomResourceDefinition

  # 4. Scoped RBAC Roles inside Argo CD
  roles:
  - name: developer
    description: "Read-only access for developers"
    policies:
    - p, proj:payment-team-project:developer, applications, get, payment-team-project/*, allow
    - p, proj:payment-team-project:developer, applications, sync, payment-team-project/*, allow
```

## Complete Production `Application` Manifest with Advanced Options

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-service-app
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: payment-team-project        # Bound to our secure AppProject!

  # 1. Declarative Source Specification
  source:
    repoURL: https://github.com/enterprise-org/payment-gitops-manifests.git
    targetRevision: main
    path: environments/production
    kustomize:
      images:
      - 'ghcr.io/enterprise/payment-api:v2.4.0'

  # 2. Destination Cluster & Namespace
  destination:
    server: https://kubernetes.default.svc
    namespace: payment-prod

  # 3. Production Sync Policy & Options
  syncPolicy:
    automated:
      prune: true                      # Deletes live resources removed from Git!
      selfHeal: true                   # Overwrites out-of-band manual changes!
    syncOptions:
      - CreateNamespace=true
      - ServerSideApply=true           # Solves massive CRD schema limits & field ownership!
      - ApplyOutOfSyncOnly=true        # High-performance sync: applies only changed objects!
      - PruneLast=true                 # Deletes dead objects ONLY after new ones are healthy!
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m
```

## Sync Waves & Resource Hooks Ordering

Use annotations in workload manifests to control exact deployment order:

```text
 ┌──────────────────────┬─────────────────────────┬───────────────────────────────────────────────────┐
 │ Phase / Wave         │ Annotation              │ Typical Use Case & Execution Rule                 │
 │──────────────────────┼─────────────────────────┼───────────────────────────────────────────────────┤
 │ **PreSync Hook**     │ `argocd/hook: PreSync`  │ Database schema migrations (`Flyway`, `Liquibase` │
 │                      │                         │ Run BEFORE any application pods update.           │
 │──────────────────────┼─────────────────────────┼───────────────────────────────────────────────────┤
 │ **Wave -1 / Wave 0** │ `argocd/sync-wave: "0"` │ Namespaces, CRDs, ConfigMaps, and SealedSecrets.  │
 │──────────────────────┼─────────────────────────┼───────────────────────────────────────────────────┤
 │ **Wave 1 / Wave 2**  │ `argocd/sync-wave: "1"` │ Deployments, StatefulSets, and DaemonSets. Waits  │
 │                      │                         │ until pods pass Readiness Probes before Wave 2!   │
 │──────────────────────┼─────────────────────────┼───────────────────────────────────────────────────┤
 │ **PostSync Hook**    │ `argocd/hook: PostSync` │ Integration smoke tests, Slack deployment alerts, │
 │                      │                         │ cache-warming jobs.                               │
 └──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

```yaml
# Example Database Migration Job using PreSync Hook:
apiVersion: batch/v1
kind: Job
metadata:
  name: payment-db-migration
  namespace: payment-prod
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded # Auto-cleans job upon success!
spec:
  template:
    spec:
      restartPolicy: OnFailure
      containers:
      - name: flyway
        image: flyway/flyway:10.0
        args: ["migrate"]
```

## Common Interview Questions

**Q1: What is the difference between an `Application` and an `AppProject` in Argo CD?**

- **`Application`**: A declarative deployment contract that binds a specific Git/Helm source repository and path to a target Kubernetes cluster and namespace, configuring sync policies, pruning, and self-healing.
- **`AppProject`**: A multi-tenant governance and security boundary. It acts as an administrative fence that restricts which Git repositories an Application can pull from, which clusters/namespaces it can deploy into, which cluster-scoped resources it is allowed to create, and what internal RBAC roles are assigned to developers.

**Q2: How do Sync Waves (`argocd.argoproj.io/sync-wave`) ensure zero-downtime multi-tier deployments?**

Sync Waves order the application of Kubernetes resources using integer values (e.g. Wave 0, Wave 1, Wave 2). Argo CD applies all resources in Wave 0 first and pauses. It waits for all Wave 0 resources to reach a **`Healthy`** status (e.g. database pods pass readiness probes or migration jobs exit 0) before initiating Wave 1. If a migration job in Wave 0 fails, Argo CD halts the rollout, preventing broken backend pods in Wave 1 from ever starting.

**Q3: What is the difference between an Argo CD `PreSync` Hook and a `PostSync` Hook?**

- **`PreSync` Hook**: Runs *before* any of the main application manifests are applied. It is typically used for database schema migrations, backup verification, or prerequisite validation.
- **`PostSync` Hook**: Runs *after* all main manifests have been successfully applied and all pods have reached a `Healthy` status. It is used for post-deployment automated integration testing, cache-warming scripts, or triggering downstream notification webhooks.

**Q4: Why should production Argo CD Applications enable `syncOptions: [ServerSideApply=true]`?**

Client-side apply (`kubectl apply`) stores the entire resource manifest in the `kubectl.kubernetes.io/last-applied-configuration` annotation, which fails with `metadata.annotations: Too long` when managing massive Custom Resource Definitions (CRDs) or large ConfigMaps (> 256KB). **Server-Side Apply (SSA)** delegates field management and 3-way merging directly to the Kubernetes API server, eliminating annotation size limits, properly tracking field ownership, and accelerating sync performance.

**Q5: What is the "App-of-Apps" pattern in Argo CD?**

The App-of-Apps pattern is an architectural bootstrap pattern where a single "Root" Argo CD `Application` points to a Git repository containing manifests of *other* Argo CD `Application` CRDs. When the root application syncs, it creates all sub-applications (e.g. Prometheus, Ingress-NGINX, Payment API, Auth Service). This enables full cluster bootstrapping from a single declarative entry point.
