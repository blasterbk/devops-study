# Chapter 1 — The 4 Core Principles of GitOps

> **Goal:** Master the architectural philosophy and operational standards of **GitOps** defined by the CNCF **OpenGitOps Working Group** — understanding why Git serves as the single authoritative source of truth for Kubernetes infrastructure and workloads, dissecting the 4 core principles (**Declarative**, **Versioned & Immutable**, **Pulled Automatically**, and **Continuously Reconciled**), analyzing automated drift detection and self-healing mechanics, and eliminating un-audited manual `kubectl` interventions.
>
> By the end of this chapter, you will understand:
> 1. The 4 official CNCF OpenGitOps principles and their architectural implications
> 2. How Git functions as the Single Source of Truth (SSoT) for cluster state
> 3. The difference between Drift Detection (observing divergence) and Drift Correction (Self-Healing)
> 4. Why direct cluster access (`kubectl apply`/`edit`) is considered an anti-pattern in GitOps
> 5. How GitOps enables instant Disaster Recovery by re-hydrating new clusters from Git commits
> 6. How to author declarative reconciliation manifests for continuous state convergence

## Real-Life Analogy

Think of GitOps as **a certified corporate architectural ledger and a team of autonomous automated construction robots**:

- **The Imperative Chaos (The Manual Worker Trap):** In traditional IT, 10 different human engineers walk into a physical server room with screwdrivers and soldering irons (**Running manual `kubectl edit` and `kubectl apply` commands on production**). Nobody writes down what they changed, there is no audit log, and if the datacenter burns down, nobody knows how to rebuild the servers (**Configuration Drift & Tribal Knowledge Disaster**).
- **The GitOps Standard (The Notarized Vault Ledger):** Under GitOps, humans are **forbidden** from touching the physical construction site (**Zero Direct Cluster Access**). Instead, all proposed changes must be written into an official blueprinted ledger (**The Git Repository**).
- **The 4 OpenGitOps Rules:**
  - **1. Declarative:** The blueprint describes the finished house (*"3 Bedrooms, 2 Baths"*), not step-by-step bricklaying instructions.
  - **2. Versioned & Immutable:** Every single blueprint revision is stamped with a tamper-proof cryptographic seal (**Git Commit SHA-1 / SHA-256**), signed by an engineer (**GPG Signature**), and approved via peer review (**Pull Request**).
  - **3. Pulled Automatically:** Autonomous robots inside the building (**Argo CD / Flux CD**) watch the blueprint ledger through a secure glass window.
  - **4. Continuously Reconciled:** If an earthquake knocks down a wall or a rogue human paints a door red (**Configuration Drift**), the autonomous robot instantly detects the divergence and repaints the door back to the blueprint specification (**Automated Self-Healing**).

## Single Source of Truth (SSoT) & The "No kubectl" Rule

In a mature GitOps organization, **human engineers do not have write permissions to the production Kubernetes API server**:

```text
 ┌────────────────────────────────────────────────────────────────────────────────────────────────────┐
 │ The Problem with Manual `kubectl` Mutations:                                                       │
 ├────────────────────────────────────────────────────────────────────────────────────────────────────┤

 │ 2. Configuration Drift: Live cluster diverges from Git manifests; future CI/CD runs overwrite fixes.│
 │ 3. Unrepeatable Disasters: If the cluster is destroyed, manual runtime tweaks are lost forever.    │
```

## Complete Production Declarative GitOps Manifest

An example Argo CD `Application` enforcing continuous reconciliation and self-healing:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-service-production
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io # Deletes resources when Application is deleted
spec:
  project: default

  # 1. Declarative & Versioned Source
  source:
    repoURL: https://github.com/enterprise-org/k8s-gitops-manifests.git
    targetRevision: main               # Tracks specific Git branch, tag, or commit SHA
    path: environments/production/payment-api

  # 2. Target Destination
  destination:
    server: https://kubernetes.default.svc
    namespace: production

  # 3. Automated Pulling & Continuous Self-Healing Sync Policy
  syncPolicy:
    automated:
      prune: true                      # Deletes cluster resources removed from Git!
      selfHeal: true                   # Instantly overwrites out-of-band manual kubectl edits!
      allowEmpty: false
    syncOptions:
      - CreateNamespace=true           # Auto-creates target namespace
      - PruneLast=true                 # Prunes resources at the end of sync wave
```

## Common Interview Questions

**Q1: What are the 4 core principles of GitOps according to the CNCF OpenGitOps standard?**

1. **Declarative**: The desired state of the entire system must be defined declaratively (e.g. Kubernetes manifests).
2. **Versioned and Immutable**: The desired state is stored in an immutable, version-controlled repository (Git) with complete commit and audit history.
3. **Pulled Automatically**: In-cluster software agents automatically pull and apply the desired state from Git without requiring external push access.
4. **Continuously Reconciled**: Software agents continuously observe the actual live state in the cluster and automatically reconcile any drift back to the declared Git state.

**Q2: Why is the "Pull-Based" reconciliation model considered superior to traditional "Push-Based" CI/CD pipelines?**

Traditional push-based CI/CD pipelines (such as Jenkins or GitLab CI runners pushing directly to Kubernetes) require storing high-privilege cluster admin credentials inside the external CI server, creating a massive security attack surface. Furthermore, external CI pipelines only execute when a code commit occurs—they cannot detect or fix out-of-band manual changes made directly inside the cluster. Pull-based GitOps agents run inside the cluster with zero external firewall ingress ports and continuously correct configuration drift.

**Q3: How does GitOps solve Disaster Recovery (DR) in a multi-region failure?**

Because Git is the single authoritative source of truth containing 100% of the declarative infrastructure and workload definitions, disaster recovery is fully automated. If an entire cloud region is destroyed: (1) Provision a clean, empty Kubernetes cluster in a secondary region; (2) Install the GitOps controller (Argo CD / Flux); and (3) Point the controller to the existing Git repository. The GitOps agent will re-hydrate the entire cluster state, spinning up all deployments, namespaces, network policies, and configs within minutes.

**Q4: What is the difference between `syncPolicy.automated.prune` and `syncPolicy.automated.selfHeal` in Argo CD?**

- **`prune: true`**: Ensures that when a resource file (e.g. a ConfigMap or Deployment) is deleted from the Git repository, the GitOps controller automatically deletes the corresponding live object from the Kubernetes cluster, preventing orphaned zombie resources.
- **`selfHeal: true`**: Ensures that if an engineer manually edits or deletes a live cluster resource via `kubectl`, the controller immediately detects the divergence and overwrites the live state with the desired state stored in Git within seconds.

**Q5: What is "Configuration Drift", and how do GitOps operators handle it?**

Configuration Drift occurs when the live state of a Kubernetes cluster diverges from the declared configuration stored in Git (such as when someone manually runs `kubectl scale` or an admission webhook mutates a field). GitOps controllers continuously compare the live `etcd` state against the Git commit tree. When drift is detected, the controller can either raise an alert (`OutOfSync` state) or immediately apply a strategic merge patch (`selfHeal`) to force the cluster back into alignment.
