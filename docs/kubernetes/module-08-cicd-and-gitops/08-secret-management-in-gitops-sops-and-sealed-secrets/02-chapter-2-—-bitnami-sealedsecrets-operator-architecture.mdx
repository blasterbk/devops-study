# Chapter 2 — Bitnami SealedSecrets Operator Architecture

> **Goal:** Master asymmetric one-way secret encryption and automated in-cluster decryption using the **Bitnami SealedSecrets Operator** — understanding the cryptographic workflow separating public encryption (`kubeseal`) from in-cluster private decryption (SealedSecrets Controller), dissecting **Encryption Scopes** (`strict`, `namespace-wide`, `cluster-wide`), mastering automated 30-day master key rotation, and authoring declarative **`SealedSecret`** Custom Resources for GitOps repositories.
>
> By the end of this chapter, you will understand:
> 1. The asymmetric cryptographic architecture of Bitnami SealedSecrets
> 2. How the `kubeseal` CLI converts raw `Secret` manifests into safe `SealedSecret` CRDs
> 3. Why asymmetric encryption allows developers to seal secrets without ability to decrypt
> 4. The 3 Encryption Scopes: `strict`, `namespace-wide`, and `cluster-wide`
> 5. How the in-cluster controller manages automated 30-day master key rotations

## Real-Life Analogy

Think of Bitnami SealedSecrets as **a physical public mailbox with a one-way mail slot and a private master key held only by the postmaster inside the secure post office**:

- **The Public Mail Slot (`kubeseal` & Public Key):** Anyone on the street (**Any Developer or CI pipeline**) can walk up to the public mailbox, drop a sensitive letter through the metal slot, and hear it drop to the bottom (**Encrypting with Public Certificate**). Once the letter drops inside, **even the person who mailed it cannot reach in and pull it back out (**One-Way Asymmetric Encryption**).
- **The Publicly Viewable Lockbox (The Git Repository):** You can pick up the entire metal mailbox and leave it in a crowded public park (**Safe to commit `SealedSecret` YAML to public Git**). Nobody can open the metal box without the master key.
- **The Postmaster in the Vault (The SealedSecrets Controller):** Inside the locked post office (**The Kubernetes Cluster**), the postmaster holds the single physical master key (**The Private Controller Key in `kube-system`**).
- **The Letter Extraction (`SealedSecret` $\to$ `Secret`):** The postmaster unlocks the mailbox, takes out the letter, decrypts the contents, and places the clean document into the secure office desk (**Standard Kubernetes `Secret` in `etcd`**) so the internal workers (**Application Pods**) can read it.

## The 3 SealedSecrets Encryption Scopes

SealedSecrets embeds the metadata name and namespace into the encryption payload to prevent cross-namespace secret theft:

```text
 ┌──────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
 │ Scope Name           │ Binding Constraint & Security Profile                                       │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`strict`**         │ **Default & Highest Security.** The Secret MUST retain its exact            │
 │                      │ `metadata.name` AND `metadata.namespace`. Renaming or moving the secret to  │
 │                      │ another namespace causes decryption failure!                                │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`namespace-**      │ The Secret can be renamed freely, but MUST be deployed inside the           │
 │ **wide`**            │ exact `metadata.namespace` it was encrypted for.                            │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`cluster-wide`**   │ Can be deployed to **any namespace** under **any name**.                    │
 │                      │ (Use with extreme caution; higher risk of secret cloning across teams!).    │
 └──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## Sealing Secrets with `kubeseal`

### Step 1: Create a standard unencrypted Kubernetes Secret manifest:
```yaml
# secret.yaml (Raw Local Secret)
apiVersion: v1
kind: Secret
metadata:
  name: payment-db-secret
  namespace: production
type: Opaque
stringData:
  DB_PASSWORD: "SuperSecretProductionPassword2026!"
```

### Step 2: Encrypt using `kubeseal` (Strict Scope by default):
```bash
kubeseal --format=yaml < secret.yaml > sealed-secret.yaml
```

### Step 3: Resulting `SealedSecret` Manifest (Safe to commit to Git!):
```yaml
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: payment-db-secret
  namespace: production
  annotations:
    sealedsecrets.bitnami.com/managed: "true"
spec:
  encryptedData:
    DB_PASSWORD: AgB8f9k7bA1...z92mP3kQ== # Asymmetrically encrypted string
  template:
    metadata:
      name: payment-db-secret
      namespace: production
    type: Opaque
```

## Disaster Recovery: Backing Up the Master Private Key

> [!CAUTION]
> If your Kubernetes cluster is destroyed and you did not back up the SealedSecrets controller private key, **all `SealedSecret` manifests in your Git repository become permanently undecryptable garbage!**

```bash
# 1. Back up all master private keys from kube-system
kubectl get secret -n kube-system -l sealedsecrets.bitnami.com/sealed-secrets-key -o yaml > /secure-backup/sealed-secrets-master-key.yaml

# 2. Restore master key to a brand-new cluster
kubectl apply -f /secure-backup/sealed-secrets-master-key.yaml

# 3. Restart the SealedSecrets controller to load the restored key
kubectl rollout restart deployment sealed-secrets-controller -n kube-system
```

## Common Interview Questions

**Q1: What is the core cryptographic mechanism behind Bitnami SealedSecrets?**

Bitnami SealedSecrets uses **asymmetric public-key cryptography (RSA-4096 combined with AES-GCM)**. The SealedSecrets controller running inside the Kubernetes cluster generates and maintains the private key in a cluster Secret. The public certificate is distributed openly to developers and CI pipelines. Developers encrypt raw Secrets using the public key via `kubeseal`. Because it is an asymmetric one-way cipher, the encrypted `SealedSecret` can only be decrypted by the in-cluster controller holding the private key.

**Q2: What are the three encryption scopes in SealedSecrets, and which one is the most secure?**

- **`strict` (Default & Most Secure)**: The encryption hash includes both the Secret's `metadata.name` and `metadata.namespace`. If an attacker copies the SealedSecret manifest to another namespace or renames it, the controller refuses to decrypt it.
- **`namespace-wide`**: Binds the encryption to the target `metadata.namespace` only, allowing the Secret to be renamed within the same namespace.
- **`cluster-wide`**: Omits name and namespace constraints, allowing the SealedSecret to be decrypted into any namespace across the cluster.

**Q3: How does master key rotation work in the SealedSecrets controller?**

The SealedSecrets controller automatically rotates its master private key every **30 days** by generating a new RSA keypair Secret in `kube-system`. When encrypting *new* secrets, `kubeseal` uses the newest public key. However, the controller retains all older private keys in its keystore, ensuring that existing historical `SealedSecret` manifests in Git continue to decrypt smoothly without requiring re-encryption.

**Q4: What happens if a Kubernetes cluster is destroyed and the SealedSecrets master private key was not backed up?**

If the cluster is destroyed and the private key Secret in `kube-system` is lost, **all `SealedSecret` manifests stored in Git are permanently unrecoverable**. It is impossible to reverse RSA-4096 asymmetric encryption without the private key. To guarantee disaster recovery, platform teams must securely back up the controller's master key secret (`sealedsecrets.bitnami.com/sealed-secrets-key`) into a secure offsite vault (e.g. AWS Secrets Manager or HashiCorp Vault).

**Q5: Why would a team choose SealedSecrets over Mozilla SOPS?**

SealedSecrets is **completely self-contained within Kubernetes**. It requires zero external cloud infrastructure, zero Cloud KMS IAM permissions, and zero third-party SaaS tools, making it ideal for bare-metal, on-premise, or air-gapped Kubernetes environments where connecting to AWS KMS or GCP Cloud KMS is impossible or restricted.
