# Chapter 1 — Progressive Delivery: Blue-Green & Canary Deployments

> **Goal:** Master advanced release engineering and blast-radius mitigation in Kubernetes using **Progressive Delivery** and **Argo Rollouts** — understanding why standard Kubernetes `Deployment` rolling updates fail to protect production workloads, dissecting the architectural mechanics of **Blue-Green** (Active vs Preview Services) and **Canary** (step-weighted traffic shifting) strategies, and configuring dynamic traffic routing integrations with Ingress-NGINX, Istio, and the Gateway API.
>
> By the end of this chapter, you will understand:
> 1. The fundamental limitations of native Kubernetes `Deployment` rolling updates
> 2. How the `Rollout` CRD acts as a drop-in replacement for standard Deployments
> 3. The exact workflow of Blue-Green deployments with automated preview verification
> 4. How Canary deployments shift traffic in granular steps (10% $\to$ 25% $\to$ 50% $\to$ 100%)
> 5. How Argo Rollouts manipulates Ingress and Service Mesh controllers for weight shifting
> 6. How to manage and promote live rollouts using the `kubectl argo rollouts` CLI

## Real-Life Analogy

Think of Progressive Delivery as **the grand opening of a newly renovated international airport terminal**:

- **The Standard Rolling Update (The Uncontrolled Passenger Rush):** The airport replaces all 20 ticket check-in desks simultaneously one by one (**Standard Kubernetes Rolling Update**). If the new computer system has a catastrophic hidden software bug, 100% of incoming passengers are immediately exposed to the failure, the entire airport gridlocks, and flights are canceled (**High Blast Radius Outage**).
- **The Blue-Green Strategy (The Secret VIP Dry Run):** The airport leaves the old Terminal Blue running for all 10,000 public passengers (**Active Service**). Meanwhile, in Terminal Green (**Preview Service**), airport executives and secret beta testers test the baggage belts and computers with real luggage. Once Terminal Green proves 100% stable, the airport flips a master directional sign at the highway entrance (**Instant Cutover**). If an issue occurs, they flip the sign back to Terminal Blue in 1 second.
- **The Canary Strategy (The 10% Gate Funnel):** The airport directs **90% of flights to the stable old gates** and **10% of flights to the new gates (**`setWeight: 10`**)**. The operations team monitors the luggage belts for 1 hour. If error rates remain at 0%, they expand traffic to 25%, then 50%, and finally 100% (**Controlled Blast Radius**).

## 1. Blue-Green Strategy Manifest

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: payment-bluegreen-rollout
  namespace: production
spec:
  replicas: 5
  selector:
    matchLabels:
      app: payment-api
  strategy:
    blueGreen:
      # 1. Active Service (Receives live customer traffic)
      activeService: payment-active-svc
      # 2. Preview Service (Used for pre-promotion smoke testing)
      previewService: payment-preview-svc
      autoPromotionEnabled: false      # Requires explicit approval before cutting over!
      scaleDownDelaySeconds: 30        # Keeps old version alive for 30s after cutover for instant rollback!
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      containers:
      - name: payment
        image: ghcr.io/enterprise/payment-api:v2.0.0
        ports:
        - containerPort: 8080
```

## 2. Canary Strategy with Ingress-NGINX Traffic Shifting

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: payment-canary-rollout
  namespace: production
spec:
  replicas: 10
  selector:
    matchLabels:
      app: payment-api
  strategy:
    canary:
      # 1. Ingress & Service Traffic Routing Configuration
      trafficRouting:
        nginx:
          stableIngress: payment-stable-ingress
      canaryService: payment-canary-svc
      stableService: payment-stable-svc

      # 2. Step-by-Step Phased Rollout Schedule
      steps:
      - setWeight: 10                  # Shift 10% traffic to Canary
      - pause: { duration: 10m }       # Soak test for 10 minutes
      - setWeight: 25                  # Shift 25% traffic to Canary
      - pause: { duration: 30m }       # Soak test for 30 minutes
      - setWeight: 50
      - pause: { duration: 15m }
      - setWeight: 100                 # Complete promotion!
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      containers:
      - name: payment
        image: ghcr.io/enterprise/payment-api:v2.1.0
        ports:
        - containerPort: 8080
```

## Managing Rollouts with the CLI

```bash
# 1. Watch rollout progression in real time
kubectl argo rollouts get rollout payment-canary-rollout -n production --watch

# 2. Manually promote a paused rollout to the next step
kubectl argo rollouts promote payment-canary-rollout -n production

# 3. Emergency Abort: Instantly cancel canary and revert 100% traffic to stable!
kubectl argo rollouts abort payment-canary-rollout -n production

# 4. Retry an aborted rollout
kubectl argo rollouts retry rollout payment-canary-rollout -n production
```

## Common Interview Questions

**Q1: Why is the standard Kubernetes `Deployment` rolling update inadequate for mission-critical production systems?**

Standard Kubernetes Deployments execute **blind, all-or-nothing rolling updates**. If a new container image passes its basic HTTP readiness probes but has a deep logical bug (e.g. throwing 500 errors on 3% of checkout transactions or leaking database connections under load), the Deployment controller will continue replacing old pods until 100% of the fleet is infected. Standard Deployments cannot: (1) Route small percentages of traffic (e.g. 2%) independently of pod count; (2) Integrate with Prometheus for metric-driven validation; or (3) Automatically abort and roll back upon error rate spikes.

**Q2: How does a Blue-Green deployment work in Argo Rollouts?**

In Blue-Green: (1) The controller maintains an **Active Service** (routing live customer traffic to the stable Blue ReplicaSet) and a **Preview Service** (routing internal test traffic to the newly created Green ReplicaSet); (2) Automated tests or QA engineers validate the Green release via the Preview Service; (3) Upon approval, the controller updates the Active Service's label selector to point to the Green ReplicaSet, achieving an **instant, zero-downtime cutover**; (4) The old Blue ReplicaSet is kept warm for a configured `scaleDownDelaySeconds` duration to allow instant zero-downtime rollback if issues appear.

**Q3: How does Argo Rollouts achieve precise percentage-based traffic shifting (e.g. 5% traffic) with only 2 pods?**

Argo Rollouts integrates with Layer 7 **Traffic Routers** (such as Ingress-NGINX, AWS ALB, Istio, Linkerd, and the Gateway API). Rather than relying on simple pod-count ratios in Kube-Proxy iptables, Argo Rollouts dynamically updates the routing rules in the Ingress or Service Mesh (e.g. injecting `nginx.ingress.kubernetes.io/canary-weight: "5"`). The Ingress proxy splits incoming HTTP requests mathematically at the network edge, sending exactly 5% of requests to the canary pod and 95% to the stable pods.

**Q4: What is the purpose of `scaleDownDelaySeconds` in Blue-Green deployments?**

When traffic is cut over to the new Green version, `scaleDownDelaySeconds: 30` instructs the controller to **keep the old Blue pods running and healthy for 30 seconds** before terminating them. If the SRE team notices an immediate spike in errors, they can execute `kubectl argo rollouts abort`, and the controller flips the Active Service back to the still-running Blue pods in **under 1 second** with zero container startup latency.

**Q5: What happens when an engineer runs `kubectl argo rollouts abort` on a Canary rollout?**

The controller instantly: (1) Reconfigures the Ingress/Service Mesh traffic router to set Canary weight to `0%`, returning 100% of customer traffic to the Stable ReplicaSet; (2) Marks the Rollout condition as `Degraded`; and (3) Scales down the failing Canary ReplicaSet pods, completely stopping the blast radius within milliseconds.
