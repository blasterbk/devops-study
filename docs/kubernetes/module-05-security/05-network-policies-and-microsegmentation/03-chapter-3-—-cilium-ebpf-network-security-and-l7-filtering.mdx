> 1. How eBPF executes sandboxed bytecode inside the Linux kernel to filter packets at native wire speed

## Real-Life Analogy

Think of Cilium eBPF security as **an AI-powered X-ray scanner stationed inside an airport terminal versus a physical paper gate guard**:

- **Legacy iptables NetworkPolicies (The Paper Checklist Guard):** A security guard stands at the gate with a 50,000-page printed binder of IP addresses. For every single passenger (packet), the guard flips through the binder page by page ($O(N)$ linear traversal). Furthermore, the guard can only check the passenger's luggage tag (IP and Port). If a passenger carries a letter stamped "Port 80", the guard lets them pass without reading the content inside the envelope (**No Layer 7 visibility**).
- **Cilium eBPF (The AI Kernel X-Ray Scanner):** Instead of an external guard, a microscopic AI chip runs directly inside the conveyor belt's motor controller (**Linux Kernel eBPF**). It inspects packets in **nanoseconds using $O(1)$ memory hash tables**.
- **Layer 7 Inspection (Reading the Letter):** The scanner inspects the actual HTTP payload inside the packet: *"You are allowed to drop off a public letter (`GET /public/info`), but you are strictly FORBIDDEN from dropping off a bomb (`DELETE /admin/database`)!"*
- **Dynamic FQDN Snooping (The Live Address Book):** When an app asks for `api.stripe.com`, Cilium intercepts the DNS answer in real time, learns that Stripe is currently at IP `54.186.20.10`, and opens the firewall for 60 seconds specifically for that IP.

## Layer 7 (L7) HTTP & gRPC Policy Filtering

A `CiliumNetworkPolicy` (CNP) operates at the application layer, restricting specific HTTP methods and URL paths:

```yaml
apiVersion: "cilium.io/v2"
kind: CiliumNetworkPolicy
metadata:
  name: secure-billing-l7-policy
  namespace: production
spec:
  endpointSelector:
    matchLabels:
      app: billing-api
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: web-frontend
    toPorts:
    - ports:
      - port: "8080"
        protocol: TCP
      # Layer 7 Application Rules:
      rules:
        http:
        # Allow read-only public endpoints
        - method: "GET"
          path: "/v1/public/.*"
        # Allow creating orders
        - method: "POST"
          path: "/v1/orders"
        # (All other paths like DELETE /v1/admin/ are automatically BLOCKED with HTTP 403!)
```

## Dynamic FQDN / DNS-Based Egress Filtering

Standard Kubernetes NetworkPolicies cannot filter by domain names. Cilium intercepts DNS traffic and dynamically manages eBPF IP tables:

```yaml
apiVersion: "cilium.io/v2"
kind: CiliumNetworkPolicy
metadata:
  name: stripe-egress-only
  namespace: production
spec:
  endpointSelector:
    matchLabels:
      app: checkout-service
  egress:
  # 1. Allow DNS lookups to CoreDNS
  - toEndpoints:
    - matchLabels:
        k8s:k8s-app: kube-dns
    toPorts:
    - ports:
      - port: "53"
        protocol: ANY
      rules:
        dns:
        - matchPattern: "*"

  # 2. Allow outbound traffic strictly to Stripe and AWS S3 domains!
  - toFQDNs:
    - matchName: "api.stripe.com"
    - matchPattern: "*.s3.amazonaws.com"
    toPorts:
    - ports:
      - port: "443"
        protocol: TCP
```

## `CiliumClusterwideNetworkPolicy` (CCNP)

To enforce mandatory baseline security across **every single namespace** without duplicating YAML:

```yaml
apiVersion: "cilium.io/v2"
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: global-block-crypto-and-metadata
spec:
  # Matches EVERY Pod across the entire cluster!
  endpointSelector: {}
  egress:
  # Block access to Cloud Metadata Service (169.254.169.254) across all namespaces!
  - toCIDR:
    - "0.0.0.0/0"
    except:
    - "169.254.169.254/32"
```

## Common Interview Questions

**Q1: How does Cilium leverage eBPF to revolutionize Kubernetes network security?**

Cilium uses Extended Berkeley Packet Filter (eBPF) to attach sandboxed, high-performance security programs directly to Linux kernel network hooks (`XDP`, `tc`, and socket layers). Instead of evaluating thousands of sequential iptables rules ($O(N)$ complexity) which degrades CPU performance in large clusters, Cilium evaluates security policies using in-kernel $O(1)$ BPF hash tables, achieving sub-microsecond packet filtering and scaling effortlessly to hundreds of thousands of pods.

**Q2: What is the difference between standard Kubernetes NetworkPolicies and `CiliumNetworkPolicy` (CNP)?**

Standard Kubernetes NetworkPolicies operate strictly at **Layer 3 (IP CIDRs) and Layer 4 (TCP/UDP ports)**. `CiliumNetworkPolicy` extends security to **Layer 7 (Application Layer)**: it allows filtering based on HTTP methods and paths (`GET /public/.*`), gRPC methods, Kafka topics, and dynamic DNS hostnames (FQDNs like `api.stripe.com`), providing deep application-aware microsegmentation.

**Q3: How does Cilium's FQDN-based egress filtering work without hardcoding IP addresses?**

When a Pod initiates a DNS lookup (e.g. resolving `api.stripe.com`), Cilium's in-kernel eBPF DNS proxy intercepts the UDP/TCP response from CoreDNS. Cilium parses the returned IP addresses from the DNS answer payload and dynamically inserts temporary allow-rules for those specific IPs into the Pod's eBPF policy map with a matching TTL. When the application opens a TLS connection to Stripe, the eBPF filter allows the connection seamlessly.

**Q4: What is a `CiliumClusterwideNetworkPolicy` (CCNP), and when should it be used?**

A `CiliumClusterwideNetworkPolicy` is a cluster-scoped custom resource that applies security rules globally across **all namespaces simultaneously**. It is used by platform engineering and security teams to enforce non-negotiable security guardrails—such as blocking access to the cloud instance metadata service (`169.254.169.254`), enforcing global egress proxies, or mandating cluster-wide CoreDNS access rules.

**Q5: How does Cilium's transparent WireGuard encryption work?**

When transparent WireGuard encryption is enabled, Cilium configures a WireGuard tunnel interface inside the Linux kernel on each worker node. When a Pod on Node A sends packets to a Pod on Node B, eBPF intercepts the packet before it leaves the host network interface, encrypts the payload using the modern ChaCha20-Poly1305 cipher, and transmits it over UDP. The receiving node's kernel decrypts the payload and routes it to the target Pod, achieving zero-trust encryption without injecting mTLS sidecars.
