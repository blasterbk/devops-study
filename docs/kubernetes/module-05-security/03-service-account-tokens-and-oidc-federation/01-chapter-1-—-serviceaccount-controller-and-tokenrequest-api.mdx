# Chapter 1 — ServiceAccount Controller & TokenRequest API

> **Goal:** Master in-cluster workload authentication in Kubernetes — understanding the transition from legacy static Secret tokens to modern Bound Service Account Tokens via the `TokenRequest` API (KEP-1205), analyzing cryptographic binding to Pod UIDs and target audiences, configuring automated in-place token rotation by Kubelet, enforcing `automountServiceAccountToken: false` security hardening, and validating bearer tokens with the `TokenReview` API.
>
> By the end of this chapter, you will understand:
> 1. The structural difference between legacy static Secret tokens and modern Bound ServiceAccount Tokens
> 2. How the `TokenRequest` API generates time-limited, audience-restricted JWT tokens
> 3. Why Bound Tokens are cryptographically tied to the Pod's lifecycle UID
> 4. How Kubelet automatically refreshes and rotates token files on disk at 80% of their TTL
> 5. How to disable automatic token injection using `automountServiceAccountToken: false`
> 6. How external applications validate ServiceAccount tokens using the `TokenReview` API

## Real-Life Analogy

Think of ServiceAccount authentication as **issuing electronic security keycards to automated cleaning robots in a hotel**:

- **Legacy Static Tokens (The Never-Expiring Master Brass Key):** In the past, the hotel cut a permanent brass master key for every robot and stored a duplicate in the front desk drawer (Static Secret in `etcd`). If a rogue employee or hacker stole the brass key from Robot #4, they could use it 5 years later to unlock every door in the entire hotel (**Critical Security Liability**).
- **Modern Bound Tokens (The Rotating RFID Room Card):** Today, the robot does not receive a brass key. The front desk (`TokenRequest` API) issues an electronic RFID keycard loaded with strict cryptographic rules:
  - **Short Expiration (`expirationSeconds: 3600`):** The card expires automatically in 1 hour.
  - **Audience Restricted (`aud: "laundry-chute"`):** The card only works on the laundry chute, not on guest rooms.
  - **Pod UID Bound (Tied to Robot Chassis):** If the robot is decommissioned or destroyed (Pod deleted), the hotel computer immediately blacklists that specific card UID across the entire building.
- **Automated Rotation (The In-Shift Key Recharge):** At the 48-minute mark (80% of TTL), the charging dock (Kubelet) wirelessly rewrites a fresh 1-hour certificate onto the card while the robot is vacuuming, without interrupting its cleaning cycle.

## Inside the Bound Token JWT Claims

When decoded, a modern Bound ServiceAccount Token contains rich cryptographic metadata:

```json
{
  "iss": "https://kubernetes.default.svc.cluster.local",
  "sub": "system:serviceaccount:production:payment-processor",
  "aud": ["https://kubernetes.default.svc.cluster.local"],
  "exp": 1723987200,
  "nbf": 1723983600,
  "kubernetes.io": {
    "namespace": "production",
    "serviceaccount": {
      "name": "payment-processor",
      "uid": "e8a9314c-1234-5678-abcd-0987654321ab"
    },
    "pod": {
      "name": "payment-processor-7b8f9c-xyz",
      "uid": "a1b2c3d4-4567-89ab-cdef-1234567890cd"
    }
  }
}
```

> [!IMPORTANT]
> Because the token includes **`kubernetes.io.pod.uid`**, if an attacker copies the token file off a compromised pod and the pod is subsequently deleted or rescheduled, the token **immediately fails authentication**, neutralizing the stolen credential.

## Security Hardening: `automountServiceAccountToken: false`

By default, Kubernetes automatically injects a ServiceAccount token into **every single Pod** created in the cluster.

If your web application or frontend microservice does not communicate with the Kubernetes API server, mounting a token creates an unnecessary security attack surface:

```yaml
# 1. Disable automount at the ServiceAccount level
apiVersion: v1
kind: ServiceAccount
metadata:
  name: static-web-sa
  namespace: frontend
automountServiceAccountToken: false
---
# 2. Or disable automount directly on the Pod / Deployment spec
apiVersion: apps/v1
kind: Deployment
metadata:
  name: public-frontend
  namespace: frontend
spec:
  template:
    spec:
      # Hardening: Prevents token from being injected into /var/run/secrets/
      automountServiceAccountToken: false
      containers:
      - name: nginx
        image: nginx:1.25-alpine
```

## The `TokenReview` API (`authentication.k8s.io/v1`)

External applications (like HashiCorp Vault or custom authentication gateways) can validate a Kubernetes ServiceAccount token by sending a `TokenReview` request to `kube-apiserver`:

```yaml
apiVersion: authentication.k8s.io/v1
kind: TokenReview
spec:
  token: <BEARER_JWT_TOKEN>
  audiences:
  - "https://vault.company.internal"
```

The API Server responds with the validation verdict:

```json
{
  "apiVersion": "authentication.k8s.io/v1",
  "kind": "TokenReview",
  "status": {
    "authenticated": true,
    "user": {
      "username": "system:serviceaccount:production:vault-auth-sa",
      "uid": "e8a9314c-1234-5678-abcd-0987654321ab",
      "groups": [
        "system:serviceaccounts",
        "system:serviceaccounts:production",
        "system:authenticated"
      ]
    }
  }
}
```

## Complete Production Manifest with Projected Bound Token

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-api-client
  namespace: default
spec:
  serviceAccountName: default
  # Disable default token automount
  automountServiceAccountToken: false
  containers:
  - name: client
    image: alpine:latest
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: custom-token-mount
      mountPath: /var/run/secrets/tokens
      readOnly: true

  volumes:
  # Explicitly configure a short-lived custom audience token!
  - name: custom-token-mount
    projected:
      sources:
      - serviceAccountToken:
          audience: "https://vault.enterprise.internal"
          expirationSeconds: 1800    # 30-minute expiration
          path: vault-token
```

## Hands-On Lab: Inspecting Bound Tokens & TokenReview

```bash
# Step 1: Create lab namespace and ServiceAccount
kubectl create namespace sa-lab
kubectl create serviceaccount lab-sa -n sa-lab

# Step 2: Deploy a Pod with default ServiceAccount token
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: sa-inspector-pod
  namespace: sa-lab
spec:
  serviceAccountName: lab-sa
  containers:
  - name: inspector
    image: alpine:latest
    command: ["sh", "-c", "sleep 3600"]
EOF

# Step 3: Wait for Pod to become Ready
kubectl wait --for=condition=Ready pod/sa-inspector-pod -n sa-lab --timeout=30s

# Step 4: Read the mounted Bound ServiceAccount Token from inside the container
TOKEN=$(kubectl exec -n sa-lab sa-inspector-pod -- cat /var/run/secrets/kubernetes.io/serviceaccount/token)
echo "Mounted Token: $TOKEN"

# Step 5: Decode the JWT payload to inspect claims and Pod UID binding
echo "$TOKEN" | cut -d'.' -f2 | base64 --decode 2>/dev/null | jq .

# Step 6: Test TokenReview API using the extracted token
cat <<EOF | kubectl create -f -
apiVersion: authentication.k8s.io/v1
kind: TokenReview
spec:
  token: $TOKEN
EOF

# Step 7: Clean up lab
kubectl delete namespace sa-lab
```

## Common Interview Questions

**Q1: What are Bound Service Account Tokens, and why did Kubernetes deprecate legacy static Secret tokens?**

Bound Service Account Tokens (introduced via the `TokenRequest` API in KEP-1205 and default since Kubernetes 1.24) are time-limited, audience-restricted JSON Web Tokens (JWTs) generated dynamically for Pods. Legacy tokens were stored permanently in `etcd` as static Secrets with infinite expiration and cluster-wide validity; if leaked, they provided indefinite access. Bound Tokens: (1) Expire automatically (default 1 hour); (2) Are bound to specific audiences; (3) Are bound to the Pod's lifecycle UID; and (4) Are never stored in `etcd`.

**Q2: How does Kubelet handle token rotation for Bound ServiceAccount Tokens?**

Kubelet provisions the token into the Pod via a local projected volume. Kubelet continuously monitors the token's lifetime; when **80% of the token's TTL has elapsed** (or when the token is older than 24 hours), Kubelet calls the API Server's `TokenRequest` API to fetch a fresh token and atomically rewrites the token file on disk in-place. Applications that periodically re-read the token from disk receive rotated credentials without requiring container restarts.

**Q3: What is the purpose of `automountServiceAccountToken: false`, and when should it be applied?**

`automountServiceAccountToken: false` prevents Kubernetes from injecting API Server credentials into `/var/run/secrets/kubernetes.io/serviceaccount/` within container filesystems. It should be applied to all frontend web apps, batch processing jobs, and microservices that do not interact with the Kubernetes control plane. Disabling automount eliminates credential theft vectors if an application suffers a remote code execution (RCE) vulnerability.

**Q4: How does the Pod UID claim in a Bound Token enhance cluster security?**

The JWT payload contains a custom claim `kubernetes.io.pod.uid` recording the unique UUID of the specific Pod sandbox. When an API call is made, the API server verifies that the Pod UID exists in `etcd`. If the Pod has been deleted, evicted, or replaced by a new Pod (even with the exact same name), the token is immediately invalidated, preventing attackers from replaying exfiltrated tokens.

**Q5: What is the `TokenReview` API, and how do external services use it?**

The `TokenReview` API (`authentication.k8s.io/v1`) allows external systems (such as HashiCorp Vault, ingress controllers, or custom API gateways) to validate Kubernetes ServiceAccount tokens. The external service forwards the bearer token in a `TokenReview` request to `kube-apiserver`. The API server verifies the cryptographic signature, expiration, and audience, returning the authenticated username, groups, and UID.
