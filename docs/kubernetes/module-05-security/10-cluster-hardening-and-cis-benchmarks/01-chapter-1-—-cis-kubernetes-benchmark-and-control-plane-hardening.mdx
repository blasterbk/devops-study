# Chapter 1 — CIS Kubernetes Benchmark & Control Plane Hardening

> **Goal:** Master the Center for Internet Security (CIS) Kubernetes Benchmark — understanding the 5 core compliance domains across control plane components, `etcd`, configuration files, worker nodes, and admission policies, deploying **Aqua `kube-bench`** for continuous automated compliance auditing, securing file permissions (`0600` root:root), hardening the Kubelet daemon, and analyzing the CIS shared responsibility model in managed cloud clusters (EKS, GKE, AKS).
>
> By the end of this chapter, you will understand:
> 1. The structure of the CIS Kubernetes Benchmark across its 5 compliance domains
> 2. The critical security flags required on `kube-apiserver`, `kube-controller-manager`, `kube-scheduler`, and `etcd`
> 3. How to harden Kubelet worker nodes (`anonymous-auth: false`, `authorization.mode: Webhook`)
> 4. How to execute automated compliance scans using Aqua `kube-bench` as a Kubernetes Job
> 5. File ownership and permission standards for `/etc/kubernetes/` manifests and kubeconfig files
> 6. The CIS shared responsibility matrix between self-managed and managed cloud environments

## Real-Life Analogy

Think of the CIS Kubernetes Benchmark as **the official National Fire Protection Association (NFPA) building code inspection for a skyscraper**:

- **The Standard Building Code (The CIS Benchmark):** A 150-page rigorous regulatory standard defining every non-negotiable safety parameter: the thickness of firewalls, the pressure of water sprinklers, emergency exit lighting, and electrical circuit breakers.
- **The Central Power Plant & Control Room (Domain 1 & 2 - Control Plane & etcd):** The building's nuclear reactor and control computer must have dual-factor biometric locks, automated fire suppression, and zero unauthorized access points (**Kube-APIServer mTLS, etcd encryption, profiling disabled**).
- **Physical Keyring & Blueprint Vault (Domain 3 - File Permissions):** The building blueprints and master master keycard files (`/etc/kubernetes/admin.conf`) cannot be left on the front lobby desk; they must be locked in a steel safe with permissions set strictly to `0600 root:root`.
- **The Floor Security Guards (Domain 4 - Kubelet Worker Nodes):** The guard at each floor cannot let random unidentified strangers walk past without checking ID (**Kubelet `anonymous-auth: false`**).
- **The Fire Marshal Audit (Aqua `kube-bench`):** Once a month, the independent fire marshal walks through the skyscraper with an automated checklist tablet (**`kube-bench` Job**), stamping every single room with `[PASS]`, `[FAIL]`, or `[WARN]`.

## The 5 CIS Benchmark Domains Breakdown

```text
 ┌──────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
 │ CIS Domain           │ Scope & Critical Enforcement Items                                          │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **1. Control Plane** │ Kube-APIServer, Controller Manager, and Scheduler.                          │
 │                      │ Mandates `--anonymous-auth=false`, disables insecure ports (`--port=0`),    │
 │                      │ enables NodeRestriction admission, disables debugging profiling.            │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **2. etcd Node**     │ Dedicated etcd configuration. Mandates client certificate authentication    │
 │                      │ (`--client-cert-auth=true`), explicit peer certs, and disables auto-TLS.    │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **3. Config Files**  │ File permissions and ownership audits. Mandates `0600` or `0644` ownership  │
 │                      │ strictly to `root:root` across all manifests and PKI keys.                  │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **4. Worker Nodes**  │ Kubelet configuration. Disables read-only port 10255 (`--read-only-port=0`),│
 │                      │ disables anonymous auth, enforces Webhook auth, enables kernel protection.  │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **5. Policies**      │ Workload governance. Enforces Pod Security Standards, NetworkPolicies,      │
 │                      │ Secrets encryption, and RBAC least-privilege.                               │
 └──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## Hardening the Worker Node Kubelet Daemon

Configured inside `/var/lib/kubelet/config.yaml`:

```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
# 1. Disable Anonymous Authentication
authentication:
  anonymous:
    enabled: false
  webhook:
    enabled: true
  x509:
    clientCAFile: /etc/kubernetes/pki/ca.crt

# 2. Enforce Webhook Authorization (Prevents unauthorized kubectl exec/logs!)
authorization:
  mode: Webhook

# 3. Disable Insecure Unauthenticated Read-Only Port 10255
readOnlyPort: 0

# 4. Protect Host Kernel Defaults
protectKernelDefaults: true

# 5. Enforce Seccomp RuntimeDefault by Default (K8s 1.25+)
seccompDefault: true
```

## Automated Compliance Auditing with `kube-bench`

Aqua Security's **`kube-bench`** is an open-source Go application that checks whether Kubernetes is deployed securely in accordance with the official CIS Kubernetes Benchmark:

```yaml
# Deploy kube-bench as a Kubernetes Job
apiVersion: batch/v1
kind: Job
metadata:
  name: kube-bench-audit
  namespace: kube-system
spec:
  template:
    spec:
      hostPID: true
      containers:
      - name: kube-bench
        image: aquasec/kube-bench:v0.7.3
        command: ["kube-bench", "run", "--targets", "master,node,etcd,policies"]
        volumeMounts:
        - name: var-lib-etcd
          mountPath: /var/lib/etcd
          readOnly: true
        - name: var-lib-kubelet
          mountPath: /var/lib/kubelet
          readOnly: true
        - name: etc-kubernetes
          mountPath: /etc/kubernetes
          readOnly: true
      restartPolicy: Never
      volumes:
      - name: var-lib-etcd
        hostPath:
          path: /var/lib/etcd
      - name: var-lib-kubelet
        hostPath:
          path: /var/lib/kubelet
      - name: etc-kubernetes
        hostPath:
          path: /etc/kubernetes
```

## Common Interview Questions

**Q1: What is the CIS Kubernetes Benchmark, and why is it considered the industry gold standard?**

The CIS (Center for Internet Security) Kubernetes Benchmark is a globally recognized, consensus-driven security guideline providing prescriptive, actionable configuration baselines for hardening Kubernetes clusters. It covers five primary domains (Control Plane components, etcd, configuration files, worker nodes, and admission policies) and is referenced by major compliance frameworks (PCI-DSS, SOC 2, HIPAA, ISO 27001) as the baseline standard for regulatory audits.

**Q2: What are the two most critical security settings for hardening worker node Kubelet daemons?**

1. **Disabling Anonymous Authentication (`authentication.anonymous.enabled: false`)**: Ensures that all incoming HTTP requests to the Kubelet HTTPS port (10250) must present a valid, verified client certificate or bearer token.
2. **Enforcing Webhook Authorization (`authorization.mode: Webhook`)**: Prevents any authenticated client from executing arbitrary commands (`kubectl exec`) on the node unless the master API server authorizes the request via a `SubjectAccessReview` RBAC check.

**Q3: How does Aqua `kube-bench` automate CIS compliance testing?**

`kube-bench` is an open-source testing harness written in Go that executes declarative YAML tests matching each numbered recommendation in the CIS Benchmark. When deployed as a Kubernetes Job or executed directly on nodes, it inspects running process arguments (e.g. checking if `kube-apiserver` has `--anonymous-auth=false`), tests file permissions and ownerships, and generates structured reports detailing `[PASS]`, `[FAIL]`, `[WARN]`, and exact remediation runbooks.

**Q4: How does the CIS shared responsibility model apply to managed Kubernetes services (Amazon EKS, Google GKE, Azure AKS)?**

In managed cloud environments, the cloud provider owns and manages the control plane infrastructure (Domains 1, 2, and 3). AWS/Google/Microsoft are contractually responsible for hardening `kube-apiserver`, `etcd`, and control-plane manifests. The customer remains 100% responsible for **Domain 4 (Worker Node Kubelet hardening, AMI updates, OS patching)** and **Domain 5 (Workload Policies, Pod Security Standards, NetworkPolicies, RBAC, and Secrets management)**.

**Q5: What permissions and file ownership are mandated for `/etc/kubernetes/admin.conf`?**

The CIS Benchmark strictly mandates that `/etc/kubernetes/admin.conf` (which contains the master cluster-admin private key and certificate) must have file permissions set to **`0600`** (read and write strictly by owner) and ownership set strictly to **`root:root`**. Any broader permissions (such as `0644` or `0777`) allow unprivileged local users or compromised containers mounting host paths to extract master admin credentials.
