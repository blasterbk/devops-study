## Real-Life Analogy

Think of Kubernetes Audit Logging as **the black box flight data recorder and court stenographer inside the cockpit of a commercial airliner**:

- **The Flight Recorder (The API Server Audit Pipeline):** Records every single button pressed by the pilot (User), every automated autopilot adjustment (Controllers), and every air traffic control communication (Worker Node Kubelets).
- **The 4 Audit Stages (The Timeline of an Event):**
  - **`RequestReceived` (The Pilot Reaches for the Switch):** The moment the pilot touches the throttle lever.
  - **`ResponseComplete` (The Engines Accelerate & Land):** The final confirmation that the plane accelerated and reached altitude safely.
- **The 4 Audit Levels (The Detail of the Court Transcript):**
  - **`None` (Ignore the White Noise):** You don't write down every breath the pilot takes (**Ignore `/healthz` probes and leader election leases**).
  - **`Metadata` (The Summary Note):** *"At 14:02:15, Pilot Alice adjusted the cabin temperature."*
  - **`RequestResponse` (The Full Audio & Video Recording):** *"At 14:05:00, Pilot Bob entered the flight plan: Route LAX $\to$ JFK."*
- **The Redaction Rule (Never Record Passenger Bank PINs):** When a passenger pays for a drink (A `Secret` write), you record that a purchase occurred (**`Metadata` Level**), but you **never print their 16-digit credit card number into the flight log (`RequestResponse` Forbidden for Secrets)**.

## The 4 Audit Stages

As an HTTP request progresses through the API server, audit events can be recorded at four distinct stages:

```text
 ┌──────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
 │ Audit Stage          │ Trigger Point & Description                                                 │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`RequestReceived`**│ Generated the instant the API server receives the request, before it is     │
 │                      │ processed by authentication, authorization, or admission handlers.          │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`ResponseStarted`**│ Generated once the HTTP response headers are sent, but before the body is   │
 │                      │ finished. (Used exclusively for long-running streaming/watch requests).     │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`ResponseComplete`**│ **The Most Common & Useful Stage.** Generated after the response body is    │
 │                      │ completely sent back to the client. Contains the final HTTP status code.    │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`Panic`**          │ Generated only if an internal unhandled panic occurred in the API server.   │
 └──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## The 4 Audit Levels

Audit levels define how much detail is recorded in the audit event:

```text
 ┌──────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
 │ Audit Level          │ Data Captured & Production Recommendation                                   │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`None`**           │ **Do NOT log events matching this rule.**                                   │
 │                      │ Used to filter out high-volume noise (read probes, leases, endpoints).      │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`Metadata`**       │ Logs request metadata: User, Group, Timestamp, Verb, Resource, Namespace,   │
 │                      │ Client IP, User-Agent, and Response Code. **Mandatory for Secrets!**         │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`Request`**        │ Logs event metadata PLUS the full request JSON body sent by the user,       │
 │                      │ but excludes the response body.                                             │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`RequestResponse`**│ **Highest Fidelity.** Logs metadata, full request body, and response body.  │
 │                      │ **WARNING: NEVER use for Secrets!** Logs cleartext passwords in audit log!  │
 └──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## Complete Production `AuditPolicy` Manifest

Saved at `/etc/kubernetes/audit-policy.yaml`:

```yaml
apiVersion: audit.k8s.io/v1
kind: Policy
# Define which stages to omit to reduce audit log size
omitStages:
  - "RequestReceived"

rules:
  # 1. DROP NOISE: Do not log read-only health checks and metrics
  - level: None
    nonResourceURLs:
      - "/healthz*"
      - "/livez*"
      - "/readyz*"
      - "/version"
      - "/metrics"

  # 2. DROP NOISE: Do not log high-frequency control-plane leader elections
  - level: None
    users: ["system:kube-scheduler", "system:kube-controller-manager"]
    verbs: ["get", "update"]
    resources:
      - group: "coordination.k8s.io"
        resources: ["leases"]

  # 3. DROP NOISE: Do not log high-frequency Kubelet node status updates
  - level: None
    userGroups: ["system:nodes"]
    verbs: ["get", "update", "patch"]
    resources:
      - group: ""
        resources: ["nodes", "nodes/status"]

  # 4. CRITICAL SECURITY: Log Secrets and ConfigMaps at METADATA level only!
  # (Prevents passwords and private keys from being exposed in audit logs!)
  - level: Metadata
    resources:
      - group: ""
        resources: ["secrets", "configmaps"]

  # 5. HIGH-RISK SECURITY: Log full Request & Response for RBAC modifications!
  - level: RequestResponse
    verbs: ["create", "update", "patch", "delete"]
    resources:
      - group: "rbac.authorization.k8s.io"
        resources: ["roles", "clusterroles", "rolebindings", "clusterrolebindings"]

  # 6. WORKLOADS: Log Request body for all write operations on Deployments/Pods
  - level: Request
    verbs: ["create", "update", "patch", "delete"]
    resources:
      - group: ""
        resources: ["pods", "services", "persistentvolumeclaims"]
      - group: "apps"
        resources: ["deployments", "statefulsets", "daemonsets"]

  # 7. CATCH-ALL: Default fallback to Metadata level for all other requests
  - level: Metadata
    omitStages:
      - "RequestReceived"
```

## API Server Configuration Flags

Configured in `/etc/kubernetes/manifests/kube-apiserver.yaml`:

```yaml
spec:
  containers:
  - name: kube-apiserver
    command:
    - kube-apiserver
    # 1. Enable Audit Policy File
    - --audit-policy-file=/etc/kubernetes/audit-policy.yaml
    # 2. Configure Log File Backend
    - --audit-log-path=/var/log/kubernetes/audit/audit.log
    - --audit-log-maxage=30          # Retain logs for 30 days
    - --audit-log-maxbackup=10       # Keep 10 rotated log files
    - --audit-log-maxsize=100        # Rotate when file reaches 100 Megabytes
    # 3. Optional: Configure Webhook Streaming Backend to SIEM
    - --audit-webhook-config-file=/etc/kubernetes/audit-webhook.yaml
    - --audit-webhook-batch-max-size=100
    - --audit-webhook-batch-max-wait=1s
```

## Common Interview Questions

**Q1: What is the primary purpose of Kubernetes API Server Audit Logging?**

API Server Audit Logging provides a chronological, security-relevant record documenting the sequence of activities that have affected the cluster. It answers four essential questions for security operations, compliance (PCI-DSS, SOC 2, HIPAA), and forensic post-mortems: **Who** made the request (User, ServiceAccount, Groups), **What** action was executed (Verb, Resource, Request Payload), **When** was it executed (Timestamp, Stages), and **What** was the result (HTTP status code, admission verdict).

**Q2: What are the four Audit Levels in Kubernetes, and what data does each level capture?**

1. `None`: Completely disables audit logging for matching events (used to drop high-volume noise like read probes).
2. `Metadata`: Logs request metadata (user, timestamp, verb, resource, namespace, response code) but excludes request and response payload bodies.
3. `Request`: Logs metadata plus the full JSON body sent in the client's request payload, but excludes the response body.
4. `RequestResponse`: Logs metadata, the full client request payload body, and the full API server response body.

**Q3: Why is logging `Secrets` and `ConfigMaps` at the `RequestResponse` level considered a severe security violation?**

If Secrets or ConfigMaps are evaluated at `Request` or `RequestResponse` levels, the API server writes the entire base64-encoded secret payload directly into the `/var/log/kubernetes/audit/audit.log` plaintext file. Anyone with access to the log files, SIEM dashboards (Splunk/Datadog), or S3 log storage archives can decode the base64 strings and steal corporate database passwords, private encryption keys, and cloud API tokens. Secrets must strictly be logged at the **`Metadata`** level.

**Q4: What are the four Audit Stages in the Kubernetes API request lifecycle?**

1. `RequestReceived`: Generated the instant the API server receives the request, before authentication or admission control.
2. `ResponseStarted`: Generated when HTTP response headers are transmitted for long-running streaming/watch requests.
3. `ResponseComplete`: Generated when the response body is completed and closed (the most useful stage for auditing).
4. `Panic`: Generated if an internal panic occurred during request processing.

**Q5: How do Audit Policy rules evaluate incoming requests?**

The API server evaluates the rules in the `AuditPolicy` manifest in strict **top-to-bottom order**. The first matching rule determines the audit level for that event. Once a match is found, evaluation halts. If an event does not match any rule in the policy, it defaults to being logged at the `None` level (no audit record produced). Therefore, policy authors place specific exclusions (`level: None` for noise) at the top, followed by critical write operations, ending with a general fallback rule at the bottom.
