## Real-Life Analogy

Think of OOMKilled terminations and Go pprof profiling as **a building code enforcement inspector and an forensic architectural auditor investigating a collapsing building**:

- **The Exit Code 137 Executioner (The Linux Kernel OOM Killer):** When an unruly tenant packs so much heavy furniture into their apartment that the ceiling begins cracking (**`working_set_bytes` exceeds `limits.memory`**), the building code officer does not send a polite warning letter. The SWAT team kicks the door down and evicts the tenant with an immediate shotgun blast (**`SIGKILL (Signal 9)` $\to$ Exit Code $128 + 9 = 137$**).
- **The 3 Types of Collapses:**
  - **1. Apartment Limit Breach (cgroup OOM):** Only Apartment 4B exceeded its individual lease limit; the rest of the building is completely fine.
  - **2. Building Foundation Collapse (Host Kernel OOM):** The entire physical skyscraper ran out of physical concrete (**Host RAM exhausted**). The kernel shoots the highest `oom_score_adj` tenant to save the building.
  - **3. Preemptive City Eviction (Kubelet Pressure Eviction):** The building manager notices that emergency stairs are getting congested (**`memory.available < 100Mi`**) and politely asks non-critical tenants to leave (**Pod Eviction**).
- **The Forensic X-Ray Auditor (Go `pprof`):** Instead of guessing which room has heavy furniture, the auditor brings an X-ray scanner (**`go tool pprof`**). The scanner instantly points to a single closet: *"80% of all building weight is coming from an unclosed database cache array in `handlers/order.go:line 42`!"*

## How to Instrument Go Microservices with `pprof`

Expose the standard Go `pprof` diagnostic endpoints by importing `net/http/pprof`:

```go
package main

import (
	"log"
	"net/http"
	_ "net/http/pprof" // Standard pprof HTTP handler registration!
)

func main() {
	// Start pprof debugging server on dedicated internal port (e.g. 6060)
	go func() {
		log.Println("Starting pprof profiling server on :6060")
		log.Println(http.ListenAndServe("0.0.0.0:6060", nil))
	}()

	// Main application logic...
	startApplicationServer()
}
```

```text
 Available pprof Endpoints:
 - `GET /debug/pprof/heap`: Heap memory allocation profile (Detects memory leaks).
 - `GET /debug/pprof/goroutine`: Stack traces of all current goroutines (Detects goroutine leaks).
 - `GET /debug/pprof/profile?seconds=30`: 30-second CPU profiling sample.
 - `GET /debug/pprof/block`: Goroutine blocking on synchronization primitives.
```

## Capturing and Analyzing Production Heap Profiles

```bash
# 1. Establish secure port-forward to the running Pod's pprof port
kubectl port-forward -n production pod/payment-api-7b8f 6060:6060 &

# 2. Capture a live 30-second Heap Profile into an interactive shell
go tool pprof http://localhost:6060/debug/pprof/heap

# Inside the pprof interactive console:
(pprof) top20 -inuse_space
(pprof) list OrderCache.Add
(pprof) png > heap_profile.png
```

```text
 Understanding inuse_space vs alloc_space:
 - `inuse_space`: Active memory currently held in RAM (Used for finding active MEMORY LEAKS).
 - `alloc_space`: Cumulative total memory allocated over the lifetime (Used for finding Garbage Collection churn).
```

## Diagnosing Goroutine Leaks

A **Goroutine Leak** occurs when a Go microservice spawns goroutines that block indefinitely on an unbuffered channel or a dead network socket, quietly consuming memory until the container is OOMKilled:

```bash
# Inspect active goroutine count in pprof
go tool pprof http://localhost:6060/debug/pprof/goroutine

(pprof) top10
# If you observe: 50,000 goroutines blocked on `chan receive`, you have a critical channel leak!
```

## Common Interview Questions

**Q1: What does Exit Code 137 mean in Kubernetes container crashes?**

In Unix-like operating systems, an exit code greater than 128 indicates that the process was terminated by an unhandled POSIX signal. The formula is:
$$\text{Exit Code} = 128 + \text{Signal Number}$$
Signal 9 is **`SIGKILL`**. Therefore, Exit Code 137 ($128 + 9 = 137$) means the container process was forcibly killed by `SIGKILL`. In Kubernetes, this most commonly occurs when the Linux kernel's Out-Of-Memory (OOM) killer terminates a container because its `container_memory_working_set_bytes` exceeded `resources.limits.memory`.

**Q2: What is the difference between a Container cgroup OOMKill and a Kubelet Node Pressure Eviction?**

- **Container cgroup OOMKill**: The container process exceeded its configured `resources.limits.memory`. The Linux kernel sends an instantaneous `SIGKILL` directly to the process. The Pod remains scheduled on the node and enters a `CrashLoopBackOff` restart cycle (`Reason: OOMKilled`).
- **Kubelet Node Pressure Eviction**: The entire physical worker node's available memory dropped below the eviction threshold (e.g. `memory.available < 100Mi`). Kubelet gracefully terminates the Pod via `SIGTERM`, removes it from the node, and marks the Pod phase as `Failed` (`Reason: Evicted`), prompting the scheduler to restart it on a different node.

**Q3: How do you differentiate between `inuse_space` and `alloc_space` when analyzing a Go heap profile?**

- **`inuse_space`**: Measures the total bytes of memory currently live in RAM that have not yet been freed by the garbage collector. This is the primary view used to detect **live memory leaks**.
- **`alloc_space`**: Measures the cumulative total memory allocated since the program started, including memory that has already been garbage collected. This view is used to identify high-allocation churn functions that trigger heavy GC CPU pauses.

**Q4: What is a Goroutine Leak, and how does it lead to an OOMKilled failure?**

A Goroutine leak occurs when an application continuously launches Go concurrency routines (goroutines) that never terminate (for example, waiting forever on an unbuffered channel that never receives data, or blocking on a network socket without a read timeout). Each goroutine allocates a minimum 2KB stack. Over days, tens of thousands of leaked goroutines accumulate, slowly consuming all container RAM until the working set breaches `limits.memory` and triggers an OOMKill.

**Q5: How can you confirm that a Pod was killed by the kernel OOM Killer by inspecting the host worker node?**

Access the host worker node and run `dmesg -T | grep -i oom` or inspect `/var/log/messages`. The Linux kernel outputs an explicit diagnostic block whenever `oom_reaper` is invoked:
`[Tue Aug 18 12:00:00 2026] Memory cgroup out of memory: Kill process 14201 (payment-api) score 950 or sacrifice child`
This confirms that the cgroup memory limit was breached.
