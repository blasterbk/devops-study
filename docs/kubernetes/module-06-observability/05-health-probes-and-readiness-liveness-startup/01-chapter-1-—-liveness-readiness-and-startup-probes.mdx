# Chapter 1 — Liveness, Readiness & Startup Probes

> **Goal:** Master container health and lifecycle management in Kubernetes — understanding the exact behavioral differences between **Startup Probes**, **Liveness Probes**, and **Readiness Probes**, analyzing how Kubelet executes probe control loops, mastering how Readiness probe failures decouple Pods from Service `Endpoints` without triggering container restarts, and tuning timing parameters (`periodSeconds`, `timeoutSeconds`, `failureThreshold`) for maximum reliability.
>
> By the end of this chapter, you will understand:
> 1. The distinct responsibilities of the 3 probe types: Startup, Liveness, and Readiness
> 2. How Startup Probes solve slow JVM and database cache warmups without inflating `initialDelaySeconds`
> 3. What happens when a Liveness Probe fails (Container Restart) vs Readiness Probe (Traffic Dropped)
> 4. How the Endpoints Controller dynamically updates `EndpointSlices` based on Readiness status
> 5. How to configure and tune the 5 probe timing parameters
> 6. How to diagnose probe failure events in `kubectl describe pod`

## Real-Life Analogy

Think of the 3 Kubernetes health probes as **the medical assessment protocols for an astronaut preparing for a space mission**:

- **Startup Probe (The Morning Wake-Up & Suit Check):** When the astronaut wakes up and puts on their 50-layer pressurized space suit (**Slow Application Startup / JVM Warmup**), they cannot talk or move for 10 minutes. The base commander does **not** assume they are dead and throw them out of the airlock. The Startup Probe waits patiently until the astronaut gives a thumbs-up (**Startup Succeeded**).
- **Liveness Probe (The Brain Activity & Heartbeat Monitor):** Once in outer space, the helmet tracks active brain waves. If the astronaut suffers a sudden stroke or total paralysis (**Deadlock / Infinite Loop**), the autopilot system triggers an emergency reboot (**Kubelet restarts the container**).
- **Readiness Probe (The Hands-Free Task Checklist):** The astronaut is alive and healthy, but their hands are currently full carrying a heavy oxygen tank (**Overloaded with background tasks / Warming cache**). The flight director does **not** shoot the astronaut; they simply stop handing them new satellite repair orders (**Removes Pod from Service Endpoints**) until their hands are free again (**Readiness Passes**).

## The 5 Probe Timing Parameters

Configured inside the container `probe` definition:

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5               # 1. Seconds to wait before 1st probe
  periodSeconds: 10                    # 2. Scrape interval (Frequency)
  timeoutSeconds: 2                    # 3. Seconds before probe is marked failed
  successThreshold: 1                  # 4. Consecutive successes to mark healthy
  failureThreshold: 3                  # 5. Consecutive failures before action
```

```text
 Total Failure Calculation:
 Time to Trigger Action = initialDelaySeconds + (periodSeconds * failureThreshold)
 Example: 5s + (10s * 3) = 35 seconds of persistent failure before Kubelet takes action.
```

## Why Startup Probes Solved the "Legacy Delay Trap"

Prior to Startup Probes, engineers running slow-starting apps (e.g. Java Spring Boot apps taking 90 seconds to boot) set:
`livenessProbe.initialDelaySeconds: 90`

```text
 The Legacy Problem:
 If the Java app crashed or deadlocked 2 minutes later, the 90-second delay was gone.
 But if the app restarted, it needed 90s. If it crashed during boot, Kubelet waited 90s to notice.
 
 The Startup Probe Solution:
 Set `startupProbe.periodSeconds: 5` and `failureThreshold: 30`.
 - Total allowed boot budget = 5s * 30 = 150 seconds!
 - If the app boots in 15 seconds, the Startup Probe succeeds at 15s and IMMEDIATELY 
   enables Liveness/Readiness without waiting for 150 seconds!
```

## Complete Production Workload Manifest (All 3 Probes)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: enterprise-payment-api
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      containers:
      - name: api
        image: payment-api:v2.4.0
        ports:
        - name: http-server
          containerPort: 8080

        # 1. Startup Probe: Accommodates slow initialization
        startupProbe:
          httpGet:
            path: /healthz/startup
            port: http-server
          failureThreshold: 30        # 30 * 5s = 150s max startup budget
          periodSeconds: 5
          timeoutSeconds: 2

        # 2. Liveness Probe: Detects hard unrecoverable deadlocks
        livenessProbe:
          httpGet:
            path: /healthz/liveness
            port: http-server
          periodSeconds: 10
          timeoutSeconds: 2
          failureThreshold: 3

        # 3. Readiness Probe: Manages traffic routing in Service Endpoints
        readinessProbe:
          httpGet:
            path: /healthz/readiness
            port: http-server
          periodSeconds: 5
          timeoutSeconds: 2
          failureThreshold: 2
          successThreshold: 1
```

```bash
# Step 1: Create lab namespace
kubectl create namespace probe-lab

cat <<EOF | kubectl apply -f - -n probe-lab

  name: failing-readiness-pod

    app: probe-demo

  containers:
  - name: web
    image: nginx:1.25-alpine

      httpGet:
        path: /non-existent-ready-path # Returns 404 Not Found!
        port: 80
      periodSeconds: 3
      failureThreshold: 2

kind: Service
metadata:
  name: probe-demo-svc
spec:
  selector:
    app: probe-demo
  ports:
  - port: 80
EOF

# Step 3: Wait 10 seconds and inspect Pod status
kubectl get pods -n probe-lab
# Observe: Pod is in Running state, but READY column shows 0/1!

# Step 4: Verify that Endpoints Controller stripped the Pod IP from the Service!
kubectl get endpoints probe-demo-svc -n probe-lab
# ENDPOINTS column is EMPTY (<none>)! Zero traffic is routed to the unready container.

# Step 5: Clean up lab
kubectl delete namespace probe-lab
```

## Common Interview Questions

**Q1: What is the operational difference between a Liveness Probe failure and a Readiness Probe failure?**

- **Liveness Probe Failure**: Indicates the container process has encountered an unrecoverable state (such as a deadlock or fatal thread stall). Kubelet immediately **terminates and restarts the container** according to the Pod's `restartPolicy`.
- **Readiness Probe Failure**: Indicates the container is temporarily unable to serve incoming network traffic (e.g. warming up caches or handling a CPU burst). Kubelet **does not kill or restart the container**; instead, the Endpoints controller removes the Pod's IP address from all matching Kubernetes Service `Endpoints` and Ingress controllers until the probe succeeds again.

**Q2: How do Startup Probes solve the problems associated with slow-starting applications?**

For legacy or heavy applications (such as large Java Spring Boot apps or machine learning models loading weights into memory), initialization can take several minutes. Without a Startup Probe, setting a high `initialDelaySeconds` on the Liveness probe creates a static delay that prevents Kubelet from restarting the app if it hangs later in production. The Startup Probe disables Liveness and Readiness checks until it passes. Once successful, Liveness checks activate immediately without arbitrary static delays.

**Q3: How does the Kubernetes Endpoints Controller interact with Readiness Probes?**

The Endpoints/EndpointSlice controller continuously watches Pod status updates from Kubelet. When a Pod's Readiness probe fails, Kubelet updates the Pod's condition `.status.conditions[type=Ready].status: "False"`. The Endpoints controller immediately removes the Pod's IP from the `Endpoints` list. Kube-proxy and Ingress controllers watch Endpoints and update local IP tables / routing maps in real time to stop sending traffic to that Pod.

**Q4: What are the risks of setting `timeoutSeconds` equal to or greater than `periodSeconds`?**

If `timeoutSeconds` is greater than or equal to `periodSeconds`, slow or hung probe requests will overlap with subsequent probe executions. This causes Kubelet probe workers to pile up, consuming node CPU and memory threads, and can lead to false failure triggers and cascading probe timeouts. Best practice mandates that `timeoutSeconds` should always be strictly smaller than `periodSeconds` (e.g. `timeoutSeconds: 2s` with `periodSeconds: 10s`).

**Q5: How can you diagnose why a Pod is failing health probes using `kubectl`?**

Run `kubectl describe pod <pod-name>`. Inspect the **Conditions** block (checking `Ready` and `ContainersReady`) and review the **Events** section at the bottom. Kubelet emits explicit warning events detailing probe failures:
`Warning  Unhealthy  Pod/my-pod  Liveness probe failed: HTTP probe failed with statuscode: 500`
