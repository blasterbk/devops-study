# Chapter 1 — OpenTelemetry Collector Architecture & OTLP

> **Goal:** Master vendor-neutral telemetry in Kubernetes using the **OpenTelemetry (OTel)** standard — understanding the OpenTelemetry Protocol (OTLP over gRPC port 4317 and HTTP port 4318), configuring the OpenTelemetry Collector pipeline components (**Receivers**, **Processors**, and **Exporters**), utilizing the `k8sattributes` processor for Kubernetes context enrichment, deploying the **OpenTelemetry Operator** for zero-code Auto-Instrumentation, and evaluating Agent vs Gateway deployment topologies.
>
> By the end of this chapter, you will understand:
> 1. The OpenTelemetry unified telemetry model across Traces, Metrics, and Logs
> 2. How the OTLP protocol serializes data with Protobuf over gRPC (4317) and HTTP (4318)
> 3. The 3-stage Collector pipeline: Receivers $\to$ Processors $\to$ Exporters
> 4. How the OpenTelemetry Operator injects auto-instrumentation agents into Pods via annotations
> 5. How `k8sattributes` automatically attaches Pod, Namespace, and Node metadata to telemetry
> 6. When to use DaemonSet Agents vs Standalone Cluster Gateway collectors

## Real-Life Analogy

Think of OpenTelemetry and the OTel Collector as **a universal international postal translation and forwarding hub**:

- **The Multi-Lingual Mess (Vendor Lock-in Anti-Pattern):** In the past, if an app wrote logs in German (Datadog SDK), metrics in French (New Relic SDK), and traces in Japanese (Zipkin SDK), you had to embed 3 heavy vendor libraries in your code. If you switched vendors, you had to rewrite 100,000 lines of code.
- **The Universal Language (OTLP - OpenTelemetry Protocol):** All your microservices speak one standardized, vendor-neutral diplomatic language (**OTLP over gRPC port 4317**).
- **The Processing Hub (The OTel Collector Pipeline):**
  - **Receivers (The Inbound Loading Dock):** Accepts telemetry from any source (OTLP, Jaeger, Prometheus, Zipkin).
  - **Processors (The Quality Control & Stamping Desk):** Bundles small letters into large boxes (**`batch`**), prevents memory overflows (**`memory_limiter`**), and stamps the sender's exact Kubernetes room number and company department onto the envelope (**`k8sattributes` processor**).
  - **Exporters (The Outbound Delivery Fleet):** Ships the data to wherever you want—splitting traces to Jaeger, metrics to Prometheus, and compliance logs to AWS S3 simultaneously.
- **The Auto-Instrumentation Injector (The Invisible Assistant):** The OpenTelemetry Operator sneaks an assistant into your room at boot time who translates your Java/Node.js app automatically without you changing a single line of application source code.

## The 3-Stage Collector Pipeline

Every pipeline declared in the OTel Collector manifest connects **Receivers**, **Processors**, and **Exporters**:

```text
 ┌──────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
 │ Pipeline Stage       │ Purpose & Standard Production Components                                    │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **1. Receivers**     │ How data enters the collector.                                              │
 │                      │ Standard: `otlp` (gRPC 4317, HTTP 4318), `jaeger`, `zipkin`, `prometheus`. │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **2. Processors**    │ Data transformation, batching, and metadata enrichment.                     │
 │                      │ Standard: `memory_limiter` (prevents OOM), `k8sattributes` (K8s context),   │
 │                      │ `batch` (compresses network payloads), `transform` (modifies fields).       │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **3. Exporters**     │ Where processed telemetry is routed.                                        │
 │                      │ Standard: `otlp` (Jaeger/Tempo/AWS X-Ray), `prometheus`, `logging`, `kafka`.│
 └──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## Zero-Code Auto-Instrumentation via OTel Operator

The **OpenTelemetry Operator** can automatically inject tracing SDKs into running applications without modifying application source code:

```yaml
# 1. Define Instrumentation Custom Resource
apiVersion: opentelemetry.io/v1alpha1
kind: Instrumentation
metadata:
  name: default-instrumentation
  namespace: production
spec:
  exporter:
    endpoint: http://opentelemetry-collector.monitoring.svc:4317
  propagators:
    - tracecontext                      # W3C TraceContext standard!
    - baggage
  java:
    image: ghcr.io/open-telemetry/opentelemetry-java-instrumentation/agent:v2.4.0
  nodejs:
    image: ghcr.io/open-telemetry/opentelemetry-operator/autoinstrumentation-nodejs:v0.51.0
  python:
    image: ghcr.io/open-telemetry/opentelemetry-operator/autoinstrumentation-python:v0.45b0
```

### Injecting Auto-Instrumentation into a Deployment:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: billing-service
  namespace: production
spec:
  template:
    metadata:
      annotations:
        # The Operator automatically mounts the Java agent into the container!
        instrumentation.opentelemetry.io/inject-java: "true"
    spec:
      containers:
      - name: billing
        image: openjdk:17-alpine
```

## Deployment Topologies: Agent (DaemonSet) vs Gateway

```text
 ┌───────────────────────────┬─────────────────────────────────┬─────────────────────────────────┐
 │ Dimension                 │ Agent Pattern (DaemonSet)       │ Gateway Pattern (Deployment)    │
 │───────────────────────────┼─────────────────────────────────┼─────────────────────────────────┤
 │ **Location**              │ 1 Collector on **every Node**.  │ Centralized load-balanced pool  │
 │                           │ Apps send to `localhost:4317`.  │ in dedicated monitoring cluster.│
 │ **Memory Footprint**      │ Low per-node footprint.         │ High (Aggregated telemetry).    │
 │ **Kubernetes Enrichment** │ **Fastest & Best.** Interacts   │ Requires querying API server for│
 │                           │ with local node Kubelet.        │ all pods across all nodes.      │
 │ **Tail-Based Sampling**   │ Cannot perform cross-node traces│ **Ideal for Tail Sampling.**    │
 │ **Best Practice**         │ **Hybrid:** Use DaemonSet Agents forwarding to a central Gateway!│
 └───────────────────────────┴─────────────────────────────────┴─────────────────────────────────┘
```

## Complete Production `OpenTelemetryCollector` Manifest

```yaml
apiVersion: opentelemetry.io/v1alpha1
kind: OpenTelemetryCollector
metadata:
  name: cluster-collector
  namespace: monitoring
spec:
  mode: daemonset                      # Deployed as a node DaemonSet!
  config: |
    receivers:
      otlp:
        protocols:
          grpc:
            endpoint: 0.0.0.0:4317
          http:
            endpoint: 0.0.0.0:4318

    processors:
      memory_limiter:
        check_interval: 1s
        limit_percentage: 75
        spike_limit_percentage: 15

      k8sattributes:
        auth_type: "serviceAccount"
        passthrough: false
        extract:
          metadata:
            - k8s.pod.name
            - k8s.pod.uid
            - k8s.namespace.name
            - k8s.node.name
            - k8s.deployment.name

      batch:
        send_batch_size: 1000
        timeout: 2s

    exporters:
      otlp/tempo:
        endpoint: tempo.monitoring.svc:4317
        tls:
          insecure: true
      prometheus:
        endpoint: 0.0.0.0:8889

    service:
      pipelines:
        traces:
          receivers: [otlp]
          processors: [memory_limiter, k8sattributes, batch]
          exporters: [otlp/tempo]
        metrics:
          receivers: [otlp]
          processors: [memory_limiter, k8sattributes, batch]
          exporters: [prometheus]
```

## Common Interview Questions

**Q1: What is OpenTelemetry (OTel), and what problem does it solve in cloud-native observability?**

OpenTelemetry is a CNCF graduated observability framework providing a unified, vendor-neutral collection of APIs, SDKs, and tooling to generate, collect, and export **Traces, Metrics, and Logs**. It eliminates proprietary vendor lock-in: instead of embedding proprietary vendor agents (Datadog, Dynatrace, New Relic) in application code, microservices use the standardized OTel SDK. Changing backends requires only editing the OpenTelemetry Collector's exporter configuration with zero changes to application code.

**Q2: What is the OpenTelemetry Protocol (OTLP), and which standard ports does it use?**

OTLP is the official communication protocol designed specifically for OpenTelemetry. It serializes telemetry payloads using Google Protocol Buffers (Protobuf) for maximum network compression and sub-millisecond serialization speeds. OTLP exposes two standard network endpoints:
- **Port 4317**: OTLP over **gRPC** (High-throughput streaming).
- **Port 4318**: OTLP over **HTTP/Protobuf** or HTTP/JSON.

**Q3: How does the `k8sattributes` processor enrich telemetry data in the Collector?**

When a Pod sends OTLP data to a node-level Collector, the data often lacks Kubernetes metadata. The `k8sattributes` processor inspects the incoming client IP address of the TCP connection, correlates the IP with the local Kubelet/API Server pod registry, and automatically attaches resource attributes (`k8s.namespace.name`, `k8s.pod.name`, `k8s.deployment.name`, `k8s.node.name`) to every Span and Metric before forwarding to storage backends.

**Q4: How does Auto-Instrumentation work in the OpenTelemetry Operator?**

The OpenTelemetry Operator injects tracing capabilities using a Mutating Admission Webhook. When a Pod with the annotation `instrumentation.opentelemetry.io/inject-<language>: "true"` is submitted to the API server, the Operator mutates the Pod spec by: (1) Adding an `initContainer` that copies the language-specific tracing agent (e.g. Java JAR or Node.js module) into a shared volume; and (2) Setting environment variables (like `JAVA_TOOL_OPTIONS: -javaagent:/otel/opentelemetry-javaagent.jar`), enabling complete distributed tracing with zero application code changes.

**Q5: What is the difference between an Agent (DaemonSet) and Gateway deployment mode in OTel Collector?**

- **Agent Mode (DaemonSet)**: Runs a Collector pod on every worker node. Applications emit telemetry to `localhost:4317`. It minimizes network hops, provides fast local buffering, and excels at `k8sattributes` enrichment.
- **Gateway Mode (Deployment)**: Runs a centralized, horizontally scalable cluster behind a Kubernetes Service. It acts as an egress proxy for external cloud backends, handles centralized API key management, and enables **Tail-Based Sampling** (evaluating full multi-service distributed traces across all nodes before deciding which traces to persist).
