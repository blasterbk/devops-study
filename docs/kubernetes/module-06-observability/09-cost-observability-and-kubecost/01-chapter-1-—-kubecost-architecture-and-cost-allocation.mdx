## Real-Life Analogy

Think of Kubecost and multi-tenant cost allocation as **an itemized restaurant bill splitting engine for a corporate dinner with 50 employees**:

- **The Problem (The Monolithic Cloud Invoice):** The restaurant server brings a single master invoice for \$5,000 (**The AWS EC2/EKS Monthly Bill**). The CFO has no idea whether the Marketing team ordered \$4,000 of expensive champagne or the Engineering team ordered \$100 of pizza.
- **The Telemetry Sensor (Prometheus Resource Scraper):** The server tracks exactly how many slices of pizza (**CPU core-hours**) and glasses of water (**RAM GiB-hours**) each person consumed.
- **The Pricing Engine (Cloud Billing Integration):** The server connects to the kitchen cash register (**AWS CUR / GCP Billing Export**) to get exact negotiated corporate discount prices for raw ingredients.
- **The Reservation Rule (Max of Request vs Usage):** If Alice reserved 8 seats at the table (**`resources.requests.cpu: 8`**) but only 1 person showed up to eat (**Actual CPU usage: 0.5**), Alice's department is still billed for all 8 reserved seats because nobody else could sit at those chairs (**You pay for what you reserve**).
- **The Empty Table Waste (Idle Capacity Allocation):** If 3 tables in the corner were completely empty all night (**Cluster Idle Waste**), Kubecost splits the cost of those empty tables fairly across all 50 diners based on their dinner size (**Idle Cost Distribution**).

## The Request vs Usage Cost Modeling Formula

In shared Kubernetes clusters, a Pod prevents other Pods from scheduling by setting **Resource Requests**, even if it doesn't actually use that capacity:

$$\text{Billed Resource Allocation} = \max(\text{Resource Request}, \text{Actual Resource Usage})$$

```text
 ┌───────────────────────────────────┬────────────────────────────────────────────────────────────────┐
 │ Scenario                          │ Cost Billing Calculation                                       │
 │───────────────────────────────────┼────────────────────────────────────────────────────────────────┤
 │ **Case A: Idle Over-Provisioned** │ Pod requests 8 CPU cores; uses only 0.5 cores.                 │
 │                                   │ ──► **Billed for 8 CPU Cores!** (Node capacity was blocked).   │
 │───────────────────────────────────┼────────────────────────────────────────────────────────────────┤
 │ **Case B: Heavy Burstable Pod**   │ Pod requests 1 CPU core; bursts to 4 cores during peak.        │
 │                                   │ ──► **Billed for 4 CPU Cores!** (Actual compute consumed).     │
 └───────────────────────────────────┴────────────────────────────────────────────────────────────────┘
```

## What is Cluster Idle Waste and How is it Distributed?

If a cluster has 10 worker nodes costing \$1,000/month, but workloads only request 40% of the CPU/RAM, **\$600/month is Idle Waste**.

```text
 ┌───────────────────────────┬────────────────────────────────────────────────────────────────────────┐
 │ Idle Allocation Strategy  │ Mathematical Distribution Method                                       │
 │───────────────────────────┼────────────────────────────────────────────────────────────────────────┤
 │ **Separate (Default)**    │ Retains Idle as a separate line item (`__idle__`), exposing cluster    │
 │                           │ infrastructure over-provisioning to DevOps managers.                   │
 │───────────────────────────┼────────────────────────────────────────────────────────────────────────┤
 │ **Proportional to Usage** │ Multiplies each microservice's bill by the cluster idle multiplier,    │
 │                           │ distributing the bill across active tenants.                           │
 └───────────────────────────┴────────────────────────────────────────────────────────────────────────┘
```

  prometheus:
    enabled: false                     # Integrate with existing Prometheus-Stack

  warmCache: true

    storage: 0.000137                  # Cost per GiB-hour EBS

    department: "department"

    env: "environment"

## The Kubecost Cost Allocation REST API

FinOps teams query the Kubecost `/model/allocation` API to automate chargeback reports:

```bash
# Query cost breakdown by Kubernetes Namespace over the last 7 days
curl -G "http://kubecost.monitoring.svc:9090/model/allocation" \
  --data-urlencode "window=7d" \
  --data-urlencode "aggregate=namespace" \
  --data-urlencode "accumulate=true" \
  --data-urlencode "idle=true" | jq .
```

## Common Interview Questions

**Q1: Why are standard AWS/GCP cloud billing invoices insufficient for multi-tenant Kubernetes clusters?**

Public cloud invoices only bill for raw Infrastructure-as-a-Service (IaaS) resources—such as 100 EC2 instances or 50 EBS volumes. In a shared multi-tenant Kubernetes cluster, hundreds of microservices belonging to different engineering teams share the exact same physical VM instances. Standard cloud bills cannot see inside Kubernetes to determine which namespace, deployment, or team label consumed what percentage of the CPU, memory, and network I/O.

**Q2: What is the $\max(\text{Request}, \text{Usage})$ cost allocation model, and why is it used?**

When a Pod sets `resources.requests.cpu: 4`, the Kubernetes scheduler reserves 4 physical CPU cores on a worker node exclusively for that container, preventing other pods from using that capacity even if the container sits idle at 0.1 cores. The $\max(\text{Request}, \text{Usage})$ formula charges the application for whichever is higher: the **capacity it blocked from the cluster (Request)** or the **raw compute it actually consumed (Usage)**, incentivizing developers to right-size their resource requests.

**Q3: How does Kubecost integrate with Cloud Provider Billing APIs (like AWS CUR)?**

While Kubecost calculates real-time estimates using public list prices, enterprise organizations receive heavy discounts (Savings Plans, Reserved Instances, Enterprise Discount Programs). Kubecost ingests **AWS Cost & Usage Reports (CUR)** from an S3 bucket or queries the GCP Cloud Billing Export. It reconciles real-time Prometheus telemetry with actual historical discount rates to produce 100% accurate amortized financial invoices.

**Q4: What is "Cluster Idle Waste", and why does it represent the biggest opportunity for cost savings?**

Cluster Idle Waste represents the unallocated CPU cores and RAM on worker nodes that are paid for in the cloud bill but are neither requested nor utilized by any running workloads. In unoptimized clusters, idle waste frequently accounts for **50% to 70% of the total monthly cloud bill**. Tracking idle waste allows platform teams to enable autoscaling, consolidate nodes, and right-size clusters.

**Q5: How does Kubecost calculate network egress costs per microservice?**

Kubecost uses a lightweight network observability daemon or eBPF network probe. It tracks cross-zone (Inter-AZ), cross-region, and internet-bound egress data streams per Pod socket, maps the transfer bytes against cloud provider network pricing tiers (e.g. \$0.01/GB Inter-AZ, \$0.09/GB Internet), and attributes the exact network egress bill to the originating microservice.
