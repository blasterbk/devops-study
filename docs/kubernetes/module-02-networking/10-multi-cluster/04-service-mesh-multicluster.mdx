# Chapter 4 — Service Mesh Multi-Cluster

> **Goal:** Understand how service meshes extend to multi-cluster environments — Istio's primary-remote and multi-primary models, Linkerd's service mirroring approach, how cross-cluster mTLS is achieved with a shared root CA, and how traffic management policies apply across cluster boundaries.
>
> By the end of this chapter, you will understand:
> 1. Istio multi-cluster deployment models: single-network vs multi-network
> 2. The east-west gateway — the cross-cluster traffic entry point for multi-network
> 3. Primary-remote vs multi-primary control plane architectures
> 4. Cross-cluster mTLS: shared trust domain and federated root CA
> 5. Linkerd multicluster: service mirroring and gateway-based cross-cluster
> 6. Cross-cluster traffic management: weighted routing, failover

## Real-Life Analogy

Single-cluster Istio is like a **corporate security system in one building** — badge readers at every door, consistent policy across all floors.

**Istio multi-cluster** is like extending that badge system **across multiple buildings on a corporate campus**:

For buildings **on the same physical network** (single-network model): the same badge system hardware works across buildings — you can walk directly from building A to B and your badge works everywhere. Simple extension.

For buildings **in different cities or countries** (multi-network model): you need **international liaison offices** (east-west gateways) at the border of each building. Your badge is recognized because both buildings were issued badges by the **same corporate HR (shared root CA)**. When you visit Building B from Building A, you go through the liaison office, which verifies your badge and escorts you in.

  │ istiod               │               │ istiod               │

## Istio Multi-Primary (Multi-Network) Setup

Most production deployments use multi-primary with separate networks:

```bash
# Step 1: Create a shared root CA
# Generate root CA key and cert (shared across all clusters)
mkdir -p certs && cd certs
make -f ../tools/certs/Makefile.selfsigned.mk root-ca
make -f ../tools/certs/Makefile.selfsigned.mk cluster-a-cacerts
make -f ../tools/certs/Makefile.selfsigned.mk cluster-b-cacerts

# Step 2: Install root certs in each cluster
kubectl create secret generic cacerts -n istio-system \
  --from-file=cluster-a/ca-cert.pem \
  --from-file=cluster-a/ca-key.pem \
  --from-file=root-cert.pem \
  --from-file=cluster-a/cert-chain.pem \
  --context=cluster-a

kubectl create secret generic cacerts -n istio-system \
  --from-file=cluster-b/ca-cert.pem \
  --from-file=cluster-b/ca-key.pem \
  --from-file=root-cert.pem \
  --from-file=cluster-b/cert-chain.pem \
  --context=cluster-b

# Step 3: Install Istio on each cluster with unique cluster/network names
istioctl install --context=cluster-a -y -f - <<EOF
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  values:
    global:
      meshID: mesh1
      multiCluster:
        clusterName: cluster-a
      network: network-a   # Network label (unique per L3 domain)
EOF

# Similar for cluster-b with network: network-b

# Step 4: Install east-west gateway in each cluster
istioctl install --context=cluster-a -y -f eastwest-gateway.yaml
# Gets a LoadBalancer IP: 1.2.3.4

istioctl install --context=cluster-b -y -f eastwest-gateway.yaml
# Gets a LoadBalancer IP: 5.6.7.8

# Step 5: Expose services through east-west gateways
kubectl apply --context=cluster-a -f \
  samples/multicluster/expose-services.yaml

# Step 6: Exchange cluster credentials (each istiod needs to watch the other's API)
istioctl create-remote-secret \
  --context=cluster-b \
  --name=cluster-b | kubectl apply --context=cluster-a -f -

istioctl create-remote-secret \
  --context=cluster-a \
  --name=cluster-a | kubectl apply --context=cluster-b -f -
```

## Cross-Cluster mTLS: Shared Trust

```text
Shared Root CA Model:
  Root CA (offline, secure)
      │
      ├── Cluster A Intermediate CA (signed by root)
      │   istiod-A signs Envoy certs with this CA
      │   SVID: spiffe://mesh1/ns/production/sa/api-sa
      │
      └── Cluster B Intermediate CA (signed by root)
          istiod-B signs Envoy certs with this CA
          SVID: spiffe://mesh1/ns/production/sa/frontend-sa

Cross-cluster mTLS:
  Pod A (cluster-a) → East-West GW A → (internet/VPN) → East-West GW B → Pod B (cluster-b)
  
  Auth: Pod A presents cert signed by Cluster-A-CA
        Cluster-B-CA trusts Cluster-A-CA (both signed by same root)
        → mTLS established, identity verified
        SPIFFE URI identifies the source unambiguously
```

## Cross-Cluster Traffic Management

Once multi-cluster is set up, VirtualServices and DestinationRules work across clusters:

```yaml
# Route 80% to local cluster, 20% to remote cluster (active-active)
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: api-multicluster
  namespace: production
spec:
  host: api-service.production.svc.cluster.local
  trafficPolicy:
    loadBalancer:
      localityLbSetting:
        enabled: true
        distribute:           # Distribute traffic by cluster/region
        - from: "cluster-a/*"
          to:
            "cluster-a/*": 80    # 80% to local cluster
            "cluster-b/*": 20    # 20% to remote cluster
        failoverPriority:
        - "topology.kubernetes.io/zone"
        - "topology.kubernetes.io/region"
---
# Failover: primary cluster-a, failover to cluster-b
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: api-failover
spec:
  host: api-service.production.svc.cluster.local
  trafficPolicy:
    loadBalancer:
      localityLbSetting:
        enabled: true
        failover:
        - from: us-east1   # If us-east1 fails
          to: us-west1     # Fail over to us-west1
    outlierDetection:      # Required for failover to trigger
      consecutive5xxErrors: 3
      interval: 10s
      baseEjectionTime: 30s
```

## Linkerd Multicluster

Linkerd's approach is simpler — service mirroring via a gateway:

```bash
# Install Linkerd multicluster extension
linkerd multicluster install | kubectl apply -f -

# Link Cluster A to Cluster B (one-directional link)
linkerd multicluster link --context=cluster-b \
  --cluster-name cluster-b | kubectl apply -f - --context=cluster-a

# Export a service from Cluster B
kubectl label service api-service \
  mirror.linkerd.io/exported=true \
  -n production --context=cluster-b

# Verify service mirror appears in Cluster A
kubectl get services -n production --context=cluster-a
# NAME                      TYPE        CLUSTER-IP
# api-service               ClusterIP   10.96.45.23    (local)
# api-service-cluster-b     ClusterIP   10.96.45.50    (mirrored from cluster-b!)
```

```text
Linkerd Service Mirroring:
  1. Service "api-service" exported in Cluster B
  2. Linkerd mirror controller in Cluster A watches Cluster B's services
  3. Creates "api-service-cluster-b" Service in Cluster A
  4. "api-service-cluster-b" routes through Cluster B's multicluster gateway
  5. Application calls "api-service-cluster-b" for cross-cluster access
     OR uses a combined ExternalName service for transparent routing
  6. mTLS: Linkerd certificates from both clusters must share a trust anchor
```

## Hands-On: Istio Multi-Cluster Validation

```bash
# 1. Verify east-west gateways are running
kubectl get pods -n istio-system -l app=istio-eastwestgateway \
  --context=cluster-a

kubectl get svc istio-eastwestgateway -n istio-system \
  --context=cluster-a
# EXTERNAL-IP: 1.2.3.4

# 2. Check remote cluster secrets are configured
kubectl get secrets -n istio-system --context=cluster-a | grep remote
# istio-remote-secret-cluster-b   ...

# 3. Verify istiod sees endpoints from both clusters
kubectl exec -n istio-system deploy/istiod --context=cluster-a -- \
  pilot-discovery request GET /debug/endpointz | \
  python3 -m json.tool | grep "cluster-b"

# 4. Deploy test service in cluster-b only
kubectl run backend --image=nginx -n production \
  --context=cluster-b

kubectl expose pod backend --port=80 -n production \
  --context=cluster-b

# 5. Call from cluster-a (should route to cluster-b via EW gateway)
kubectl run client --image=curlimages/curl -n production \
  --context=cluster-a \
  --rm -it --restart=Never -- \
  curl http://backend.production.svc.cluster.local
# Should succeed, response from cluster-b nginx

# 6. Verify cross-cluster traffic in Kiali (shows inter-cluster edges)
istioctl dashboard kiali --context=cluster-a

# 7. Test failover (scale cluster-a backend to 0)
kubectl scale deployment backend -n production --replicas=0 \
  --context=cluster-a
# Traffic should automatically fail over to cluster-b
```

## Common Interview Questions

**Q1: What are the two Istio multi-cluster deployment models and when do you use each?**

(1) **Single-network model**: all cluster Pods can directly route to each other (same L3 network, BGP or VPC peering with non-overlapping CIDRs). One istiod can manage sidecars in multiple clusters (primary-remote). No east-west gateways needed — Envoy can directly connect to cross-cluster Pods. (2) **Multi-network model**: clusters are on separate L3 networks (can't route Pod IPs directly). Requires east-west gateways in each cluster — cross-cluster traffic enters/exits through gateway LoadBalancers. Each cluster runs its own istiod (multi-primary). Most cloud multi-region deployments use multi-network.

**Q2: Why does Istio multi-cluster require a shared root CA?**

mTLS authentication works by verifying that the peer's certificate is signed by a trusted CA. In single-cluster Istio, all certs are signed by istiod, which is the CA. In multi-cluster, Cluster A's istiod signs certs for Cluster A Pods, and Cluster B's istiod signs certs for Cluster B Pods. For Cluster A Pods to trust Cluster B Pod certificates (and vice versa), they must share the same root CA (or have cross-signed intermediates). Without this, the mTLS handshake fails — Cluster A's Envoy rejects Cluster B's cert because it was signed by an untrusted CA.

**Q3: What is the east-west gateway in Istio multi-cluster and why is it needed?**

The east-west gateway is a dedicated Istio `Gateway` deployed with a LoadBalancer service specifically for handling cross-cluster traffic in multi-network deployments. When a Pod in Cluster A needs to reach a service in Cluster B, its Envoy routes the request to the east-west gateway of Cluster A (which forwards via the internet/VPN to Cluster B's east-west gateway), which then delivers to the destination Pod. It serves as the border crossing for inter-cluster traffic, presenting mTLS certificates for mutual authentication. Cluster A's Envoy cannot directly reach Cluster B's Pods (different networks), so all cross-cluster connections are proxied through these gateways.

**Q4: How does Linkerd multicluster's service mirroring approach work?**

Linkerd's service mirroring controller watches exported services in remote clusters. When a service is labeled `mirror.linkerd.io/exported=true` in Cluster B, the mirror controller in Cluster A creates a local "mirror" Service named `<svc-name>-<cluster-name>` (e.g., `api-service-cluster-b`). This mirror service routes traffic through Cluster B's multicluster gateway (a LoadBalancer-type Service). Applications in Cluster A call the mirrored service name explicitly. Traffic gets normal Linkerd mTLS, load balancing, and metrics. The trust anchor (root certificate) must be shared across both clusters for mTLS to work cross-cluster.

**Q5: What is locality-based load balancing in Istio and how does it enable active-active multi-cluster?**

Locality-based load balancing routes traffic preferentially to endpoints in the same locality (zone → region → global). Configured in DestinationRule's `localityLbSetting`, you can: distribute traffic by specifying `from → to` percentages (e.g., 80% to local cluster, 20% to remote), or configure failover (if local cluster healthy endpoints drop to 0%, fail over to remote). This requires `outlierDetection` to be configured so Envoy knows when to trigger failover. In active-active multi-cluster: Cluster A serves 80% with Cluster B handling 20%, both running in parallel — if Cluster A degrades, traffic automatically shifts to Cluster B.
