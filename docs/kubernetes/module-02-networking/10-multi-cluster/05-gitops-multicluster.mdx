> **Goal:** Understand how GitOps tools solve the operational challenge of managing workloads across dozens of clusters — Argo CD ApplicationSet generators, Flux multi-cluster with GitRepository references, cluster fleet management patterns, and multi-cluster RBAC governance.

> 6. Multi-cluster RBAC governance and policy propagation

## Real-Life Analogy

Without GitOps for multi-cluster: a team of operators manually `kubectl apply`s to each of 20 clusters, maintaining drift between them. It's like a franchise owner who calls every store manager daily with instructions — error-prone, slow, and impossible to audit.

**GitOps for multi-cluster** is like a **franchise central operations system**: the HQ (Git repository) publishes the official menu, pricing, and procedures. Every store (cluster) has an agent (Flux/Argo CD) that continuously checks the HQ system and applies exactly what's specified. If a store deviates from the spec (configuration drift), the agent immediately corrects it. New stores (clusters) are automatically configured the moment they register.

## Why GitOps for Multi-Cluster

```text
Problems GitOps solves for multi-cluster:

1. Drift prevention:
   Without: cluster-a has v1.2.0, cluster-b has v1.1.9 (forgot to update)
   With: Git is authoritative, both clusters auto-sync to v1.2.0

2. Audit trail:
   Every cluster change is a git commit with author, time, and diff
   "Who changed cluster-b's config at 3am?" → git log

3. Rollback:
   git revert → all clusters automatically roll back
   vs manually finding the right kubectl apply command for 20 clusters

4. New cluster bootstrapping:
   Register cluster-d → ApplicationSet auto-deploys all standard workloads
   No manual runbook needed

5. Policy enforcement:
   Cluster fleet policies (NetworkPolicy, PodSecurityPolicy, RBAC)
   defined in Git → automatically applied and re-applied if removed
```

## Argo CD ApplicationSet: Cluster Generator

ApplicationSet generates one Argo CD Application per matching cluster:

```yaml
# Deploy to ALL clusters registered in Argo CD
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: deploy-api-all-clusters
  namespace: argocd
spec:
  generators:
  - clusters: {}    # All clusters in Argo CD's cluster registry

  template:
    metadata:
      name: "api-{{cluster}}"   # Unique app name per cluster
    spec:
      project: default
      source:
        repoURL: https://github.com/org/kubernetes-configs
        targetRevision: HEAD
        path: apps/api/base   # Same base for all clusters
      destination:
        server: "{{server}}"     # Each cluster's API server URL
        namespace: production
      syncPolicy:
        automated:
          prune: true            # Remove resources deleted from Git
          selfHeal: true         # Auto-fix configuration drift
---
# Deploy only to clusters with specific labels (subset of clusters)
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: deploy-api-production
spec:
  generators:
  - clusters:
      selector:
        matchLabels:
          environment: production    # Only production clusters
          region: us-east            # Only US East region

  template:
    metadata:
      name: "api-prod-{{name}}"
    spec:
      source:
        path: apps/api/overlays/production   # Production-specific overlay
      destination:
        server: "{{server}}"
        namespace: production
```

## ApplicationSet: Git Generator

Generate applications from directory structure in Git:

```yaml
# One Application per directory in /clusters/
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
spec:
  generators:
  - git:
      repoURL: https://github.com/org/kubernetes-configs
      revision: HEAD
      directories:
      - path: clusters/*   # Each subdirectory = one Application

  template:
    metadata:
      name: "{{path.basename}}"   # Directory name = app name
    spec:
      source:
        path: "{{path}}"    # Use the matched directory as source
      destination:
        server: https://kubernetes.default.svc
        namespace: production
```

### Matrix Generator: Combining Generators

```yaml
# Cross-product: all apps × all clusters
spec:
  generators:
  - matrix:
      generators:
      - git:
          directories:
          - path: apps/*           # All app directories
      - clusters:
          selector:
            matchLabels:
              environment: production
  template:
    metadata:
      name: "{{path.basename}}-{{name}}"  # app-cluster pairs
    spec:
      source:
        path: "{{path}}"
      destination:
        server: "{{server}}"
```

## Flux Multi-Cluster Pattern

Flux uses a GitOps Toolkit approach with Kustomize overlays:

```text
Repository structure for Flux multi-cluster:
  /
  ├── base/                          # Shared base configs
  │   ├── api-deployment.yaml
  │   └── kustomization.yaml
  │
  ├── clusters/
  │   ├── cluster-a/
  │   │   ├── kustomization.yaml     # Cluster-A-specific overrides
  │   │   └── flux-system/           # Flux bootstrap for cluster-a
  │   │       ├── gotk-components.yaml
  │   │       └── gotk-sync.yaml
  │   └── cluster-b/
  │       ├── kustomization.yaml
  │       └── flux-system/
```

```yaml
# clusters/cluster-a/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
bases:
- ../../base
patches:
- patch: |
    - op: replace
      path: /spec/replicas
      value: 5              # More replicas for cluster-a (production)
  target:
    kind: Deployment
    name: api-deployment
```

```yaml
# Flux Kustomization CRD (not the kubectl kustomization)
# Applied in each cluster — watches its own cluster directory
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: cluster-config
  namespace: flux-system
spec:
  interval: 10m           # Reconcile every 10 minutes
  path: ./clusters/cluster-a
  prune: true             # Remove resources deleted from Git
  sourceRef:
    kind: GitRepository
    name: cluster-config
  targetNamespace: production
```

## Fleet Management at Scale

Managing 50+ clusters requires fleet-level tooling:

```bash
# Argo CD: manage all clusters from CLI
argocd cluster list
# SERVER                    NAME       STATUS   MESSAGE
# https://cluster-a-api     cluster-a  Unknown  Cluster was added
# https://cluster-b-api     cluster-b  Successful

# Check sync status across all clusters
argocd app list
# NAME             CLUSTER     NAMESPACE   STATUS    HEALTH
# api-cluster-a    cluster-a   production  Synced    Healthy
# api-cluster-b    cluster-b   production  OutOfSync Healthy  ← Drift detected!

# Force sync a drifted cluster
argocd app sync api-cluster-b

# Diff between Git and live state across all apps
argocd app diff api-cluster-a

# Argo CD ApplicationSet — pull-request preview environments
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
spec:
  generators:
  - pullRequest:
      github:
        owner: org
        repo: app
        tokenRef:
          secretName: github-token
          key: token
      requeueAfterSeconds: 60   # Poll for new PRs every 60s
  template:
    metadata:
      name: "pr-{{number}}"
    spec:
      source:
        targetRevision: "{{head_sha}}"
```

## Multi-Cluster RBAC Governance

```yaml
# OCM Policy: propagate RBAC to all managed clusters
# Using OCM's Policy framework (governance)
apiVersion: policy.open-cluster-management.io/v1
kind: Policy
metadata:
  name: enforce-readonly-rbac
  namespace: default
spec:
  remediationAction: enforce   # enforce = auto-fix; inform = just report
  disabled: false
  policy-templates:
  - objectDefinition:
      apiVersion: rbac.authorization.k8s.io/v1
      kind: ClusterRole
      metadata:
        name: view-only
      rules:
      - apiGroups: [""]
        resources: ["pods", "services"]
        verbs: ["get", "list", "watch"]
---
# Bind this policy to a PlacementRule (all production clusters)
apiVersion: policy.open-cluster-management.io/v1
kind: PlacementBinding
metadata:
  name: bind-rbac-to-production
spec:
  placementRef:
    name: production-placement
    apiGroup: cluster.open-cluster-management.io
    kind: Placement
  subjects:
  - name: enforce-readonly-rbac
    apiGroup: policy.open-cluster-management.io
    kind: Policy
```

## Hands-On: ApplicationSet Debugging

```bash
# 1. List all ApplicationSets
kubectl get applicationsets -n argocd

# 2. Check ApplicationSet generated Applications
kubectl get applications -n argocd | grep "api-"
# api-cluster-a   cluster-a   Synced    Healthy
# api-cluster-b   cluster-b   OutOfSync Degraded

# 3. Debug a failing Application
argocd app get api-cluster-b
argocd app logs api-cluster-b

# 4. Check why ApplicationSet didn't generate for a cluster
kubectl describe applicationset deploy-api-production -n argocd
# Look for: "Clusters selected: 2, Generated: 2" or errors

# 5. Verify cluster labels match selector
kubectl get secret -n argocd -l argocd.argoproj.io/secret-type=cluster \
  -o jsonpath='{range .items[*]}{.metadata.name}: {.metadata.labels}{"\n"}{end}'

# 6. Add label to a cluster (so ApplicationSet selects it)
kubectl label secret cluster-c-secret \
  environment=production \
  region=us-east \
  -n argocd

# 7. Trigger immediate reconciliation
argocd app sync api-cluster-a --force

# 8. Check for drift across all apps
argocd app list --output wide | grep "OutOfSync"
```

## Common Interview Questions

**Q1: Why is GitOps the recommended operational model for multi-cluster Kubernetes?**

GitOps solves three multi-cluster operational challenges: (1) **Drift** — without GitOps, clusters gradually diverge as operators make ad-hoc changes; GitOps continuously reconciles live state to Git state. (2) **Auditability** — every change is a git commit with author, timestamp, and diff; in multi-cluster environments this is essential for compliance and incident investigation. (3) **Scale** — manually applying to 20 clusters is error-prone; GitOps agents in each cluster pull and apply their own config automatically. New clusters are bootstrapped by simply registering them — the agent pulls and applies all required manifests from Git.

**Q2: What is an Argo CD ApplicationSet and how does the cluster generator work?**

An ApplicationSet is an Argo CD CRD that generates multiple Application resources from a template and a set of generators. The cluster generator queries Argo CD's cluster registry and creates one Application per matching cluster (optionally filtered by label selectors). The generated Application's destination server is set to `{{server}}` (the cluster's API URL) and its name to `{{name}}` or a template expression. This means: adding a new cluster to Argo CD automatically creates the Application for it, and removing a cluster cleans up its Application — no manual Application creation needed.

**Q3: What is the difference between Argo CD ApplicationSet and Flux's multi-cluster approach?**

Argo CD ApplicationSet is **hub-centric** — a central Argo CD instance generates Applications targeting multiple clusters and pushes configurations to them. Argo CD must have API credentials for all managed clusters. Flux is **agent-centric** (pull model) — each cluster runs its own Flux instance that pulls its specific configuration (path) from Git. The hub only needs a Git repository, not access to each cluster. Flux is more secure (no central credential store) but requires Flux bootstrap on each cluster. For organizations with strict security requirements, Flux's pull model is preferred.

**Q4: How does the Argo CD matrix generator work and what problem does it solve?**

The matrix generator creates a cross-product of two other generators. Example: combine a git generator (all app directories) with a clusters generator (all production clusters) → creates one Application per app-per-cluster combination. This solves the "deploy all apps to all clusters" use case without manually listing every combination. A matrix of 5 apps × 10 clusters automatically generates 50 Applications. If you add a new app directory to Git, 10 new Applications are created (one per cluster). If you add a new cluster, 5 new Applications are created (one per app).

**Q5: How do you enforce consistent RBAC and security policies across dozens of clusters?**

Several approaches: (1) **OCM Policy** (Open Cluster Management) — a `Policy` CRD defines the desired state (e.g., a ClusterRole); a `PlacementBinding` binds it to a Placement selecting clusters; the OCM governance controller propagates and enforces the policy, remediating drift automatically. (2) **Argo CD ApplicationSet** — store RBAC manifests in Git, generate one Application per cluster targeting the RBAC directory; Argo CD auto-applies and self-heals. (3) **Kyverno/OPA in each cluster** — policies applied via GitOps ensure consistent admission control across clusters. The combination of GitOps (OCM or Argo CD) + policy-as-code (Kyverno/OPA) is the production standard.
