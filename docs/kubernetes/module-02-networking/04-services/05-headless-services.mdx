# Chapter 5 — Headless Services

> **Goal:** Understand what headless Services are, how they return all Pod IPs directly through DNS, why StatefulSets depend on them for stable identity, and how they enable client-side load balancing and service mesh integration.
>
> By the end of this chapter, you will understand:
> 1. What makes a Service "headless" (`clusterIP: None`)
> 2. How CoreDNS returns individual Pod IPs for headless Services
> 3. How StatefulSets use headless Services for stable Pod DNS names
> 4. Client-side load balancing with headless Services
> 5. When to use headless vs ClusterIP Services
> 6. How service meshes (Istio, Linkerd) use headless Services

---

## Real-Life Analogy

A normal ClusterIP Service is like a **switchboard** — you dial one number and the operator decides which desk to connect you to. You never know which desk you're at.

A Headless Service is like a **company directory** that lists every individual employee's direct phone number. When you call, you get the full list: "John's direct line: ext 101, Sarah's: ext 102, Mike's: ext 103." You decide who to call and manage the conversation yourself.

This is useful for databases (MySQL Cluster, MongoDB replica sets) where the application must know specific member IPs — not just any member — to initiate replication or connect to the primary specifically.

## Architecture Diagram

```text
              Headless vs ClusterIP DNS Response

Normal ClusterIP Service (my-svc):
  DNS query: my-svc.default.svc.cluster.local
  CoreDNS response:
  ┌──────────────────────────────────────┐
  │  A record: 10.96.45.23 (ClusterIP)  │
  └──────────────────────────────────────┘
  Client connects to virtual IP → kube-proxy DNAT → any Pod

Headless Service (my-headless-svc, clusterIP: None):
  DNS query: my-headless-svc.default.svc.cluster.local
  CoreDNS response:
  ┌──────────────────────────────────────┐
  │  A record: 10.244.1.5  (Pod A IP)   │
  │  A record: 10.244.2.3  (Pod B IP)   │
  │  A record: 10.244.2.7  (Pod C IP)   │
  └──────────────────────────────────────┘
  Client sees all Pod IPs → decides which to connect to
```

## Creating a Headless Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-headless-svc
  namespace: default
spec:
  clusterIP: None      # THIS is what makes it headless
  selector:
    app: myapp
  ports:
  - name: http
    port: 80
    targetPort: 8080
```

```bash
kubectl apply -f headless-svc.yaml
kubectl get svc my-headless-svc

# Output:
# NAME               TYPE        CLUSTER-IP  EXTERNAL-IP  PORT(S)  AGE
# my-headless-svc   ClusterIP   None        <none>       80/TCP   5s
# ← No IP allocated!

# DNS response shows all Pod IPs:
kubectl run dnstest --image=busybox --restart=Never -- \
  nslookup my-headless-svc.default.svc.cluster.local
kubectl logs dnstest
# Server: 10.96.0.10
# Name: my-headless-svc.default.svc.cluster.local
# Address: 10.244.1.5    ← Pod A
# Address: 10.244.2.3    ← Pod B
# Address: 10.244.2.7    ← Pod C
```

## StatefulSets + Headless Services: Stable Identity

StatefulSets use headless Services to give each Pod a **stable, predictable DNS name**. This is critical for stateful applications (databases, Kafka, Zookeeper) where replicas need to know each other.

```yaml
# StatefulSet with headless Service
apiVersion: v1
kind: Service
metadata:
  name: mongo           # Headless Service for StatefulSet
spec:
  clusterIP: None
  selector:
    app: mongo
  ports:
  - port: 27017
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongo
spec:
  serviceName: "mongo"   # Must reference the headless Service
  replicas: 3
  selector:
    matchLabels:
      app: mongo
  template:
    metadata:
      labels:
        app: mongo
    spec:
      containers:
      - name: mongo
        image: mongo:6.0
        ports:
        - containerPort: 27017
```

### Resulting DNS Names

StatefulSet Pod names are deterministic: `<statefulset-name>-<ordinal>`. Combined with the headless Service, each Pod gets a stable FQDN:

```text
Pod 0: mongo-0.mongo.default.svc.cluster.local → 10.244.1.5
Pod 1: mongo-1.mongo.default.svc.cluster.local → 10.244.2.3
Pod 2: mongo-2.mongo.default.svc.cluster.local → 10.244.2.7

Format: <pod-name>.<service-name>.<namespace>.svc.cluster.local
```

```bash
# These DNS names are stable across Pod restarts
# If mongo-1 Pod is deleted and rescheduled, it gets a new IP
# BUT mongo-1.mongo.default.svc.cluster.local still resolves to it

# MongoDB replica set config uses these stable names:
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "mongo-0.mongo.default.svc.cluster.local:27017" },
    { _id: 1, host: "mongo-1.mongo.default.svc.cluster.local:27017" },
    { _id: 2, host: "mongo-2.mongo.default.svc.cluster.local:27017" }
  ]
})
```

This is why `spec.serviceName` in StatefulSet must point to a headless Service — it's what enables the per-Pod DNS naming.

## Client-Side Load Balancing

For gRPC and other protocols that maintain persistent connections, standard ClusterIP round-robin doesn't work well:

```text
Problem with ClusterIP for gRPC:
  Client opens 1 long-lived connection to ClusterIP
  kube-proxy DNAT: fixed to Pod A for this connection's lifetime
  Result: 100% of gRPC requests go to Pod A — zero load balancing

Headless Service solution:
  Client DNS lookup → gets all 3 Pod IPs
  gRPC library (or application code) creates connections to all 3
  Client library distributes requests across all 3 connections
  Real per-RPC load balancing!
```

```python
# Python gRPC with headless Service (client-side LB)
import grpc
from grpc import experimental

channel = grpc.insecure_channel(
    "my-grpc-svc.default.svc.cluster.local:50051",
    options=[
        # Tell gRPC to re-resolve DNS and connect to all returned IPs
        ("grpc.lb_policy_name", "round_robin"),
        # Re-resolve every 30 seconds for new Pods
        ("grpc.service_config", '{"loadBalancingConfig": [{"round_robin": {}}]}'),
    ],
)
```

## Headless Without Selector

A headless Service without a selector has no automatic endpoint management. Combine with manual EndpointSlices for external services that need multiple IP resolution:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-cluster
spec:
  clusterIP: None    # Headless
  # No selector
  ports:
  - port: 9200
---
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  name: external-cluster-slice
  labels:
    kubernetes.io/service-name: external-cluster
addressType: IPv4
ports:
- port: 9200
endpoints:
- addresses: ["10.100.1.1"]
  conditions: { ready: true }
- addresses: ["10.100.1.2"]
  conditions: { ready: true }
- addresses: ["10.100.1.3"]
  conditions: { ready: true }
```

DNS resolution returns all three external IPs — useful for Elasticsearch, Cassandra, and other multi-node external clusters.

## Service Mesh Integration

Service meshes (Istio, Linkerd) typically intercept traffic by injecting sidecar proxies. With a headless Service:

```text
Istio + Headless Service:
  1. Pod starts with Envoy sidecar injected
  2. Client Pod resolves headless DNS → gets all backend Pod IPs
  3. Client connects to backend Pod IP directly
  4. Envoy sidecar on CLIENT intercepts the connection (iptables redirect)
  5. Envoy applies Istio policy: retries, circuit breaking, mTLS
  6. Envoy forwards to the specific backend Pod IP (no DNAT)

Result: Istio gets per-Pod traffic visibility and control
        (vs ClusterIP where Envoy can't distinguish between backends)
```

This is why Istio recommends headless Services for StatefulSets — it gives Istio fine-grained per-Pod traffic management.

## Hands-On: Debugging Headless Services

```bash
# 1. Create a headless Service and Deployment
kubectl create deployment headless-app --image=nginx --replicas=3
kubectl expose deployment headless-app --port=80 \
  --cluster-ip=None --name=headless-app-svc

# 2. Verify no ClusterIP
kubectl get svc headless-app-svc -o jsonpath='{.spec.clusterIP}'
# Output: None

# 3. DNS lookup returns all Pod IPs
kubectl run nslookup --image=busybox --restart=Never -- \
  nslookup headless-app-svc.default.svc.cluster.local
kubectl logs nslookup

# 4. Compare with regular ClusterIP DNS lookup
kubectl expose deployment headless-app --port=80 --name=clusterip-svc
kubectl run nslookup2 --image=busybox --restart=Never -- \
  nslookup clusterip-svc.default.svc.cluster.local
kubectl logs nslookup2  # Returns only 1 ClusterIP

# 5. Inspect per-Pod DNS records for StatefulSet
# Scale a StatefulSet and test individual Pod DNS:
kubectl run pod-dns-test --image=busybox --restart=Never -- \
  nslookup mongo-0.mongo.default.svc.cluster.local
kubectl logs pod-dns-test

# 6. Watch DNS updates as Pods scale
# Terminal 1: watch DNS in loop
kubectl exec -it test-pod -- sh -c \
  "while true; do nslookup headless-app-svc.default.svc.cluster.local 2>&1 | grep Address; sleep 2; done"

# Terminal 2: scale the Deployment
kubectl scale deployment headless-app --replicas=5
# Watch Terminal 1 — new IPs appear as Pods become ready
```

## ClusterIP vs Headless: Decision Guide

| Use Case | Recommendation |
|----------|---------------|
| Standard web microservices | ClusterIP |
| Stateful apps (databases, Kafka, ZK) | Headless + StatefulSet |
| gRPC services with persistent connections | Headless (client-side LB) |
| Service mesh (Istio) with per-Pod policy | Headless |
| Simple L4 load balancing | ClusterIP |
| Application needs to know all member IPs | Headless |
| Need stable per-Pod DNS names | Headless + StatefulSet |

## Common Interview Questions

**Q1: What is a headless Service and how is it created?**

A headless Service is a Service with `clusterIP: None`. No virtual IP is allocated, no iptables/IPVS rules are created, and no kube-proxy involvement occurs. When a Pod queries DNS for a headless Service, CoreDNS returns individual A records for each Pod IP backing the Service (rather than a single ClusterIP). Applications receive all backend IPs and make connection decisions themselves.

**Q2: Why do StatefulSets require a headless Service?**

StatefulSets create Pods with stable, sequential names (`pod-0`, `pod-1`, `pod-2`). Combined with a headless Service (`serviceName` field), each Pod gets a stable DNS FQDN: `<pod-name>.<service-name>.<namespace>.svc.cluster.local`. These names resolve to the current Pod IP even after restarts (the Pod name and DNS name are stable, only the IP changes). Distributed databases (MongoDB, Cassandra, Kafka) use these stable names to configure replication — they need to address specific members, not random backends.

**Q3: Why is headless preferred over ClusterIP for gRPC services?**

gRPC uses persistent HTTP/2 connections. When a client connects to a ClusterIP, kube-proxy DNATs the connection to one specific backend Pod for the lifetime of that TCP connection — all subsequent gRPC calls on that connection go to the same Pod, giving zero load balancing benefit. With a headless Service, the gRPC client receives all Pod IPs and creates separate connections to each. The gRPC client library then distributes individual RPCs across these connections — real per-call load balancing.

**Q4: What DNS records does CoreDNS create for a headless Service with 3 backends?**

CoreDNS creates: (1) Multiple A records for `<svc>.<ns>.svc.cluster.local` — one per ready Pod IP. (2) For StatefulSets: individual A records for `<pod-name>.<svc>.<ns>.svc.cluster.local` mapping each Pod name to its current IP. (3) SRV records for named ports: `_<port-name>._<protocol>.<svc>.<ns>.svc.cluster.local`. No CNAME, no single aggregated IP.

**Q5: What is the difference between a headless Service and an ExternalName Service?**

A headless Service (`clusterIP: None`) has a selector — it returns real Pod IPs from the cluster's own workloads. It enables per-Pod DNS names and client-side load balancing. An ExternalName Service (`type: ExternalName`) returns a DNS CNAME to an external hostname — it doesn't return any Pod IPs. It's purely for aliasing external hostnames. They both avoid creating a ClusterIP virtual IP, but for completely different reasons and purposes.
