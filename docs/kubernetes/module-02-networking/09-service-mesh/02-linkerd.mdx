## Real-Life Analogy

If Istio is a **full diplomatic corps** (powerful, feature-rich, complex), Linkerd is a **specialized security escort service**:

Every employee (Pod) gets a personal escort (linkerd2-proxy sidecar). The escort's job is narrow but done exceptionally well: authenticate every conversation (mTLS), route intelligently (EWMA load balancing), and report accurately (metrics). No speech writers, no protocol officers, no elaborate ceremony — just reliable, secure, efficient communication.

The escort is also incredibly lightweight — barely noticeable, consuming minimal resources. You trust them completely because the code is simple enough to audit fully.

## Installing Linkerd

```bash
# Install the Linkerd CLI
curl --proto '=https' --tlsv1.2 -sSfL https://run.linkerd.io/install | sh
export PATH=$HOME/.linkerd2/bin:$PATH

# Pre-flight checks
linkerd check --pre

# Install CRDs
linkerd install --crds | kubectl apply -f -

# Install Linkerd control plane
linkerd install | kubectl apply -f -

# Wait and verify
linkerd check

# Install viz extension (Prometheus + dashboard)
linkerd viz install | kubectl apply -f -
linkerd viz check

# Open dashboard
linkerd viz dashboard
```

## Zero-Config mTLS

Linkerd's most celebrated feature — all meshed traffic is automatically mTLS encrypted and authenticated with **zero configuration**:

```text
How it works:
  1. identity control plane acts as a Certificate Authority
  2. Each linkerd2-proxy requests a SPIFFE certificate on startup:
     SPIFFE URI: spiffe://cluster.local/ns/production/sa/api-service-account
  3. Proxy presents this cert for every outbound connection
  4. Receiving proxy verifies the cert against the trust anchor
  5. If verified: mTLS connection established
  6. If not verified: connection rejected

No ServiceEntry, no PeerAuthentication, no DestinationRule.
No YAML. Automatic. Always on.
```

```bash
# Verify mTLS is active for a service
linkerd viz edges -n production
# SRC                    DST                    TLS
# frontend               api-service            √ (mTLS)
# api-service            postgres               √ (mTLS)
# loadgenerator          frontend               √ (mTLS)

# Check certificate identity for a Pod
linkerd viz tap -n production deploy/api-deployment | grep tls
# tls=true src_id=spiffe://cluster.local/ns/production/sa/api-sa
```

## EWMA Load Balancing

Linkerd uses **EWMA (Exponential Weighted Moving Average)** for latency-aware load balancing:

```text
Standard Kubernetes kube-proxy:
  Round-robin at TCP connection level
  No awareness of backend latency or queue depth

Linkerd EWMA:
  For each request, measures the backend's response latency
  Maintains exponentially weighted moving average of latency per endpoint
  Routes new requests to the endpoint with the LOWEST estimated latency
  Adapts in real-time: if one Pod becomes slow, traffic shifts away immediately

Effect:
  - Better tail latency (P99, P999)
  - Automatic "unhealthy" backend avoidance
  - No need for explicit circuit breaker config for many cases
```

## Linkerd ServiceProfile

ServiceProfiles add route-level metrics and retries per service:

```yaml
apiVersion: linkerd.io/v1alpha2
kind: ServiceProfile
metadata:
  name: api-service.production.svc.cluster.local
  namespace: production
spec:
  routes:
  - name: GET /api/users
    condition:
      method: GET
      pathRegex: /api/users(/.*)?
    responseClasses:
    - condition:
        status:
          min: 500
          max: 599
      isFailure: true   # Mark 5xx as failure for success rate metrics

  - name: POST /api/orders
    condition:
      method: POST
      pathRegex: /api/orders
    isRetryable: true     # Retry on failure
    timeout: 10s          # Per-request timeout
    retryBudget:
      retryRatio: 0.2     # At most 20% additional requests from retries
      minRetriesPerSecond: 10
      ttl: 10s
```

## Linkerd vs Istio Comparison

| Feature | Linkerd | Istio |
|---------|---------|-------|
| **Proxy** | linkerd2-proxy (Rust, ~4MB) | Envoy (C++, ~70MB) |
| **Memory/proxy** | ~10-20MB | ~50-100MB |
| **mTLS** | Automatic, zero-config | Requires PeerAuthentication |
| **L7 traffic mgmt** | ServiceProfile (basic) | VirtualService (advanced) |
| **L7 policy (HTTP method/path)** | Via ServiceProfile | Via VirtualService + CiliumNetworkPolicy |
| **Complexity** | Low (simple mental model) | High (many CRDs, concepts) |
| **Protocol support** | HTTP/1, HTTP/2, gRPC, TCP | All + WebSocket, MongoDB protocol |
| **WebAssembly extensions** | Not supported | Supported (WASM plugins) |
| **Multi-cluster** | Linkerd-multicluster | Istio multi-cluster (complex) |
| **Best for** | Teams wanting simple, secure mesh | Teams needing full traffic mgmt |

## Common Interview Questions

**Q1: What is linkerd2-proxy and why was it written in Rust instead of using Envoy?**

linkerd2-proxy is a purpose-built micro-proxy written in Rust, designed exclusively for the Linkerd service mesh. It was written in Rust (not using Envoy) for several reasons: (1) **Memory safety** — Rust's ownership model prevents entire classes of bugs (buffer overflows, use-after-free) without garbage collection overhead; (2) **Footprint** — the binary is ~4MB vs Envoy's ~70MB, using ~10-20MB RAM vs 50-100MB per proxy; (3) **Simplicity** — purpose-built for Linkerd's specific needs, with a simpler codebase that's easier to audit and maintain than Envoy's general-purpose architecture.

**Q2: How does Linkerd implement mTLS without any YAML configuration?**

Linkerd's identity control plane acts as a Certificate Authority. When a linkerd2-proxy starts, it automatically requests an X.509 certificate from the identity component using its Kubernetes ServiceAccount credential as proof of identity. The certificate uses SPIFFE URI format: `spiffe://cluster.local/ns/<ns>/sa/<serviceaccount>`. The proxy presents this certificate for all outbound connections. The receiving proxy verifies it against the trust anchor (the cluster's root CA). This entire process is automatic — no PeerAuthentication, no DestinationRule, no service-level config needed.

**Q3: What is EWMA load balancing and why is it better than round-robin for microservices?**

EWMA (Exponential Weighted Moving Average) load balancing routes each request to the backend with the lowest exponentially-weighted moving average response latency. Unlike round-robin (which ignores backend performance), EWMA continuously measures actual response latency per backend and shifts traffic away from slow or overloaded endpoints. This is especially valuable in microservices where backends can have high latency variability — EWMA automatically avoids the slow Pod in real-time, improving tail latency (P99/P999) without explicit circuit breaker configuration.

**Q4: What is a Linkerd ServiceProfile and what does it add?**

A ServiceProfile is a Linkerd CRD that adds per-route configuration for a Service. It enables: per-route metrics (success rate, latency broken down by route/method/path), retries (mark certain responses as failures and retry them), per-request timeouts, and a retry budget (limits total retry overhead as a percentage of original requests). Without a ServiceProfile, Linkerd tracks metrics at the service level only. With it, you get method+path-level visibility — useful for identifying which specific API endpoint has high error rates.

**Q5: When would you choose Linkerd over Istio?**

Choose Linkerd when: (1) you prioritize simplicity — Linkerd has fewer CRDs and a simpler mental model; (2) resource efficiency matters — Linkerd uses ~10x less memory per proxy than Istio/Envoy, critical for large clusters or resource-constrained nodes; (3) you primarily need mTLS and golden signal metrics with minimal configuration; (4) your team is small and maintaining complex Istio configuration is a burden. Choose Istio when: you need advanced L7 traffic management (VirtualService canary, fault injection, header-based routing), WASM extensions, or multi-protocol support beyond HTTP/gRPC.
