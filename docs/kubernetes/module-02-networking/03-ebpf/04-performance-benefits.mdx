# Chapter 4 — eBPF Performance Benefits

> **Goal:** Quantify and understand the performance improvements eBPF provides over traditional kernel networking — in terms of throughput, latency, CPU efficiency, and connection rate — with real benchmark data and measurement tools.
>
> By the end of this chapter, you will understand:
> 1. Why eBPF is faster than iptables at the kernel architecture level
> 2. XDP line-rate performance numbers (millions of packets per second)
> 3. Throughput and latency comparisons: iptables vs IPVS vs eBPF
> 4. CPU overhead reduction from skipping Netfilter
> 5. Connection tracking cost and how eBPF reduces it
> 6. How to benchmark and measure network performance in Kubernetes

## Real-Life Analogy

Imagine processing **100,000 visa applications per day** at an airport:

**iptables approach:** Each traveler must stand in a single queue. One officer scans a growing printed list from top to bottom to find the right stamp. At 1,000 rules it takes 5 seconds per traveler. At 50,000 rules it takes 4 minutes per traveler. The queue stretches out the door.

**eBPF approach:** Each traveler scans their passport at an automated kiosk. The kiosk does one hash lookup (< 1 microsecond). No queue. Processing 100,000 travelers takes the same time per traveler regardless of whether the rulebook has 100 or 100,000 entries.

The difference isn't just speed — it's **the absence of degradation at scale**.

## Architecture Diagram

```text
              Kernel Network Stack Comparison

iptables path (Netfilter):
  Packet → NIC → Driver → sk_buff allocation
    → PREROUTING chain (N rules, sequential scan)
    → Routing decision
    → FORWARD chain (N rules)
    → POSTROUTING chain (N rules)
    → NIC → Wire
  
  CPU cost: O(N) per packet, grows with rule count
  Conntrack: every flow creates a table entry (memory)

eBPF XDP path (pre-stack):
  Packet → NIC driver → XDP hook (before sk_buff)
    → eBPF program: hash map lookup O(1)
    → XDP_PASS / XDP_DROP / XDP_REDIRECT / XDP_TX
  
  CPU cost: O(1), constant regardless of rule count
  Conntrack: optional (stateless for known flows)

eBPF TC path (in-stack):
  Packet → NIC → Driver → sk_buff → TC hook
    → eBPF program: 2-3 hash map lookups
    → Redirect / modify / drop
  
  CPU cost: O(1), slightly more than XDP (sk_buff overhead)
```

## Quantified Performance Comparisons

### XDP Raw Throughput

XDP can process packets at near line rate because it runs before the kernel network stack:

```text
Benchmark environment:
  Server: 2x Intel Xeon Gold 6148 (20C/40T each)
  NIC: Mellanox ConnectX-5 100GbE

Results:
  Single-core XDP (drop): ~14 million packets/second (14 Mpps)
  Multi-core XDP (drop):  ~100 Mpps (close to 100GbE line rate)
  
  Traditional iptables (drop): ~1-2 Mpps (10-14x slower)
  
  XDP forward (redirect to another interface): ~25-30 Mpps
```

### Service Routing (kube-proxy vs Cilium eBPF)

Real-world benchmarks from the Cilium project (2022, with k8s cluster):

```text
10 Services, 3 backends each:
  kube-proxy iptables: 2.1M req/s
  kube-proxy IPVS:     2.4M req/s
  Cilium eBPF:         2.8M req/s (+33% over iptables)

5,000 Services, 3 backends each:
  kube-proxy iptables: 0.3M req/s  ← severe degradation
  kube-proxy IPVS:     2.3M req/s  ← stable
  Cilium eBPF:         2.8M req/s  ← no degradation

50,000 Services:
  kube-proxy iptables: ~0.05M req/s  ← near unusable
  Cilium eBPF:         2.8M req/s    ← identical to 10 Services
```

The critical insight: **iptables throughput collapses at scale; eBPF remains constant.**

### Latency Comparison

```text
HTTP request latency (p50/p99), 1000 concurrent connections:

             p50          p99
iptables:    0.8ms        4.2ms
IPVS:        0.7ms        3.1ms
Cilium eBPF: 0.6ms        1.8ms
Cilium + DSR: 0.4ms       1.2ms   ← removes return-path hop

At scale (5000 Services):
iptables p99:    18ms  (4x worse)
Cilium eBPF p99: 1.8ms (unchanged)
```

### CPU Efficiency

```text
kube-proxy iptables (1000 Services, 10K req/s):
  - iptables rule processing: ~15% CPU on one core
  - conntrack lookups: ~8% CPU
  - Total network processing overhead: ~23%

Cilium eBPF (1000 Services, 10K req/s):
  - eBPF map lookups: ~3% CPU
  - No conntrack for established flows: 0%
  - Total network processing overhead: ~3%

Reduction: ~87% lower CPU overhead for network processing
```

## Why eBPF Is Faster: Technical Breakdown

### 1. Elimination of Netfilter Overhead

Netfilter (the kernel framework powering iptables) processes every packet through multiple hooks even if no rule matches:

```text
Packet traverses these Netfilter hooks regardless of rules:
  PREROUTING → ROUTING DECISION → (FORWARD or INPUT) → POSTROUTING

Each hook: function call overhead + traversal of all registered modules
Even an empty iptables has Netfilter overhead.

Cilium eBPF with kube-proxy replacement:
  Detaches from Netfilter for traffic it handles
  → Zero Netfilter overhead for most cluster traffic
```

### 2. Elimination of conntrack for Known Flows

The Linux connection tracking table (`nf_conntrack`) creates an entry for every TCP/UDP flow. At high connection rates:

```text
conntrack impact:
  - Memory: each entry ~300 bytes
  - At 1M concurrent connections: ~300MB just for conntrack
  - Lookup cost: hash table lookup per packet
  - Lock contention: conntrack table has per-bucket locks

Cilium's conntrack bypass:
  - For eBPF-handled flows: uses its own cilium_ct map
  - For accelerated socket-level paths: zero conntrack involvement
  - Result: eliminates conntrack lock contention at high QPS
```

### 3. O(1) Service Lookup

```text
iptables Service routing:
  N Services × M endpoints = N*M rules
  Each packet: scan rules until match
  Average: N*M/2 comparisons per packet

Cilium eBPF Service routing:
  1 hash table lookup in cilium_lb_services: always O(1)
  1 hash table lookup for backend: always O(1)
  Adding more Services: zero impact on per-packet cost
```

### 4. Socket-Level Acceleration (Fastest Path)

For Pod-to-Pod communication on the same node, Cilium can use the socket-level acceleration path:

```text
Traditional path:
  Send syscall → sk_buff allocation → routing → veth → kernel bridge → veth → receive

Cilium sockops path:
  Send syscall → eBPF sockops hook → direct socket redirect (bpf_sk_redirect)
  → receive syscall
  
  Completely bypasses: sk_buff routing, veth pairs, bridges
  Result: near loopback performance for same-node Pod communication
```

## Measuring Network Performance in Kubernetes

### Tools and Benchmarks

```bash
# 1. iperf3 — raw TCP/UDP throughput between Pods
kubectl run iperf-server --image=networkstatic/iperf3 \
  --command -- iperf3 -s
kubectl run iperf-client --image=networkstatic/iperf3 \
  --command -- iperf3 -c <server-pod-ip> -P 4 -t 30
# -P 4: 4 parallel streams
# -t 30: 30 second test

# 2. netperf — latency and throughput benchmark
kubectl run netperf-server --image=cilium/netperf
kubectl exec -it netperf-client -- netperf -H <server-ip> -t TCP_RR
# TCP_RR: measures request-response latency

# 3. k8s network benchmark (knb)
# https://github.com/InfraBuilder/k8s-bench-suite
curl -LO https://github.com/InfraBuilder/k8s-bench-suite/releases/latest/download/knb
chmod +x knb
./knb --server-node node1 --client-node node2

# 4. hey — HTTP benchmark for Service performance
# Measures Service routing overhead
kubectl expose pod test-nginx --port=80
hey -n 100000 -c 100 http://<cluster-ip>/

# 5. measure iptables rule count and reload time
iptables -t nat -L | wc -l
time iptables-save > /dev/null

# 6. measure conntrack table usage
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max

# 7. Monitor eBPF program execution time
# (requires kernel 5.2+ with BPF statistics)
sysctl -w kernel.bpf_stats_enabled=1
bpftool prog list  # Shows avg/max execution time per program
```

### What Numbers to Expect

```text
Same-node Pod-to-Pod (Cilium eBPF):
  TCP bandwidth: ~90% of loopback (30-40Gbps on 40G NIC)
  TCP_RR latency: ~20-40 microseconds

Cross-node Pod-to-Pod (no encapsulation):
  TCP bandwidth: wire speed (limited by NIC)
  TCP_RR latency: ~100-200 microseconds (dominated by physical RTT)

Cross-node Pod-to-Pod (VXLAN overlay):
  TCP bandwidth: ~90-95% of native (small encap overhead)
  TCP_RR latency: +5-15 microseconds vs native

Service ClusterIP (eBPF vs iptables at 5000 services):
  iptables: 0.3M req/s
  eBPF:     2.8M req/s
```

## Production Tuning for eBPF Performance

```bash
# 1. Enable huge pages for eBPF maps (reduces TLB pressure)
echo 512 > /proc/sys/vm/nr_hugepages

# 2. Increase conntrack table size (for non-eBPF traffic)
sysctl -w net.netfilter.nf_conntrack_max=2097152

# 3. Enable NIC hardware offloading for VXLAN
ethtool -K eth0 tx-udp_tnl-segmentation on
ethtool -K eth0 tx-udp_tnl-csum-segmentation on

# 4. Tune XDP busy polling (reduces latency)
# On supported NICs (Intel i40e, Mellanox mlx5):
ethtool -C eth0 rx-usecs 0 adaptive-rx off

# 5. CPU pinning for network processing
# Set IRQ affinity for NIC queues
cat /proc/interrupts | grep eth0
echo 2 > /proc/irq/<irq-num>/smp_affinity  # Pin to CPU 1

# 6. Increase ring buffer size
ethtool -G eth0 rx 4096 tx 4096

# 7. Verify Cilium BPF compilation settings
kubectl exec -n kube-system cilium-<id> -- cilium config | grep -i bpf
```

## Common Interview Questions

**Q1: At what point does kube-proxy iptables performance become unacceptable?**

kube-proxy iptables begins showing measurable degradation around 1,000-2,000 Services. At 5,000 Services throughput drops by ~85% (from 2.1M req/s to 0.3M req/s). At 10,000+ Services, rule reloads take minutes and cause packet drops. Additionally, conntrack table exhaustion (default max 131,072 entries) becomes a problem at high connection rates, causing silent packet drops. Most Kubernetes deployments with serious production scale (500+ Services, high QPS) see real impact.

**Q2: How does Cilium achieve near wire-speed networking for same-node Pod communication?**

Cilium uses socket-level acceleration via eBPF `sockops` and `sk_skb` programs. When two Pods on the same node communicate, Cilium intercepts the `connect()` and `sendmsg()` syscalls and uses `bpf_sk_redirect()` to redirect data directly from the sender's socket buffer to the receiver's socket buffer. This bypasses all kernel networking layers: no sk_buff allocation, no routing, no veth pairs, no bridge. The result is near-loopback performance (~30-40Gbps on a 40G NIC).

**Q3: What is the conntrack problem and how does eBPF address it?**

The Linux connection tracking table (nf_conntrack) creates an entry (~300 bytes) for every TCP/UDP flow to track NAT state. At high connection rates (100K+ new connections/second), this causes: memory pressure, lock contention on the hash table, and potential table exhaustion. Cilium with kube-proxy replacement maintains its own `cilium_ct` eBPF maps for DNAT state and avoids Netfilter's conntrack for eBPF-handled traffic. For socket-accelerated paths, no connection tracking is needed at all.

**Q4: Why doesn't adding more Services affect Cilium's forwarding performance?**

Because Cilium uses eBPF hash maps with O(1) lookup complexity. Finding a Service VIP in `cilium_lb_services` is a single hash table lookup regardless of whether there are 10 or 100,000 Services. The same applies to backend selection (Maglev table lookup). In contrast, kube-proxy iptables must scan through all iptables rules sequentially — each additional Service adds more rules to scan, directly increasing per-packet processing time.

**Q5: How would you benchmark network performance between eBPF and iptables on the same cluster?**

Deploy two clusters (or before/after migration): run `iperf3` for raw TCP throughput, `netperf TCP_RR` for request-response latency, and `hey`/`wrk` for HTTP Service throughput. Measure at different Service counts (10, 100, 1000, 5000) to observe scaling behavior. Also monitor: `nf_conntrack_count` growth, CPU usage with `perf top` (looking for `ipt_do_table`, `nf_conntrack_*` functions), and iptables reload times. With Cilium eBPF enabled, these Netfilter functions should disappear from `perf top`.
