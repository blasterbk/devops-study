> **Why do I get HTTP 409 Conflict when two people update the same object simultaneously?**

> **How does kubectl watch know exactly which events it missed during a disconnect?**

# What is ResourceVersion?

`resourceVersion` is a string value stored in every Kubernetes object's `metadata`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
  namespace: default
  resourceVersion: "182934"
```

It is also present on List responses representing the state of the entire collection:

```json
{
  "kind": "DeploymentList",
  "metadata": {
    "resourceVersion": "183021"
  },
  "items": [...]
}
```

### Key Properties

```text
1. Opaque string — do not parse or compare numerically
2. Monotonically increasing — higher value = more recent state
3. Cluster-level — ResourceVersion reflects changes across all resources
4. etcd-backed — corresponds to the etcd revision number internally
```

> **Important:** Never try to parse `resourceVersion` as an integer in production code. Treat it as an opaque string. Only equality comparisons are valid.

# Optimistic Concurrency Control

Kubernetes uses ResourceVersion for **optimistic concurrency control** — allowing concurrent reads while detecting conflicting writes.

```text
Controller A reads Deployment
  resourceVersion: "100"
        |
Controller B reads Deployment
  resourceVersion: "100"
        |
Controller A writes update (includes resourceVersion: "100")
  -> API Server checks: current version == "100"? YES
  -> Write succeeds: new resourceVersion = "101"
        |
Controller B writes update (includes resourceVersion: "100")
  -> API Server checks: current version == "100"? NO (it is "101")
  -> HTTP 409 Conflict returned to Controller B
        |
Controller B re-reads Deployment (resourceVersion: "101")
  -> Re-applies its change
  -> Write succeeds: new resourceVersion = "102"
```

This prevents **lost updates** — a situation where two concurrent writers silently overwrite each other's changes.

# HTTP 409 Conflict

When the API Server detects a ResourceVersion conflict, it returns:

```http
HTTP/1.1 409 Conflict
Content-Type: application/json

{
  "kind": "Status",
  "reason": "Conflict",
  "message": "Operation cannot be fulfilled on deployments.apps \"nginx\": the object has been modified; please apply your changes to the latest version and try again"
}
```

The client **must** re-read the object, apply its changes to the fresh version, and retry the write.

# ResourceVersion in Watch Requests

ResourceVersion is equally important for Watch streams. It tells the API Server where to start sending events:

```http
GET /apis/apps/v1/namespaces/default/deployments?watch=true&resourceVersion=182934
```

This means: *"Send me all events that happened after resourceVersion 182934."*

```text
Client lists Deployments -> resourceVersion: "182934"
  |
  v
Client starts Watch with resourceVersion: "182934"
  |
  v
API Server sends only events AFTER version 182934
  |
  v
Client sees no gaps — perfect continuity
```

# Special ResourceVersion Values

| Value | Meaning |
| :--- | :--- |
| `""` (empty string) | Serve from cache; may be slightly stale. Most efficient for non-critical reads. |
| `"0"` | Serve the most recent cached state; may be slightly stale. Not a consistent read. |
| `"<specific value>"` | Serve the state at or after that specific version. Consistent point-in-time read. |

> **Important:** `resourceVersion: "0"` in a List request means *"give me any recent state"*, not necessarily the latest. For strongly consistent reads (e.g., before an update), omit `resourceVersion` or use the specific value from a prior Get.

# ResourceVersion in List Requests

```text
kubectl get pods
  -> GET /api/v1/namespaces/default/pods
  -> Response includes: metadata.resourceVersion: "183100"

kubectl get pods --watch
  -> Starts watch from resourceVersion: "183100"
  -> Sees all events after the List result
```

This List + Watch pattern (used by Informers) ensures no events are lost between the initial List and the subsequent Watch.

---

# ResourceVersion Expiration (410 Gone)

The API Server's watch cache holds events up to a configurable history window. If a client reconnects with an old ResourceVersion that has expired from the cache:

```http
HTTP/1.1 410 Gone
{
  "reason": "Expired",
  "message": "too old resource version: 12345 (183100)"
}
```

The correct recovery is to **re-List** from the current state and start a new watch:

```text
Watch returns 410 Gone
  |
  v
Re-List all resources (get new resourceVersion)
  |
  v
Start new Watch from new resourceVersion
  |
  v
No events missed
```

This is exactly what Kubernetes Informers do automatically.

# How Controllers Use ResourceVersion Correctly

```text
Controller reconciles Deployment:
  |
  v
1. GET Deployment (receives object with resourceVersion: "200")
  |
  v
2. Modify the local copy
  |
  v
3. PUT/PATCH with metadata.resourceVersion: "200"
  |
  v
4a. Success (200 OK)  ->  Continue
4b. Conflict (409)    ->  Back to Step 1 (re-read, re-apply, retry)
```

> **Important:** Kubernetes controllers must handle `HTTP 409 Conflict` as a normal, expected condition — not an error. Retry with re-read is the correct pattern.

# Common Interview Questions

### Q1. What is ResourceVersion in Kubernetes?
`resourceVersion` is an opaque, monotonically increasing string stored in every object's metadata and in List responses. It reflects the etcd revision at which the object was last written.

### Q2. How does ResourceVersion prevent concurrent update conflicts?
When a client updates an object, it must include the `resourceVersion` it read. The API Server compares this against the current version. If they differ (another writer has changed the object), the API Server returns HTTP 409 Conflict, forcing the client to re-read and retry.

### Q3. What does HTTP 409 Conflict mean in Kubernetes?
A ResourceVersion mismatch: the object was modified between when the client read it and when it submitted the update. The client should re-read the object and retry the update.

### Q4. How does ResourceVersion enable consistent watch streams?
A client first Lists resources (receiving a snapshot `resourceVersion`), then starts a Watch from that `resourceVersion`. The API Server sends all events after that point, ensuring no events are missed between the list and the watch.

### Q5. What happens when a Watch receives HTTP 410 Gone?
The requested `resourceVersion` has expired from the watch cache. The client must re-List from the current state to get a new `resourceVersion`, then start a new Watch. This is the standard Informer recovery pattern.

### Q6. What does `resourceVersion: "0"` mean?
It means the client accepts any recent cached state — the most recent available in the watch cache, but not necessarily the absolute latest from etcd. It is efficient but not strongly consistent.

# Troubleshooting Guide

| Symptom | Likely Cause | Action |
| :--- | :--- | :--- |
| `HTTP 409 Conflict` on update | Concurrent modification by another controller/user | Re-read the object and reapply changes; implement retry loop |
| `HTTP 410 Gone` on watch | Watch cache history exceeded | Re-List from current state and start a fresh watch |
| Controller stuck retrying 409 | No exponential backoff or jitter on retry | Add backoff with jitter between retries |
| Stale data returned by List | Using `resourceVersion: "0"` with cache hit | Remove `resourceVersion` parameter for consistent reads |
