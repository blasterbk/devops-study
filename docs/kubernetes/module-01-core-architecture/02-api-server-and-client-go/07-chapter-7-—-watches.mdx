# Why Should You Learn This?

Common interview questions include:

> **How does the Deployment Controller know that a Pod was deleted?**

> **How does `kubectl get pods --watch` show changes instantly?**

> **How does ArgoCD immediately detect that a resource has drifted from Git?**

The answer is **Watches** — Kubernetes' push-based event delivery mechanism.

Without Watches:
- Every controller would need to poll the API Server constantly
- A cluster with 10,000 Pods and 50 controllers would have 500,000 unnecessary requests per second
- Controller reaction time would depend on the poll interval
- ArgoCD, Flux, and all GitOps tools would have polling-based sync delays

---

# Real-Life Analogy

Think of Watches like phone notifications vs. manually checking for messages.

```text
Polling (wrong):
  You pick up phone every 5 seconds to check for new message
  -> Wasteful, slow, drains battery

Watch (correct):
  Phone notifies you the moment a message arrives
  -> Instant, efficient
```

| Phone Analogy | Kubernetes |
| :--- | :--- |
| Picking up phone to check | Polling the API Server |
| Notification pushed to phone | Watch event pushed to controller |
| New message arrives | Object created/modified/deleted in etcd |
| Notification sound | ADDED/MODIFIED/DELETED event |
| App handles notification | Controller reconciliation loop triggered |

# The Problem with Polling

Imagine a cluster with 10,000 Pods and a controller that wants to know when a Pod changes:

```text
Without Watch (Polling):

Controller -> GET /api/v1/pods -> No change
Controller -> GET /api/v1/pods -> No change
Controller -> GET /api/v1/pods -> No change   (every 5 seconds)
Controller -> GET /api/v1/pods -> Pod deleted!
```

Problems:
- **High API Server load** — N controllers × N resources × poll interval = massive request volume
- **Latency** — Pod deletion detected after up to 5 seconds
- **Wasted bandwidth** — full resource lists transferred even when nothing changed

---

# What is a Watch?

A Watch is a **long-lived HTTP connection** that streams change events from `kube-apiserver` to a client in real-time.

```text
Client  --> GET /api/v1/pods?watch=true&resourceVersion=182934
        <-- HTTP 200 (connection stays open)
        <-- {"type":"ADDED","object":{...}}
        <-- {"type":"MODIFIED","object":{...}}
        <-- {"type":"DELETED","object":{...}}
        <-- {"type":"BOOKMARK","object":{...}}
        (connection remains open, events stream continuously)
```

The client does not need to re-request. The server pushes events as they happen.

---

# Watch Event Types

| Event Type | Meaning |
| :--- | :--- |
| `ADDED` | A new object matching the watch was created |
| `MODIFIED` | An existing watched object was updated |
| `DELETED` | A watched object was deleted |
| `BOOKMARK` | No object change; used to advance the client's resourceVersion |
| `ERROR` | An error occurred (often 410 Gone — watch must be restarted) |

---

# How Watch Streams Work Over HTTP

The Watch API uses **HTTP chunked transfer encoding** — the connection stays open and the server sends newline-delimited JSON objects as events occur:

```text
GET /apis/apps/v1/namespaces/default/deployments?watch=true

HTTP/1.1 200 OK
Transfer-Encoding: chunked

{"type":"ADDED","object":{"kind":"Deployment","metadata":{"name":"nginx","resourceVersion":"183001"},...}}
{"type":"MODIFIED","object":{"kind":"Deployment","metadata":{"name":"nginx","resourceVersion":"183045"},...}}
{"type":"BOOKMARK","object":{"kind":"Deployment","metadata":{"resourceVersion":"183100"}}}
```

Each line is a complete, self-contained JSON event.

---

# The Watch Cache

Directly proxying every Watch to `etcd` would overload it in large clusters. Instead, `kube-apiserver` maintains an in-memory **Watch Cache**:

```text
etcd sends change events to kube-apiserver
  |
  v
kube-apiserver Watch Cache
  [circular ring buffer, configurable size]
  Stores last N events per resource type
  |
  v
All Watch clients subscribe to Watch Cache
(not to etcd directly)
```

Benefits:
- Reduces etcd read load dramatically
- Multiple Watch clients share one etcd stream
- Watch history window allows reconnecting clients to catch up

> **Important:** The Watch Cache is not a full copy of etcd. It only holds recent events (history window). Very old `resourceVersion` values may no longer exist in the cache, causing HTTP 410 Gone.

---

# Bookmark Events

Bookmark events carry no object change — their only purpose is to advance the client's `resourceVersion`:

```json
{
  "type": "BOOKMARK",
  "object": {
    "kind": "Deployment",
    "apiVersion": "apps/v1",
    "metadata": {
      "resourceVersion": "183200"
    }
  }
}
```

Why Bookmarks matter:
- Without them, a client that receives no events for a long time would have an old `resourceVersion`
- If it disconnects and reconnects, it might request events from a `resourceVersion` that has expired (410 Gone)
- Bookmarks keep the client's `resourceVersion` fresh even during quiet periods

---

# Reconnect Logic

Watch connections eventually disconnect (network timeout, server restart). The correct recovery pattern is:

```text
Watch disconnects
  |
  v
Client checks disconnect reason:
        |
        +-- Temporary network error
        |      -> Reconnect with last known resourceVersion
        |
        +-- 410 Gone (resourceVersion expired)
               -> Re-List from current state
               -> Start new Watch from new resourceVersion
```

This is the core of the **List + Watch** pattern used by every Kubernetes Informer.

---

# Complete Watch Lifecycle

```text
1. Client lists all Pods
   GET /api/v1/namespaces/default/pods
   Response: { items: [...], metadata: { resourceVersion: "183000" } }
  |
  v
2. Client starts Watch from resourceVersion 183000
   GET /api/v1/namespaces/default/pods?watch=true&resourceVersion=183000
  |
  v
3. API Server streams events:
   ADDED   (new Pod created at rv 183001)
   MODIFIED (Pod status updated at rv 183045)
   BOOKMARK (quiet period, rv advanced to 183200)
  |
  v
4. Watch disconnects (timeout / network issue)
  |
  v
5. Client reconnects from last seen rv (183200)
   GET .../pods?watch=true&resourceVersion=183200
   [All events after 183200 are replayed]
  |
  v
6. If 410 Gone -> Re-List + new Watch
```

# Why Watch Works at Scale

```text
1 etcd stream per resource type
  |
  v
kube-apiserver Watch Cache
  |
  v
N Watch clients (controllers, kubelet, operators, kubectl)
```

- 1 etcd connection serves N client Watch streams
- Watch Cache absorbs reconnection storms
- Clients get push notifications with millisecond latency

# Common Interview Questions

### Q1. What is a Kubernetes Watch?
A Watch is a long-lived HTTP connection that streams change events (ADDED, MODIFIED, DELETED) from `kube-apiserver` to a client in real-time, eliminating the need for polling.

### Q2. Why is polling inefficient compared to Watches?
Polling requires the client to repeatedly request the full resource list even when nothing has changed, wasting CPU, network bandwidth, and API Server capacity. Watches push only changes, consuming resources only when objects actually change.

### Q3. What are Watch Event types?
`ADDED` (new object), `MODIFIED` (changed object), `DELETED` (removed object), `BOOKMARK` (no change; used to advance resourceVersion), and `ERROR` (watch error, usually 410 Gone requiring restart).

### Q4. What is the Watch Cache?
An in-memory circular ring buffer in `kube-apiserver` that stores recent object change events. It serves all Watch clients, preventing each of them from maintaining a direct watch connection to `etcd`.

### Q5. What are Bookmark events and why do they exist?
Bookmarks carry no object change. They advance the client's `resourceVersion` during quiet periods, preventing the client's cached `resourceVersion` from expiring and triggering unnecessary re-Lists.

### Q6. What is the correct recovery when a Watch returns HTTP 410 Gone?
Re-List the full resource collection to get a current `resourceVersion` snapshot, then start a new Watch from that `resourceVersion`. This is the standard Informer recovery pattern.

### Q7. How does the List + Watch pattern guarantee no lost events?
By starting the Watch from the `resourceVersion` of the preceding List response, the client asks for all events that occurred after the list snapshot, ensuring continuity with no gap between the list and the watch stream.

# Troubleshooting Guide

| Symptom | Likely Cause | Action |
| :--- | :--- | :--- |
| Controller slow to react to changes | Using polling or long poll interval | Switch to Watch-based Informer pattern |
| Watch frequently returns 410 Gone | Watch cache history too small or high event rate | Increase `--watch-cache-sizes` on kube-apiserver |
| Watch events delivered out of order | Bug in event processing or concurrent goroutines | Ensure single-threaded event handler per Watch |
| High etcd read load | Too many Watch clients querying etcd directly | Ensure clients use kube-apiserver Watch (not etcd Watch) |
| Controller misses events during restart | Re-list after restart with old resourceVersion expired | Use List+Watch Informer pattern with proper resync |
