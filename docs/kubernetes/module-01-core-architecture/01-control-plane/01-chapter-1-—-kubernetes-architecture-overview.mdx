# Chapter 1 — Kubernetes Architecture Overview

## Goal

Before learning any Kubernetes internals, you need to understand **how Kubernetes thinks**.

This chapter builds your mental model of Kubernetes.

Once you understand this chapter, every other Kubernetes component becomes much easier to understand.

---

# Before Kubernetes

Imagine you built an application.

```text
My Application

Frontend

Backend

Database
```

Initially, everything runs on a single server.

```text
+---------------------------+
| Server                    |
|                           |
| Frontend                  |
| Backend                   |
| MySQL                     |
+---------------------------+
```

Everything works perfectly.

---

## Your Application Grows

As more users start using your application:

```text
100 Users

↓

1,000 Users

↓

10,000 Users

↓

100,000 Users

↓

1 Million Users
```

A single server is no longer enough.

You purchase additional servers.

```text
Server 1

Server 2

Server 3

Server 4

Server 5
```

---

# The Problems Begin

Now imagine **Server 2 crashes**.

```text
Server 2

❌ Down
```

Immediately many questions appear.

- Which applications were running?
- How do you restart them?
- Which server has enough CPU?
- Which server has enough RAM?
- What if another server also fails?
- How do users find the new server?
- How do you scale during traffic spikes?

Managing all of this manually becomes impossible.

---

# Docker Solved One Problem

Docker introduced containers.

Instead of manually installing software, you build a Docker image.

```text
Docker Image

↓

Container

↓

Runs Anywhere
```

Docker solved:

- Packaging
- Dependencies
- Environment consistency

---

## But Docker Doesn't Solve

Docker alone does **not** provide:

- Multi-server scheduling
- Automatic recovery
- Service discovery
- Rolling updates
- Load balancing
- Auto Scaling
- Cluster Management

This is where Kubernetes comes in.

---

# Kubernetes Solves These Problems

Think of Kubernetes as the **Operating System of a Cluster**.

Just as Linux manages:

- CPU
- Memory
- Processes
- Files

Kubernetes manages:

- Nodes
- Pods
- Networking
- Storage
- Scheduling
- Recovery
- Scaling

---

## Easy Analogy

| Linux Operating System | Kubernetes |
|------------------------|------------|
| Process | Pod |
| CPU Scheduler | kube-scheduler |
| Process Manager | Controller Manager |
| File System | etcd (Cluster State) |
| System Calls | Kubernetes API |

This analogy is not perfect, but it helps understand Kubernetes quickly.

---

# What is Kubernetes?

Most interview answers are:

> Kubernetes is a container orchestration platform.

That answer is correct but incomplete.

A deeper answer is:

> Kubernetes is a distributed, API-driven control system that continuously works to make the cluster's **actual state** match the user's **desired state**.

Every word in that sentence is important.

Let's understand each one.

---

# 1. Kubernetes is a Distributed System

Kubernetes is **not one program**.

It consists of many independent components working together.

```text
                 Kubernetes

            API Server

   Scheduler        Controllers

               etcd

          Worker Nodes

      kubelet    containerd
```

Each component has only one responsibility.

This follows the Unix philosophy:

> Do one thing and do it well.

For example:

- Scheduler decides **where** a Pod should run.
- Controller decides **whether** a Pod should exist.
- kubelet ensures Pods are actually running.
- API Server coordinates the entire cluster.

---

# 2. Kubernetes is API-Driven

One of the most important Kubernetes concepts is:

> **Everything goes through the API Server.**

Not sometimes.

Not most of the time.

**Every single request.**

---

## Real-Life Analogy

Imagine a company.

```text
               Company

          Reception Desk

                │
      ┌─────────┼──────────┐
      │         │          │
     HR      Finance   Engineering
```

Nobody walks directly into Finance.

Everyone first visits Reception.

The API Server works exactly like that.

---

## Kubernetes Communication

```text
kubectl

↓

API Server

↓

etcd
```

```text
Scheduler

↓

API Server
```

```text
kubelet

↓

API Server
```

```text
Terraform

↓

API Server
```

Even Kubernetes components communicate through the API Server.

---

## Why?

Because the API Server provides:

- Authentication
- Authorization
- Validation
- Audit Logging
- API Version Conversion
- Consistent Storage

Without a central gateway, every component would need to implement these features separately.

---

# 3. Kubernetes is Declarative

Suppose you create:

```yaml
replicas: 3
```

Notice what you did **not** say.

You didn't write:

```text
Create Pod 1

Create Pod 2

Create Pod 3
```

Instead you simply declared:

> I always want **3 Pods**.

Kubernetes decides how to achieve that.

This is called the **Desired State**.

---

# Desired State

Desired State is the configuration stored inside Kubernetes.

Example:

```text
Deployment

Replicas = 3
```

That becomes Kubernetes' target.

---

# Actual State

Now suppose one Pod crashes.

Desired:

```text
3 Pods
```

Reality:

```text
2 Pods
```

Now Desired State and Actual State are different.

---

# Reconciliation

Controllers continuously compare:

```text
Desired State

↓

Actual State

↓

Difference?

↓

Fix It

↓

Repeat Forever
```

This continuous correction process is called **Reconciliation**.

This is the heart of Kubernetes.

---

# Self-Healing

Suppose you accidentally delete a Pod.

```bash
kubectl delete pod nginx
```

Many beginners think:

> The Pod is gone.

Actually, Kubernetes sees:

```text
Desired = 3

Actual = 2
```

The Deployment Controller immediately creates another Pod.

```text
Need One Pod

↓

Create Pod

↓

Scheduler Selects Node

↓

kubelet Starts Container

↓

3 Pods Again
```

This automatic recovery is called **Self-Healing**.

---

# Event-Driven Architecture

Does Kubernetes continuously check every object every second?

No.

Instead, Kubernetes uses **Watch Events**.

```text
Deployment Created

↓

API Server

↓

etcd

↓

Watch Event

↓

Deployment Controller

↓

ReplicaSet Created

↓

Watch Event

↓

Scheduler

↓

Watch Event

↓

kubelet
```

Instead of repeatedly asking:

> Has anything changed?

components are automatically notified.

This reduces:

- CPU Usage
- Network Traffic
- API Server Load
- Latency

You'll study Watches and Informers in Module 1.2.

---

# Two Halves of Kubernetes

Every Kubernetes cluster has two logical sections.

```text
+----------------------------------------+
| Kubernetes Cluster                     |
|                                        |
|  +------------------+                  |
|  | Control Plane    |                  |
|  +------------------+                  |
|                                        |
|  +------------------+                  |
|  | Worker Nodes     |                  |
|  +------------------+                  |
+----------------------------------------+
```

---

# Control Plane

Think of the Control Plane as the **Brain**.

It makes decisions.

It decides:

- What should run?
- Where should it run?
- Who can access the cluster?
- Is the cluster healthy?
- Should another Pod be created?

Main Components:

- kube-apiserver
- kube-scheduler
- kube-controller-manager
- etcd

---

# Worker Nodes

Worker Nodes are the **Muscles**.

They execute the work decided by the Control Plane.

Each Worker Node contains:

- kubelet
- containerd
- kube-proxy
- Pods

Worker Nodes never decide what should exist.

They simply execute the instructions sent by the Control Plane.

---

# Mental Model

Whenever you're confused, ask yourself two questions.

### Question 1

**Who decides?**

Usually:

- API Server
- Scheduler
- Controller Manager

---

### Question 2

**Who executes?**

Usually:

- kubelet
- containerd
- Worker Node

This single mental model makes Kubernetes much easier to understand.
