# Real-Life Analogy

Think of Image Management like an app store with a local install cache.

```text
App Store Cache Analogy:

App store (container registry) hosts application packages (images)
Phone (Node) has local storage for installed apps (containerd image cache)
Installing an app: download layers from store, extract to local storage
Next time: check if app is already installed (IfNotPresent: skip download)
Always re-check: ask store if there's a newer version (Always: check digest)
Private app (private registry): need a password/token (imagePullSecret)
Phone storage full: OS removes least-used apps (Image GC)
```

| App Store | Image Management |
| :--- | :--- |
| App store | Container registry (Docker Hub, ECR, GCR) |
| Application package | Container image |
| App version number | Image tag (e.g., `nginx:1.25`) |
| App fingerprint/checksum | Image digest (sha256 hash) |
| Local storage | containerd content store (image cache) |
| Private app password | `imagePullSecret` |
| Removing unused apps | Image Garbage Collection |

> **Important:** `imagePullPolicy: Always` does **NOT** always re-pull the full image data. It checks the registry for the **current digest** of the tag and only downloads layers that are not already in the local cache. If the digest matches, no data is transferred. This is why `Always` has minimal overhead when the image hasn't changed, but still fails if the registry is unreachable.

# What is a Container Image?

A container image is an immutable package containing everything required to run an application.

It typically contains:

```text
Application Binary

Libraries

Runtime

Configuration

Metadata

Filesystem Layers
```

An image is **read-only**.

Containers never modify the original image.

```text

     |
```

# Always

Workflow:

```text
Pod Starts
  |
  v
Check Registry
  |
  v

  |
  v

```

---

# Never

Workflow:

```text
Image Cached?

|

|

|

+-- No

     |

     ▼
```

Useful for air-gapped environments or preloaded images.

# Pull Policy Comparison

| Policy | Behavior |
|----------|----------|
| Always | Always checks the registry before starting the container |
| IfNotPresent | Uses cached image if available |
| Never | Never contacts a registry |

# Production Best Practices

✔ Use immutable version tags or image digests instead of `latest`.

✔ Keep frequently used images cached on Nodes where practical.

✔ Use private registries for proprietary applications.

✔ Store registry credentials in `imagePullSecrets`.

✔ Rotate registry credentials regularly.

✔ Monitor image pull latency.

✔ Enable image garbage collection to prevent disk exhaustion.

✔ Remove unused images from build and test Nodes.

✔ Sign and verify images as part of your software supply chain (covered in the Security module).

# Common Misconceptions

### ❌ Misconception 1

Every Pod downloads its own image.

**Correct:** Images are cached per Node and shared among containers on that Node.

---

### ❌ Misconception 2

`imagePullPolicy: Always` always downloads the full image.

**Correct:** The runtime checks the registry and only downloads layers that are missing or have changed.

---

### ❌ Misconception 3

The kubelet downloads images directly.

**Correct:** The kubelet requests `PullImage()` through CRI; the container runtime performs the download.

---

### ❌ Misconception 4

Deleting an image immediately stops running containers.

**Correct:** Running containers continue using their existing snapshots. Image garbage collection targets unused images.

---

### ❌ Misconception 5

Private registries work automatically.

**Correct:** Authentication credentials must be supplied, commonly using `imagePullSecrets`.

---

### ❌ Misconception 6

`:latest` is recommended for production.

**Correct:** Immutable version tags or image digests provide reproducible deployments and should be preferred.

# Common Interview Questions

### Q1. What is the image pull workflow?

kubelet requests `PullImage()` through CRI, the runtime checks its cache, downloads missing layers from the registry if necessary, stores them locally, and then creates the container.

---

### Q2. What are the three image pull policies?

Always, IfNotPresent, and Never.

---

### Q3. What is the purpose of the local image cache?

To reuse previously downloaded images and reduce startup time and network traffic.

---

### Q4. How are private registry credentials supplied?

Using a Kubernetes Secret of type `kubernetes.io/dockerconfigjson`, referenced through `imagePullSecrets`.

---

### Q5. What causes `ImagePullBackOff`?

Repeated failures to pull an image, such as authentication failures, nonexistent images, or registry connectivity issues.

---

### Q6. Does `imagePullPolicy: Always` always download every layer?

No. The runtime checks the registry but reuses unchanged cached layers.

---

### Q7. What is the purpose of image garbage collection?

To reclaim disk space by removing unused images when storage thresholds are reached.

---

### Q8. Why should production workloads avoid the `latest` tag?

Because it is mutable and can lead to inconsistent, non-reproducible deployments.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| `ImagePullBackOff` | Authentication failure, image not found, or registry unavailable |
| `ErrImagePull` | Incorrect image name, network issue, or registry error |
| Slow container startup | Large image download or cache miss |
| Disk usage continuously increasing | Image garbage collection not reclaiming enough space or many unused images |
| Private image cannot be pulled | Missing or incorrect `imagePullSecrets` |
| Image updates not appearing | Cached image with `IfNotPresent` or unchanged image tag |
