# Chapter 2 — containerd & runc Internals

> **Goal:** Understand how **containerd**, **containerd-shim**, and **runc** work together to create and manage Linux containers. Learn the complete container creation workflow, the OCI Runtime Specification, and the lifecycle of a container process from image to execution.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. containerd architecture: daemon, gRPC API, plugins, snapshotter
> 2. containerd-shim: the per-container intermediary process
> 3. runc: the OCI-compliant low-level runtime that creates the container
> 4. Container creation workflow: CRI call -> containerd -> shim -> runc
> 5. OCI Runtime Specification: the bundle (config.json + rootfs)
> 6. Linux namespaces created by runc: PID, Network, Mount, UTS, IPC
> 7. cgroups: CPU and memory limits enforced by runc on behalf of kubelet
> 8. Container lifecycle: created, running, paused, stopped, deleted
> ```

# Real-Life Analogy

Think of containerd & runc like a restaurant kitchen with a head chef and line cooks.

```text
Restaurant Kitchen Analogy:

Head chef (containerd) receives the order from the waiter (kubelet via CRI)
Head chef assigns the order to a station manager (containerd-shim)
Station manager assigns a line cook (runc) to prepare the dish
Line cook prepares the dish (creates the container process) and leaves
Station manager stays to serve and monitor the dish (shim stays alive)
If head chef takes a break (containerd restarts): station manager keeps dish warm
```

| Kitchen | containerd & runc |
| :--- | :--- |
| Head chef | containerd |
| Order ticket | CRI RunPodSandbox / CreateContainer request |
| Station manager | containerd-shim (per-container process) |
| Line cook | runc (OCI runtime) |
| Line cook prepares dish and leaves | runc creates container process and exits |
| Station manager stays | containerd-shim stays alive to own the container |
| Head chef takes a break | containerd restarts |

> **Important:** After `runc` creates the container process, **runc exits**. The container process is then owned by `containerd-shim`, not runc or containerd. This means if `containerd` crashes and restarts, **running containers are not affected** — the shim processes keep them alive. This is a deliberate design choice for container process lifecycle isolation.

# What is containerd?

**containerd** is a high-level container runtime responsible for managing the complete lifecycle of containers.

It is responsible for:

- Image management
- Snapshot management
- Container metadata
- Container lifecycle
- Task management
- CRI integration
- Event handling

Think of containerd as the **container management platform**.

  |

The shim becomes the parent process.

# Production Best Practices

✔ Use containerd as the default runtime for Kubernetes.

✔ Monitor containerd and containerd-shim separately.

✔ Keep OCI runtimes (such as runc) updated with security patches.

✔ Monitor image storage and snapshot usage.

✔ Avoid manually killing containerd-shim processes.

✔ Investigate repeated container exits instead of relying solely on automatic restarts.

✔ Secure access to the containerd socket.

# Common Misconceptions

### ❌ Misconception 1

containerd creates Linux namespaces directly.

**Correct:** containerd prepares the environment and invokes an OCI runtime (such as runc) to create the container.

---

### ❌ Misconception 2

runc is a long-running daemon.

**Correct:** runc is a short-lived executable that creates the container and exits.

---

### ❌ Misconception 3

containerd-shim is optional.

**Correct:** The shim keeps containers running independently of the containerd daemon and manages their lifecycle.

---

### ❌ Misconception 4

A container is the same as a running process.

**Correct:** A container is configuration and filesystem state. A task is the running process inside that container.

---

### ❌ Misconception 5

If containerd crashes, all containers stop immediately.

**Correct:** Existing containers continue running because they are managed by their respective containerd-shim processes.

---

### ❌ Misconception 6

OCI defines Kubernetes APIs.

**Correct:** OCI defines container image and runtime standards. Kubernetes communicates with runtimes using CRI.

# Common Interview Questions

### Q1. What is containerd?

A high-level container runtime that manages images, snapshots, metadata, tasks, and container lifecycle.

---

### Q2. What is the purpose of containerd-shim?

It becomes the parent process for containers, manages their lifecycle, and keeps them running even if containerd restarts.

---

### Q3. What is runc?

A low-level OCI-compliant runtime that creates Linux containers using namespaces, cgroups, mounts, and other kernel features.

---

### Q4. Why does runc exit after creating the container?

Its responsibility is limited to container creation. Ongoing lifecycle management is handled by containerd-shim.

---

### Q5. What is an OCI Bundle?

A directory containing the container root filesystem (`rootfs`) and a `config.json` file describing how the container should be created.

---

### Q6. What is the difference between a container and a task in containerd?

A container is the stored configuration and metadata, while a task is the running process created from that container.

---

### Q7. What happens if containerd crashes?

Existing containers continue running under their shims, but new container operations cannot be performed until containerd is available again.

---

### Q8. Which component actually creates Linux namespaces?

The OCI runtime (such as runc).

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| New Pods fail to start | containerd unavailable or CRI communication failure |
| Existing containers still running after containerd restart | Expected behavior due to containerd-shim |
| Container exits immediately | Application error, incorrect command, or OCI configuration issue |
| Snapshot creation fails | Storage exhaustion or snapshotter problems |
| runc errors during startup | Invalid OCI bundle, namespace, mount, or cgroup configuration |
| Container status not updating | Shim unable to report status or containerd communication problems |
