# Module 1.7 — Container Runtime Internals

# Chapter 5 — RuntimeClass

> **Goal:** Understand how Kubernetes allows different Pods to use different container runtimes through **RuntimeClass**. Learn how **Runtime Handlers**, **containerd**, **Kata Containers**, and **gVisor** work together to provide different levels of performance, compatibility, and isolation.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. What RuntimeClass is: per-Pod runtime selection
> 2. Runtime Handlers: the named configurations in containerd that map to OCI runtimes
> 3. RuntimeClass resource: apiVersion, kind, handler field
> 4. Pod spec: spec.runtimeClassName field
> 5. runc: the default OCI runtime (process isolation via Linux namespaces)
> 6. gVisor (runsc): userspace kernel intercepting syscalls (strong isolation)
> 7. Kata Containers: hardware VM isolation using lightweight VMs
> 8. When to use each: performance vs security vs compatibility tradeoffs
> ```

---

# Real-Life Analogy

Think of RuntimeClass like passport control choosing which customs lane to use.

```text
Passport Control Analogy:

Airport has multiple customs lanes (runtimes: runc, gVisor, Kata)
Default lane (runc): standard processing, fast, trusted travelers
Enhanced screening lane (gVisor): extra checks, slower but more secure
Diplomatic lane (Kata Containers): completely separate VIP processing
Passenger presents passport with visa type (Pod sets runtimeClassName)
Airport authority configured which lanes exist (Node + containerd handler config)
Not all lanes available at all gates (not all Nodes may have all runtimes)
```

| Passport Control | RuntimeClass |
| :--- | :--- |
| Airport authority | Cluster administrator |
| Customs lane | Runtime handler (runc / runsc / kata) |
| Default lane | runc (used when no runtimeClassName set) |
| Enhanced screening lane | gVisor (`runsc`): syscall interception |
| Diplomatic lane | Kata Containers: hardware VM isolation |
| Passenger's visa type | `spec.runtimeClassName` in Pod spec |
| Lane configuration | `RuntimeClass` Kubernetes resource |

> **Important:** The **default runtime** (`runc`) is used when a Pod does **not** set `spec.runtimeClassName`. gVisor and Kata Containers only activate when a Pod explicitly requests them. Additionally, not every Node in a cluster may have every runtime installed — you must use `nodeSelector` or `scheduling` in the RuntimeClass to ensure Pods only land on Nodes that have the requested runtime available.


# RuntimeClass and Scheduling

RuntimeClass selects **how** a Pod runs.

It does **not** decide **where** the Pod runs.

Scheduling is still performed by the Kubernetes Scheduler.

However, runtime-specific nodes are commonly labeled and selected using node selectors, affinities, or taints so that Pods are scheduled only onto Nodes that support the requested runtime.

# Production Best Practices

✔ Use runc for general-purpose workloads.

✔ Use Kata Containers for highly sensitive or strongly isolated workloads.

✔ Use gVisor when balancing security and resource efficiency.

✔ Verify that every runtime handler is installed on Nodes that advertise it.

✔ Combine RuntimeClass with node labels, taints, tolerations, and affinities when runtimes are available only on selected Nodes.

✔ Benchmark applications before changing runtimes.

✔ Monitor startup latency and memory usage for sandboxed runtimes.

✔ Keep runtime implementations updated with security patches.

# Common Misconceptions

### ❌ Misconception 1

RuntimeClass is a container runtime.

**Correct:** RuntimeClass is a Kubernetes resource that selects a runtime handler.

---

### ❌ Misconception 2

RuntimeClass replaces CRI.

**Correct:** RuntimeClass works with CRI. kubelet still communicates with the runtime through the CRI interface.

---

### ❌ Misconception 3

Every Node automatically supports every runtime.

**Correct:** Each runtime must be installed and configured on the Node's container runtime.

---

### ❌ Misconception 4

Kata Containers are ordinary Linux namespaces.

**Correct:** Kata launches each Pod inside a lightweight virtual machine with its own guest kernel.

---

### ❌ Misconception 5

gVisor uses a virtual machine.

**Correct:** gVisor primarily provides a userspace kernel (`runsc`), not a hardware virtual machine.

---

### ❌ Misconception 6

RuntimeClass influences scheduling decisions.

**Correct:** RuntimeClass selects the runtime implementation. Scheduling is still handled by the Kubernetes Scheduler, though scheduling constraints are commonly added to ensure Pods land on compatible Nodes.

---

### ❌ Misconception 7

runc is always the best runtime.

**Correct:** runc offers excellent performance, but workloads requiring stronger isolation may benefit from gVisor or Kata Containers.

# Common Interview Questions

### Q1. What is RuntimeClass?

A Kubernetes resource that selects which runtime handler should be used to run a Pod.

---

### Q2. What is a Runtime Handler?

A runtime-specific identifier configured in the container runtime (such as containerd) that maps to a particular OCI runtime implementation.

---

### Q3. What happens if a Pod does not specify a RuntimeClass?

The Node's default runtime handler is used, which is commonly configured to use runc.

---

### Q4. What is the difference between RuntimeClass and Runtime Handler?

RuntimeClass is a Kubernetes API object; the Runtime Handler is a configuration inside the container runtime.

---

### Q5. Why would someone use Kata Containers?

To obtain stronger workload isolation by running Pods inside lightweight virtual machines.

---

### Q6. How does gVisor improve security?

It intercepts many system calls through a userspace kernel, reducing direct interaction with the host kernel.

---

### Q7. Can one Kubernetes cluster use multiple runtimes?

Yes. Different Pods can use different RuntimeClasses that map to different runtime handlers.

---

### Q8. Does RuntimeClass replace the scheduler?

No. The scheduler still selects the Node. RuntimeClass only influences how the Pod is executed on that Node.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Pod fails during sandbox creation | Requested runtime handler not configured on the Node |
| RuntimeClass not found | Incorrect `runtimeClassName` or missing RuntimeClass resource |
| Pod scheduled but never starts | Runtime installed incorrectly or CRI runtime handler unavailable |
| Unexpected runtime used | No `runtimeClassName` specified or default runtime selected |
| Higher startup latency | Using Kata Containers or another sandboxed runtime |
| Application incompatible with selected runtime | Runtime-specific limitations or unsupported kernel features |
