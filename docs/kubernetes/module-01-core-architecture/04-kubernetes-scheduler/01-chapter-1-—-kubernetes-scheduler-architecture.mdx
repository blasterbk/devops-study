# Real-Life Analogy

Think of the Kubernetes Scheduler like an airport control tower.

```text
Airport Control Tower Analogy:

Aircraft (Pods) request landing clearance (node assignment)
Control tower (Scheduler) sees all runways (Nodes) in real-time
Tower checks runway capacity, length, weather (Filter + Score)
Tower assigns aircraft to the best runway (selects Node)
Tower updates the flight manifest (writes spec.nodeName)
Aircraft autonomously lands on assigned runway (kubelet starts Pod)
```

| Airport | Kubernetes Scheduler |
| :--- | :--- |
| Aircraft waiting to land | Unscheduled Pod in the Scheduling Queue |
| Control tower | kube-scheduler |
| Runway capacity and status | Node resources and conditions |
| Checking runway suitability | Filter plugins |
| Ranking the best runway | Score plugins |
| Assigning runway to aircraft | Binding (writing `spec.nodeName`) |
| Aircraft lands autonomously | kubelet starts the Pod |

> **Important:** The Scheduler reads **all Node and Pod state from its local in-memory cache** (not from the API Server or etcd directly) during scheduling. This cache is kept up-to-date via Informers and Watch streams. This design makes scheduling extremely fast even in large clusters.

# Responsibilities of kube-scheduler

The Scheduler is responsible for:

- Watching for unscheduled Pods
- Finding candidate Nodes
- Filtering unsuitable Nodes
- Scoring suitable Nodes
- Selecting the best Node
- Binding the Pod

It is **not** responsible for:

- Creating containers
- Pulling images
- Starting Pods
- Monitoring containers
- Restarting applications

Those responsibilities belong to the kubelet.

# Production Architecture

Highly available clusters usually deploy multiple Scheduler instances.


# Production Best Practices

✔ Run multiple Scheduler replicas for high availability.

✔ Keep Scheduler close to the API Server to minimize latency.

✔ Monitor scheduling latency.

✔ Monitor queue depth.

✔ Avoid excessive custom scheduling logic.

✔ Keep Scheduler Cache synchronized through Informers.

✔ Use Scheduler Profiles instead of maintaining separate scheduler binaries when possible.

✔ Monitor failed scheduling events.

# Common Interview Questions

### Q1. Why does Kubernetes need a Scheduler?

Because Kubernetes must decide which Node should run each unscheduled Pod while satisfying resource constraints and scheduling policies.

---

### Q2. What triggers the Scheduler?

A watch event for a Pod that does not yet have a `spec.nodeName`.

---

### Q3. Does the Scheduler communicate directly with etcd?

No. It watches and updates resources through the API Server.

---

### Q4. Why does the Scheduler maintain a local cache?

To avoid querying the API Server for every scheduling decision and to make scheduling fast and scalable.

---

### Q5. What is the Scheduling Queue?

An internal queue that stores Pods waiting to be scheduled, along with retry mechanisms for failed scheduling attempts.

---

### Q6. What is the difference between the Scheduling Cycle and the Binding Cycle?

The Scheduling Cycle selects the best Node. The Binding Cycle commits that decision by binding the Pod through the API Server.

---

### Q7. Why is the Scheduling Framework plugin-based?

To allow Kubernetes and platform teams to extend scheduling behavior without rewriting the core scheduler.

---

### Q8. What happens after a Pod is bound?

The API Server persists the binding, the kubelet on the selected node observes the assigned Pod, and the container runtime starts the containers.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Pods remain `Pending` | No suitable Node, resource shortage, taints, affinity rules, or scheduling constraints |
| Slow scheduling | Large scheduling queue, expensive plugins, stale cache, or overloaded Scheduler |
| Scheduler not reacting to new Pods | Informer/watch issues, API Server connectivity, or Scheduler failure |
| Frequent scheduling retries | Resource pressure, conflicting policies, or transient cluster state |
| High scheduling latency | Large cluster, plugin overhead, or API Server performance issues |
| Multiple Scheduler instances scheduling the same Pod | Leader election misconfiguration (rare in correctly configured clusters) |
