# Module 1.4 — Kubernetes Scheduler Internals

# Chapter 7 — Filter Plugins

> **Goal:** Understand how Kubernetes eliminates unsuitable Nodes before ranking them. Learn what Filter Plugins are, how they execute, how built-in plugins such as `NodeResourcesFit`, `NodeAffinity`, `TaintToleration`, `NodePorts`, `NodeName`, `VolumeBinding`, and `NodeUnschedulable` work, and how Kubernetes efficiently filters thousands of Nodes in production clusters.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. What filtering means in the scheduling cycle
> 2. NodeResourcesFit — checking CPU, memory, and extended resources
> 3. NodeAffinity — enforcing node label matching rules
> 4. TaintToleration — enforcing taint/toleration pairs
> 5. NodePorts — checking host port availability
> 6. VolumeBinding — checking PVC/PV availability on the node
> 7. NodeUnschedulable — skipping cordoned nodes
> 8. Parallel filtering and the percentageOfNodesToScore optimization
> ```

---

# Real-Life Analogy

Think of Filter Plugins like a multi-checkpoint security screening at an airport.

```text
Airport Security Analogy:

Passengers (Pods) must pass ALL checkpoints to board
ID check (NodeName) -> only specific passengers allowed on this flight
Baggage size check (NodeResourcesFit) -> must fit in overhead bin
Liquid check (TaintToleration) -> restricted items require permits
Visa check (NodeAffinity) -> must have correct labels/credentials
Gate check (NodePorts) -> gate must be available
Fail any check -> passenger is rejected from THIS flight
All checks in parallel for speed
```

| Airport Security | Filter Plugins |
| :--- | :--- |
| Passenger at checkpoint | Pod being evaluated against a Node |
| ID check | `NodeName` plugin |
| Baggage size limit | `NodeResourcesFit` plugin |
| Restricted items / permit | `TaintToleration` plugin |
| Visa / credential check | `NodeAffinity` plugin |
| Gate availability | `NodePorts` plugin |
| Parallel screening lanes | Parallel filter execution |

> **Important:** Filter plugins are evaluated **in parallel across all Nodes** simultaneously, not sequentially. A single plugin failure on one Node does **not** affect evaluation of other Nodes. All Nodes are evaluated — filtering is **not** first-match-wins. The result is a **feasible node list** of all Nodes that passed all plugins.

# What Does Filtering Mean?

Filtering answers one simple question:

> **Can this Pod run on this Node?**

Notice the wording.

Not:

> Is this the best Node?

Only:

> Is this Node eligible?

# Scheduling Philosophy

Scheduling consists of two steps:

```text
Filter

v

Who Can Run?

v

Score

v

Who Should Run?
```

Filtering removes impossible Nodes.

Scoring ranks the remaining Nodes.

# Filter Result

Each plugin returns one of two outcomes.

```text
Pass
```

or

```text
Unschedulable
```

If **any** Filter Plugin rejects the Node,

that Node is immediately removed.

# Requested vs Actual Usage

Very important:

NodeResourcesFit evaluates:

```text
Requested Resources
```

Not:

```text
Actual Runtime Usage
```

```text

4 CPU

Actually Uses

1 CPU
```


Because Kubernetes schedules based on guarantees,

# Important Note

Normally, Pods with `spec.nodeName` already set are **not scheduled** by the default Scheduler because they are considered pre-assigned. The `NodeName` filtering logic is primarily relevant in scheduling flows where a specific target node must be validated.

# Why Use nodeName?

Typical scenarios:

- Debugging
- Static workloads
- Custom schedulers
- Special operational tasks

It is generally **not recommended** for normal application deployments because it bypasses the Scheduler's placement logic.

# Short-Circuit Evaluation

Once a plugin rejects a Node:

```text

v

Rejected

v

Stop Further Checks
```

Remaining Filter Plugins do not need to evaluate that Node.

This improves scheduling performance.

# Production Best Practices

✔ Always define realistic CPU and memory requests.

✔ Use `nodeAffinity` instead of hardcoding `nodeName` for most workloads.

✔ Reserve specialized Nodes using taints and tolerations.

✔ Use `kubectl cordon` before maintenance.

✔ Keep storage topology aligned with workload requirements.

✔ Avoid unnecessary `hostPort` usage when Services can be used instead.

✔ Prefer labels and affinity for flexible scheduling policies.

✔ Monitor scheduling failures to identify recurring Filter Plugin rejections.

# Common Misconceptions

### ❌ Misconception 1

Filtering selects the best Node.

Wrong.

Filtering only removes unsuitable Nodes.

Scoring selects the best Node.

---

### ❌ Misconception 2

NodeResourcesFit uses actual CPU usage.

Wrong.

It evaluates requested resources, not real-time utilization.

---

### ❌ Misconception 3

A Node passes if most Filter Plugins succeed.

Wrong.

Every required Filter Plugin must pass.

One rejection eliminates the Node.

---

### ❌ Misconception 4

`nodeName` is the recommended way to target a Node.

Wrong.

It bypasses normal scheduling and is intended for special cases.

---

### ❌ Misconception 5

Taints move Pods away from Nodes.

Wrong.

Taints prevent new Pods from being scheduled unless they tolerate the taint. Existing Pods are handled by taint effects and controllers, depending on the effect.

---

### ❌ Misconception 6

`hostPort` conflicts are detected by kubelet.

Wrong.

The Scheduler checks HostPort conflicts before assigning the Pod.

---

### ❌ Misconception 7

Filter Plugins always execute sequentially across all Nodes.

Wrong.

The Scheduler evaluates many candidate Nodes in parallel to improve throughput.

# Common Interview Questions

### Q1. What is the purpose of Filter Plugins?

To eliminate Nodes that cannot run the Pod before scoring begins.

---

### Q2. What is the difference between filtering and scoring?

Filtering determines feasibility. Scoring ranks feasible Nodes.

---

### Q3. Does `NodeResourcesFit` use actual resource usage?

No. It evaluates requested resources and allocatable capacity.

---

### Q4. What does the `NodeAffinity` plugin check?

Whether a Node satisfies the Pod's required affinity or selector rules.

---

### Q5. What is the purpose of the `TaintToleration` plugin?

To ensure the Pod can tolerate the Node's taints before scheduling.

---

### Q6. Why does the Scheduler check HostPorts?

To prevent multiple Pods from using the same HostPort on the same Node.

---

### Q7. What happens if a Node is cordoned?

The `NodeUnschedulable` plugin filters it out for new scheduling decisions.

---

### Q8. Why is short-circuit evaluation important?

Once a Node fails a Filter Plugin, additional filter checks are unnecessary, reducing scheduling overhead.

---

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Pod remains Pending | All candidate Nodes were rejected by one or more Filter Plugins |
| "Insufficient CPU" events | `NodeResourcesFit` rejected all Nodes |
| "Node(s) didn't match node affinity" | `NodeAffinity` filter failed |
| "Node(s) had taint ..." | `TaintToleration` rejected available Nodes |
| HostPort conflict | Another Pod already reserves the requested HostPort on candidate Nodes |
| PVC scheduling failures | `VolumeBinding` could not satisfy storage constraints |
| Node skipped unexpectedly | Node is cordoned or marked unschedulable |
