# Real-Life Analogy

Think of building a Custom Scheduler like building your own GPS routing app.

```text
Custom GPS App Analogy:

Google Maps exists (default kube-scheduler) and works for most users
Some users need specialized routing (toll avoidance, truck height limits)
They can use Google Maps plugins/settings (Scheduler Framework plugins)
Or build their own GPS app from scratch (Custom Scheduler)
Both apps read the same road network (Kubernetes API / cluster state)
Both output the same result: a route (a binding: Pod -> Node)
Building from scratch = maximum control, maximum complexity
```

| Custom GPS App | Custom Scheduler |
| :--- | :--- |
| Google Maps (default) | Default `kube-scheduler` |
| Custom routing app | Custom Scheduler binary |
| Specialized routing rules | Custom node selection logic |
| Road network data | Kubernetes API (Nodes, Pods, etc.) |
| Outputting a route | Binding Pod to Node |
| Plugin settings | Scheduler Framework plugins (preferred) |

> **Important:** For **99% of production use cases**, extending the default scheduler via **Scheduler Framework plugins** is the correct approach. A full Custom Scheduler is only justified when you need a **completely different scheduling loop** — for example, a separate scheduler for IoT edge nodes, custom binpacking for specialized hardware, or integration with an external resource management system.

# What is a Custom Scheduler?

A Custom Scheduler is:

> **A scheduler implementation that makes Pod placement decisions instead of (or alongside) the default Kubernetes Scheduler for selected Pods.**

It follows the same fundamental workflow:

```text
Watch Pods

v

Find Candidate Nodes

v

Choose Best Node

v

Bind Pod
```

The scheduling policy is what changes.

---

# Why Build a Custom Scheduler?

The default Scheduler is designed for **general-purpose** workloads.

Most organizations never need another scheduler.

However,

some workloads have unique scheduling requirements.

Examples:

- AI/ML clusters
- High Performance Computing (HPC)
- Telecom infrastructure
- Edge computing
- FPGA scheduling
- Scientific computing
- Regulatory or compliance placement
- Custom hardware allocation

---

# When Should You NOT Build One?

Many scheduling requirements can already be implemented using:

- Node Affinity
- Taints & Tolerations
- Topology Spread Constraints
- Priority Classes
- Scheduler Profiles
- Scheduler Framework Plugins

A completely new Scheduler should usually be the **last option**.

# schedulerName

How does Kubernetes know which Scheduler should process a Pod?

Every Pod contains:

```yaml
spec:
  schedulerName: default-scheduler
```

or

```yaml
spec:
  schedulerName: custom-scheduler
```

The Scheduler only processes Pods matching its configured scheduler name.

---

# Example

General application:

```yaml
spec:
  schedulerName: default-scheduler
```

AI workload:

```yaml
spec:
  schedulerName: ai-scheduler
```

Research workload:

```yaml
spec:
  schedulerName: research-scheduler
```

Each Scheduler ignores Pods intended for other schedulers.

A Scheduler Extender is:

> **An external HTTP service that assists the Scheduler with filtering and/or prioritizing Nodes.**

Instead of replacing the Scheduler,

# Typical Use Cases

Historically,

Extenders were used for:

- GPU scheduling
- Storage-aware scheduling
- Network-aware scheduling
- Specialized hardware
- Enterprise infrastructure

---

# Limitations of Extenders

Extenders introduced several challenges:

- Additional network latency
- External service availability
- More operational complexity
- Separate deployment lifecycle

Because of these limitations,

the Scheduler Framework became the preferred extension mechanism.

---

# Scheduler Framework Plugins

Modern Kubernetes recommends:

```text
Scheduler Framework Plugins
```

instead of building a completely new Scheduler in most cases.

---

# Why?

Plugins execute:

```text
Inside

kube-scheduler
```

Benefits:

- No network hop
- Lower latency
- Better integration
- Easier maintenance
- Native Scheduler APIs

---

# Comparison

| Scheduler Extender | Scheduler Framework Plugin |
|--------------------|----------------------------|
| External HTTP service | Runs inside Scheduler |
| Network communication | In-process execution |
| Higher latency | Lower latency |
| More operational overhead | Easier to maintain |
| Legacy extension model | Recommended modern approach |

---

# Custom Scheduler vs Scheduler Framework

| Custom Scheduler | Scheduler Framework |
|------------------|---------------------|
| Entire scheduling loop | Extend existing Scheduler |
| Watches Pods | Built into Scheduler |
| Maintains cache | Shared cache |
| Performs binding | Built-in binding support |
| Highest flexibility | Preferred for most extensions |
| Highest maintenance | Lower maintenance |

# Performance Considerations

A production-quality Scheduler should:

- Use Informers instead of polling.
- Maintain an internal Scheduler Cache.
- Minimize API Server requests.
- Avoid long-running scheduling decisions.
- Support leader election.
- Handle thousands of scheduling events per second.

Poor Scheduler design can become a cluster-wide bottleneck.

---

# Production Best Practices

✔ Use the default Scheduler whenever possible.

✔ Prefer Scheduler Framework Plugins over building a new Scheduler.

✔ Use a unique `schedulerName`.

✔ Use Informers and Watches instead of polling.

✔ Maintain an internal cache for scheduling decisions.

✔ Implement leader election for high availability.

✔ Keep scheduling decisions deterministic and fast.

✔ Thoroughly test under production-scale workloads before deployment.

# Common Misconceptions

### ❌ Misconception 1

A Custom Scheduler replaces Kubernetes.

Wrong.

It only replaces or supplements the scheduling component.

---

### ❌ Misconception 2

Every Pod is scheduled by the Custom Scheduler.

Wrong.

Only Pods whose `schedulerName` matches the Custom Scheduler are processed.

---

### ❌ Misconception 3

A Custom Scheduler communicates directly with kubelet.

Wrong.

Like the default Scheduler, it binds Pods through the API Server, and kubelet learns about assignments via Watch events.

---

### ❌ Misconception 4

Scheduler Extenders are the recommended way to customize scheduling.

Wrong.

The Scheduler Framework is the preferred extension mechanism for modern Kubernetes.

---

### ❌ Misconception 5

A Custom Scheduler must poll the API Server continuously.

Wrong.

Production schedulers use Informers and Watch streams.

---

### ❌ Misconception 6

Building a Custom Scheduler is easier than writing a plugin.

Wrong.

Writing a complete Scheduler is significantly more complex than extending the Scheduler Framework.

---

### ❌ Misconception 7

Every organization needs a Custom Scheduler.

Wrong.

Most scheduling requirements can be satisfied using built-in features, Scheduler Profiles, or Scheduler Framework Plugins.

# Common Interview Questions

### Q1. Why would you build a Custom Scheduler?

To implement scheduling policies that cannot be achieved using built-in features or Scheduler Framework plugins.

---

### Q2. How does a Pod choose a Custom Scheduler?

By setting the appropriate `schedulerName` in its specification.

---

### Q3. What resources does a Scheduler watch?

Typically Pods, Nodes, PersistentVolumes, PersistentVolumeClaims, and other scheduling-related resources through Informers and Watch APIs.

---

### Q4. How does a Custom Scheduler assign a Pod to a Node?

It sends a binding request to the Kubernetes API Server after selecting the target Node.

---

### Q5. Does a Custom Scheduler communicate directly with kubelet?

No. kubelet receives the Pod assignment through API Server Watch events.

---

### Q6. What is a Scheduler Extender?

An external HTTP service that extends the Scheduler with additional filtering or prioritization logic.

---

### Q7. Why is the Scheduler Framework preferred over Scheduler Extenders?

Because plugins run inside the Scheduler process, avoiding network overhead and providing tighter integration.

---

### Q8. What are the main responsibilities of a production-quality Custom Scheduler?

Watching resources, maintaining a cache, selecting Nodes efficiently, binding Pods correctly, and supporting high availability through leader election.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Pods remain Pending indefinitely | `schedulerName` does not match any running Scheduler |
| Custom Scheduler sees no Pods | Watch configuration or RBAC permissions are incorrect |
| Scheduler makes slow decisions | Missing cache, inefficient algorithms, or excessive API calls |
| Pods never start after scheduling | Binding failed or kubelet has not received the updated Pod assignment |
| Scheduler becomes unavailable | Leader election not configured or Scheduler process failed |
| Specialized workloads scheduled incorrectly | Custom scheduling logic or plugin configuration is incomplete |

# Chapter Summary

In this chapter, you learned how Kubernetes can be extended through **Custom Schedulers** to support highly specialized scheduling requirements.

You learned:

- Why organizations build Custom Schedulers
- How `schedulerName` directs Pods to the appropriate Scheduler
- How a Scheduler interacts with the Kubernetes API
- How Informers and Watch APIs provide real-time scheduling events
- How Nodes are filtered, scored, and selected
- How binding commits scheduling decisions through the API Server
- How Scheduler Extenders evolved into the modern Scheduler Framework
- How production systems implement scalable, highly available Custom Scheduler architectures
- Why most organizations should prefer Scheduler Framework plugins unless a completely different scheduling loop is required

A Custom Scheduler gives complete control over the scheduling lifecycle, from watching Pods to binding them to Nodes. While this flexibility is powerful, it comes with significant operational complexity. For most production environments, extending the existing Scheduler through the Scheduler Framework provides a simpler and more maintainable solution, reserving fully custom schedulers for truly specialized infrastructure.
