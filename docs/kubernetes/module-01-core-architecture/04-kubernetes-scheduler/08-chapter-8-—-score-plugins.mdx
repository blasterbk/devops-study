# Chapter 8 — Score Plugins

> **Goal:** Understand how Kubernetes selects the **best** Node after filtering. Learn why scoring exists, how Score Plugins work, how different scoring strategies evaluate Nodes, how scores are normalized and weighted, and how the Scheduler finally selects the winning Node in a production cluster.
>

> 4. ImageLocality — preferring nodes that already have the image
> 5. PodTopologySpread — spreading Pods across zones and nodes
> 6. InterPodAffinity scoring — co-location and anti-affinity preferences
> 7. Score normalization: per-plugin 0-100 scale
> 8. Plugin weights and final node selection

# Real-Life Analogy

Think of Score Plugins like a company's interview scoring panel.

```text
Interview Panel Analogy:

Multiple candidates (Nodes) passed initial screening (Filter)
Each interviewer (Score plugin) scores each candidate independently
Interviewers have different expertise weights (plugin weights)
Scores are normalized to a common scale (0-100 per plugin)
Weighted scores are combined for a final ranking
Highest-scoring candidate (Node) gets the offer (Pod)
```

| Interview Panel | Score Plugins |
| :--- | :--- |
| Candidate | Feasible Node (passed Filter) |
| Interviewer | Score plugin |
| Interviewer's specialty weight | Plugin weight in scheduler config |
| Normalized interview score | Plugin score (0–100) |
| Combined weighted total | Final Node score |
| Candidate with highest total | Selected Node for binding |

> **Important:** Each Score plugin produces a score in its own range, then Kubernetes **normalizes** all plugin scores to 0–100 before applying weights. The final Node score is the **weighted sum** of all normalized plugin scores. If multiple Nodes share the highest score, the Scheduler selects one at **random** among the tied Nodes.

Which one should Kubernetes choose?

Without scoring:

```text

```

That would produce:

- Poor utilization
- Hotspots
- Uneven workloads
- Slower application startup
- Increased infrastructure cost

Scoring solves this problem.

---

# Simple Definition

Scoring is:

> **The process of ranking all feasible Nodes and selecting the one that best satisfies Kubernetes scheduling policies.**

Filtering removes impossible Nodes.

Scoring ranks the remaining candidates.

# MostAllocated Strategy

Purpose:

> **Prefer Nodes that are already heavily utilized.**

This may sound surprising.

---

```text

```

Result:


High.

Instead:

MostAllocated packs workloads together.

```text

```

# Benefits

MostAllocated helps:

- Consolidate workloads
- Reduce infrastructure cost
- Free completely unused Nodes
- Improve cluster autoscaling opportunities

# LeastAllocated vs MostAllocated

| LeastAllocated | MostAllocated |
|----------------|---------------|
| Spreads workloads | Packs workloads |
| Leaves spare capacity | Maximizes utilization |
| Good for unpredictable workloads | Good for cost optimization |
| Reduces immediate pressure | Helps Cluster Autoscaler scale down |

# Production Best Practices

✔ Choose resource scoring strategies that match workload patterns.

✔ Use `LeastAllocated` for burst-heavy, general-purpose clusters.

✔ Use `MostAllocated` to improve infrastructure utilization and autoscaler efficiency.

✔ Enable topology spread for highly available applications.

✔ Avoid excessive affinity preferences that complicate placement.

✔ Keep image registries healthy to maximize ImageLocality benefits.

✔ Tune plugin weights carefully—small changes can significantly alter scheduling behavior.

✔ Monitor scheduler metrics to understand scoring decisions in production.

# Common Misconceptions

### ❌ Misconception 1

Scoring decides whether a Node is valid.

Wrong.

Filtering determines validity.

Scoring ranks already valid Nodes.

---

### ❌ Misconception 2

The highest CPU Node always wins.

Wrong.

Multiple plugins contribute to the final score.

---

### ❌ Misconception 3

LeastAllocated is always better.

Wrong.

Its suitability depends on workload characteristics and operational goals.

---

### ❌ Misconception 4

MostAllocated wastes resources.

Wrong.

It intentionally consolidates workloads to improve utilization and enable cluster scale-down.

---

### ❌ Misconception 5

ImageLocality guarantees the Node will be selected.

Wrong.

It is only one contributor to the overall weighted score.

---

### ❌ Misconception 6

Topology spread only works across availability zones.

Wrong.

It can operate across any supported topology domain, including Nodes, racks (via labels), or zones.

---

### ❌ Misconception 7

Plugin weights affect filtering.

Wrong.

Weights influence only the scoring phase.

# Common Interview Questions

### Q1. Why does Kubernetes need scoring?

To rank feasible Nodes and choose the most suitable placement after filtering.

---

### Q2. What is the difference between filtering and scoring?

Filtering removes invalid Nodes, while scoring ranks the remaining valid Nodes.

---

### Q3. What does `NodeResourcesBalancedAllocation` optimize?

It prefers Nodes with balanced CPU and memory utilization to reduce resource fragmentation.

---

### Q4. What is the difference between `LeastAllocated` and `MostAllocated`?

`LeastAllocated` spreads workloads by preferring Nodes with more free resources. `MostAllocated` packs workloads onto already utilized Nodes to improve infrastructure efficiency.

---

### Q5. Why does Kubernetes track image locality?

To reduce image pull time, network usage, and Pod startup latency.

---

### Q6. What is the purpose of `PodTopologySpread`?

To distribute Pods evenly across topology domains for better availability and resilience.

---

### Q7. Why are scores normalized?

To convert plugin outputs into a comparable range before weighting and aggregation.

---

### Q8. How does Kubernetes select the final Node?

It aggregates normalized, weighted scores from all enabled Score Plugins and selects the highest-ranked Node.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Pod consistently lands on unexpected Nodes | Plugin weights or scoring strategies favor those Nodes |
| Uneven cluster utilization | `LeastAllocated`/`MostAllocated` strategy not aligned with workload goals |
| Slow Pod startup despite available resources | ImageLocality scores are low because required images are absent |
| Pods concentrated in one zone | Missing or misconfigured `PodTopologySpread` constraints |
| Autoscaler rarely scales down | Workloads are spread too evenly, preventing Node consolidation |
| Scheduling decisions seem inconsistent | Multiple Score Plugins interact; review Scheduler Profile configuration and plugin weights |
