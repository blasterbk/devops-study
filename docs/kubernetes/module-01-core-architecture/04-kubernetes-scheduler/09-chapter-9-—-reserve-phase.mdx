# Module 1.4 — Kubernetes Scheduler Internals

# Chapter 9 — Reserve Phase

> **Goal:** Understand how Kubernetes temporarily reserves resources after selecting the best Node but before binding the Pod. Learn how the Reserve Plugin works, how resource reservation prevents race conditions, how rollback is performed on failures, how the Scheduler Cache is updated, and why the Reserve phase is critical for correctness in large production clusters.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. Why Reserve exists (preventing double-allocation between scheduling and binding)
> 2. How Reserve updates the Scheduler Cache (assumed Pod state)
> 3. Reserve plugin interface and implementation
> 4. What "assumed Pod" means in cache terminology
> 5. Reservation lifecycle: Reserve -> binding -> confirmed or expired
> 6. Unreserve: rollback when binding fails
> 7. Why Reserve is in-memory only (not written to API Server)
> 8. Production examples: stateful workloads, volume reservations
> ```

# Real-Life Analogy

Think of the Reserve Phase like holding a hotel room with a credit card.

```text
Hotel Room Hold Analogy:

You find the perfect room (scoring selected the Node)
Hotel places a hold on your credit card (Reserve phase)
Room is marked unavailable to other guests (cache update)
You haven't checked in yet (binding not confirmed)
If you cancel, hold is released (Unreserve on failure)
If you check in, hold becomes a charge (binding confirmed)
```

| Hotel Room | Reserve Phase |
| :--- | :--- |
| Finding the perfect room | Score phase selected the Node |
| Credit card hold | Reserve: deducting resources in cache |
| Room marked unavailable | Node's allocatable updated in Scheduler Cache |
| Not checked in yet | Binding not yet confirmed |
| Canceling the hold | Unreserve called on binding failure |
| Successful check-in | Binding confirmed; assumed state finalized |

> **Important:** Reserve is **in-memory only** — it updates the Scheduler Cache but does **not** write anything to the API Server or etcd. If binding fails after Reserve, the Scheduler **must call Unreserve** to roll back the in-memory resource deduction, otherwise the Node will appear over-allocated in the cache until the assumption expires.

# Simple Definition

The Reserve Phase is:

> **A temporary reservation of the selected Node's resources inside the Scheduler before binding is attempted.**

It is **not** a Kubernetes API operation.

It is entirely internal to the Scheduler.

# Performance Considerations

Reserve is intentionally lightweight.

Why?

Because every scheduled Pod executes it.

Typical operations involve:

- Updating NodeInfo
- Creating an assumed Pod
- Adjusting resource accounting

No API Server communication occurs during Reserve.

This keeps scheduling latency low.

---

# Production Best Practices

✔ Keep Reserve plugins fast and deterministic.

✔ Never perform long-running network operations inside Reserve.

✔ Always implement corresponding `Unreserve()` logic for custom Reserve plugins.

✔ Treat the Scheduler Cache as the authoritative source during scheduling.

✔ Ensure rollback fully restores resource accounting.

✔ Avoid external side effects unless absolutely necessary.

✔ Test reservation failures under production-scale workloads.

✔ Monitor scheduling failures caused by Reserve plugins separately from Filter and Score failures.

# Common Misconceptions

### ❌ Misconception 1

Reserve allocates resources in Kubernetes.

Wrong.

Reserve only updates the Scheduler's internal state.

---

### ❌ Misconception 2

Reserve updates the API Server.

Wrong.

Only the Binding phase modifies Kubernetes objects.

---

### ❌ Misconception 3

Resources become permanently allocated after Reserve.

Wrong.

Reservations are temporary until binding succeeds.

---

### ❌ Misconception 4

Assumed Pods are running Pods.

Wrong.

They exist only inside the Scheduler Cache.

---

### ❌ Misconception 5

Rollback is optional.

Wrong.

Every successful Reserve implementation must be reversible if later stages fail.

---

### ❌ Misconception 6

Other scheduling cycles ignore reservations.

Wrong.

They observe updated NodeInfo through the Scheduler Cache.

---

### ❌ Misconception 7

Reserve prevents all scheduling conflicts.

Wrong.

Reserve prevents conflicts within the Scheduler's decision-making process. Final correctness still depends on successful binding and the latest cluster state.

# Common Interview Questions

### Q1. Why does Kubernetes have a Reserve phase?

To temporarily reserve resources and prevent race conditions before binding.

---

### Q2. What is the Reserve Plugin?

A Scheduling Framework extension point that performs temporary Scheduler-side resource reservation.

---

### Q3. What is an Assumed Pod?

A temporary Scheduler Cache entry representing a Pod expected to be bound to a Node.

---

### Q4. Does Reserve update the API Server?

No.

Reserve only updates the Scheduler Cache.

---

### Q5. Why is the Scheduler Cache updated during Reserve?

So concurrent scheduling cycles immediately see reserved resources.

---

### Q6. What happens if Reserve fails?

The Scheduler executes `Unreserve()`, removes temporary reservations, restores the cache, and retries scheduling.

---

### Q7. What is the purpose of rollback?

To undo temporary Scheduler-side state when scheduling cannot continue.

---

### Q8. What is the difference between Reserve and Bind?

Reserve is temporary and internal to the Scheduler, while Bind persists the scheduling decision through the API Server.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Pod repeatedly fails after scoring | Reserve plugin failure or custom reservation logic error |
| Incorrect available resources reported by Scheduler | Assumed Pod not removed or rollback failed |
| Resource conflicts during concurrent scheduling | Reservation logic missing or custom plugin not updating Scheduler Cache correctly |
| Scheduler memory shows reserved resources after failures | `Unreserve()` implementation incomplete or failed |
| Binding never starts | Reserve or Permit phase failed before the Binding Cycle |
| Frequent reservation failures | External reservation systems, plugin errors, or inconsistent Scheduler Cache state |

In this chapter, you learned how Kubernetes safely transitions from selecting a Node to committing that decision.

You learned:

- Why the Reserve phase exists
- How the Reserve Plugin performs temporary resource reservation
- How the Scheduler uses Assumed Pods to represent pending assignments
- How the Scheduler Cache is updated with temporary resource accounting
- Why these updates prevent race conditions during concurrent scheduling
- How reservation failures trigger rollback through `Unreserve()`

The Reserve phase acts as a protective layer between **decision** and **commitment**. By temporarily updating the Scheduler Cache before binding, Kubernetes ensures that concurrent scheduling decisions are made using the most up-to-date view of available resources while remaining fully reversible if later stages fail.
