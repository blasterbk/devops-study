# Module 1.4 — Kubernetes Scheduler Internals

# Chapter 5 — Scheduler Cache

> **Goal:** Understand one of the most important performance optimizations inside Kubernetes Scheduler—the **Scheduler Cache**. Learn why it exists, how it maintains an in-memory view of the cluster, what `NodeInfo` and `PodInfo` contain, how image and resource information are tracked, how Informers keep the cache synchronized, and how Kubernetes achieves high scheduling throughput without constantly querying the API Server.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. Why Scheduler Cache exists (avoiding API Server calls during scheduling)
> 2. NodeInfo: per-node resource accounting, conditions, Pod list
> 3. PodInfo: per-pod resource requests tracked in NodeInfo
> 4. Image cache: node-to-image mapping for locality scoring
> 5. Assumed state: optimistic resource deduction before binding confirms
> 6. How Informers keep the cache synchronized with API Server events
> 7. Cache consistency: handling expired assumptions
> 8. Performance: why O(1) node lookup matters in large clusters
> ```

# Real-Life Analogy

Think of the Scheduler Cache like a whiteboard snapshot of the entire conference room.

```text
Conference Room Whiteboard Analogy:

Whiteboard shows which desks are taken, which are free
Room manager (Scheduler) reads whiteboard, not the actual desks
When someone sits down, whiteboard is updated immediately
Manager pencils in a reservation before person arrives (assumed state)
If person doesn't arrive, pencil mark is erased (expired assumption)
```

| Conference Room | Scheduler Cache |
| :--- | :--- |
| Whiteboard showing desk status | Scheduler Cache (NodeInfo map) |
| Desk capacity | Node allocatable resources |
| Occupied desks | Running Pods on the Node |
| Penciling in a reservation | Assumed state after scheduling |
| Erasing if person doesn't arrive | Expiring assumed state if binding times out |
| Room manager reads whiteboard | Scheduler reads cache, not API Server |

> **Important:** When a Pod is scheduled, the Scheduler immediately applies **assumed state** to its cache — deducting the Pod's resource requests from the target Node **before** the binding is confirmed. This allows the next scheduling cycle to begin immediately without double-allocating the same resources, even though the Pod is not yet running.

# Why Does Scheduler Cache Exist?

Imagine a Kubernetes cluster with:

```text
5,000 Nodes

100,000 Running Pods

20,000 Scheduling Decisions
Per Minute
```

Now imagine that for **every scheduling decision**, the Scheduler asks the API Server:

```text
How much CPU
is available on Node-1?

v

How much Memory
is available on Node-2?

v

Which Pods
are running on Node-3?

v

Which images
exist on Node-4?

v

Repeat...
```

This would generate **millions of API calls per minute.**

---

# Without Scheduler Cache

```text
Scheduler

v

API Server

v

etcd

v

API Server

v

Scheduler

v

Next Node

v

API Server

v

etcd
```

Every Node evaluation requires network communication.

Result:

- High latency
- API Server overload
- etcd overload
- Poor scheduling performance

---

# With Scheduler Cache

Instead:

```text
Scheduler

v

Local Memory

v

Decision
```

Only cache updates come from the API Server.

---

# Core Idea

The Scheduler keeps an **in-memory copy** of the cluster state.

Instead of asking:

```text
API Server

v

What's happening?
```

The Scheduler already knows.

---

# Simple Definition

The Scheduler Cache is:

> **An in-memory representation of cluster resources that allows the Scheduler to make scheduling decisions without querying the API Server for every scheduling cycle.**

Suppose:

```text

Reads
```

# Cache vs Snapshot

| Scheduler Cache | Scheduling Snapshot |
|-----------------|---------------------|
| Continuously changing | Immutable during one scheduling cycle |
| Updated by Informers | Created from the cache |
| Global cluster view | Point-in-time view |
| Shared across cycles | Used by one scheduling cycle |

# Common Misconceptions

### ❌ Misconception 1

The Scheduler queries the API Server for every scheduling decision.

Wrong.

It primarily uses the Scheduler Cache.

---

### ❌ Misconception 2

NodeInfo is just the Kubernetes Node object.

Wrong.

NodeInfo is an aggregated structure containing the Node plus scheduling-related metadata.

---

### ❌ Misconception 3

The Scheduler Cache never changes during scheduling.

Wrong.

The cache is continuously updated, while each scheduling cycle uses an immutable snapshot.

---

### ❌ Misconception 4

PodInfo duplicates the Pod object unnecessarily.

Wrong.

PodInfo stores preprocessed scheduling information to avoid repeated parsing.

---

### ❌ Misconception 5

Image information is irrelevant to scheduling.

Wrong.

Image locality can significantly reduce container startup time and network usage.

---

### ❌ Misconception 6

Assumed Pods are already running.

Wrong.

They are temporary Scheduler-side assumptions until binding succeeds.

---

### ❌ Misconception 7

Snapshots replace the Scheduler Cache.

Wrong.

Snapshots are temporary, point-in-time views created from the continuously updated Scheduler Cache.

# Common Interview Questions

### Q1. Why does the Scheduler Cache exist?

To maintain an in-memory view of cluster state and avoid querying the API Server for every scheduling decision.

---

### Q2. What is NodeInfo?

An aggregated structure containing all scheduling-relevant information about a Node, including resources, Pods, images, labels, taints, and more.

---

### Q3. What is PodInfo?

A preprocessed representation of a Pod containing scheduling-relevant information such as resource requests, affinity, and priority.

---

### Q4. Why does the Scheduler track images?

To enable ImageLocality scoring, reducing image pull times and improving Pod startup performance.

---

### Q5. What is resource accounting?

The Scheduler's process of tracking requested, allocatable, and available resources for every Node.

---

### Q6. How is the Scheduler Cache updated?

Through Informers receiving watch events from the API Server.

---

### Q7. What is an Assumed Pod?

A temporary Scheduler-side reservation used before binding completes to prevent race conditions.

---

### Q8. Why does the Scheduler create a snapshot?

To ensure every plugin in a scheduling cycle evaluates a consistent, immutable view of the cluster.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Scheduler decisions appear outdated | Cache not synchronized, informer lag, or watch disruptions |
| High scheduling latency | Large NodeInfo structures, expensive plugins, or stale cache updates |
| Incorrect resource calculations | Delayed cache updates or resource accounting bugs |
| Repeated scheduling conflicts | Assumed Pods not released after failures or race conditions |
| Pods repeatedly marked unschedulable | Cache reflects genuine resource shortages or stale topology information |
| Excessive API Server traffic from Scheduler | Custom plugins bypassing the Scheduler Cache and querying the API Server directly |
