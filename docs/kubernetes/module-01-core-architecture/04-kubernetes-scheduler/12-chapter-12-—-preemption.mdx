# Real-Life Analogy

Think of Preemption like airline overbooking and bumping standby passengers.

```text
Airline Overbooking Analogy:

Flight (Node) is full (resources exhausted)
High-priority passenger (VIP Pod) arrives with no seat
Airline finds lowest-priority standby passengers to bump
Bumped passengers (victim Pods) are moved to next flight
VIP passenger gets their seat (Pod schedules on now-free Node)
Bumped passengers may rebook (victim Pods reschedule elsewhere)
```

| Airline | Preemption |
| :--- | :--- |
| Full flight | Node with no allocatable capacity |
| VIP passenger | High-priority Pod (`priorityClassName`) |
| Standby passengers | Lower-priority running Pods |
| Bumping standby passengers | Evicting victim Pods |
| VIP boards | High-priority Pod schedules on freed Node |
| Bumped passenger rebooks | Evicted Pod reschedules on another Node |

> **Important:** Preemption **evicts victim Pods** but does **not guarantee** the preemptor will immediately schedule on that Node. Between eviction and reschedule, other Pods may claim the freed resources. The preemptor sets `nominatedNodeName` as a hint, but must still compete normally in the next scheduling cycle.

# Simple Definition

Preemption is:

> **The process of evicting lower-priority Pods so that a higher-priority Pod can be scheduled.**

It is a last-resort scheduling mechanism.

# When Does Preemption Happen?

Only after:

```text
Filter

v

No Candidate Nodes
```

If at least one feasible Node exists,

preemption is **not** performed.

---

# Important Design Principle

Preemption is expensive.

It causes:

- Pod eviction
- Application restart
- Temporary disruption
- Controller reconciliation

Therefore,

Kubernetes avoids preemption whenever possible.

# What Cannot Be Preempted?

Pods with:

```text
Equal Priority
```

or

```text
Higher Priority
```

cannot be preempted by a lower-priority Pod.

Example:

```text
Incoming Pod

Priority

100

Running Pod

Priority

100
```

No preemption occurs between them based solely on priority.

# PodDisruptionBudget (PDB)

Preemption should minimize application disruption.

Kubernetes considers:

```text
PodDisruptionBudget
```

during victim selection.

---

# What Is a PDB?

A PodDisruptionBudget defines:

> **How many Pods of an application should remain available during voluntary disruptions.**

Example:

```text
Application

5 Pods

v

Minimum Available

4
```

Only one Pod should be disrupted at a time.

---

# Example

Deployment:

```text
Web

5 Pods
```

PDB:

```yaml
minAvailable: 4
```

Already unavailable:

```text
1 Pod
```

Scheduler avoids preempting another Pod from this workload if doing so would violate the PDB.

---

# Important Clarification

PDBs are **best-effort** during preemption.

If no alternative exists,

Kubernetes may still preempt Pods in situations where scheduling a higher-priority workload is necessary.

---

# Why Respect PDB?

Without PDB awareness:

```text
Preempt

v

Too Many Pods Removed

v

Application Down
```

PDB reduces unnecessary disruption.

# Why Not Bind Immediately?

Because victims must first:

- Receive termination signal
- Shut down gracefully
- Release resources
- Be removed from the Node

Only then can the new Pod be scheduled.

# Performance Considerations

Preemption is more expensive than normal scheduling because it requires:

- Evaluating potential victims
- Considering PDBs
- Triggering Pod eviction
- Waiting for graceful termination
- Performing another scheduling attempt

Therefore,

it should remain an exceptional event rather than a routine scheduling strategy.

---

# Production Best Practices

✔ Use PriorityClasses only for truly important workloads.

✔ Avoid assigning very high priorities to every application.

✔ Configure PodDisruptionBudgets for highly available services.

✔ Monitor preemption events to identify resource shortages.

✔ Reserve cluster capacity for critical workloads whenever possible.

✔ Design applications to tolerate Pod restarts.

✔ Keep graceful termination periods reasonable for high-priority environments.

✔ Regularly review PriorityClass values to prevent priority inflation.

# Common Misconceptions

### ❌ Misconception 1

Preemption happens before filtering.

Wrong.

Preemption is considered only after normal scheduling fails.

---

### ❌ Misconception 2

Higher-priority Pods always preempt immediately.

Wrong.

Victims must terminate and release resources before the new Pod can be scheduled.

---

### ❌ Misconception 3

Any Pod can be selected as a victim.

Wrong.

Only lower-priority Pods are eligible for preemption based on priority.

---

### ❌ Misconception 4

PodDisruptionBudgets completely prevent preemption.

Wrong.

The Scheduler tries to minimize PDB violations, but PDBs are best-effort during preemption.

---

### ❌ Misconception 5

The Nominated Node already contains the new Pod.

Wrong.

It is only the Scheduler's preferred future target while waiting for resources.

---

### ❌ Misconception 6

Preemption immediately frees resources.

Wrong.

Resources become available only after victim Pods terminate.

---

### ❌ Misconception 7

Preemption is a sign that Kubernetes is malfunctioning.

Wrong.

It is an intentional scheduling mechanism designed to prioritize critical workloads under resource pressure.

# Common Interview Questions

### Q1. Why does Kubernetes implement preemption?

To allow higher-priority Pods to run by reclaiming resources from lower-priority Pods when no feasible Node exists.

---

### Q2. When does preemption occur?

After the normal scheduling process fails to find any feasible Node.

---

### Q3. What determines whether one Pod can preempt another?

Their relative priorities, as determined by `PriorityClass` values.

---

### Q4. What is a victim Pod?

A lower-priority Pod selected for eviction to free resources for a higher-priority Pod.

---

### Q5. What is a Candidate Node during preemption?

A Node where evicting lower-priority Pods could make scheduling the incoming Pod feasible.

---

### Q6. What is the purpose of a PodDisruptionBudget?

To reduce application disruption by limiting voluntary Pod interruptions, which the Scheduler considers during preemption when possible.

---

### Q7. What is a Nominated Node?

A Node identified as the preferred future placement for a high-priority Pod while waiting for victim Pods to terminate.

---

### Q8. Does preemption immediately schedule the incoming Pod?

No. The Scheduler waits until victim Pods terminate and resources become available before retrying scheduling.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| High-priority Pod remains Pending | Victim Pods are still terminating or no suitable preemption candidate exists |
| Frequent preemption events | Cluster resource pressure or overly aggressive PriorityClass usage |
| Important applications unexpectedly restarted | Lower-priority workloads selected as preemption victims |
| Scheduler ignores some Nodes for preemption | Evicting Pods on those Nodes cannot make the incoming Pod schedulable |
| Preemption takes longer than expected | Long Pod termination grace periods delay resource release |
| Unexpected service disruption | Missing or insufficient PodDisruptionBudget configuration |
