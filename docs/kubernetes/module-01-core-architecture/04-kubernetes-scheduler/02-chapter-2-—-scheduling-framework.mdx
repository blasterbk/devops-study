# Real-Life Analogy

Think of the Scheduling Framework like a manufacturing assembly line with quality inspection stations.

```text
Assembly Line Analogy:

Product (Pod) moves through fixed stations in order
Each station (plugin) inspects and approves or rejects
Any station can halt the line (plugin returns Unschedulable)
Stations can be added/removed without rebuilding the entire line
Last stations handle packaging and shipping (Bind phase)
```

| Assembly Line | Scheduling Framework |
| :--- | :--- |
| Product moving through stations | Pod passing through extension points |
| Inspection station | Scheduling plugin |
| Station rejects product | Plugin returns Unschedulable/Error |
| Adding a new station | Registering a new plugin |
| Quality control phase | Filter phase (elimination) |
| Ranking/grading phase | Score phase (prioritization) |
| Shipping phase | Bind phase (writing spec.nodeName) |

> **Important:** The Scheduling Framework **replaced the old predicates and priorities system** entirely (removed in Kubernetes 1.23). Every built-in scheduling behavior is now implemented as Framework plugins. All modern schedulers — including the default `kube-scheduler` — use the Framework. Writing a scheduler without the Framework is now a last resort.

# What is Framework Handle?

Framework Handle is an interface exposing Scheduler services.

It allows plugins to access:

- Scheduler Cache
- Shared Informers
- ClientSet
- Event Recorder
- Shared Listers
- Waiting Pods
- Snapshot Data

without tightly coupling to Scheduler implementation.

---

# Stage 1 — QueueSort

Purpose:

Determine:

```text
Which Pod

Schedules First?
```

Example:

High-priority Pod before low-priority Pod.

---

# Stage 2 — PreFilter

Runs before evaluating Nodes.

Typical work:

- Parse Pod
- Validate requests
- Precompute expensive calculations

Executed once per Pod.

---

# Stage 3 — Filter

Runs for:

```text
Every Candidate Node
```

Question:

```text
Can

This Pod

Run Here?
```

Possible result:

```text
Pass

or

Reject
```

---

# Stage 4 — PostFilter

Runs only when:

```text
No Node

Passed Filter
```

Typical responsibility:

```text
Preemption
```

We'll study this later.

---

# Stage 5 — PreScore

Runs before scoring.

Purpose:

Prepare information required by Score plugins.

Executed once.

---

# Stage 6 — Score

Runs for every remaining Node.

Example:

```text
Node A

85

Node B

93

Node C

71
```

Highest score wins.

---

# Stage 7 — Reserve

Temporarily reserves resources.

Purpose:

Avoid race conditions while binding.

---

# Stage 8 — Permit

Optional approval phase.

Can:

```text
Approve

Reject

Wait
```

Useful for:

Gang Scheduling

Batch Scheduling

AI workloads

---

# Stage 9 — PreBind

Runs immediately before binding.

Final validation.

---

# Stage 10 — Bind

Assigns:

```yaml
spec:
  nodeName: worker-3
```

The Pod is officially scheduled.

---

# Stage 11 — PostBind

Executed after successful binding.

Typical usage:

- Metrics
- Logging
- Notifications
- Cleanup

✔ Keep plugin chains simple.

✔ Avoid unnecessary custom plugins.

# Common Misconceptions

### ❌ Misconception 1

The Scheduling Framework replaces the Scheduler.

Wrong.

The Framework is part of the Scheduler.

---

### ❌ Misconception 2

Plugins execute randomly.

Wrong.

Every extension point has a predefined execution order.

---

### ❌ Misconception 3

One plugin decides everything.

Wrong.

Multiple plugins collaborate to produce the final decision.

---

### ❌ Misconception 4

Plugins access Scheduler internals directly.

Wrong.

They communicate through the Framework Handle.

---

### ❌ Misconception 5

Filtering and scoring are the same.

Wrong.

Filtering removes invalid Nodes.

Scoring ranks valid Nodes.

---

### ❌ Misconception 6

Every extension point is mandatory.

Wrong.

Some phases, such as Permit or PostBind, may have no active plugins.

---

### ❌ Misconception 7

Plugins always execute sequentially.

Wrong.

Several plugin stages evaluate multiple candidate Nodes in parallel for better performance.

# Common Interview Questions

### Q1. Why was the Scheduling Framework introduced?

To make the Scheduler extensible through plugins instead of modifying core scheduler code.

---

### Q2. What is an Extension Point?

A predefined stage in the scheduling pipeline where one or more plugins can execute.

---

### Q3. What is the Framework Handle?

An interface that gives plugins controlled access to Scheduler services such as the cache, client, informers, and event recorder.

---

### Q4. What is the difference between Filter and Score plugins?

Filter plugins eliminate unsuitable Nodes, while Score plugins rank the remaining candidate Nodes.

---

### Q5. Why does the Scheduler create a snapshot before scheduling?

To ensure all plugins evaluate the same consistent view of cluster state during one scheduling cycle.

---

### Q6. Why is plugin ordering important?

Because later stages depend on the results of earlier stages. For example, only valid Nodes should be scored.

---

### Q7. Can a plugin participate in multiple extension points?

Yes. A single plugin may implement multiple framework interfaces and execute in multiple stages.

---

### Q8. Why are some plugin executions parallel?

To improve scheduling throughput by evaluating many candidate Nodes simultaneously.

---

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Slow scheduling latency | Expensive Filter or Score plugins, large cluster, or excessive custom logic |
| Pods remain Pending | Filter plugins rejected every candidate Node |
| Unexpected Node selection | Plugin weights, scoring logic, or profile configuration |
| Custom plugin not executing | Plugin not registered or not enabled in the Scheduler profile |
| Different scheduling behavior after upgrade | Plugin configuration or enabled plugin set changed |
| High CPU usage in Scheduler | Large node count, expensive scoring algorithms, or inefficient custom plugins |
