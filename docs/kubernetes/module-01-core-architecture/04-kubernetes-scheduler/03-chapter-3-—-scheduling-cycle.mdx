# Module 1.4 — Kubernetes Scheduler Internals

# Chapter 3 — Scheduling Cycle

> **Goal:** Understand the complete Kubernetes Scheduling Cycle from the moment a Pod enters the Scheduling Queue until the Scheduler selects the best Node and hands the Pod to the Binding Cycle. Learn how Queue processing, PreFilter, Filter, Score, Reserve, and Permit work together to make every scheduling decision.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. How the Scheduling Cycle begins: Pod dequeued from ActiveQ
> 2. PreFilter — pre-processing and cycle-level state initialization
> 3. Filter — eliminating unsuitable Nodes (runs in parallel)
> 4. PostFilter / Preemption — fallback when no Node passes Filter
> 5. PreScore — shared state before scoring
> 6. Score — ranking feasible Nodes (normalized 0-100 per plugin)
> 7. Reserve — marking resources as tentatively allocated
> 8. Permit — final approval gate before binding begins
> ```

---

# Real-Life Analogy

Think of the Scheduling Cycle like apartment hunting.

```text
Apartment Hunting Analogy:

You have requirements (budget, location, size) -> Filter
You see all available apartments -> candidate Nodes
You eliminate unaffordable or unsuitable ones -> Filter phase
You rank remaining apartments by preference -> Score phase
You put a holding deposit on the best one -> Reserve phase
Landlord does final background check -> Permit phase
You sign the lease -> Binding cycle begins
```

| Apartment Hunt | Scheduling Cycle |
| :--- | :--- |
| Your requirements | Pod resource requests + affinity rules |
| All apartments available | All Nodes in the cluster |
| Eliminating unsuitable ones | Filter plugins |
| Ranking by preference | Score plugins |
| Holding deposit | Reserve phase (in-memory resource hold) |
| Background check / approval | Permit phase |
| Signing the lease | Binding cycle (writing spec.nodeName) |

> **Important:** If **no Node passes the Filter phase**, the Pod is moved to the **Unschedulable queue** — it is **not deleted**. It remains pending and is retried when cluster state changes (new Node added, resource freed, affinity rules relaxed). The event `FailedScheduling` is emitted.

# What is the Scheduling Cycle?

One of the biggest misconceptions is:

> **Scheduling means assigning a Pod to a Node.**

That is only partially correct.

Scheduling is actually divided into **two major phases**:

```text
Scheduling Cycle

v

Binding Cycle
```

The Scheduling Cycle **chooses** a Node.

The Binding Cycle **commits** that decision.

---

# Simple Definition

The Scheduling Cycle is:

> **The process of evaluating the cluster and selecting the most appropriate Node for an unscheduled Pod.**

No changes are written to the API Server yet.

It is only a decision-making process.

---

# Scheduling vs Binding

| Scheduling Cycle | Binding Cycle |
|------------------|---------------|
| Finds the best Node | Assigns the Pod to that Node |
| Runs plugins | Calls the API Server |
| Uses Scheduler Cache | Updates Pod `spec.nodeName` |
| Makes a decision | Persists the decision |
| No cluster modification | Cluster state changes |

---

# Why Two Separate Cycles?

Imagine this workflow:

```text
Find Node

v

Write API

v

Find Node

v

Write API
```

Every scheduling decision would wait for API operations.

Instead:

```text
Scheduling

v

Decision

v

Binding

v

API Update
```

This separation improves:

- Throughput
- Concurrency
- Extensibility
- Failure recovery

# Production Best Practices

✔ Keep Filter plugins lightweight.

✔ Use PreFilter for expensive calculations performed once per Pod.

✔ Avoid unnecessary custom Score plugins.

✔ Monitor scheduling latency.

✔ Monitor queue depth.

✔ Ensure Scheduler Cache remains synchronized.

✔ Use appropriate plugin weights instead of overly complex scoring logic.

✔ Profile scheduling performance in large clusters.

# Common Misconceptions

### ❌ Misconception 1

Scheduling immediately updates the Pod.

Wrong.

Scheduling only selects a Node.

Binding updates the Pod.

---

### ❌ Misconception 2

The Scheduler queries the API Server for every Node.

Wrong.

It uses the Scheduler Cache snapshot.

---

### ❌ Misconception 3

Filtering chooses the best Node.

Wrong.

Filtering only eliminates unsuitable Nodes.

Scoring chooses the winner.

---

### ❌ Misconception 4

Reserve permanently allocates resources.

Wrong.

Reserve is temporary until binding succeeds.

---

### ❌ Misconception 5

Permit always executes.

Wrong.

Permit plugins are optional and only run when configured.

---

### ❌ Misconception 6

The Scheduling Cycle modifies cluster state.

Wrong.

Cluster state changes during the Binding Cycle.

---

### ❌ Misconception 7

Plugins see changing cluster state while scheduling.

Wrong.

They evaluate a consistent Scheduler Snapshot.

# Common Interview Questions

### Q1. What is the Scheduling Cycle?

The Scheduling Cycle is the process of selecting the most appropriate Node for an unscheduled Pod without modifying cluster state.

---

### Q2. Why is the Scheduling Cycle separated from the Binding Cycle?

To improve concurrency, throughput, and fault isolation by separating decision-making from API updates.

---

### Q3. Why does the Scheduler create a snapshot before scheduling?

To ensure every plugin evaluates the same consistent view of the cluster during a scheduling attempt.

---

### Q4. What is the purpose of the Filter phase?

To eliminate Nodes that cannot run the Pod.

---

### Q5. What is the purpose of the Score phase?

To rank all remaining candidate Nodes and select the best one.

---

### Q6. Why does the Reserve phase exist?

To temporarily reserve resources and prevent race conditions before binding.

---

### Q7. What can happen during the Permit phase?

A plugin may approve, reject, or temporarily delay scheduling.

---

### Q8. When does the Scheduling Cycle end?

After a Node has been selected, reserved, permitted (if applicable), and the Binding Cycle has been triggered.

---

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Pod remains Pending | No Node passed the Filter phase or Permit rejected the scheduling attempt |
| Slow scheduling | Expensive Filter/Score plugins, large queue, or high cluster load |
| Unexpected Node selected | Plugin weights, scoring configuration, or Scheduler Profile behavior |
| Frequent scheduling retries | Resource shortages, affinity conflicts, taints, or transient cluster state |
| Reservation failures | Reserve plugin errors or resource conflicts during scheduling |
| High Scheduler CPU usage | Large clusters, expensive scoring algorithms, or inefficient custom plugins |

# Chapter Summary

In this chapter, you followed a Pod through the complete Scheduling Cycle—from leaving the Scheduling Queue to selecting the best Node.

You learned:

- Why Kubernetes separates scheduling from binding
- How the Scheduler builds a consistent snapshot of cluster state
- How Pods are evaluated through the PreFilter, Filter, PreScore, and Score phases
- How candidate Nodes are filtered and ranked
- Why the Reserve phase prevents resource races
- How the optional Permit phase enables advanced scheduling patterns such as gang scheduling
- When the Scheduling Cycle ends and the Binding Cycle begins

The Scheduling Cycle is the heart of Kubernetes placement logic. Every Pod that does not specify a `spec.nodeName` passes through this pipeline before it can run anywhere in the cluster.
