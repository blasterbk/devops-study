# Module 1.5 — Kubernetes Controller Manager Internals

# Chapter 11 — Node Controller

> **Goal:** Understand how the Kubernetes **Node Controller** continuously monitors every Node in the cluster, detects failures, updates Node health, applies taints, evicts Pods from unhealthy Nodes, and enables self-healing at the infrastructure level.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. Node heartbeats: kubelet updates the Node Lease every 10s
> 2. Node Lease objects: efficient heartbeat in kube-node-lease namespace
> 3. Node Conditions: Ready, MemoryPressure, DiskPressure, PIDPressure
> 4. Node failure detection: NodeMonitorGracePeriod (40s default)
> 5. Automatic tainting: node.kubernetes.io/not-ready, unreachable
> 6. Pod eviction: triggered after NodeEvictionRate delay
> 7. Zone-aware eviction: reduced rate when multiple nodes fail in one zone
> 8. Node lifecycle: CIDR assignment, cloud-provider integration
> ```

---

# Real-Life Analogy

Think of the Node Controller like a building security monitoring system.

```text
Building Security Analogy:

Each floor (Node) has a check-in sensor (Node Lease heartbeat)
Security control room (Node Controller) monitors all sensors
If a sensor misses 4 check-ins (NodeMonitorGracePeriod): alert raised
Floor marked as unsafe (Node tainted: not-ready)
Occupants (Pods) ordered to evacuate after a grace period (eviction)
If multiple floors fail in one zone: slower evacuation to avoid panic
Once floor reports healthy again: taint removed, floor reopens
```

| Building Security | Node Controller |
| :--- | :--- |
| Floor check-in sensor | Node Lease heartbeat (updated by kubelet every 10s) |
| Security control room | Node Controller |
| Missed check-ins threshold | `NodeMonitorGracePeriod` (default 40s) |
| Floor marked unsafe | Node tainted `node.kubernetes.io/not-ready` |
| Occupant evacuation order | Pod eviction after `NodeEvictionRate` delay |
| Multi-floor failure: slow eviction | Zone-aware eviction: reduced eviction rate |

> **Important:** Pod eviction from an unhealthy Node is **not instant**. Kubernetes waits for `tolerationSeconds` (default 300s for `not-ready` taint) before evicting Pods. This grace period prevents mass evictions from transient network blips. Evicted Pods are **gracefully terminated** using `terminationGracePeriodSeconds` — not force-killed immediately.

# Responsibilities

The Node Controller is responsible for:

- Monitoring Node health
- Tracking heartbeats
- Monitoring Node Leases
- Updating Node Conditions
- Detecting failures
- Applying NoExecute taints
- Triggering Pod eviction
- Monitoring Availability Zones
- Recovering workloads

The Node Controller does **not** run workloads.

# Node Lease

Modern Kubernetes optimizes heartbeat traffic using:

```text

```

under:

```text

```

Instead of continuously updating the large Node object:

```text

v

Large Update
```

```text

```

This greatly reduces API Server and etcd load.

# Performance Considerations

The Node Controller scales efficiently because it:

- Uses Shared Informers
- Reads Node Leases instead of full Node updates whenever possible
- Processes Node events through WorkQueues
- Applies rate limiting during large failures
- Cooperates with workload Controllers instead of directly recreating Pods

---

# Production Best Practices

✔ Enable Node Lease support (default in modern Kubernetes).

✔ Monitor heartbeat latency.

✔ Monitor Ready condition transitions.

✔ Alert on frequent Node flapping.

✔ Configure workloads with appropriate PodDisruptionBudgets where applicable.

✔ Use multiple Availability Zones for production clusters.

✔ Investigate recurring MemoryPressure and DiskPressure conditions.

✔ Regularly validate Node recovery procedures.

# Common Misconceptions

### ❌ Misconception 1

The Scheduler detects failed Nodes.

Wrong.

The Node Controller detects Node failures.

---

### ❌ Misconception 2

The Node Controller recreates Pods.

Wrong.

Workload Controllers (ReplicaSet, StatefulSet, Job, etc.) create replacement Pods.

---

### ❌ Misconception 3

Node Leases replace Node objects.

Wrong.

Leases provide lightweight heartbeats, while Node objects still store conditions and metadata.

---

### ❌ Misconception 4

A missed heartbeat immediately deletes all Pods.

Wrong.

The controller first detects failure, updates Node state, applies taints, and then performs eviction according to Kubernetes policies and grace periods.

---

### ❌ Misconception 5

MemoryPressure means the Node has already crashed.

Wrong.

It is an early warning condition indicating resource pressure.

---

### ❌ Misconception 6

Zone Awareness schedules Pods across zones.

Wrong.

The Scheduler places Pods. The Node Controller uses zone awareness to manage failure recovery behavior.

---

### ❌ Misconception 7

The Node Controller communicates directly with kubelet.

Wrong.

Communication occurs through the API Server using Node and Lease objects.

# Common Interview Questions

### Q1. What is the responsibility of the Node Controller?

To monitor Node health, detect failures, update Node conditions, apply taints, and initiate Pod eviction.

---

### Q2. What is a Node heartbeat?

A periodic signal from kubelet indicating that the Node is alive.

---

### Q3. Why were Node Leases introduced?

To reduce the overhead of frequent full Node status updates by using lightweight Lease objects for heartbeats.

---

### Q4. What is the purpose of the Ready condition?

It indicates whether the Node is healthy enough to accept and run workloads.

---

### Q5. How does Kubernetes detect Node failures?

The Node Controller monitors heartbeat freshness and Lease renewals.

---

### Q6. What happens after a Node becomes unreachable?

The Node Controller updates conditions, applies appropriate taints, and begins Pod eviction according to Kubernetes policies.

---

### Q7. Who recreates Pods after eviction?

The owning Controller, such as a ReplicaSet Controller or StatefulSet Controller.

---

### Q8. Why is zone awareness important?

It prevents aggressive mass eviction during large-scale zone failures, improving overall cluster stability.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Node remains NotReady | kubelet failure, network connectivity issues, or underlying Node problems |
| Pods remain on failed Node | Eviction delay, tolerations, or communication issues |
| Frequent Ready/NotReady transitions | Network instability, overloaded kubelet, or infrastructure issues |
| Scheduler avoids Node | MemoryPressure, DiskPressure, PIDPressure, or NotReady condition |
| Large-scale recovery is slow | Zone-aware eviction rate limiting during widespread failures |
| Lease not updating | kubelet stopped, API Server unreachable, or network partition |
