# Module 1.5 — Kubernetes Controller Manager Internals

# Chapter 12 — Controller Runtime

> **Goal:** Understand the internal architecture of **controller-runtime**, the framework used to build production Kubernetes Operators and Custom Controllers. Learn how the Manager, Cache, Client, Reconciler, Builder, Watches, and Predicates work together to implement Kubernetes reconciliation patterns.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. What controller-runtime is and where it fits in the ecosystem
> 2. Manager: the central coordinator (owns Cache, Client, Informers, Leader Election)
> 3. Cache: shared informer-backed in-memory object store
> 4. Client: read-from-cache + write-to-API Server in one interface
> 5. Reconciler interface: the single Reconcile(ctx, Request) function
> 6. Builder: fluent API for wiring Watches to Reconcilers
> 7. Predicates: filtering Watch events before they reach the WorkQueue
> 8. Owns, Watches, EnqueueRequestFor: advanced owner-tracking patterns
> ```

---

# Real-Life Analogy

Think of controller-runtime like scaffolding for a construction project.

```text
Construction Scaffolding Analogy:

Building a skyscraper (Kubernetes Operator) from scratch is dangerous
Scaffolding (controller-runtime) provides the safe structure to work from
Scaffolding handles: platforms, safety rails, material hoists (Manager, Cache, Client)
Architect focuses on: the actual building design (Reconcile logic)
Different construction companies (kubebuilder, Operator SDK) use the same scaffolding
When done, scaffolding is hidden behind the finished building
```

| Scaffolding | controller-runtime |
| :--- | :--- |
| Scaffolding system | controller-runtime library |
| Safety platforms | Manager: Leader Election, Health probes, Metrics |
| Material delivery system | Cache: shared Informer, pre-populated object store |
| Tool interface | Client: read cache + write API Server |
| Actual building work | Reconcile() function: your custom logic |
| Construction company style | kubebuilder / Operator SDK (use controller-runtime underneath) |

> **Important:** `controller-runtime` is the **foundation underneath both `kubebuilder` and the `Operator SDK`**. When you generate an Operator with either tool, they both produce Go code that imports and uses `sigs.k8s.io/controller-runtime`. Understanding controller-runtime directly means you understand all Operators built on top of it.

# What is controller-runtime?

controller-runtime is:

> **A high-level Go framework built on top of client-go that simplifies building Kubernetes Controllers and Operators.**

It is **not** part of the Kubernetes API Server.

It is a Go library used by controller applications.

# Production Best Practices

✔ Keep Reconcile functions idempotent.

✔ Read from the cache whenever possible.

✔ Write only when necessary.

✔ Keep reconciliation fast and deterministic.

✔ Use Predicates to reduce unnecessary reconciliations.

✔ Watch only resources relevant to the controller.

✔ Handle deleted resources gracefully.

✔ Use Status fields to report observed state.

✔ Return appropriate requeue behavior instead of busy loops.

✔ Never assume cached data reflects writes immediately; account for eventual consistency.

✔ Run controllers with leader election enabled in production.

✔ Instrument controllers with metrics, health checks, and structured logging.

# Performance Considerations

controller-runtime scales well because it:

- Uses Shared Informers
- Shares caches across Controllers
- Uses WorkQueues
- Supports concurrent workers
- Filters events using Predicates
- Reads primarily from memory
- Minimizes API Server load

# Common Misconceptions

### ❌ Misconception 1

controller-runtime replaces client-go.

Wrong.

It is built **on top of** client-go.

---

### ❌ Misconception 2

The Manager performs reconciliation.

Wrong.

Reconcilers perform reconciliation.

The Manager orchestrates infrastructure.

---

### ❌ Misconception 3

The Client always reads directly from the API Server.

Wrong.

The default split client reads from the cache and writes to the API Server.

---

### ❌ Misconception 4

Every Watch event results in reconciliation.

Wrong.

Predicates may filter events before they reach the WorkQueue.

---

### ❌ Misconception 5

Reconcilers receive full Kubernetes objects.

Wrong.

They receive a reconcile request (typically namespace/name) and fetch the latest object using the Client.

---

### ❌ Misconception 6

One Manager can run only one Controller.

Wrong.

A single Manager commonly hosts many Controllers.

---

### ❌ Misconception 7

controller-runtime is only for Operators.

Wrong.

It is a general-purpose framework for building Kubernetes Controllers. Many Operators are built with it, but it is equally suitable for standalone custom controllers.

# Common Interview Questions

### Q1. What is controller-runtime?

A Go framework built on top of client-go that simplifies writing Kubernetes Controllers and Operators.

---

### Q2. What is the responsibility of the Manager?

It starts and manages shared infrastructure such as caches, controllers, leader election, metrics, and health endpoints.

---

### Q3. Why does controller-runtime use a cache?

To reduce API Server traffic and provide fast in-memory reads.

---

### Q4. What is a split client?

A client that typically reads from the cache while sending writes directly to the API Server.

---

### Q5. What is the purpose of the Reconciler?

To implement business logic that continuously drives actual cluster state toward the desired state.

---

### Q6. What does the Builder do?

It configures Controllers, Watches, Predicates, and owned resources before registering them with the Manager.

---

### Q7. Why are Predicates useful?

They filter unnecessary events, reducing reconciliation frequency and improving performance.

---

### Q8. Why is controller-runtime preferred over raw client-go?

Because it provides reusable controller infrastructure, significantly reducing boilerplate while following Kubernetes best practices.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Reconcile never executes | Watch not registered, cache not synchronized, or Manager not started |
| Reconcile executes repeatedly | Continuous object updates, improper status handling, or missing event filtering |
| Controller reads stale data | Reading from cache immediately after a write; eventual consistency is expected |
| API Server overloaded | Excessive direct API calls or unnecessary writes |
| Multiple controller instances act simultaneously | Leader election disabled or misconfigured |
| High CPU usage | Excessive reconciliation, missing Predicates, or expensive Reconcile logic |
