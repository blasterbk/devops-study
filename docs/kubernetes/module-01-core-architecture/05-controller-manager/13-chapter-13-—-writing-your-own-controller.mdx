# Module 1.5 — Kubernetes Controller Manager Internals

# Chapter 13 — Writing Your Own Controller

> **Goal:** Learn how to build a production-grade Kubernetes Controller from scratch using **controller-runtime**. Understand how Custom Resource Definitions (CRDs), Watches, WorkQueues, Reconcilers, OwnerReferences, Finalizers, Status updates, error handling, testing, and deployment work together to create a fully functional Kubernetes Operator.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. CRDs: extending the Kubernetes API with custom resource types
> 2. Scaffolding a controller with kubebuilder: project structure
> 3. Watches: registering which resources trigger your reconcile function
> 4. Reconcile(): implementing desired-vs-actual comparison and correction
> 5. OwnerReferences: linking child resources to parent for garbage collection
> 6. Finalizers: ensuring cleanup before an object is permanently deleted
> 7. Status subresource: reporting observed state back to the cluster
> 8. Testing: envtest, fake clients, unit and integration tests
> ```

# Real-Life Analogy

Think of writing a custom controller like opening a franchise restaurant.

```text
Franchise Restaurant Analogy:

Franchise HQ (controller-runtime) provides the operating system
You provide the menu (CRD: your custom resource type)
Kitchen staff (reconcile function) prepares food to match each order
If a dish is already made correctly: no action needed (idempotent check)
If an ingredient is missing: order more (create child resource)
If a customer cancels: clean up the kitchen (finalizer cleanup)
Manager reports order status on receipt (status subresource update)
```

| Franchise | Writing Your Own Controller |
| :--- | :--- |
| Franchise operating system | controller-runtime framework |
| Your menu | CRD (Custom Resource Definition) |
| Customer order | Custom resource instance (`kubectl apply`) |
| Kitchen preparing food | Reconcile() function executing desired state |
| Cleaning up cancelled order | Finalizer: clean up before deletion |
| Receipt with order status | Status subresource: observed state report |

> **Important:** Your `Reconcile()` function **must be idempotent**. It will be called repeatedly — on creation, updates, periodic resyncs, and retries. If you call `Create()` without first checking whether the resource exists, you will get an `AlreadyExists` error on every subsequent reconcile. Always read first, compare, then act only on the diff.

Kubernetes includes built-in controllers:


# Production Best Practices

✔ Keep reconciliation idempotent.

✔ Read from the cache; write only when necessary.

✔ Use OwnerReferences for Kubernetes-managed child resources.

✔ Use Finalizers only when external cleanup is required.

✔ Update the Status subresource instead of modifying Spec.

✔ Handle transient and permanent errors differently.

✔ Avoid long-running operations inside `Reconcile()`; delegate lengthy work and return quickly.

✔ Use leader election in production.

✔ Expose metrics, health probes, and readiness probes.

✔ Use structured logging with resource identifiers.

✔ Limit RBAC permissions to the minimum required.

✔ Test every reconciliation path, including failures and deletion.

# Common Mistakes

### ❌ Mistake 1

Polling the API continuously.

Correct approach:

Use Watches.

---

### ❌ Mistake 2

Creating duplicate child resources.

Correct approach:

Read first, compare desired vs actual, then create only if needed.

---

### ❌ Mistake 3

Ignoring OwnerReferences.

Correct approach:

Set ownership so Kubernetes can perform garbage collection and event mapping.

---

### ❌ Mistake 4

Deleting external resources without Finalizers.

Correct approach:

Use Finalizers to guarantee cleanup before the custom resource disappears.

---

### ❌ Mistake 5

Updating Spec instead of Status.

Correct approach:

Controllers normally update the Status subresource to report observed state.

---

### ❌ Mistake 6

Returning errors for permanent configuration problems forever.

Correct approach:

Record the problem in Status and requeue only when appropriate or after relevant changes.

---

### ❌ Mistake 7

Performing expensive operations on every reconciliation.

Correct approach:

Compare desired and actual state before making changes.

# Common Interview Questions

### Q1. What is the first step in writing a Kubernetes Controller?

Define a Custom Resource Definition (CRD) for the new API.

---

### Q2. Why does a Controller use Watches instead of polling?

Watches provide efficient, event-driven reconciliation with significantly lower API load.

---

### Q3. What is stored in the WorkQueue?

Typically the namespace/name key identifying the resource to reconcile.

---

### Q4. Why must `Reconcile()` be idempotent?

Because reconciliation may run repeatedly due to retries, resyncs, or multiple events.

---

### Q5. What is the purpose of OwnerReferences?

To establish ownership relationships for garbage collection and event mapping.

---

### Q6. When should Finalizers be used?

When cleanup must occur before Kubernetes permanently deletes an object.

---

### Q7. Why are Spec and Status separated?

Spec represents the desired state; Status reports the observed state.

---

### Q8. How should production Controllers be deployed?

As highly available Deployments with leader election, health checks, metrics, and appropriate RBAC.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Controller never reconciles | Watch not registered, cache not synchronized, or Manager not running |
| Child resources created repeatedly | Reconcile logic not idempotent or existing resources not checked |
| Custom resource stuck deleting | Finalizer not removed after cleanup |
| Status never updates | Status subresource not enabled or update logic incorrect |
| Child resources remain after deletion | Missing OwnerReferences or external cleanup incomplete |
| Excessive API traffic | Direct API reads instead of cache, unnecessary writes, or missing event filtering |

# Chapter Summary

In this chapter, you learned how to build a complete Kubernetes Controller using **controller-runtime**.

You learned:

- How CRDs extend the Kubernetes API
- How Watches detect changes efficiently
- How the WorkQueue buffers reconciliation requests
- How `Reconcile()` implements the desired-state reconciliation loop
- How OwnerReferences establish ownership and enable garbage collection
- How Finalizers guarantee cleanup before deletion
- How Status updates communicate observed state
- How Controllers handle retries and errors safely
- How Controllers should be tested at the unit, integration, and end-to-end levels
- How production Controllers are deployed with leader election, health checks, metrics, and minimal RBAC

A production Kubernetes Controller is fundamentally an **event-driven reconciliation engine**. Rather than executing imperative workflows, it continuously observes cluster state, compares it with the desired state declared in Custom Resources, and makes only the changes required to converge the two. By combining **CRDs**, **Watches**, **WorkQueues**, **Reconcilers**, **OwnerReferences**, **Finalizers**, and **Status reporting**, custom Controllers become first-class citizens of the Kubernetes control plane, enabling sophisticated automation for virtually any infrastructure or application domain.
