# Module 1.5 — Kubernetes Controller Manager Internals

# Chapter 3 — Shared Informers

> **Goal:** Understand how Kubernetes Controllers efficiently monitor millions of cluster events without overwhelming the API Server. Learn how Shared Informers, Reflectors, Watches, DeltaFIFO, Local Cache, and Event Handlers work together to provide a scalable, event-driven architecture for the entire Kubernetes control plane.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. Why Informers exist: avoiding constant API Server polling
> 2. List + Watch: the two-phase startup of every Informer
> 3. Reflector: the component that runs the Watch stream
> 4. DeltaFIFO: ordered queue of change events
> 5. Local Cache (Store/Indexer): in-memory object index
> 6. Event Handlers: AddFunc, UpdateFunc, DeleteFunc callbacks
> 7. Shared Informers: one Informer shared by all controllers for the same resource
> 8. Cache synchronization: HasSynced() and WaitForCacheSync()
> ```

---

# Real-Life Analogy

Think of Shared Informers like a library catalog index.

```text
Library Catalog Analogy:

Library (API Server) has millions of books (Kubernetes objects)
Catalog system (Informer) keeps a local index of all books
Catalog syncs with library on startup (List phase)
Library sends change notifications to catalog (Watch stream)
Multiple librarians (controllers) all use the SAME catalog index
No librarian goes directly to the shelves to count books
```

| Library | Shared Informer |
| :--- | :--- |
| Library | API Server + etcd |
| Book collection | All Kubernetes objects (Pods, Nodes, etc.) |
| Catalog index | Local in-memory Store/Indexer |
| Initial catalog scan | List phase on startup |
| Library update notifications | Watch event stream |
| Librarians sharing catalog | Multiple controllers sharing one Informer |

> **Important:** All controllers inside `kube-controller-manager` that watch the same resource type (e.g., Pods) share **one single Informer instance** — not one per controller. This is the "Shared" in Shared Informer. This means `kube-controller-manager` maintains only **one Watch stream** per resource type to the API Server, regardless of how many controllers need that resource.

# What is an Informer?

An Informer is:

> **A component that continuously synchronizes Kubernetes resources into an in-memory cache and delivers change notifications to registered event handlers.**

Think of it as:

```text
API Listener

+

Cache

+

Event Dispatcher
```

---

# Responsibilities of an Informer

An Informer performs:

- Initial List
- Continuous Watch
- Local Cache
- Event Distribution
- Cache Synchronization
- ResourceVersion Tracking

It is much more than a simple Watch client.

# Cache Synchronization

Controllers should not start reconciling immediately after startup.

Why?

Because the cache may still be empty.

---

# Startup Sequence

```text
Controller Starts

v

Informer Starts

v

List Existing Objects

v

Populate Cache

v

Cache Sync Complete

v

Start Workers
```

Only after synchronization is complete should reconciliation begin.

---

# Why Cache Synchronization Matters

Suppose:

Reality:

```text
1,000 Pods
```

Controller starts.

Cache contains:

```text
0 Pods
```

If reconciliation begins immediately,

the Controller may incorrectly conclude:

```text
Need

1,000 New Pods
```

Waiting for cache synchronization prevents incorrect decisions.

---

# hasSynced()

Controllers typically wait for:

```text

v

Fully Synced

v

```

This guarantees the cache reflects the latest observed cluster state before reconciliation begins.

# Reflector

The Reflector is the component responsible for:


# Reflector Responsibilities

The Reflector:

- Performs the initial List
- Starts the Watch
- Tracks ResourceVersion
- Handles Watch restarts
- Sends changes into DeltaFIFO

It does **not** reconcile resources.


```text

```

The Reflector ensures updates are processed in order relative to the observed ResourceVersion stream.

# DeltaFIFO

Reflector does not update the cache directly.

Instead,

```text

```

---

# What is DeltaFIFO?

DeltaFIFO is:

> **A queue that stores the sequence of changes (deltas) for Kubernetes objects before they are processed by the Informer.**

It buffers updates between the Reflector and the cache.

---

# Why "Delta"?

Because it stores:

```text
What Changed

not

Everything
```

Example:

```text
Pod Modified

v

Only Modification

Queued
```

---

# FIFO

FIFO means:

```text
First In

v

First Out
```

Events are processed in arrival order.

---

```text
v

v

```

DeltaFIFO acts as the bridge between incoming Watch events and the Informer.

# Performance Considerations

Shared Informers are optimized by:

- Using a single List + Watch stream
- Maintaining a shared in-memory cache
- Delivering only incremental changes
- Buffering events through DeltaFIFO
- Processing changes asynchronously
- Reusing caches across multiple Controllers

These optimizations are critical for clusters containing tens or hundreds of thousands of resources.

---

# Production Best Practices

✔ Use Shared Informers instead of creating independent Watches.

✔ Always read objects from the Informer cache during reconciliation whenever possible.

✔ Wait for cache synchronization before starting worker threads.

✔ Keep event handlers lightweight; enqueue work instead of performing reconciliation directly.

✔ Reuse existing Informers for the same resource type.

✔ Handle Watch interruptions gracefully.

✔ Design Controllers assuming events may arrive rapidly or in bursts.

✔ Monitor cache synchronization and Watch health in production clusters.

# Common Misconceptions

### ❌ Misconception 1

Informers replace Controllers.

Wrong.

Informers detect and distribute changes. Controllers reconcile those changes.

---

### ❌ Misconception 2

Every Controller creates its own Watch connection.

Wrong.

Controllers typically share Informers, which share List, Watch, and cache resources.

---

### ❌ Misconception 3

Controllers should query the API Server for every reconciliation.

Wrong.

They usually read from the Informer cache, reducing API Server load.

---

### ❌ Misconception 4

The Reflector performs reconciliation.

Wrong.

The Reflector synchronizes objects from the API Server into the Informer pipeline.

---

### ❌ Misconception 5

DeltaFIFO stores every object in the cluster.

Wrong.

It stores pending changes (deltas) awaiting processing, not the entire cluster state.

---

### ❌ Misconception 6

Event handlers should perform all business logic.

Wrong.

Event handlers should enqueue work; reconciliation should happen in worker threads.

---

### ❌ Misconception 7

Controllers can begin processing immediately after startup.

Wrong.

They should wait until the Informer cache has synchronized with the API Server.

# Common Interview Questions

### Q1. Why do Kubernetes Informers exist?

To efficiently synchronize Kubernetes resources into a local cache and deliver change notifications without repeatedly querying the API Server.

---

### Q2. What is a Shared Informer?

A Shared Informer allows multiple Controllers to reuse the same List, Watch, and local cache for a resource type.

---

### Q3. Why is the Watch API preferred over polling?

Because it provides real-time updates with significantly lower API traffic and latency.

---

### Q4. What is the role of the Reflector?

The Reflector performs the initial List, maintains the Watch connection, tracks ResourceVersion, and feeds updates into DeltaFIFO.

---

### Q5. What is DeltaFIFO?

A queue that stores object changes (deltas) before they are applied to the Informer cache and delivered to event handlers.

---

### Q6. Why do Controllers use a local cache?

To avoid repeated API Server requests and improve reconciliation performance.

---

### Q7. Why must Controllers wait for cache synchronization?

To ensure reconciliation decisions are based on a complete and up-to-date view of cluster state.

---

### Q8. What do event handlers typically do?

They respond to Add, Update, and Delete events by enqueueing objects for reconciliation.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Controller processes incomplete cluster state | Cache synchronization was not completed before workers started |
| Excessive API Server traffic | Informers are not being shared or Controllers bypass the cache |
| Missed updates after network interruption | Watch reconnection or Reflector synchronization issues |
| High memory usage | Large Informer caches or unnecessary resource watches |
| Slow reconciliation after updates | WorkQueue backlog or delayed event processing |
| Duplicate processing of the same object | Multiple events generated for the object; reconciliation must remain idempotent |
