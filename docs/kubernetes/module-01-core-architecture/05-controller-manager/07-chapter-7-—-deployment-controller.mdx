# Module 1.5 — Kubernetes Controller Manager Internals

# Chapter 7 — Deployment Controller

> **Goal:** Understand how the Kubernetes **Deployment Controller** manages application rollouts by orchestrating ReplicaSets. Learn how Deployments perform rolling updates, support zero-downtime deployments, maintain revision history, perform rollbacks, and safely upgrade applications in production clusters.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. Deployment position in the ownership chain: Deployment -> ReplicaSet -> Pod
> 2. How a Deployment reconciles: desired ReplicaSet vs current ReplicaSets
> 3. Rolling update strategy: maxSurge and maxUnavailable
> 4. How new ReplicaSets are created on image change
> 5. How old ReplicaSets are scaled down during rollout
> 6. Revision history: revisionHistoryLimit and rollback mechanism
> 7. Paused Deployments: halting rollout mid-flight
> 8. ProgressDeadlineSeconds: detecting stuck rollouts
> ```

# Real-Life Analogy

Think of the Deployment Controller like a project manager overseeing team leads.

```text
Project Manager Analogy:

You tell the project manager: "Deploy version 2 of our product"
PM (Deployment Controller) never writes a single line of code directly
PM creates a new team (new ReplicaSet) to build v2
PM gradually moves engineers from the old team (old RS) to new team
PM watches progress: if new team struggles, PM can pause or roll back
Old team is kept on standby during rollout (scaled to 0, not deleted)
Revision history is kept so PM can reinstate the old team instantly
```

| Project Manager | Deployment Controller |
| :--- | :--- |
| Project manager | Deployment Controller |
| Engineering team lead | ReplicaSet |
| Engineers (workers) | Pods |
| Assigning engineers to teams | Scaling ReplicaSets up/down |
| New version rollout | Rolling update: new RS scales up, old RS scales down |
| Rollback to previous version | Scale old RS back up, scale new RS to 0 |

> **Important:** The Deployment Controller **never creates Pods directly**. It only creates and scales ReplicaSets. All Pod creation is delegated to the ReplicaSet Controller. This layered ownership is why `kubectl get pods` shows `ownerReference` pointing to a ReplicaSet, not the Deployment.

Deployment solves these problems.

---

# What is a Deployment?

A Deployment is:

> **A higher-level Kubernetes resource that manages ReplicaSets and provides declarative application updates, rollbacks, scaling, and rollout strategies.**

A Deployment **never creates Pods directly.**

Instead:

```text
Deployment

v

ReplicaSet

v

Pods
```

---

# Example Deployment

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: nginx

spec:
  replicas: 3

  selector:
    matchLabels:
      app: nginx

  template:
    metadata:
      labels:
        app: nginx

    spec:
      containers:
      - name: nginx
        image: nginx:1.30
```

---

# Deployment Responsibilities

Deployment Controller is responsible for:

- Creating ReplicaSets
- Updating ReplicaSets
- Scaling ReplicaSets
- Rolling updates
- Rollbacks
- Revision history
- Deployment status
- Monitoring rollout progress

It is **not** responsible for creating Pods directly.

---

Deployment orchestrates multiple ReplicaSets.

# ReplicaSet Management

The Deployment Controller watches:

- Deployments
- ReplicaSets

Whenever the Pod Template changes,

it creates a **new ReplicaSet**.

---

# Example

Version 1:

```yaml
image: nginx:1.29
```

ReplicaSet:

```text
ReplicaSet A
```

Later:

```yaml
image: nginx:1.30
```

Deployment Controller:

```text
Create

ReplicaSet B
```

The old ReplicaSet remains until the rollout completes (and may remain afterward for rollback history).

# Why Create a New ReplicaSet?

Question:

Why not simply modify the existing ReplicaSet?

Because Kubernetes wants:

- Safe upgrades
- Rollbacks
- Version history
- Controlled transitions

Each Pod template revision gets its own ReplicaSet.

# Max Surge

During rolling updates,

Deployments may temporarily create extra Pods.

This is controlled by:

```text

```

---

# What is Max Surge?

Max Surge defines:

> **The maximum number of additional Pods that may exist above the desired replica count during a rolling update.**

---

# Example

Desired:

```text
10 Pods
```

Configuration:

```yaml
maxSurge: 2
```

Maximum temporary Pods:

```text
12
```

The Deployment can create up to two extra Pods before removing old ones.

---

# Rolling Update with Max Surge

```text
Desired

10

v

Create

2 New Pods

v

Total

12

v

Delete

2 Old Pods

v

Back To

10
```

Extra capacity helps reduce downtime.

---

# Percentage Example

```yaml

```

Desired:

```text
20 Pods
```

Maximum surge:

```text
5 Additional Pods
```

Total during rollout:

```text
25 Pods
```

Percentages are calculated relative to the desired replica count.

# Why Max Unavailable?

It balances:

- Deployment speed

Smaller values:

```text

```

Larger values:


# Progress Deadline

Deployments monitor rollout progress.

---

# What is Progress Deadline?

A Deployment expects rollout progress within a configured time.

Configuration:

```yaml
progressDeadlineSeconds: 600
```

Meaning:

```text
If rollout makes no progress

for 600 seconds

v

Mark Deployment

ProgressDeadlineExceeded
```

---

# Why Progress Deadline Exists

Suppose:

New Pods:

```text
CrashLoopBackOff
```

The rollout never advances.

Without a deadline:

```text
Deployment

Waiting Forever
```

Instead,

the Deployment reports rollout failure.

---

# Example

```text
ReplicaSet Created

v

Pods Never Become Ready

v

Deadline Exceeded

v

Deployment Condition Updated
```

The Deployment does **not** automatically roll back simply because the deadline is exceeded; it reports the failure so operators or higher-level automation can respond.

---

# Performance Considerations

Deployment Controllers scale efficiently because they:

- Use Shared Informers
- Reconcile from local caches
- Enqueue only Deployment keys
- Manage ReplicaSets rather than Pods directly
- Coordinate with ReplicaSet Controllers
- Perform idempotent reconciliation

---

# Production Best Practices

✔ Use Deployments instead of standalone ReplicaSets for long-running applications.

✔ Configure appropriate `maxSurge` and `maxUnavailable` values based on application availability requirements.

✔ Use readiness probes to ensure new Pods receive traffic only after becoming healthy.

✔ Configure `progressDeadlineSeconds` for production workloads.

✔ Retain sufficient revision history for rollback.

✔ Monitor Deployment conditions during rollouts.

✔ Perform gradual rollouts for critical applications.

✔ Test rollback procedures regularly.

# Common Misconceptions

### ❌ Misconception 1

Deployments create Pods directly.

Wrong.

Deployments create and manage ReplicaSets. ReplicaSets create Pods.

---

### ❌ Misconception 2

Updating the image modifies the existing ReplicaSet.

Wrong.

A new Pod template results in a new ReplicaSet.

---

### ❌ Misconception 3

Rolling updates delete all old Pods first.

Wrong.

Deployments gradually replace Pods according to the rollout strategy.

---

### ❌ Misconception 4

Max Surge permanently increases replica count.

Wrong.

Additional Pods exist only temporarily during the rollout.

---

### ❌ Misconception 5

Progress deadline automatically rolls back a Deployment.

Wrong.

The Deployment reports rollout failure through its status. Automatic rollback requires additional tooling or operator action.

---

### ❌ Misconception 6

Revision history stores old Pods.

Wrong.

Revision history is represented by ReplicaSets (and their Pod templates), not by retained Pods.

---

### ❌ Misconception 7

Deployments schedule Pods onto Nodes.

Wrong.

Scheduling is performed by the Kubernetes Scheduler after ReplicaSets create Pods.

# Common Interview Questions

### Q1. What is the purpose of a Deployment?

To manage ReplicaSets and provide declarative updates, scaling, rollbacks, and rollout strategies.

---

### Q2. Does a Deployment create Pods directly?

No. It creates ReplicaSets, which create Pods.

---

### Q3. Why does every Pod template change create a new ReplicaSet?

To support controlled rollouts, revision history, and rollbacks.

---

### Q4. What is a rolling update?

A deployment strategy that gradually replaces old Pods with new Pods while maintaining application availability.

---

### Q5. What is Max Surge?

The maximum number of additional Pods allowed above the desired replica count during a rolling update.

---

### Q6. What is Max Unavailable?

The maximum number of desired Pods that may be unavailable during a rolling update.

---

### Q7. What is the purpose of revision history?

To retain previous Deployment revisions so rollbacks are possible.

---

### Q8. What happens when the progress deadline is exceeded?

The Deployment reports that the rollout has stalled by updating its status conditions.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Deployment rollout never completes | New Pods are not becoming Ready, image issues, or scheduling failures |
| New ReplicaSet created but no Pods run | ReplicaSet reconciliation, scheduling, or resource constraints |
| Rollout slower than expected | Conservative `maxSurge`/`maxUnavailable` settings or slow readiness |
| Old ReplicaSets accumulate | `revisionHistoryLimit` retains previous revisions |
| Deployment shows `ProgressDeadlineExceeded` | Rollout stalled because new Pods failed to make progress |
| Rollback does not restore application health | Previous revision also contains configuration or application problems |
