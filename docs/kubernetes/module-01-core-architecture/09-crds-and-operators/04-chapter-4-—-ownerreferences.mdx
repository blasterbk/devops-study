# Module 1.9 — CRDs & Operators

# Chapter 4 — OwnerReferences

> **Goal:** Understand how Kubernetes automatically manages relationships between resources using **OwnerReferences** and the **Garbage Collector (GC)**. By the end of this chapter, you'll understand how Kubernetes safely deletes dependent resources, prevents orphaned objects, and maintains ownership hierarchies across the cluster.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. OwnerReferences schema: apiVersion, kind, name, uid, controller, blockOwnerDeletion
> 2. The Garbage Collector (GC) Controller: GraphBuilder and attemptToDeleteItem
> 3. Cascading deletion strategies: Foreground, Background, and Orphan
> 4. `controller: true` flag: designating exactly one primary manager per child
> 5. `blockOwnerDeletion: true`: preventing parent deletion until child finalizers finish
> 6. Dynamic adoption and orphaning of child resources during controller failover
> 7. Strict cross-namespace isolation rules for OwnerReferences
> 8. How `controllerutil.SetControllerReference()` wires relationships in Go operators
> ```

# Real-Life Analogy

Think of OwnerReferences like a legal guardianship and family tree inheritance system.

```text
Family Guardianship Analogy:

Parent (Custom Resource: `WebSite`) creates child resources (Service, Deployment, Ingress)
Each child is given an official birth certificate listing the Parent (OwnerReference with UID)
Only one parent can be designated as the primary legal guardian (`controller: true`)
If the Parent moves away (Parent deleted):
  - Background cascade: Parent is removed immediately, children cleaned up shortly after
  - Foreground cascade: Children must pack up and finish cleanup before parent departs
  - Orphan policy: Children are legally emancipated and continue running independently
```

| Family Tree | OwnerReferences Internals |
| :--- | :--- |
| Parent | Owner object (Deployment, CR) |
| Child | Dependent object (ReplicaSet, Pod, Service) |
| Official birth certificate | `metadata.ownerReferences` slice on child |
| Legal guardian designation | `controller: true` boolean |
| Child cleanup before parent leaves | `blockOwnerDeletion: true` / Foreground deletion |
| Emancipation | `propagationPolicy=Orphan` |

> **Important:** OwnerReferences **cannot cross namespaces**. A namespaced child resource (like a Secret or Pod) can **only** be owned by a parent object in the **exact same namespace** (or by a cluster-scoped parent like a ClusterRole). Attempting to set an OwnerReference pointing to a parent in a different namespace is considered invalid and will cause the Garbage Collector to immediately treat the child as orphaned or reject the reference.

# Where This Chapter Fits

In the previous chapter, we learned how **Finalizers** ensure resources are cleaned up before deletion.

Now another question arises.

Suppose we have:

```text
Deployment
  |
  v
ReplicaSet
  |
  v
Pods
```

If the Deployment is deleted,

who deletes the ReplicaSet?

Who deletes the Pods?

Does the Deployment Controller manually delete everything?

**No.**

This responsibility belongs to the **Kubernetes Garbage Collector** using **OwnerReferences**.

---

# The Problem

Imagine Kubernetes without OwnerReferences.

User creates:

```text
Deployment
  |
  v
ReplicaSet
  |
  v
Pods
```

Later:

```bash
kubectl delete deployment nginx
```

Result:

```text
Deployment

Deleted

ReplicaSet

Still Exists

Pods

Still Running
```

These leftover resources are called **orphaned resources**.

Over time they waste:

- CPU
- Memory
- Storage
- IP addresses
- Cluster resources

---

# Kubernetes Solution

Instead of manually deleting everything,

Kubernetes records ownership.

```text
Deployment

Owns
  |
  v
ReplicaSet

Owns
  |
  v
Pods
```

When the owner disappears,

the Garbage Collector automatically handles the dependents.

---

# What is the Kubernetes Garbage Collector?

The Garbage Collector (GC) is a built-in controller inside the Controller Manager.

Its job is to automatically remove Kubernetes resources whose owners no longer exist.

High-level architecture:

```text
API Server
  |
  v
Watch Objects
  |
  v
Garbage Collector
  |
  v
Delete Dependent Resources
```

Unlike Finalizers,

the Garbage Collector only manages **Kubernetes resources**.

It does **not** delete cloud databases, DNS records, or external systems.

---

# What is an OwnerReference?

An OwnerReference is metadata stored on a child resource.

Example:

```yaml
metadata:
  ownerReferences:
  - apiVersion: apps/v1
    kind: Deployment
    name: nginx
    uid: 5e8c...
```

It tells Kubernetes:

> "This object belongs to another object."

---

# Where OwnerReferences are Stored

Every child object stores its owner.

Example:

```text
ReplicaSet
  |
  v
Metadata
  |
  v
OwnerReferences
  |
  v
Deployment
```

Similarly,

```text
Pod
  |
  v
Metadata
  |
  v
OwnerReferences
  |
  v
ReplicaSet
```

---

# Parent–Child Relationship

OwnerReferences create dependency trees.

Example:

```text
Deployment
  |
  v
ReplicaSet
  |
  v
Pods
```

Each child knows its parent.

The parent does **not** maintain a list of children.

This is an important design decision.

---

# Why Store Ownership on the Child?

Imagine a Deployment managing 10,000 Pods.

If the Deployment stored every child,

every Pod creation or deletion would require updating the Deployment.

Instead:

```text
Every Child
  |
  v
Points to Parent
```

This scales much better.

---

# Controller References

A special type of OwnerReference is a **Controller Reference**.

Example:

```yaml
ownerReferences:
- controller: true
```

Only one OwnerReference may have:

```yaml
controller: true
```

This identifies the controller responsible for managing that child resource.

---

# Why Controller References Exist

Suppose multiple resources reference the same Pod.

Which controller should reconcile it?

Example:

```text
Deployment
  |
  v
ReplicaSet
  |
  v
Pod
```

The ReplicaSet is the managing controller.

Therefore:

```yaml
controller: true
```

is set on the ReplicaSet OwnerReference.

---

# OwnerReference Structure

Example:

```yaml
ownerReferences:
- apiVersion: apps/v1
  kind: Deployment
  name: nginx
  uid: 5e8c...
  controller: true
  blockOwnerDeletion: true
```

Important fields:

- apiVersion
- kind
- name
- uid
- controller
- blockOwnerDeletion

---

# Complete Ownership Tree

```text
Deployment
  |
  v
ReplicaSet
  |
  v
Pods
  |
  v
ConfigMaps
  |
  v
Secrets
```

Every dependent resource contains an OwnerReference.

# Garbage Collector Workflow

Deletion process:

```text
Delete Owner
  |
  v
Garbage Collector Detects
  |
  v
Find Dependents
  |
  v
Delete Dependents
  |
  v
Finished
```

Everything happens automatically.

# How Garbage Collector Works Internally

The Garbage Collector watches the API Server.

```text
API Server
  |
  v
Watch Events
  |
  v
Garbage Collector
  |
  v
Build Dependency Graph
  |
  v
Delete Resources
```

It continuously maintains an internal graph of ownership relationships.

---

# Internal Dependency Graph

Example:

```text
Deployment

+--──────── ReplicaSet

|

+--──────── Service

|

+--──────── ConfigMap
```

The Garbage Collector understands these relationships.

---

# Cascading Deletion

The default behavior is **cascading deletion**.

Example:

```text
Delete Deployment
  |
  v
Delete ReplicaSet
  |
  v
Delete Pods
```

The entire ownership tree is removed.

---

# Cascading Deletion Example

Before deletion:

```text
Deployment
  |
  v
ReplicaSet
  |
  v
Pods
```

After deletion:

```text
Nothing Remains
```

This keeps the cluster clean.

---

# Foreground Deletion

In foreground deletion:

```text
Delete Deployment
  |
  v
Wait
  |
  v
Delete Children
  |
  v
Delete Deployment
```

The owner remains until all dependents are gone.

---

# Background Deletion

In background deletion:

```text
Delete Deployment
  |
  v
Deployment Removed
  |
  v
Garbage Collector
  |
  v
Delete Children
```

The owner disappears immediately while the Garbage Collector removes dependents asynchronously.

---

# Orphan Deletion

Sometimes users want to keep child resources.

Example:

```text
Delete Deployment
  |
  v
ReplicaSet Remains
  |
  v
Pods Continue Running
```

This is called **orphaning**.

---

# Orphaning Resources

Workflow:

```text
Delete Owner
  |
  v
Remove OwnerReference
  |
  v
Keep Children
```

The resources become independent.

---

# Why Orphan Resources?

Example:

Administrator wants to investigate:

- Logs
- Containers
- Data
- Current state

Deleting the owner should not always destroy everything.

---

# BlockOwnerDeletion

Another important field:

```yaml
blockOwnerDeletion: true
```

Meaning:

```text
Owner
  |
  v
Cannot Finish Deletion
  |
  v
Until Child Is Gone
```

This ensures dependent resources are handled first.

---

# Relationship with Finalizers

These concepts work together.

Workflow:

```text
Owner Deleted
  |
  v
Garbage Collector
  |
  v
Delete Child
  |
  v
Child Has Finalizer?
  |
  v
Yes
  |
  v
Cleanup
  |
  v
Remove Finalizer
  |
  v
Delete Child
  |
  v
Delete Owner
```

Garbage Collection and Finalizers complement each other.

---

# Adoption

Controllers sometimes adopt existing resources.

Example:

A Pod exists without an owner.

Later,

a ReplicaSet discovers:

```text
Labels Match
  |
  v
Adopt Pod
  |
  v
Add OwnerReference
```

This prevents unnecessary Pod recreation.

---

# Adoption Workflow

```text
Existing Pod
  |
  v
No Owner
  |
  v
ReplicaSet
  |
  v
Labels Match
  |
  v
Add OwnerReference
  |
  v
Now Managed
```

# Cross-Namespace Restrictions

OwnerReferences have namespace rules.

### Namespaced Resource

May own:

```text
Resources
  |
  v
Same Namespace
```

Cannot own:

```text
Resource
  |
  v
Different Namespace
```

---

### Cluster-Scoped Resources

Cluster-scoped resources may own:

- Cluster-scoped resources
- Namespaced resources (where allowed by Kubernetes)

Example:

```text
ClusterResource
  |
  v
Namespace Resource
```

---

# Why Cross-Namespace Restrictions Exist

Imagine:

```text
Namespace A
  |
  v
Owns
  |
  v
Namespace B
```

Deleting Namespace A could unexpectedly remove resources belonging to another tenant.

To avoid this,

Kubernetes restricts cross-namespace ownership.

---

# OwnerReference vs Finalizer

| OwnerReference | Finalizer |
|---------------|-----------|
| Creates ownership | Delays deletion |
| Used by Garbage Collector | Used by Controllers |
| Deletes Kubernetes resources | Cleans external resources |
| Automatic | Application-specific |
| Metadata relationship | Metadata deletion guard |

# Best Practices

✔ Set OwnerReferences immediately after creating managed resources.

✔ Use Controller References correctly.

✔ Let the Garbage Collector delete Kubernetes resources.

✔ Use Finalizers only for external resources.

✔ Avoid manually removing OwnerReferences.

✔ Understand namespace ownership rules.

✔ Test deletion behavior before production deployment.

# Common Misconceptions

### ❌ Misconception 1

OwnerReferences and Finalizers are the same.

**Correct:** OwnerReferences define ownership. Finalizers control deletion timing.

---

### ❌ Misconception 2

The parent stores its children.

**Correct:** Each child stores references to its parent.

---

### ❌ Misconception 3

Garbage Collector deletes cloud resources.

**Correct:** It only deletes Kubernetes resources.

---

### ❌ Misconception 4

Multiple controllers can manage the same resource.

**Correct:** Only one OwnerReference may have `controller: true`.

---

### ❌ Misconception 5

Deleting a Deployment manually deletes Pods.

**Correct:** The Garbage Collector performs cascading deletion based on OwnerReferences.

---

### ❌ Misconception 6

OwnerReferences work across any namespace.

**Correct:** Kubernetes enforces namespace restrictions for ownership relationships.

---

### ❌ Misconception 7

Controllers must manually delete every child resource.

**Correct:** When OwnerReferences are configured correctly, Kubernetes Garbage Collection handles dependent Kubernetes resources automatically.

# Common Interview Questions

### Q1. What is an OwnerReference?

A metadata relationship indicating that one Kubernetes object is owned by another.

---

### Q2. What is the purpose of the Garbage Collector?

To automatically remove Kubernetes resources whose owners have been deleted.

---

### Q3. Why are OwnerReferences stored on child objects?

To avoid maintaining potentially large child lists on parent resources and to improve scalability.

---

### Q4. What is a Controller Reference?

The OwnerReference with `controller: true`, identifying the managing controller for a resource.

---

### Q5. What is cascading deletion?

Automatically deleting dependent resources when the owner is deleted.

---

### Q6. What is `blockOwnerDeletion`?

A field that can prevent owner deletion from completing until dependent resources are handled appropriately.

---

### Q7. What is orphaning?

Deleting the owner while intentionally keeping the dependent resources.

---

### Q8. Can a namespaced resource own resources in another namespace?

No. Kubernetes restricts cross-namespace ownership for namespaced resources.

---

### Q9. How are OwnerReferences different from Finalizers?

OwnerReferences define ownership for Kubernetes resources, while Finalizers delay deletion until cleanup is complete.

---

### Q10. Why is adoption useful?

It allows controllers to take ownership of existing matching resources instead of unnecessarily recreating them.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Child resource not deleted | Missing OwnerReference |
| Resource unexpectedly orphaned | OwnerReference removed or orphan deletion policy used |
| Duplicate managed resources | Controller failed to adopt existing resources |
| Owner deletion blocked | Child resources still exist with `blockOwnerDeletion` or pending finalization |
| Cross-namespace ownership rejected | Invalid OwnerReference across namespaces |
| Garbage Collector not cleaning resources | Incorrect or missing ownership metadata |
