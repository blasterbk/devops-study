# Real-Life Analogy

Think of a CRD like registering a custom building blueprint with the city planning office.

```text
City Blueprint Analogy:

City office (API Server) has standard built-in permits (Pods, Services, Deployments)
Architect submits a new custom building design template (CRD: DatabaseCluster)
City validates the permit template structure (OpenAPI v3 schema)
Once approved, citizens can submit individual construction applications (Custom Resources)
City records the applications in the registry (etcd)
However, city inspectors (API Server) DO NOT build the building!
You need a licensed contractor on-site (Custom Controller) to actually construct it
```

| City Planning Office | Kubernetes CRDs |
| :--- | :--- |
| Custom permit template | CustomResourceDefinition (CRD) |
| Permit validation rules | OpenAPI v3 validation schema |
| Citizen's permit application | Custom Resource instance (`kubectl apply -f cr.yaml`) |
| City records archive | etcd storage |
| Building contractor on site | Custom Controller (reconciles CR state) |

> **Important:** A CRD **only registers the API schema** with `kube-apiserver`. When you create a Custom Resource, the API Server validates the YAML against the OpenAPI schema and persists it into etcd. **Nothing actually runs or happens to create the requested infrastructure until a Custom Controller is running** to watch that resource and execute the desired state!

# Why This Module Matters

Everything in Kubernetes is built using the same pattern.

For example,

```text
Deployment
  |
  v
ReplicaSet Controller
  |
  v
ReplicaSets
  |
  v
Pods
```

or

```text
Job
  |
  v
Job Controller
  |
  v
Pods
```

or

```text
StatefulSet
  |
  v
StatefulSet Controller
  |
  v
Pods
```

These are **not special features hardcoded into Kubernetes**.

They are implemented using the exact same architecture that you will learn in this module.

This means you can build your own Kubernetes-native APIs and controllers that behave just like built-in resources.
