# Module 1.9 — CRDs & Operators

# Chapter 2 — Custom Controllers

> **Goal:** Understand how Kubernetes Controllers continuously watch the cluster, compare the desired state with the actual state, and automatically reconcile any differences. By the end of this chapter, you'll understand the architecture behind every Kubernetes controller—from the Deployment Controller to production Operators like cert-manager, Prometheus Operator, Crossplane, and Argo CD.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. The fundamental control loop: Watch, Informer, WorkQueue, Reconcile
> 2. Shared Informer caching: reducing API Server load through local IndexedStores
> 3. WorkQueue mechanics: rate limiting, deduplication, and exponential backoff
> 4. Event handlers (Add/Update/Delete) and enqueueing resource keys
> 5. Desired State (spec) vs Observed State (status) reconciliation
> 6. Handling transient failures vs non-retryable configuration errors
> 7. Leader election for high availability without split-brain reconciliation
> 8. Production Operator design patterns across cert-manager, Crossplane, and Argo CD

# Real-Life Analogy

Think of a Custom Controller like a specialized building maintenance manager.

```text
Building Maintenance Manager Analogy:

Tenant submits a maintenance ticket: "Set up a high-security server room" (Custom Resource)
Ticket manager places the request into an urgent task tray (WorkQueue)
Maintenance manager (Reconciler) inspects the actual room:
  - Is air conditioning running? No -> turn it on (Create Child Resource: Deployment)
  - Are security cameras installed? No -> install them (Create Service / Secret)
  - Is access card active? Yes -> do nothing (idempotency check)
Manager stamps the ticket as "Active & Healthy" (Update Status Subresource)
Manager checks the room periodically to ensure everything remains operational (Drift detection)
```

| Building Maintenance | Custom Controller |
| :--- | :--- |
| Work order ticket | Custom Resource instance |
| Task tray | Rate-limiting WorkQueue |
| Maintenance manager | Reconcile loop (`Reconcile(ctx, req)`) |
| Inspecting room hardware | Cache / Indexer lookup for actual state |
| Installing missing equipment | Creating child resources (`k8sClient.Create()`) |
| Status stamp on ticket | Status Subresource update (`k8sClient.Status().Update()`) |
| Periodic room inspection | Informer periodic resync & drift correction |

> **Important:** Custom controllers should **never poll or make direct `GET` requests to the API Server** during normal reconciliation. Instead, always read through the **Informer Cache (Indexer)**. Direct API calls bypass the local cache and will overload `kube-apiserver` and etcd when reconciling large fleets of resources. Only write operations (`Create`, `Update`, `Patch`, `Delete`) should hit the API server directly.

# Where This Chapter Fits

In Chapter 1, we learned that a CRD only defines a **new API object**.

For example:

```text
DatabaseCluster
```

After creating the CRD, Kubernetes can now store objects like:

```yaml
apiVersion: database.example.com/v1
kind: DatabaseCluster
metadata:
  name: production-db
```

But...

Will Kubernetes automatically create a database?

**No.**

Why?

Because a CRD only extends the API.

It does **not** contain any business logic.

That responsibility belongs to a **Controller**.

# What is a Controller?

A Controller is a control loop.

It continuously performs three actions:

```text
Observe
  |
  v
Compare
  |
  v
Act
```

This repeats forever.

Unlike traditional applications,

Controllers **never finish**.

They run continuously for the lifetime of the cluster.

# Informers

A controller does **not** constantly query the API Server.

That would overwhelm the cluster.

Instead,

it uses an Informer.

```text
API Server
  |
  v
Watch
  |
  v
Informer
  |
  v
Local Cache
```

The Informer keeps a local copy of resources.

---

# Why Informers?

Without Informers:

```text
Controller
  |
  v
API Call
  |
  v
API Call
  |
  v
API Call
  |
  v
API Call
```

Thousands of Controllers would overload the API Server.

Instead:

```text
One Watch
  |
  v
Local Cache
  |
  v
Read Cache
```

This dramatically reduces API traffic.

---

# Watches

The Informer uses a Watch.

Workflow:

```text
API Server
  |
  v
Watch Stream
  |
  v
Informer
  |
  v
Cache Updated
```

Whenever an object changes,

the Informer immediately knows.

# Event Handlers

The Informer itself does not perform business logic.

```text
  v
```

# Why Event Handlers?

Suppose:

```text
100 Objects Updated
```

The Informer immediately receives all updates.

Should it reconcile immediately?

No.

Instead:

```text
Event
  |
  v
Queue
```

This decouples event processing from reconciliation.

# WorkQueue

The WorkQueue stores reconciliation requests.

Architecture:

```text
Event
  |
  v
Queue
  |
  v
Worker
  |
  v
Reconcile()
```

The Queue smooths bursts of activity.

---

# Why WorkQueues?

Imagine:

```text
1,000 Objects Updated
```

Without a Queue:

```text
1,000 Concurrent Reconciles
```

This could overwhelm the controller.

Instead:

```text
Queue
  |
  v
Controlled Processing
```

---

# Queue Deduplication

Suppose one object changes many times.

```text
Object A
  |
  v
Update
  |
  v
Update
  |
  v
Update
```

The WorkQueue typically keeps one pending key for that object until it is processed, avoiding unnecessary duplicate reconciliations.

This is one reason controllers remain efficient during frequent updates.

---

# Worker Threads

Controllers usually have multiple workers.

```text
Queue
  |
  v
Worker 1

Worker 2

Worker 3

Worker 4
```

Each worker processes reconciliation requests independently.

---

# Reconcile Loop

The heart of every controller.

```text
Queue
  |
  v
Reconcile()
  |
  v
Observe
  |
  v
Compare
  |
  v
Act
  |
  v
Return
```

Everything eventually reaches the Reconcile function.

---

# Reconcile Inputs

The Reconcile function does **not** receive the full object.

Instead,

it receives:

```text
Namespace

+

Name
```

Example:

```text
default
  |
  v
production-db
```

The controller then retrieves the latest object from the cache or API Server.

---

# Why Only Namespace/Name?

Suppose:

Object changed while waiting in queue.

If the queue contained the old object,

it would already be outdated.

Instead:

```text
Queue
  |
  v
Object Key
  |
  v
Fetch Latest State
```

The controller always works with current data.

---

Not every reconciliation succeeds.

```text

  |
  v
4 Seconds
  |

  |
```

# Leader Election

Large clusters often run multiple controller replicas.

Example:

```text
Controller A

Controller B

Controller C
```

Should all three reconcile the same object?

No.

One becomes the leader.

---

# Leader Election Workflow

```text
Multiple Controllers
  |
  v
Leader Election
  |
  v
Leader
  |
  v
Reconcile
  |
  v
Followers Stand By
```

If the leader fails,

another replica becomes leader.

---

# Controller Scaling

Controllers scale by increasing worker threads or controller replicas.

Example:

```text

  |
  v
10 Workers
  |
  v
Parallel Reconciliation
```

Leader election ensures only one active controller instance performs reconciliation for a given controller deployment.

# Production Best Practices

✔ Keep reconciliation idempotent.

✔ Read from the Informer cache whenever possible.

✔ Keep Reconcile() fast and deterministic.

✔ Update the Status subresource instead of modifying Spec.

✔ Handle retries gracefully.

✔ Use leader election for high availability.

✔ Process only object keys in the WorkQueue.

✔ Treat every reconciliation as if it might be retried.

# Common Misconceptions

### ❌ Misconception 1

A CRD automatically creates resources.

**Correct:** A CRD only extends the API. A Controller performs the automation.

---

### ❌ Misconception 2

Controllers continuously poll the API Server.

**Correct:** Controllers use Watches and Informers to receive event-driven updates.

---

### ❌ Misconception 3

The queue stores full Kubernetes objects.

**Correct:** The WorkQueue stores object keys (namespace/name), and the latest object is fetched during reconciliation.

---

### ❌ Misconception 4

Reconcile() runs only once.

**Correct:** Reconcile() may execute many times for the same object throughout its lifecycle.

---

### ❌ Misconception 5

Controllers modify the Spec.

**Correct:** Users own the Spec. Controllers typically modify cluster resources and update the Status.

---

### ❌ Misconception 6

Every event results in immediate reconciliation.

**Correct:** Events are placed into a WorkQueue and processed by workers.

---

### ❌ Misconception 7

Running multiple controller replicas causes duplicate work.

**Correct:** Leader election ensures only one replica actively reconciles at a time (for the same controller deployment).

# Common Interview Questions

### Q1. Why does Kubernetes need Controllers?

To continuously reconcile the actual cluster state with the desired state defined by users.

---

### Q2. Why isn't a CRD enough?

A CRD defines a new API resource, but it contains no automation logic.

---

### Q3. Why do Controllers use Informers?

To maintain a local cache and avoid repeatedly querying the API Server.

---

### Q4. Why use a WorkQueue?

To buffer events, control processing rate, and avoid excessive reconciliation.

---

### Q5. What does Reconcile() receive?

Typically a `NamespacedName` (namespace and object name), not the full object.

---

### Q6. Why compare desired and actual state?

To determine what actions are required to bring the cluster into the requested state.

---

### Q7. Why are retries necessary?

Because transient failures are common in distributed systems.

---

### Q8. Why use leader election?

To ensure only one controller replica actively reconciles resources while providing high availability.

---

### Q9. Why should reconciliation be idempotent?

Because the same object may be reconciled multiple times, and repeating the operation should not produce incorrect results.

---

### Q10. What is the typical controller architecture?

Watch → Informer → Cache → Event Handler → WorkQueue → Workers → Reconcile → Status Update.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| CR created but nothing happens | Controller not running or not watching the CR |
| Reconcile never called | Informer/watch not configured correctly |
| Endless reconciliation | Non-idempotent logic or constantly changing resources |
| Status never updates | Status subresource missing or update failing |
| Duplicate resource creation | Reconcile logic not checking existing resources |
| Controller becomes inactive | Leader election issue or controller crash |
| High API Server load | Controller bypassing Informer cache with unnecessary API reads |
| Large reconciliation delays | Worker count too low or queue backlog too large |
