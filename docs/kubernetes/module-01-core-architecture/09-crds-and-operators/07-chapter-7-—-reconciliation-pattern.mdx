# Module 1.9 — CRDs & Operators

# Chapter 7 — Reconciliation Pattern

> **Goal:** Understand the **Reconciliation Pattern**, the core design principle behind every Kubernetes Controller and Operator. By the end of this chapter, you'll understand how Kubernetes continuously observes the cluster, detects drift, corrects differences, handles failures safely, and eventually converges the cluster to the user's desired state.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. The Observe–Compare–Act control loop: level-triggered reconciliation
> 2. Desired State (spec) vs Actual Observed State (status & cluster resources)
> 3. Idempotency: why Reconcile() must safely produce identical results when repeated
> 4. Drift detection: automatically repairing external or manual cluster state divergence
> 5. Requeue strategies: RequeueAfter, RequeueWithError, and rate-limited backoff
> 6. Event-driven triggers vs periodic full resync sweeps
> 7. Communicating state via standardized Status Conditions and observedGeneration
> 8. Complete production reconciliation workflow from API event to convergence
> ```

# Real-Life Analogy

Think of the Reconciliation Pattern like an autonomous vehicle's cruise control system.

```text
Cruise Control Analogy:

Driver sets target speed: 65 MPH (Desired State: `spec`)
Car radar & speedometer measure current speed: 58 MPH (Observed State: `status`)
Cruise computer runs the reconcile loop:
  - Phase 1 (Observe): Read current speed from speedometer (58 MPH)
  - Phase 2 (Compare): Target (65) != Current (58) -> Delta = +7 MPH
  - Phase 3 (Act): Apply throttle smoothly to accelerate
Computer repeats this check 20 times per second
When speed reaches 65 MPH -> delta is 0 -> computer maintains throttle without side effects (Idempotent)
If a gust of wind slows car to 62 MPH -> computer detects drift and corrects immediately
```

| Cruise Control | Reconciliation Pattern |
| :--- | :--- |
| Target speed setting (65 MPH) | Desired State (`spec` definition) |
| Speedometer reading | Observed State (`status` / cluster cache) |
| Phase 1: Read speedometer | **Observe** phase (read CR and child resources) |
| Phase 2: Compute speed delta | **Compare** phase (compute diff between spec and actual) |
| Phase 3: Adjust throttle | **Act** phase (Create/Update/Delete child resources) |
| Steady speed (no adjustment needed) | Idempotent convergence (zero operations needed) |
| Wind gust slowing down car | Cluster drift (manual edit, node crash, pod kill) |

> **Important:** Kubernetes controllers are **level-triggered, not edge-triggered**. Your `Reconcile()` function must never assume it was called because of a single specific event, nor that events arrive in order. Instead, every execution of `Reconcile()` must observe the **entire current state**, compare it against the desired state in `spec`, and perform only the necessary idempotent mutations to converge the cluster.

# What is Reconciliation?

Reconciliation is the process of continuously making the **actual state** of the cluster match the **desired state**.

It is not a one-time operation.

It is an infinite control loop.

```text
Observe
  |
  v
Compare
  |
  v
Act
  |
  v
Repeat Forever
```

---

# Why Kubernetes Uses Reconciliation

Imagine Kubernetes without reconciliation.

User creates:

```yaml
replicas: 5
```

Controller creates five Pods.

Done.

Now suppose:

```text
Node Crash
  |
  v
2 Pods Lost
```

Without reconciliation:

```text
Desired = 5

Actual = 3

Nothing Happens
```

The application stays degraded forever.

---

# Kubernetes Solution

Controllers continuously verify cluster state.

```text
Desired = 5
  |
  v
Observe
  |
  v
Actual = 3
  |
  v
Difference Found
  |
  v
Create 2 Pods
  |
  v
Desired = Actual
```

This continuous correction is reconciliation.

---

# Control Loop

Every controller runs an infinite control loop.

```text
while(true)
  |
  v
Observe
  |
  v
Compare
  |
  v
Act
  |
  v
Sleep / Wait
  |
  v
Repeat
```

Unlike traditional applications,

Controllers never "finish."

# Observe–Compare–Act Pattern

Every reconciliation follows exactly three phases.

```text
Observe
  |
  v
Compare
  |
  v
Act
```

Everything else is an implementation detail.

---

# Phase 1 — Observe

The controller gathers information.

Sources include:

- Custom Resource
- Pods
- StatefulSets
- Services
- Secrets
- ConfigMaps
- Nodes

Example:

```text
DatabaseCluster
  |
  v
Read Spec
  |
  v
Read StatefulSet
  |
  v
Read Pods
  |
  v
Read Status
```

The controller builds a complete picture of the cluster.

---

# Phase 2 — Compare

Now the controller asks:

```text
Desired State

==

Actual State?
```

Possible outcomes:

```text
Equal
  |
  v
Nothing To Do
```

or

```text
Different
  |
  v
Need Changes
```

---

# Phase 3 — Act

If differences exist:

```text
Create

Update

Delete

Patch
```

resources until reality matches the specification.

---

# Complete Pattern

```text
Observe
  |
  v
Compare
  |
  v
Act
  |
  v
Update Status
  |
  v
Return
```

---

# Desired State

Desired state is what the user requested.

Usually stored in:

```yaml
spec:
```

Example:

```yaml
spec:
  replicas: 5
```

The controller must never assume this state already exists.

---

# Actual State

Actual state represents reality inside the cluster.

Example:

```text
Pods Running
  |
  v
3
```

Other examples:

- Ready replicas
- Existing Services
- PVCs
- Secrets
- Node availability

---

# Desired vs Actual

Example:

Desired:

```text
5 Pods
```

Actual:

```text
3 Pods
```

Difference:

```text
2 Pods Missing
```

Controller action:

```text
Create 2 Pods
```

---

# Another Example

Desired:

```text
Database Version = 16
```

Actual:

```text
Database Version = 15
```

Controller:

```text
Rolling Upgrade
```

---

# Reconciliation is Continuous

Even after success,

the controller does not stop.

```text
Desired = Actual
  |
  v
Wait
  |
  v
Watch Event
  |
  v
Observe Again
```

Clusters constantly change.

---

# Idempotency

One of the most important principles.

A reconciliation should produce the same result no matter how many times it runs.

Example:

Desired:

```text
Service Exists
```

Controller runs:

```text
100 Times
```

Result:

```text
Exactly One Service
```

Not 100 Services.

---

# Why Idempotency Matters

Controllers may reconcile:

- Multiple times
- Duplicate events
- Retries
- Restarts
- Leadership changes

Every reconciliation must remain safe.

---

# Non-Idempotent Example

Bad logic:

```text
Always Create Service
```

Result:

```text
Duplicate Resource Errors
```

or repeated failures.

---

# Idempotent Example

Correct logic:

```text
Service Exists?
  |
  v
Yes
  |
  v
Update If Needed
  |
  v
Done
```

Existing resources are reused.

---

# Drift Detection

Clusters constantly drift away from the desired state.

Example:

Administrator deletes:

```text
Service
```

Controller observes:

```text
Desired
  |
  v
Service Should Exist

Actual
  |
  v
Missing
```

Controller recreates it.

---

# Another Drift Example

Someone manually edits:

```text
Replicas
  |
  v
10
```

Desired:

```text
Replicas = 5
```

Controller restores:

```text
Replicas = 5
```

---

# Self-Healing

Drift detection enables self-healing.

```text
Unexpected Change
  |
  v
Detect Drift
  |
  v
Reconcile
  |
  v
Restore Desired State
```

This is one of Kubernetes' defining features.

# Requeue Strategy

Not every reconciliation completes immediately.

Sometimes more work is required.

The controller requests another reconciliation.

```text
Reconcile()
  |
  v
Need More Work
  |
  v
Requeue
```

---

# Why Requeue?

Example:

```text
Create StatefulSet
  |
  v
Pods Not Ready
  |
  v
Wait
  |
  v
Check Again
```

The controller needs another reconciliation after some time.

---

# Types of Requeue

Immediate:

```text
Return
  |
  v
Requeue Immediately
```

Useful after creating dependent resources.

---

Delayed:

```text
Return
  |
  v
Requeue After 30 Seconds
```

Useful for polling external systems.

---

No Requeue:

```text
Return
  |
  v
Wait For Event
```

Preferred whenever possible.

# Observed Generation

A commonly used Status field:

```yaml

  observedGeneration: 7
```

> "The controller has processed generation 7."


# Error Handling

Failures are expected.

Example:

```text
Create Service
  |
  v
API Timeout
```

Should reconciliation stop forever?

No.

The controller returns an error.

---

# Error Flow

```text
Reconcile
  |
  v
Error
  |
  v
WorkQueue
  |
  v
Retry
```

Temporary failures are retried automatically.

---

# Transient vs Permanent Errors

Transient:

```text
Network Timeout
  |
  v
Retry
```

Examples:

- API timeout
- Temporary network issue
- Rate limiting

---

Permanent:

```text
Invalid Configuration
  |
  v
Update Status
  |
  v
No Automatic Fix
```

Examples:

- Invalid CR specification
- Unsupported version
- Missing required configuration

---

# Exponential Backoff

Repeated failures should not overwhelm dependencies.

Retry pattern:

```text
1 Second
  |
  v
2 Seconds
  |
  v
4 Seconds
  |
  v
8 Seconds
  |
  v
16 Seconds
  |
  v
32 Seconds
```

This reduces unnecessary load.

---

# Why Backoff Matters

Without backoff:

```text
Controller
  |
  v
1000 Requests/Second
  |
  v
Failed API
```

This can create cascading failures.

Backoff protects both the controller and dependent systems.

# Long-Running Operations

Some actions take minutes.

Examples:

- Database backup
- Cloud provisioning

# Production Best Practices

✔ Keep reconciliation idempotent.

✔ Read the latest object before making decisions.

✔ Keep `Reconcile()` short and deterministic.

✔ Update Status after meaningful changes.

✔ Handle deletion before normal reconciliation.

✔ Requeue only when necessary.

✔ Distinguish transient and permanent failures.

✔ Never assume a previous reconciliation succeeded.

✔ Design for repeated execution.

✔ Treat reconciliation as a convergence process, not a workflow engine.

# Common Misconceptions

### ❌ Misconception 1

Reconcile() runs only once.

**Correct:** It may run hundreds or thousands of times for the same object.

---

### ❌ Misconception 2

Reconciliation creates resources only.

**Correct:** It may create, update, delete, patch, or simply verify resources.

---

### ❌ Misconception 3

Controllers always fix everything in one reconciliation.

**Correct:** Complex operations often require multiple reconciliation cycles.

---

### ❌ Misconception 4

Every reconciliation changes the cluster.

**Correct:** If desired and actual state already match, reconciliation should make no changes.

---

### ❌ Misconception 5

Duplicate reconciliation is a bug.

**Correct:** Multiple reconciliations are expected and are fundamental to Kubernetes.

---

### ❌ Misconception 6

Requeue should always be used.

**Correct:** Most controllers rely primarily on event-driven reconciliation and requeue only when necessary.

---

### ❌ Misconception 7

Returning an error means the controller has failed permanently.

**Correct:** Errors usually trigger retries with exponential backoff.

---

### ❌ Misconception 8

Status and Spec are the same.

**Correct:** Spec describes the desired state; Status reports the observed state.

# Common Interview Questions

### Q1. What is the Reconciliation Pattern?

A continuous control loop that makes the actual cluster state converge to the desired state.

---

### Q2. What are the three phases of reconciliation?

Observe → Compare → Act.

---

### Q3. What is the difference between desired state and actual state?

Desired state comes from the resource specification, while actual state reflects the current cluster.

---

### Q4. Why must reconciliation be idempotent?

Because reconciliation can execute repeatedly due to events, retries, and controller restarts.

---

### Q5. What is drift detection?

Detecting differences between the desired configuration and the current cluster state.

---

### Q6. When should a controller requeue?

When additional work is required or when waiting for asynchronous operations to complete.

---

### Q7. What is the difference between event-driven and periodic reconciliation?

Event-driven reconciliation reacts to Kubernetes events, while periodic reconciliation verifies state at scheduled intervals, often for external systems.

---

### Q8. Why are Status Conditions important?

They communicate the current health and progress of reconciliation to users and other controllers.

---

### Q9. What is `observedGeneration`?

A Status field indicating the latest resource generation processed by the controller.

---

### Q10. Why is exponential backoff used?

To prevent excessive retries from overwhelming Kubernetes or external dependencies during failures.

---

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Endless reconciliation | Non-idempotent logic or constantly changing resources |
| Status never changes | Status updates missing or failing |
| Resources repeatedly recreated | Drift caused by manual modifications or incorrect comparison logic |
| Controller loops continuously | Always returning requeue unnecessarily |
| External resources never converge | Missing periodic reconciliation or failed external checks |
| Slow recovery after failures | Excessive backoff or repeated transient errors |
| Duplicate objects | Controller creating resources without checking existing state |
| Spec changes ignored | Controller not observing the latest generation |
