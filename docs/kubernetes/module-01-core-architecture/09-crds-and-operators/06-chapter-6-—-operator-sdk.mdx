# Module 1.9 — CRDs & Operators

# Chapter 6 — Operator SDK

> **Goal:** Learn how the **Operator SDK** simplifies the development, packaging, distribution, and lifecycle management of Kubernetes Operators. By the end of this chapter, you'll understand the Operator SDK architecture, different Operator types, Operator Lifecycle Manager (OLM), packaging, deployment, upgrades, and production best practices.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. Operator SDK ecosystem and relationship with Kubebuilder / controller-runtime
> 2. Operator types: Go-based (full control), Helm-based (declarative), Ansible-based (automation)
> 3. Operator Capability Model: Level 1 (Basic Install) to Level 5 (Auto-Pilot)
> 4. Operator Lifecycle Manager (OLM): Catalogs, Subscriptions, InstallPlans, CSVs
> 5. ClusterServiceVersion (CSV) packaging for OperatorHub.io publishing
> 6. Automated rolling upgrades and channel-based update paths (stable, beta)
> 7. Scorecard testing tool for validating production readiness
> 8. Production deployment workflows using Helm, OLM, or direct manifests
> ```

# Real-Life Analogy

Think of Operator SDK like a standardized global franchise licensing and distribution system.

```text
Franchise Distribution Analogy:

You designed a proprietary burger business model (Custom Controller application)
Kubebuilder helps you construct the physical kitchen mechanics
Operator SDK packages the entire business into a turnkey franchise box (OLM Bundle)
Store directory (OperatorHub.io / CatalogSource) lists available franchises
Customer orders franchise with one click (Subscription: channel 'stable')
Automated delivery truck installs and wires the franchise (InstallPlan & CSV)
When you release a new recipe, OLM automatically rolls out store upgrades across all locations
```

| Franchise System | Operator SDK & OLM |
| :--- | :--- |
| Franchise business model | Kubernetes Operator |
| Kitchen construction | Kubebuilder / Go scaffolding |
| Turnkey franchise box | OLM Bundle (`bundle/` with CSV manifest) |
| Global franchise catalog | OperatorHub.io / `CatalogSource` |
| Franchise purchase order | `Subscription` resource |
| Automated installation crew | `InstallPlan` & `ClusterServiceVersion` (CSV) |
| Central recipe update rollout | Automated channel upgrades (`channel: stable`) |

> **Important:** While Kubebuilder focuses strictly on **Go-based controller development**, Operator SDK builds upon Kubebuilder and adds **multi-language engines (Helm & Ansible)** as well as first-class integration with **Operator Lifecycle Manager (OLM)**. If you are building an enterprise operator intended to be published to OperatorHub.io or OpenShift, Operator SDK provides the CSV packaging, bundle validation, and scorecard testing tools out of the box.

# What is Operator SDK?

Operator SDK is an open-source framework for building, testing, packaging, and distributing Kubernetes Operators.

It extends the Operator development workflow by providing:

- Project scaffolding
- Testing
- Packaging
- Bundle generation
- OLM integration
- Operator distribution

Unlike Kubebuilder,

Operator SDK focuses not only on development but also on the **Operator lifecycle**.

---

```text
               Operator SDK CLI

  v
          Generates Project Structure
  |
  v
            controller-runtime
  |
  v
              Kubernetes Operator
  |
  v
          OLM / Kubernetes Cluster
```

---

# Operator SDK vs Kubebuilder

This is one of the most common interview questions.

| Kubebuilder | Operator SDK |
|-------------|--------------|
| Official Kubernetes scaffolding framework | Framework built on top of Kubebuilder and controller-runtime |
| Focuses on API and Controller generation | Focuses on Operator development and lifecycle |
| Generates project boilerplate | Adds packaging, bundles, OLM support, testing |
| Primarily developer-focused | Developer + Operations focused |

Today,

Go-based Operators created using Operator SDK typically rely on the same `controller-runtime` library used by Kubebuilder.

# Go Operators

The most powerful Operator type.

Architecture:

```text

  |
  v

  v

```

- External API integration
- Advanced workflows
- Maximum performance

Suitable for:

- Database Operators
- Cloud Infrastructure Operators
- Networking Operators
- Storage Operators

# Helm Operators

Instead of writing Go code,

the Operator manages Helm charts.

Architecture:

```text

  |
  v
Helm Chart
  |
  v
Rendered Templates
  |
  v
Kubernetes Resources
```

The reconciliation process applies Helm releases based on the Custom Resource.

---

# Advantages of Helm Operators

- Minimal Go programming
- Reuse existing Helm charts
- Faster Operator development
- Easier application packaging

Limitations:

- Less flexible than Go Operators
- Complex business logic is harder to implement

# What is OLM?

OLM stands for **Operator Lifecycle Manager**.

It is a Kubernetes application that manages Operators throughout their lifecycle.

Responsibilities include:

# Production Best Practices

✔ Prefer Go Operators for complex business logic.

✔ Use Helm Operators when a mature Helm chart already exists.

✔ Use Ansible Operators if infrastructure automation is already Ansible-based.

✔ Keep bundle metadata accurate.

✔ Version CRDs carefully.

✔ Test upgrades before production rollout.

✔ Maintain backward compatibility whenever possible.

✔ Use semantic versioning.

✔ Package Operators for OLM deployment.

✔ Validate upgrade paths between releases.

# Common Misconceptions

### ❌ Misconception 1

Operator SDK replaces Kubebuilder.

**Correct:** Modern Go Operators created with Operator SDK build upon the same controller-runtime ecosystem and complement Kubebuilder's scaffolding.

---

### ❌ Misconception 2

Operator SDK is only for Go Operators.

**Correct:** It also supports Helm and Ansible Operators.

---

### ❌ Misconception 3

OLM is required to run an Operator.

**Correct:** Operators can be deployed directly using Kubernetes manifests. OLM is optional but provides lifecycle management.

---

### ❌ Misconception 4

Operator Bundles contain container images.

**Correct:** Bundles contain metadata and manifests that reference Operator images.

---

### ❌ Misconception 5

Helm Operators execute reconciliation without a controller.

**Correct:** A controller still performs reconciliation; it uses Helm to manage Kubernetes resources.

---

### ❌ Misconception 6

Upgrading an Operator automatically upgrades Custom Resources safely.

**Correct:** Operators must explicitly handle API compatibility and reconciliation across versions.

---

### ❌ Misconception 7

Operator SDK changes how reconciliation works.

**Correct:** The reconciliation pattern remains the same regardless of whether the Operator is built with Kubebuilder or Operator SDK.

# Common Interview Questions

### Q1. What is Operator SDK?

A framework for building, testing, packaging, and distributing Kubernetes Operators.

---

### Q2. How is Operator SDK different from Kubebuilder?

Kubebuilder focuses on scaffolding Kubernetes APIs and Controllers, while Operator SDK adds packaging, bundle generation, and OLM integration.

---

### Q3. What Operator types does Operator SDK support?

Go Operators, Helm Operators, and Ansible Operators.

---

### Q4. What is an Operator Bundle?

A package containing CRDs, metadata, RBAC, CSV, and other manifests required for Operator installation.

---

### Q5. What is OLM?

Operator Lifecycle Manager, a Kubernetes application that installs, upgrades, and manages Operators.

---

### Q6. What is a ClusterServiceVersion (CSV)?

An OLM resource describing an Operator's version, permissions, CRDs, install strategy, and upgrade metadata.

---

### Q7. What is a CatalogSource?

A repository of Operator bundles that OLM can discover and install.

---

### Q8. Is OLM mandatory?

No. Operators can be deployed manually without OLM.

---

### Q9. When should you choose a Helm Operator?

When the application already has a mature Helm chart and minimal custom reconciliation logic is required.

---

### Q10. Why is versioning important for Operators?

Because Operators, CRDs, and Custom Resources evolve independently and must remain compatible during upgrades.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Operator installs but CRDs missing | Bundle or CSV incomplete |
| OLM cannot install Operator | Invalid InstallPlan, CSV, or dependencies |
| Upgrade fails | Incompatible CRD or Operator version |
| Operator lacks permissions | RBAC missing from bundle |
| Subscription not upgrading | CatalogSource not updated or InstallPlan not approved |
| Helm Operator not reconciling | Helm chart rendering or values issue |
| Go Operator starts but watches nothing | Controller not registered with Manager |
