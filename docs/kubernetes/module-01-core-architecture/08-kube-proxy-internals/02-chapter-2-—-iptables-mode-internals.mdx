# Module 1.8 — kube-proxy Internals

# Chapter 2 — iptables Mode Internals

> **Goal:** Understand how Kubernetes implements Services using **iptables**. Learn how **Linux Netfilter**, **NAT tables**, **Kubernetes iptables chains**, **DNAT**, **SNAT**, and **Hairpin NAT** work together to transparently forward traffic from a Service Virtual IP to backend Pods.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. Linux Netfilter architecture and netfilter packet traversal hooks
> 2. How iptables organizes rules into tables (nat, filter, mangle) and chains
> 3. Kubernetes custom iptables chains: KUBE-SERVICES, KUBE-SVC-*, KUBE-SEP-*
> 4. Destination NAT (DNAT): translating ClusterIP to selected Pod IP
> 5. Source NAT (SNAT / MASQUERADE): handling cross-node and external traffic
> 6. Random load balancing across Pods using iptables statistic module
> 7. Hairpin NAT: allowing a Pod to communicate with its own Service
> 8. Performance bottlenecks: why O(n) rule evaluation degrades at scale
> ```

# Real-Life Analogy

Think of iptables mode like a customs officer with a rulebook.

```text
Customs Officer Analogy:

Traveler (packet) arrives at checkpoint (Node network interface)
Customs officer (Netfilter) flips through a massive rulebook line-by-line
Rule 1: If going to VIP A -> reroute to Booth 101 with 33% chance
Rule 2: If going to VIP A -> reroute to Booth 102 with 50% chance
Rule 3: If going to VIP A -> reroute to Booth 103
Officer stamps traveler and changes destination on ticket (DNAT)
When the rulebook has 50,000 rules, checking every traveler becomes very slow
```

| Customs Officer | iptables Mode |
| :--- | :--- |
| Traveler | Network packet |
| Checkpoint | Netfilter hooks (PREROUTING, OUTPUT, POSTROUTING) |
| Rulebook | iptables NAT table chains |
| Checking line-by-line | Sequential rule evaluation ($O(n)$ complexity) |
| Changing destination ticket | DNAT (`KUBE-SEP` chain rewrites destination IP/port) |
| Return stamp | conntrack state entry + SNAT/MASQUERADE |

> **Important:** iptables rules are evaluated **linearly per packet**. In large clusters with thousands of Services and tens of thousands of Endpoints, the kernel must traverse sequential rules until a match is found. This $O(n)$ complexity causes significant CPU overhead and packet latency, which led to the creation of IPVS mode and modern eBPF replacements.

# The Problem

Suppose a Service exists.

```text
Service

10.96.0.15
```

Pods:

```text
Pod A

10.244.1.5

────────────

Pod B

10.244.2.8
```

No application is listening on:

```text
10.96.0.15
```

Yet traffic reaches the Pods.

How?

---

# The Answer

kube-proxy creates Linux **iptables rules**.

Packets destined for:

```text
10.96.0.15
```

are rewritten to:

```text
10.244.1.5

or

10.244.2.8
```

This rewrite occurs entirely inside the Linux kernel.

# What is Netfilter?

Before understanding iptables,


# Hairpin NAT

Hairpin NAT is one of the most confusing Kubernetes networking topics.

Suppose:

```text
Pod A
```

calls:

```text
Its Own Service
```

Flow:

```text
Pod A
  |
  v
Service VIP
  |
  v
Pod A
```

Without special handling,

the packet can fail.

---

# Why?

Initially:

```text
Source

Pod A

Destination

Service VIP
```

After DNAT:

```text
Source

Pod A

Destination

Pod A
```

The packet leaves and returns to the same Pod.

Without Hairpin NAT,

Linux networking may reject or mishandle this path.

---

# Hairpin NAT Solution

The kernel performs additional NAT so the connection behaves correctly.

Conceptually:

```text
Pod
  |
  v
Service
  |
  v
DNAT
  |
  v
SNAT
  |
  v
Same Pod
```

This allows Pods to access themselves through their own Service IP.

# Performance Characteristics

iptables performs well for small and medium clusters.

However,

each packet may traverse rule chains until a match is found.

As clusters grow:

```text
More Services
  |
  v
More Rules
  |
  v
Longer Rule Chains
```

Rule synchronization also becomes more expensive.

---

# Advantages

✔ Mature Linux technology

✔ Stable

✔ Kernel-based forwarding

✔ Widely supported

✔ Easy to troubleshoot

---

# Limitations

✖ Large rule sets

✖ Rule updates can become expensive

✖ Sequential rule traversal

✖ Less scalable than modern eBPF dataplanes for very large environments

# Common Misconceptions

### ❌ Misconception 1

iptables forwards packets itself.

**Correct:** iptables is a configuration tool. Netfilter inside the Linux kernel processes packets.

---

### ❌ Misconception 2

The Service IP belongs to a network interface.

**Correct:** A ClusterIP is a virtual IP implemented through packet translation.

---

### ❌ Misconception 3

DNAT changes the source IP.

**Correct:** DNAT changes the destination IP.

---

### ❌ Misconception 4

SNAT changes the destination IP.

**Correct:** SNAT changes the source IP.

---

### ❌ Misconception 5

Hairpin NAT is required for every Service request.

**Correct:** It is primarily required when a Pod accesses itself through its own Service.

---

### ❌ Misconception 6

kube-proxy executes iptables rules.

**Correct:** kube-proxy generates the rules. Netfilter executes them.

---

### ❌ Misconception 7

Each Service has one iptables rule.

**Correct:** A Service is typically represented by multiple chains and rules (for Service matching, endpoint selection, masquerading, and destination translation).

# Common Interview Questions

### Q1. What is Netfilter?

The Linux kernel framework responsible for packet filtering, NAT, and packet manipulation.

---

### Q2. What is iptables?

A userspace tool used to configure Netfilter rules.

---

### Q3. What is the purpose of the NAT table?

To perform address translation such as DNAT and SNAT.

---

### Q4. What happens in PREROUTING?

Destination NAT can occur before the kernel makes its routing decision.

---

### Q5. What is the role of KUBE-SERVICES?

It matches incoming traffic for Kubernetes Services and forwards it to the appropriate Service-specific chain.

---

### Q6. What is the role of KUBE-SVC?

It selects one of the available backend endpoints for a Service.

---

### Q7. What is the role of KUBE-SEP?

It performs endpoint-specific processing, including the destination translation to a Pod IP.

---

### Q8. What is Hairpin NAT?

A mechanism that allows a Pod to successfully access itself through its own Service IP.

---

### Q9. Why does kube-proxy use `iptables-restore`?

To update many rules atomically and more efficiently than issuing individual commands.

---

### Q10. Why does iptables become less efficient in very large clusters?

Because large rule sets increase rule synchronization costs and packet matching may require traversing longer chains.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| ClusterIP unreachable | Missing or incorrect iptables rules, networking issue, or kube-proxy failure |
| Pod cannot access its own Service | Hairpin NAT configuration issue |
| Traffic reaches wrong backend | Stale EndpointSlice or outdated iptables rules |
| New Pods receive no traffic | kube-proxy has not yet synchronized updated rules |
| High packet latency | Very large iptables rule sets or underlying network bottlenecks |
| Return traffic fails | SNAT/masquerading issue or routing problem |
