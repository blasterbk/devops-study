# Real-Life Analogy

Think of kube-proxy like the routing department inside a large post office.

```text
Post Office Routing Analogy:

Post office (cluster) has a central P.O. Box number (Service ClusterIP)
Customers (clients) send letters to the P.O. Box (Service IP)
Routing department (kube-proxy) sets up forwarding rules in the mail system
Rules say: "P.O. Box 100 -> Deliver to any of: Room 1, Room 2, Room 3"
Letter (packet) is delivered directly by the mail carrier (Linux kernel)
Routing department does NOT carry letters: it only sets up the rules
If a room closes (Pod dies): routing department updates its rules
```

| Post Office | kube-proxy |
| :--- | :--- |
| P.O. Box number | Service ClusterIP (virtual IP) |
| Routing department | kube-proxy |
| Forwarding rules | iptables / IPVS rules in Linux kernel |
| Mail carrier delivering letters | Linux kernel forwarding packets |
| Room addresses | Pod IPs (backend Endpoints) |
| Room closes | Pod deleted -> Endpoint removed -> rules updated |
| Central mailroom notification | kube-proxy Watch on API Server |

> **Important:** kube-proxy does **NOT** proxy traffic at the application layer. It programs **iptables or IPVS rules in the Linux kernel**, then steps aside. After rules are programmed, **kube-proxy is not in the packet path at all** — the kernel forwards packets directly using those rules. This is why kube-proxy has almost zero overhead per connection once rules are in place.

Today:



# But There is a Mystery

Question:

```text
Service IP
  |
  v
Where Does It Exist?
```


---

# The Answer

The Service IP is a **virtual IP (VIP)**.

Packets destined for the VIP are intercepted and rewritten before reaching the application.

Historically,

this packet rewriting is performed by **kube-proxy**.

---

# What is kube-proxy?

kube-proxy is a Kubernetes Node component responsible for implementing the Service abstraction.

It watches the Kubernetes API and programs the Node's networking stack so that packets sent to Service IPs reach the correct backend Pods.

Important:

> kube-proxy **does not proxy packets in userspace** in modern Kubernetes.

Instead,

it programs Linux networking.

---

# High-Level Architecture

```text
               API Server

                    |

             Watch Services

             Watch Endpoints

                    |

                    ▼

              kube-proxy

                    |

       Programs Linux Network

                    |

         ┌──────────┼──────────┐

         ▼          ▼          ▼

      iptables     IPVS      (or)

                               ▼

                             eBPF
```

---

# Responsibilities of kube-proxy

kube-proxy is responsible for:

- Watching Services
- Watching EndpointSlices
- Programming forwarding rules
- Maintaining load balancing configuration
- Supporting session affinity
- Cleaning obsolete rules

It does **not**:

- Forward every packet in userspace
- Terminate TCP connections
- Replace the CNI plugin

---

# iptables Mode

This is the most widely deployed kube-proxy mode.

Instead of forwarding packets,

It allows rules such as:

```text

  v
```

# Characteristics

Advantages:

- Mature
- Stable
- Simple
- No additional kernel subsystem required

Limitations:

- Very large rule sets in huge clusters
- Rule updates become increasingly expensive
- Rule traversal is sequential

# IPVS Mode

IPVS stands for:

```text
IP Virtual Server
```

It is another Linux kernel subsystem dedicated to load balancing.

Instead of long rule chains,

IPVS maintains efficient lookup tables.

---

# Architecture

```text
API Server
  |
  v
kube-proxy
  |
  v
IPVS Table
  |
  v
Linux Kernel
  |
  v
Backend Pods
```

---

# Why IPVS?

Suppose:

```text
20 Services
```

iptables works well.

Now suppose:

```text
40,000 Services
```

Sequential rule traversal becomes less efficient.

IPVS uses optimized kernel data structures designed for load balancing.

---

# IPVS Load Balancing Algorithms

IPVS supports multiple scheduling algorithms.

Examples include:

```text
Round Robin

Least Connections

Source Hashing

Weighted Round Robin
```

Historically, kube-proxy has primarily used round-robin style scheduling, though IPVS itself supports many algorithms.

---

# Packet Flow

```text
Client
  |
  v
Service VIP
  |
  v
IPVS Lookup
  |
  v
Backend Pod
  |
  v
Application
```

No long iptables traversal is required for backend selection.

---

# iptables vs IPVS

| Feature | iptables | IPVS |
|----------|----------|------|
| Implementation | Netfilter rules | Kernel load balancer |
| Rule Lookup | Sequential | Efficient lookup structures |
| Scalability | Good | Better for very large numbers of Services |
| Scheduling Algorithms | Limited | Multiple algorithms |
| Complexity | Simpler | More components |

# What is conntrack?

**conntrack** (Connection Tracking) is the Linux kernel subsystem that tracks the state of network connections.

It remembers:

```text
TCP

UDP

ICMP
```

connections after the first packet.

---

# Why conntrack Exists

Suppose a TCP connection begins.

Packet 1:

```text
Client
  |
  v
Service
  |
  v
Pod A
```

Packet 2 must also reach:

```text
Pod A
```

Otherwise the TCP session breaks.

---

# Without conntrack

```text
Packet 1
  |
  v
Pod A

────────────

Packet 2
  |
  v
Pod B
```

TCP fails.

---

# With conntrack

```text
Packet 1
  |
  v
Pod A
  |
  v
Connection Recorded
  |
  v
Packet 2
  |
  v
Pod A
```

Connection consistency is preserved.

---

# conntrack Workflow

```text
New Connection
  |
  v
Select Backend
  |
  v
Store Mapping
  |
  v
Future Packets
  |
  v
Reuse Mapping
```




# Production Best Practices

✔ Use EndpointSlices instead of relying on the legacy Endpoints object.

✔ Monitor conntrack table utilization on busy Nodes.

✔ Choose an appropriate dataplane for your cluster size and operational model.

✔ Keep kube-proxy configuration consistent across Nodes.

✔ Understand Service traffic before troubleshooting applications.

✔ Use eBPF-based dataplanes when their operational and feature trade-offs align with your environment.

✔ Regularly monitor packet drops, latency, and conntrack exhaustion.

# Common Misconceptions

### ❌ Misconception 1

kube-proxy is a network proxy process that forwards every packet.

**Correct:** Modern kube-proxy primarily programs Linux networking (iptables or IPVS). The kernel forwards the packets.

---

### ❌ Misconception 2

A Service IP belongs to a Pod.

**Correct:** A Service IP is a virtual IP implemented through networking rules.

---

### ❌ Misconception 3

iptables mode sends traffic to userspace.

**Correct:** Packet forwarding occurs inside the Linux kernel after kube-proxy installs the rules.

---

### ❌ Misconception 4

IPVS replaces Services.

**Correct:** IPVS is one implementation used by kube-proxy to realize the Service abstraction.

---

### ❌ Misconception 5

eBPF is another kube-proxy mode.

**Correct:** Most eBPF solutions replace the kube-proxy dataplane rather than acting as another built-in kube-proxy mode.

---

### ❌ Misconception 6

conntrack performs load balancing.

**Correct:** conntrack tracks connection state. Backend selection is performed before connection tracking maintains consistency.

---

### ❌ Misconception 7

kube-proxy watches Pods directly.

**Correct:** kube-proxy watches Services and EndpointSlices to determine available backends.

# Common Interview Questions

### Q1. What is kube-proxy?

A Node component that implements Kubernetes Services by programming the Linux networking stack.

---

### Q2. Why is kube-proxy needed?

To translate Service virtual IPs into backend Pod IPs and provide Service load balancing.

---

### Q3. What is the difference between iptables and IPVS mode?

iptables uses Netfilter rules for packet rewriting, while IPVS uses a dedicated kernel load-balancing subsystem with efficient lookup structures.

---

### Q4. What is conntrack?

The Linux kernel's connection-tracking subsystem that maintains state for network connections.

---

### Q5. Why is conntrack important?

It ensures packets belonging to an existing connection continue reaching the same backend.

---

### Q6. Does kube-proxy forward packets itself?

No. It configures the kernel; the kernel performs packet forwarding.

---

### Q7. Why are eBPF-based dataplanes becoming popular?

They reduce overhead, improve scalability, and enable advanced networking and observability features directly inside the kernel.

---

### Q8. What resource tells kube-proxy which Pods belong to a Service?

EndpointSlices.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Service unreachable | Missing or incorrect kube-proxy rules, eBPF program issues, or networking problems |
| Service has no backends | EndpointSlice contains no ready endpoints |
| Traffic reaches only one Pod | Session affinity configuration or only one healthy backend |
| New Pods receive no traffic | EndpointSlice update not reflected in dataplane |
| Random connection failures | conntrack exhaustion, networking issues, or backend instability |
| High latency | Large rule updates, networking bottlenecks, or dataplane configuration problems |
