# Real-Life Analogy

Think of IPVS mode like an airport departure board with smart automated routing.

```text
Airport Departure Board Analogy:

Traveler (packet) arrives with a Flight Code (Service VIP)
Instead of walking through a 5,000-page book line-by-line (iptables)
Traveler looks up Flight Code instantly in an indexed digital screen (IPVS hash table O(1))
Screen immediately routes traveler to Gate 4B (Pod IP) using chosen strategy:
  - Alternate gates evenly (Round Robin)
  - Choose gate with fewest passengers (Least Connections)
Routing happens instantly regardless of whether there are 10 or 10,000 flights
```

| Airport Board | IPVS Mode |
| :--- | :--- |
| Flight Code | Service Virtual IP (ClusterIP:Port) |
| Digital index lookup | IPVS hash table lookup ($O(1)$ complexity) |
| Departure Gates | Real Servers (Backend Pod IPs) |
| Gate assignment algorithm | Scheduling algorithms (`rr`, `lc`, `sed`, `sh`) |
| Boarding ticket stamp | IPVS connection entry + Netfilter NAT |

> **Important:** IPVS uses **kernel hash tables with $O(1)$ lookup time**. Unlike iptables, the rule evaluation time in IPVS does not increase as you add more Services. However, IPVS **does not completely eliminate iptables** — kube-proxy still programs a minimal set of iptables rules and `ipset` sets for packet marking, source NAT (SNAT/MASQUERADE), and handling NodePort/ExternalIP traffic.

# The Problem with Large iptables Rule Sets

iptables works by evaluating rules until a match is found.

Conceptually:

```text
Rule 1
  |
  v
Rule 2
  |
  v
Rule 3
  |
  v
...
  |
  v
Rule N
  |
  v
Match
```

Although modern kernels optimize many operations, very large rule sets increase synchronization cost and can increase packet processing overhead.

# Why IPVS Was Introduced

Linux already had a mature load-balancing subsystem.

It was called:

```text
IPVS

(IP Virtual Server)
```

Instead of maintaining long NAT rule chains,

IPVS maintains efficient lookup tables inside the kernel.

---

# What is IPVS?

IPVS is a Linux kernel load balancer.

Originally designed for:

- Layer 4 Load Balancing
- High-performance TCP Load Balancing
- High-performance UDP Load Balancing

Kubernetes later adopted it as an alternative Service dataplane.

# IPVS vs iptables Philosophy

iptables says:

```text

  |
  v

  |
  v

```

IPVS says:

```text
Packet

  |
```

Instead of rule chains,

IPVS maintains dedicated load-balancing data structures.

# Important Relationship

Many engineers assume:

```text
IPVS
  |
  v
No iptables
```

This is **not completely true**.

In Kubernetes,

IPVS mode still uses a small number of iptables rules for functions such as directing traffic into the IPVS datapath and handling certain NAT scenarios.

IPVS replaces most Service load-balancing logic—not every iptables rule.

# Virtual Server

The **Virtual Server** represents the Kubernetes Service.

Example:

```text

10.96.0.15
```

```text
Virtual Server

```

It does **not** represent a Pod.

It represents the Service.

# Scheduling Algorithms

IPVS supports many scheduling algorithms.

The most commonly discussed are:

- Round Robin
- Least Connections
- Source Hash
- Weighted Round Robin

---

# Round Robin

The simplest scheduler.

Traffic rotates evenly.

```text
Request 1
  |
  v
Pod A

────────────

Request 2
  |
  v
Pod B

────────────

Request 3
  |
  v
Pod C

────────────

Request 4
  |
  v
Pod A
```

Every backend receives traffic in turn.

---

# Advantages

✔ Simple

✔ Fair distribution

✔ Works well for identical Pods

---

# Limitations

Not ideal when:

- One Pod is slower
- Different hardware capacities exist
- Existing connection counts differ

---

# Least Connections

Instead of rotating,

choose:

```text
Fewest Active Connections
```

Example:

```text
Pod A

5 Connections

────────────

Pod B

20 Connections

────────────

Pod C

8 Connections
```

Next request:

```text
v

Pod A
```

---

# Advantages

Works well for:

- Long-lived TCP connections
- Uneven workloads
- Variable request duration

---

# Source Hash

Hash based on:

```text
Client IP
```

Example:

```text
Client A
  |
  v
Pod A

────────────

Client A
  |
  v
Pod A

Again
```

The same client generally reaches the same backend while the backend set remains stable.

---

# Advantages

Useful for:

- Client affinity
- Session persistence
- Cache locality

---

# Weighted Round Robin

Not every server is equal.

Example:

```text
Pod A

Weight 1

────────────

Pod B

Weight 3

────────────

Pod C

Weight 2
```

Traffic distribution:

```text
Pod B
  |
  v
Most Requests
```

Higher-capacity servers receive proportionally more traffic.

---

# Scheduler Summary

| Algorithm | Best For |
|------------|----------|
| Round Robin | Equal backend capacity |
| Least Connections | Long-running connections |
| Source Hash | Client affinity |
| Weighted Round Robin | Mixed hardware capacity |

# Internal Connection Table

IPVS maintains:

```text
Client
  |
  v
Virtual Server
  |
  v
Chosen Backend
```

Future packets reuse the existing mapping until the connection expires.

---


# Performance Characteristics

IPVS was designed specifically for load balancing.

Compared to large iptables rule sets:

- Faster backend lookup
- Better scalability
- Efficient kernel data structures
- Multiple scheduling algorithms

Rule synchronization is also generally more efficient for large numbers of Services.

# IPVS vs iptables

| Feature | iptables | IPVS |
|----------|----------|------|
| Primary Mechanism | Netfilter Rules | Kernel Load Balancer |
| Backend Lookup | Rule Matching | Table Lookup |
| Scheduling Algorithms | Limited | Multiple |
| Large Cluster Performance | Good | Better |
| Connection Table | conntrack | IPVS + conntrack integration |
| Rule Synchronization | Larger rule updates | Kernel table updates |

# When Should IPVS Be Used?

Historically,

large production clusters often selected IPVS mode because of its scalability and scheduling capabilities.

However,

today many new Kubernetes environments adopt eBPF-based dataplanes instead of either iptables or IPVS.

# Production Best Practices

✔ Use IPVS for large clusters if operating a kube-proxy IPVS dataplane.

✔ Monitor connection counts and active sessions.

✔ Choose scheduling algorithms based on workload characteristics.

✔ Keep kube-proxy synchronized with EndpointSlice updates.

✔ Monitor backend health and connection persistence.

✔ Understand that IPVS still relies on parts of the Linux networking stack and may coexist with some iptables rules.

✔ Evaluate eBPF-based dataplanes for new deployments where appropriate.

# Common Misconceptions

### ❌ Misconception 1

IPVS replaces Linux networking.

**Correct:** IPVS is a Linux kernel subsystem that works within the existing networking stack.

---

### ❌ Misconception 2

IPVS does not use iptables at all.

**Correct:** Kubernetes IPVS mode still relies on a limited set of iptables rules for certain traffic handling and integration tasks.

---

### ❌ Misconception 3

Every packet is scheduled independently.

**Correct:** The scheduler selects a backend when a new connection is created. Existing packets in that connection reuse the stored mapping.

---

### ❌ Misconception 4

A Virtual Server is a Pod.

**Correct:** A Virtual Server represents a Kubernetes Service.

---

### ❌ Misconception 5

A Real Server is a physical machine.

**Correct:** In Kubernetes, a Real Server corresponds to a backend endpoint, typically a Pod IP.

---

### ❌ Misconception 6

IPVS always uses Round Robin.

**Correct:** IPVS supports multiple scheduling algorithms, each optimized for different scenarios.

---

### ❌ Misconception 7

IPVS is always the preferred Kubernetes dataplane.

**Correct:** Many modern clusters now use eBPF-based dataplanes, depending on operational requirements and platform choice.

# Common Interview Questions

### Q1. Why was IPVS introduced?

To provide a more scalable and feature-rich kernel load-balancing implementation than large iptables rule sets.

---

### Q2. What is a Virtual Server?

The kernel representation of a Kubernetes Service.

---

### Q3. What is a Real Server?

A backend endpoint associated with a Service, typically a Pod IP.

---

### Q4. What does the IPVS Scheduler do?

It selects the backend for new connections according to the configured scheduling algorithm.

---

### Q5. What scheduling algorithms does IPVS support?

Examples include Round Robin, Least Connections, Source Hash, and Weighted Round Robin.

---

### Q6. Does kube-proxy perform load balancing itself?

No. kube-proxy programs the Linux IPVS subsystem, which performs the actual backend selection.

---

### Q7. Why do packets in one TCP connection reach the same backend?

Because IPVS stores a connection mapping and reuses it for subsequent packets.

---

### Q8. Is IPVS completely independent of iptables?

No. Kubernetes IPVS mode still uses some iptables rules for integration and packet handling.

---

### Q9. What happens when a Deployment scales?

kube-proxy updates the IPVS Virtual Server and Real Server configuration based on EndpointSlice changes.

---

### Q10. When is IPVS generally preferable to iptables?

Traditionally in larger clusters where scalable backend lookup and richer scheduling capabilities are beneficial.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Service unreachable | Missing Virtual Server, kube-proxy synchronization issue, or networking problem |
| Traffic reaches only one backend | Single healthy endpoint, scheduler configuration, or connection persistence behavior |
| New Pods receive no traffic | EndpointSlice not synchronized to IPVS tables |
| Connections fail after Pod removal | Backend removed while active sessions still existed |
| Uneven traffic distribution | Scheduler choice, backend health, or long-lived persistent connections |
| High memory usage | Large connection table or many Services and endpoints |
