# Module 1.8 — kube-proxy Internals

# Chapter 5 — Service Load Balancing

> **Goal:** Understand how Kubernetes Services distribute traffic across Pods. Learn how kube-proxy performs endpoint selection, how EndpointSlices work, how traffic policies affect routing, how rolling updates occur without downtime, and how Kubernetes maintains reliable load balancing in production clusters.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. Service load balancing mechanics across iptables, IPVS, and eBPF
> 2. Endpoint vs EndpointSlice: scaling beyond 1,000 backend Pods
> 3. Random distribution (iptables probability) vs scheduling algorithms (IPVS)
> 4. Session affinity: ClientIP configuration and timeout enforcement
> 5. internalTrafficPolicy: Cluster (all nodes) vs Local (node-local pods only)
> 6. externalTrafficPolicy: Cluster (extra hop, SNAT) vs Local (preserves client IP)
> 7. Zero-downtime rolling updates: readiness probe transitions and endpoint removal
> 8. Topology-aware routing and Traffic Distribution hints
> ```

# Real-Life Analogy

Think of Service Load Balancing like a customer support call routing system.

```text
Call Center Routing Analogy:

Customer dials main support hotline (Service ClusterIP)
Automated switchboard (kube-proxy programmed kernel) picks a free agent (Pod)
Normal mode: routes to any agent randomly across all call centers
Sticky mode (sessionAffinity): routes returning caller to same agent if within timeout
Local office mode (trafficPolicy: Local): route only to agents in caller's local branch
When an agent clocks out (Pod terminating): switchboard stops routing new calls immediately
```

| Call Center | Service Load Balancing |
| :--- | :--- |
| Support hotline number | Service Virtual IP (ClusterIP) |
| Active agents list | EndpointSlice object |
| Random agent assignment | iptables probability rule / IPVS round-robin |
| Return caller to same agent | `sessionAffinity: ClientIP` with `timeoutSeconds` |
| Local branch preference | `internalTrafficPolicy: Local` / `externalTrafficPolicy: Local` |
| Agent clocking out gracefully | Readiness probe fail -> EndpointSlice removal -> conntrack drain |

> **Important:** By default, Kubernetes Service load balancing is **connection-level, not request-level (L4, not L7)**. For persistent TCP protocols like HTTP/2 or gRPC, all requests in a single TCP connection go to the exact same backend Pod! To achieve true per-request load balancing for gRPC/HTTP2, you must use an L7 proxy (such as Ingress-NGINX, Envoy, or a Service Mesh) rather than standard kube-proxy Service routing.

# Ready Endpoints

Not every Pod receives traffic.

Suppose:

```text
Pod A

Ready

────────────

Pod B

Ready

────────────

Pod C

Not Ready
```

Only Ready endpoints are normally included for Service traffic.

---

# Why?

Traffic should never reach a Pod that cannot serve requests.

Readiness determines whether a Pod participates in load balancing.

---

# Session Affinity

Normally,

every new connection may reach a different backend.

Sometimes,

this is undesirable.

Example:

```text
Shopping Cart
  |
  v
Client
  |
  v
Same Backend
```

---

# What is Session Affinity?

Session Affinity attempts to send requests from the same client to the same backend.

Conceptually:

```text
Client A
  |
  v
Pod B

────────────

Client A
  |
  v
Pod B

Again
```

---

# Why Use Session Affinity?

Useful for:

- Legacy applications
- In-memory sessions
- Stateful applications
- Cache locality

---

# ClientIP Affinity

Kubernetes currently supports:

```text
ClientIP
```

Requests from the same client IP are directed to the same backend for the configured affinity timeout period, provided that backend remains eligible.

---

# ClientIP Workflow

```text
Client
  |
  v
Remember Backend
  |
  v
Future Requests
  |
  v
Same Pod
```

---

# Important Note

Session Affinity is **not** the same as TCP connection tracking.

Connection tracking ensures packets in a connection stay together.

Session Affinity attempts to keep **multiple connections** from the same client directed to the same backend.

---

# conntrack vs Session Affinity

| conntrack | Session Affinity |
|------------|------------------|
| Same TCP connection | Multiple connections |
| Kernel feature | Kubernetes Service feature |
| Always required | Optional |
| Packet consistency | Client stickiness |

# InternalTrafficPolicy

Sometimes traffic should remain:

```text
Inside Same Node
```

This is controlled by:

```text
InternalTrafficPolicy
```

Possible values:

```text
Cluster

Local
```

---

# Cluster Policy

```text
Node A
  |
  v
Pod Anywhere
```

Traffic may be forwarded to Pods on any Node.

---

# Local Policy

```text
Node A
  |
  v
Only Local Pods
```

If no local endpoints exist,

the Service has no eligible backend for traffic originating from that Node.

---

# Why Use Local?

Advantages:

- Lower latency
- Reduced cross-node traffic
- Better network locality

Trade-off:

Potentially uneven traffic distribution if endpoint placement is imbalanced.

---

# ExternalTrafficPolicy

This policy applies to traffic entering the cluster through:

- NodePort
- LoadBalancer Services

Possible values:

```text
Cluster

Local
```

---

# ExternalTrafficPolicy = Cluster

Traffic may arrive at:

```text
Node A
```

and be forwarded to:

```text
Pod on Node B
```

This maximizes backend availability.

---

# ExternalTrafficPolicy = Local

Traffic entering:

```text
Node A
```

can only be forwarded to Pods on:

```text
Node A
```

If no local endpoints exist,

that Node does not serve external traffic for the Service.

---

# Why Use Local?

One major advantage:

```text
Preserve Client IP
```

Because unnecessary cross-node forwarding and SNAT can often be avoided.

Trade-offs include reduced load distribution flexibility if some Nodes have no local endpoints.

# Production Best Practices

✔ Always configure Readiness Probes.

✔ Use EndpointSlices (default in modern Kubernetes).

✔ Use Session Affinity only when required.

✔ Prefer stateless applications whenever possible.

✔ Use InternalTrafficPolicy=Local only when the locality benefits outweigh reduced flexibility.

✔ Use ExternalTrafficPolicy=Local when preserving client IP is required.

✔ Monitor endpoint counts during large rollouts.

✔ Verify endpoint readiness before investigating networking issues.

# Common Misconceptions

### ❌ Misconception 1

Services store Pod IPs.

**Correct:** EndpointSlices store backend endpoint information.

---

### ❌ Misconception 2

Every request is randomly distributed.

**Correct:** Distribution depends on the dataplane implementation, connection state, and optional affinity settings.

---

### ❌ Misconception 3

Session Affinity and conntrack are the same.

**Correct:** conntrack tracks packets within a connection; Session Affinity influences backend selection across multiple connections.

---

### ❌ Misconception 4

A Pod receives traffic immediately after creation.

**Correct:** Traffic is normally sent only after the Pod becomes Ready.

---

### ❌ Misconception 5

Rolling updates require downtime.

**Correct:** Proper readiness handling allows traffic to shift gradually without interruption.

---

### ❌ Misconception 6

InternalTrafficPolicy affects external clients.

**Correct:** It applies only to traffic originating from inside the cluster.

---

### ❌ Misconception 7

ExternalTrafficPolicy=Local guarantees better performance.

**Correct:** It preserves client IP and can reduce cross-node hops, but it may also reduce load distribution flexibility and depends on local endpoint availability.

# Common Interview Questions

### Q1. How does a Service discover backend Pods?

Through label selectors, the EndpointSlice controller, and EndpointSlices.

---

### Q2. What is an EndpointSlice?

A scalable Kubernetes resource that stores backend endpoint information for Services.

---

### Q3. Why were EndpointSlices introduced?

To improve scalability compared to the older Endpoints resource.

---

### Q4. What is Session Affinity?

A Service feature that attempts to route multiple connections from the same client to the same backend.

---

### Q5. What is ClientIP affinity?

A session affinity mode that uses the client IP address to maintain backend stickiness for a configurable period.

---

### Q6. What is InternalTrafficPolicy?

A Service setting that controls whether internal traffic can use cluster-wide endpoints or only local Node endpoints.

---

### Q7. What is ExternalTrafficPolicy?

A Service setting for NodePort and LoadBalancer Services that controls whether external traffic can be forwarded to remote Nodes or only local endpoints.

---

### Q8. Why are Readiness Probes important?

Only Ready endpoints normally receive Service traffic.

---

### Q9. What happens during a rolling update?

New Ready Pods are added to EndpointSlices before old Pods are removed, allowing seamless traffic transition.

---

### Q10. What happens when a Pod crashes?

Its readiness fails (or it is removed), EndpointSlices are updated, and traffic is redirected to remaining healthy endpoints.

---

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Service has no endpoints | Label selector mismatch or no Ready Pods |
| New Pods receive no traffic | Readiness Probe failing |
| Traffic still reaches terminating Pod | Endpoint update or termination still in progress |
| Client IP not preserved | ExternalTrafficPolicy set to Cluster or SNAT behavior |
| Uneven traffic distribution | Session Affinity, long-lived connections, or endpoint imbalance |
| Traffic never stays on local Node | InternalTrafficPolicy configured as Cluster |
