# Module 1.8 — kube-proxy Internals

# Chapter 6 — eBPF-Based kube-proxy Replacement

> **Goal:** Understand how modern Kubernetes networking replaces kube-proxy using **eBPF**. Learn how eBPF programs execute inside the Linux kernel, how Service load balancing works without iptables or IPVS, how Cilium implements a kube-proxy-free dataplane, and why many large Kubernetes platforms have adopted this architecture.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. The fundamental limitations of iptables and IPVS at cloud scale
> 2. What eBPF is: sandboxed bytecode running safely inside Linux kernel space
> 3. Packet hook points: XDP (network card driver), TC (traffic control), socket layer
> 4. BPF Maps: high-speed kernel key-value stores for Service VIP and Endpoint lookup
> 5. Socket-level load balancing (sock_ops): translating VIP to Pod IP at connect() time
> 6. Direct Server Return (DSR): allowing backend Pods to reply directly to clients without return SNAT
> 7. kube-proxy-free architecture: how Cilium replaces kube-proxy entirely
> 8. Observability advantages: Hubble, transparent encryption, and L7 policy enforcement
> ```

# Real-Life Analogy

Think of eBPF replacement like a smart highway with electronic overhead gantries.

```text
Smart Highway Analogy:

Traditional toll booth (iptables): every car stops and queues up in lane 1..N
Automated toll gate (IPVS): cars slow down to pass through high-speed gate
Smart Highway overhead sensors (eBPF / XDP):
  - Sensors read car license plate at full highway speed (packet at NIC / XDP)
  - Instantly directs car to express exit lane without any speed reduction
  - Zero toll booths, zero queues, zero bottlenecks
```

| Smart Highway | eBPF Replacement |
| :--- | :--- |
| Traditional toll booth queue | iptables linear chain traversal |
| Automated electronic gate | IPVS kernel hash tables |
| Overhead sensor at highway speed | XDP / TC eBPF hook at driver/kernel boundary |
| Express routing without stopping | Socket-layer translation (`cgroup/connect4`) |
| Central speed database | BPF Maps (Service & Endpoint kernel lookup) |
| Direct return route | Direct Server Return (DSR) bypassing router |

> **Important:** With eBPF socket-layer load balancing (`sock_ops` / `cgroup/connect4`), the destination IP translation happens **directly inside the client application's `connect()` syscall** before any packet is even created on the network stack. The packet leaves the client socket already addressed to the backend Pod IP, completely bypassing Netfilter, iptables, and conntrack overhead!

# What is eBPF?

eBPF stands for:

```text
Extended Berkeley Packet Filter
```

Originally,

BPF was designed for packet filtering.

Modern eBPF has evolved into a general-purpose programmable execution environment inside the Linux kernel.

---

# Important Definition

eBPF is **not** a networking tool.

It is a kernel technology that allows verified programs to run safely inside the Linux kernel.

Networking is only one of its many use cases.

# Why is eBPF Safe?

Running arbitrary code in the kernel would be dangerous.

Before execution,

every eBPF program passes through the:

```text
Verifier
```

The verifier checks:

- Program safety
- Memory safety
- Loop correctness
- Execution limits

Only verified programs are loaded.

BPF Maps are shared kernel data structures.

Think of them as extremely fast kernel key-value stores.

# Common Misconceptions

### ❌ Misconception 1

eBPF replaces the Linux kernel.

**Correct:** eBPF runs inside the Linux kernel.

---

### ❌ Misconception 2

eBPF is only for networking.

**Correct:** eBPF supports networking, security, tracing, observability, and many other kernel extensions.

---

### ❌ Misconception 3

BPF Maps are user-space databases.

**Correct:** BPF Maps are kernel-resident data structures shared between user space and eBPF programs.

---

### ❌ Misconception 4

XDP and TC are the same.

**Correct:** XDP executes much earlier in the packet path, while TC executes later with additional networking context.

---

### ❌ Misconception 5

Every eBPF implementation behaves identically.

**Correct:** Different platforms implement connection tracking, load balancing, and advanced features differently.

---

### ❌ Misconception 6

eBPF eliminates connection tracking.

**Correct:** Stateful networking still requires connection tracking. The implementation may use Linux conntrack, custom eBPF-based tracking, or both.

---

### ❌ Misconception 7

Cilium is only a CNI plugin.

**Correct:** Cilium is a comprehensive networking platform that provides CNI functionality, Service load balancing, network policies, observability, and optional kube-proxy replacement.

# Common Interview Questions

### Q1. Why are organizations replacing kube-proxy?

To reduce dataplane overhead, improve scalability, and enable programmable kernel networking.

---

### Q2. What is eBPF?

A safe programmable execution environment inside the Linux kernel.

---

### Q3. What is the purpose of the eBPF verifier?

To ensure programs are safe before they are loaded into the kernel.

---

### Q4. What is the difference between XDP and TC?

XDP executes at the earliest packet processing stage, while TC executes later within the networking stack.

---

### Q5. What are BPF Maps?

Kernel-resident key-value data structures used by eBPF programs to store and retrieve state.

---

### Q6. How does Service lookup work in an eBPF dataplane?

The eBPF program performs a lookup in BPF Maps to retrieve backend information instead of traversing iptables rules.

---

### Q7. What is Direct Server Return (DSR)?

A networking technique in which response traffic returns directly from the backend to the client instead of passing back through the ingress forwarding Node.

---

### Q8. What does kube-proxy-free Kubernetes mean?

Service networking is implemented by eBPF programs rather than kube-proxy-managed iptables or IPVS rules.

---

### Q9. What role does Cilium play?

Cilium provides an eBPF-powered Kubernetes networking platform, including CNI, Service load balancing, network policies, observability, and optional kube-proxy replacement.

---

### Q10. Is eBPF always better than IPVS?

Not necessarily. eBPF offers many advantages, but the best choice depends on kernel support, operational expertise, feature requirements, and workload characteristics.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Service unreachable | Missing or stale BPF Map entries, agent synchronization issue, or networking problem |
| Incorrect backend selection | Outdated BPF Maps or endpoint synchronization failure |
| High packet drops | eBPF program issue, policy enforcement, or underlying network problem |
| Client IP unexpectedly changed | DSR configuration, NAT behavior, or traffic policy configuration |
| Poor performance after migration | Kernel compatibility, configuration issues, or workload-specific behavior |
| eBPF programs not loaded | Verifier rejection, unsupported kernel features, or agent failure |
