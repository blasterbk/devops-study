# Real-Life Analogy

Think of the Admission Control module summary like the master operations center of an international airport.

```text
Airport Operations Center Analogy:

The operations center coordinates all security layers across the entire terminal:
  - Gate 1 (AuthN): Passenger Identity Verification
  - Gate 2 (AuthZ): Ticket and Boarding Clearance
  - Gate 3 (Mutating): Luggage Auto-Tagging & Safety Wrapping
  - Gate 4 (Schema Validation): Physical Luggage Dimensions
  - Gate 5 (Validating & CEL): X-Ray & Automated Threat Detection
  - Cargo Hold (etcd): Safe luggage storage aboard the aircraft
Every system has redundant backup generators and emergency bypass protocols (failurePolicy)
```

| Master Operations Center | Kubernetes Admission System |
| :--- | :--- |
| Passenger identity clearance | Authentication (TLS, Bearer Token) |
| Boarding ticket clearance | Authorization (RBAC) |
| Luggage auto-tagging / wrapping | Mutating Webhooks (JSON Patch mutations) |
| Luggage size check | OpenAPI v3 Schema Validation |
| High-speed X-Ray scanner | Validating Admission Webhooks & `ValidatingAdmissionPolicy` (CEL) |
| Cargo hold storage | etcd persistence |
| Emergency bypass protocol | `failurePolicy: Ignore` / Namespace exclusion |

> **Important:** Admission Control is the **last line of defense** before data reaches etcd. Once an object passes Validating Admission and Schema Validation, it is immediately written to disk and controllers begin acting upon it. Designing robust, highly available, and low-latency admission policies is the foundation of multi-tenant Kubernetes security and cluster reliability.

# Mutating vs Validating

| Mutating | Validating |
|----------|------------|
| Changes object | Never changes object |
| Runs first | Runs later |
| Returns JSON Patch | Returns Allow/Deny |
| Adds defaults | Enforces policies |
| May inject containers | May reject requests |

---

# Built-in vs Webhooks

| Built-in Admission | Admission Webhooks |
|--------------------|--------------------|
| Inside API Server | External HTTPS service |
| No network | Requires network |
| Lower latency | Higher latency |
| Kubernetes functionality | Organization functionality |

|--------------------------|--------------------|

# Performance Considerations

Every webhook introduces additional work.

Sources of latency:

- Rule matching
- AdmissionReview creation
- JSON serialization
- TLS negotiation
- Network latency
- Webhook execution
- Response processing

Built-in admission plugins avoid most of these costs.

---

# Performance Optimization

✔ Prefer built-in admission plugins.

✔ Use ValidatingAdmissionPolicy for declarative validation.

✔ Minimize webhook count.

✔ Use namespace selectors.

✔ Use object selectors.

✔ Avoid external API calls.

✔ Keep webhook logic lightweight.

✔ Return responses quickly.

---

# Security Best Practices

✔ Use TLS for every webhook.

✔ Rotate certificates regularly.

✔ Protect webhook Pods.

✔ Use least-privilege RBAC.

✔ Audit rejected requests.

✔ Validate incoming objects thoroughly.

✔ Avoid unnecessary mutation.

✔ Monitor admission failures.

✔ Separate mutation from validation responsibilities.

# Common Misconceptions

### ❌ Misconception 1

Admission Controllers create Pods.

**Correct:** They only evaluate API requests. Controllers create and reconcile workloads after objects are stored.

---

### ❌ Misconception 2

Admission happens after etcd.

**Correct:** Admission completes before persistence.

---

### ❌ Misconception 3

Mutating Webhooks validate requests.

**Correct:** They modify objects. Validation is performed later.

---

### ❌ Misconception 4

Validating Webhooks can modify objects.

**Correct:** They only return an allow or deny decision.

---

### ❌ Misconception 5

ValidatingAdmissionPolicy replaces every webhook.

**Correct:** It replaces many declarative validation use cases but not complex logic requiring external systems.

---

### ❌ Misconception 6

Webhook failures always reject requests.

**Correct:** The outcome depends on the configured `failurePolicy`.

---

### ❌ Misconception 7

Controllers participate in Admission.

**Correct:** Controllers only observe objects after they have been stored in etcd.

# Complete Interview Revision

### Q1. Where do Admission Controllers execute?

Inside the Kubernetes API Server.

---

### Q2. When does Admission occur?

After Authentication and Authorization, before persistence to etcd.

---

### Q3. Why does mutation happen before validation?

Validators must evaluate the final object after all mutations are complete.

---

### Q4. What is AdmissionReview?

The request/response protocol used by the API Server to communicate with admission webhooks.

---

### Q5. What is JSON Patch?

A standard format used by mutating webhooks to describe incremental changes to an object.

---

### Q6. What is the difference between Built-in Admission and Dynamic Admission?

Built-in admission uses plugins compiled into the API Server. Dynamic admission invokes externally configured webhooks.

---

### Q7. When should you use ValidatingAdmissionPolicy?

For declarative validation that depends only on Kubernetes object data and can be expressed in CEL.

---

### Q8. Why should admission webhooks be idempotent?

Because requests may be retried under certain failure conditions.

---

### Q9. Why are webhook Services typically deployed with multiple replicas?

To ensure high availability and avoid blocking API requests if a single Pod fails.

---

### Q10. What happens if admission rejects a request?

The object is never persisted to etcd, and the client receives an error response.

# Module Summary

Throughout **Module 1.10**, you explored one of the most important stages of the Kubernetes control plane—the **Admission Control pipeline**.

You learned that every API request follows a carefully ordered sequence:

1. **Authentication** verifies identity.
2. **Authorization** verifies permissions.
3. **Built-in Admission Controllers** apply Kubernetes defaults and enforce core platform policies.
4. **Mutating Admission Webhooks** dynamically modify objects using JSON Patch.
5. **Built-in Validating Admission Controllers**, **ValidatingAdmissionPolicy**, and **Validating Admission Webhooks** enforce security, governance, and organizational rules.
6. **API schema validation** confirms the object conforms to the Kubernetes API.
7. The object is **persisted to etcd**, after which controllers begin reconciliation.

You also learned how Kubernetes dynamically discovers webhook configurations, secures communication with TLS and CA bundles, routes AdmissionReview requests, handles failures, and scales webhook infrastructure for production environments.

With this module complete, you now understand not only **what Admission Controllers are**, but **how they are implemented inside the Kubernetes API Server**, **how they interact with external systems**, and **how they are used to build secure, governed, multi-tenant production Kubernetes platforms**.
