# Real-Life Analogy

Think of Dynamic Admission Control like a diplomatic courier service with mutual TLS credentials.

```text
Diplomatic Courier Analogy:

API Server (Foreign Embassy) prepares a diplomatic dispatch (AdmissionReview payload)
Embassy looks up delivery destination in treaty index (WebhookConfiguration clientConfig)
Courier establishes secure encrypted channel using trusted embassy seals (TLS with caBundle)
Foreign ministry office (Webhook Pod) verifies seal, reads dispatch, and stamps decision
Courier returns the signed response back to the embassy
Deadlock rule: The embassy security guards must NEVER inspect their own security vehicles!
  (Namespace exemptions for webhook pods to prevent chicken-and-egg boot loops)
```

| Diplomatic Courier | Dynamic Admission Control |
| :--- | :--- |
| Diplomatic treaty index | `MutatingWebhookConfiguration` / `ValidatingWebhookConfiguration` |
| Diplomatic dispatch | JSON `AdmissionReview` payload |
| Trusted embassy seal | Base64-encoded `caBundle` in `clientConfig` |
| Foreign ministry office | Webhook server Pod behind a Kubernetes Service |
| Signed decision stamp | `AdmissionResponse` with `allowed: true/false` |
| Security guard exemption | Exemption labels (`control-plane`, `kube-system`) to prevent boot deadlocks |

> **Important:** Dynamic webhooks **must serve traffic over HTTPS with a valid certificate matching the `caBundle` in their configuration**. A classic production disaster occurs when a webhook configured with `failurePolicy: Fail` is deployed without excluding its own namespace. If the webhook pod restarts, the API Server cannot start the replacement pod because it tries to call the non-existent webhook first, resulting in an unrecoverable **webhook deadlock**. Always exempt critical namespaces like `kube-system`!

# What is Dynamic Admission Control?

Dynamic Admission Control is the Kubernetes framework that allows the API Server to dynamically discover and invoke external admission webhooks without modifying Kubernetes source code.

Instead of compiling new admission plugins into the API Server, administrators register webhook configurations that the API Server loads and executes at runtime.

---

```text
API Server
```

---

## Dynamic

```text
API Server
  |
  v

  |
  v

  |
  v
```

Configured at runtime.

- Different security rules

Without Dynamic Admission:


Dynamic Admission solves this problem.

# API Server Responsibilities

The API Server is responsible for:

- Discovering webhook configurations
- Matching incoming requests
- Calling webhooks
- Applying patches
- Collecting validation decisions
- Handling failures
- Persisting approved objects

The webhook never contacts the API Server directly.

The API Server always initiates communication.

---

# Dynamic Webhook Discovery

How does the API Server know which webhooks exist?

It watches Kubernetes resources.

```text
MutatingWebhookConfiguration

ValidatingWebhookConfiguration
```

Whenever these resources change,

the API Server updates its in-memory webhook registry.

---

# Discovery Workflow

```text

  |

  v

  |
  v

  |

Ready for Future Requests
```

No API Server restart is required.

# Sequential Webhook Execution

Multiple webhooks may match the same request.

Execution order:

```text
Webhook A
  |
  v
Webhook B
  |
  v
Webhook C
```

Each webhook receives the latest version of the object after previous mutations.

---

# Why Sequential Execution?

Suppose:

Webhook A adds:

```text
Sidecar
```

Webhook B validates:

```text
All Containers
```

Webhook B must see the sidecar.

Therefore,

mutating webhooks execute sequentially.

---

```text
  v

  |
  v
```

Validation always evaluates the final object.

# Failure Handling

- Network timeout
- DNS failure

- Service unavailable

# Timeout Handling

Every webhook has a timeout.

```text
API Server
  |
  v
Wait
  |
  v
Timeout
  |
  v

```

Slow webhooks delay every API request.

---

# Retry Behavior

The API Server may retry admission requests under certain failure scenarios (for example, transient transport failures before receiving a response). Because of this, webhook implementations should always be **idempotent**.

Never assume a webhook will be invoked exactly once.

---

# High Availability

Production deployments should use multiple replicas.

```text
                Service

          ┌──────┼──────┐

          v      v      v

      Webhook Webhook Webhook

       Pod 1   Pod 2   Pod 3
```

One Pod failure should not block admission.

---

# Load Balancing

The Kubernetes Service distributes requests.

```text

  |
```

# Scaling

Large clusters may process thousands of admission requests per second.

Webhook services should:

- Scale horizontally
- Be stateless
- Respond quickly
- Avoid blocking operations

# Performance Considerations

Dynamic Admission introduces additional overhead compared to built-in admission plugins.

Sources of latency:

- HTTPS connection establishment (or reuse)
- TLS verification
- JSON serialization/deserialization
- Network communication
- Webhook execution time

Minimize these costs wherever possible.

---

# Security Considerations

Production webhook deployments should:

✔ Use valid TLS certificates.

✔ Rotate certificates before expiration.

✔ Restrict webhook permissions using least-privilege RBAC.

✔ Avoid exposing webhook services outside the cluster unless required.

✔ Protect webhook Pods using NetworkPolicies where appropriate.

✔ Audit webhook failures and rejected requests.

---

# Production Best Practices

✔ Keep webhook logic deterministic.

✔ Make webhooks idempotent.

✔ Deploy multiple replicas.

✔ Configure readiness and liveness probes.

✔ Use short timeout values.

✔ Avoid long-running operations.

✔ Cache frequently used data when safe.

✔ Prefer ValidatingAdmissionPolicy for simple declarative rules.

✔ Continuously monitor latency and failures.

✔ Test Failure Policy behavior before production deployment.

# Common Misconceptions

### ❌ Misconception 1

The webhook contacts the API Server.

**Correct:** The API Server always initiates webhook communication.

---

### ❌ Misconception 2

Dynamic Admission requires restarting the API Server.

**Correct:** The API Server watches webhook configuration resources and updates dynamically.

---

### ❌ Misconception 3

HTTP is sufficient for admission webhooks.

**Correct:** Kubernetes requires HTTPS with certificate validation.

---

### ❌ Misconception 4

Webhook execution order is random.

**Correct:** Matching webhooks execute sequentially according to the API Server's admission processing.

---

### ❌ Misconception 5

Only one webhook can evaluate a request.

**Correct:** Multiple mutating and validating webhooks may evaluate the same request.

---

### ❌ Misconception 6

Slow webhooks affect only webhook performance.

**Correct:** Slow webhooks increase API request latency and can reduce overall cluster responsiveness.

---

### ❌ Misconception 7

Webhook Pods can safely maintain local state.

**Correct:** Production webhook services should generally be stateless so they can scale horizontally and recover easily.

# Common Interview Questions

### Q1. What is Dynamic Admission Control?

A Kubernetes framework that allows external admission webhooks to participate in API request processing without modifying Kubernetes source code.

---

### Q2. How does the API Server discover admission webhooks?

By watching `MutatingWebhookConfiguration` and `ValidatingWebhookConfiguration` resources.

---

### Q3. Does the API Server or the webhook initiate communication?

The API Server initiates all webhook communication.

---

### Q4. Why is HTTPS mandatory?

Admission requests may contain sensitive Kubernetes objects, so communication must be encrypted and authenticated.

---

### Q5. What is the purpose of the CA Bundle?

It allows the API Server to verify the webhook server's TLS certificate.

---

### Q6. Why are mutating webhooks executed before validating webhooks?

Because validators must evaluate the final object after all mutations have been applied.

---

### Q7. Why should admission webhooks be idempotent?

Because requests may be retried under certain failure scenarios.

---

### Q8. Why should webhook services be stateless?

To support horizontal scaling, load balancing, and reliable failover.

---

### Q9. What happens if a webhook times out?

The API Server applies the configured Failure Policy (`Fail` or `Ignore`).

---

### Q10. Why are slow webhooks dangerous?

They increase API Server admission latency and can negatively affect overall cluster performance.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Webhook never invoked | Rules, selectors, or match conditions do not match |
| TLS handshake failed | Invalid certificate or incorrect CA bundle |
| Admission timeout | Slow webhook or network issue |
| Requests unexpectedly rejected | Failure Policy set to `Fail` and webhook unavailable |
| High API latency | Slow webhook processing or excessive webhook chain |
| Connection refused | Service or webhook Pods unavailable |
| Certificate expired | TLS certificate rotation required |
| Uneven load | Insufficient webhook replicas or Service issues |
