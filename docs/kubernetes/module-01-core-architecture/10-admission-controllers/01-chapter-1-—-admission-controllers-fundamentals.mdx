> **Goal:** Understand how every Kubernetes API request passes through the Admission Control pipeline before being stored in etcd. # Real-Life Analogy

Think of Admission Control like an international airport customs and security checkpoint.

```text
Airport Security Analogy:

1. Authentication: Passport control verifies who you are (User / ServiceAccount)
2. Authorization: Boarding pass check verifies if you have permission to board (RBAC)
3. Mutating Admission: Baggage handling attaches baggage tags and applies safety wraps (Mutations)
4. Schema Validation: Physical dimensions check verifies luggage fits in standard overhead bins
5. Validating Admission: Security scanner checks for prohibited items (Validations)
6. Persistence: Luggage is loaded into the cargo hold (Committed to etcd)
Note: Looking at flight schedule monitors (Read-only GET/LIST) requires no security scan
```

| Airport Security Stage | Kubernetes API Pipeline |
| :--- | :--- |
| Passport verification | Authentication (TLS certs, Bearer Tokens) |
| Boarding pass check | Authorization (RBAC, Webhook, ABAC) |
| Baggage auto-tagging / wrapping | **Mutating Admission** (defaults, sidecar injection) |
| Luggage dimension check | OpenAPI Schema Validation |
| Security scanner / metal detector | **Validating Admission** (OPA, Kyverno, CEL policies) |
| Loaded into airplane cargo | Written into etcd key-value store |
| Looking at flight monitors | Read-only requests (`GET`, `LIST`, `WATCH`) |

> **Important:** Admission controllers **only intercept write/modifying requests** (`CREATE`, `UPDATE`, `DELETE`, `CONNECT`). Read-only operations (`GET`, `LIST`, `WATCH`) completely bypass the admission control pipeline and are served directly from the API Server cache or etcd after authentication and authorization. You cannot use Admission Webhooks to restrict or audit read-only data access.

# Where This Chapter Fits

Throughout previous modules we learned:

```text
kubectl
  |
  v
API Server
  |
  v
etcd
```

But something important is missing.

When a user creates a Pod,

does the API Server immediately store it?

**No.**

Before the object reaches etcd, Kubernetes performs several security and policy checks.

These checks are performed by the **Admission Control Pipeline**.

---

# The Problem

Suppose a developer creates the following Pod.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - image: nginx
```

Questions Kubernetes must answer:

- Is the user authenticated?
- Is the user authorized?
- Should defaults be added?
- Does it violate ResourceQuota?
- Does it violate Pod Security?
- Should labels be added?
- Should sidecars be injected?
- Should the request be rejected?

Without answering these questions,

the cluster would be insecure.

---

# Kubernetes Solution

Every API request passes through multiple stages.

```text
kubectl
  |
  v
Authentication
  |
  v
Authorization
  |
  v
Admission Controllers
  |
  v
Persist to etcd
```

Admission Controllers are responsible for the third stage.

# What are Admission Controllers?

Admission Controllers are plugins executed by the Kubernetes API Server.

Their responsibility is to:

- Inspect requests
- Modify requests
- Validate requests
- Approve or reject requests

They execute **before** objects are written to etcd.

---

# Simple Definition

Think of Admission Controllers as:

```text
API Request
  |
  v
Security Guard
  |
  v
Policy Checker
  |
  v
Object Modifier
  |
  v
Approval Gate
```

If every check succeeds,

the object is stored.

Otherwise,

the request is rejected.

---

# Why Admission Controllers Exist

Imagine a cluster without Admission Controllers.

Developer creates:

```yaml
privileged: true
```

API Server accepts it.

Developer creates:

```yaml
cpu: 500
memory: 10Ti
```

API Server accepts it.

Developer forgets:

```yaml
namespace
```

API Server accepts it.

Eventually:

- Nodes run out of memory
- Security policies are bypassed
- Resource limits disappear
- Organization policies are violated

Admission Controllers prevent these problems.

---

# Responsibilities of Admission Controllers

Admission Controllers can:

✔ Modify objects

✔ Reject invalid objects

✔ Apply defaults

✔ Enforce security

✔ Enforce quotas

✔ Apply organization policies

✔ Inject sidecars

✔ Add labels

✔ Add annotations

---

# What Admission Controllers Cannot Do

Admission Controllers do **not**:

❌ Schedule Pods

❌ Start Containers

❌ Watch Resources

❌ Reconcile Objects

❌ Execute Workloads

Those responsibilities belong to other Kubernetes components.

---

# Admission Pipeline

The Admission phase itself consists of two stages.

```text
Admission

+--────── Mutating

+--────── Validating
```

Mutation always happens before validation.

---

# Internal Admission Flow

```text
Incoming Request
  |
  v
Mutating Admission
  |
  v
Modified Object
  |
  v
Validating Admission
  |
  v
Approved?
  |
  v
Store in etcd
```

---

# Why Mutation Happens First

Imagine validation occurred first.

User creates:

```yaml
metadata:
  labels: {}
```

A Mutating Admission Controller would later add:

```yaml
team: platform
```

Validation already happened.

The new label was never validated.

To prevent this inconsistency,

Kubernetes always mutates first,

then validates.

---

# Authentication

Admission Controllers assume the user has already been authenticated.

Authentication answers:

```text
Who Are You?
```

Example:

```text
Alice
  |
  v
Authenticated
```

If authentication fails,

Admission Controllers are never reached.

---

# Authorization

After authentication,

Kubernetes verifies permissions.

Authorization answers:

```text
Can You Perform This Action?
```

Example:

```text
Alice
  |
  v
Create Pod?
  |
  v
Allowed
```

Only then does Admission begin.

---

# Admission

Admission answers:

```text
Should This Request Be Allowed?
```

Unlike Authorization,

Admission evaluates:

- Object contents
- Policies
- Organization rules
- Security requirements

---

# Complete Decision Flow

```text
Create Pod
  |
  v
Authentication
  |
  v
Authorization
  |
  v
Admission
  |
  v
Persist
```

Failure at any stage rejects the request.

---

# Mutating Admission

Mutating Admission Controllers modify requests.

Examples:

```text
Incoming Pod
  |
  v
Add Labels
  |
  v
Add Sidecar
  |
  v
Add Defaults
  |
  v
Continue
```

The original request changes.

---

# Example Mutation

User submits:

```yaml
containers:
- image: nginx
```

Admission adds:

```yaml
imagePullPolicy: IfNotPresent
```

The stored object differs from the original request.

---

# More Mutation Examples

Mutating Admission may:

```text
Add Labels
  |
  v
Add Annotations
  |
  v
Inject Sidecars
  |
  v
Set Defaults
  |
  v
Modify Resources
```

These changes happen transparently.

---

# Validating Admission

Validation does **not** modify objects.

Instead,

it answers:

```text
Allowed?

or

Rejected?
```

---

# Example Validation

Request:

```yaml
privileged: true
```

Policy:

```text
Privileged Pods Forbidden
```

Result:

```text
Rejected
```

Nothing is stored.

---

# Mutation vs Validation

| Mutating | Validating |
|-----------|------------|
| Can modify object | Cannot modify object |
| Runs first | Runs after mutation |
| Returns updated object | Returns allow/deny |
| Adds defaults | Enforces policies |
| May inject sidecars | May reject requests |

# Dynamic Admission

Organizations often require custom policies.

Instead of modifying Kubernetes source code,

dynamic admission allows external components to participate.

Examples:

```text

  |
  v
Webhook
  |
  v
Decision
  |
  v
Continue
```

These external components are called Admission Webhooks.

# Admission Chain

Internally,

```text

  v

  |

  |
  v

  |
```

Each plugin executes in sequence.

```text

+--────── Authorization

+--────── Storage
```

Admission is not a separate Kubernetes component.

It is part of the API Server request pipeline.

# Production Best Practices

✔ Keep admission logic fast.

✔ Prefer built-in Admission Controllers whenever possible.

✔ Use Mutating Admission only for defaulting and controlled transformations.

✔ Use Validating Admission for policy enforcement.

✔ Ensure admission decisions are deterministic.

✔ Avoid unnecessary external webhook calls.

✔ Monitor admission latency.

✔ Fail securely when enforcing critical policies.

# Common Misconceptions

### ❌ Misconception 1

Admission Controllers are Controllers.

**Correct:** Admission Controllers run inside the API Server before persistence. Controllers watch objects after they are stored.

---

### ❌ Misconception 2

Admission happens after objects are stored.

**Correct:** Admission happens before persistence to etcd.

---

### ❌ Misconception 3

Authentication and Admission are the same.

**Correct:** Authentication verifies identity. Admission evaluates the request itself.

---

### ❌ Misconception 4

Validation happens before mutation.

**Correct:** Kubernetes performs mutation before validation.

---

### ❌ Misconception 5

Admission Controllers schedule Pods.

**Correct:** Scheduling is performed later by the Kubernetes Scheduler.

---

### ❌ Misconception 6

Admission Controllers can reconcile resources.

**Correct:** Reconciliation is performed by Controllers, not Admission Controllers.

---

### ❌ Misconception 7

Every Admission Controller can modify objects.

**Correct:** Only Mutating Admission Controllers can modify objects. Validating Admission Controllers only allow or deny requests.

# Common Interview Questions

### Q1. What is an Admission Controller?

A plugin that intercepts Kubernetes API requests before objects are stored in etcd to mutate or validate them.

---

### Q2. Where do Admission Controllers execute?

Inside the Kubernetes API Server.

---

### Q3. When does Admission occur?

After Authentication and Authorization, but before persistence to etcd.

---

### Q4. Why are Admission Controllers needed?

To enforce policies, apply defaults, validate requests, and improve cluster security and governance.

---

### Q5. What is the difference between Authentication, Authorization, and Admission?

- Authentication verifies identity.
- Authorization verifies permissions.
- Admission evaluates and optionally modifies the request.

---

### Q6. Why does mutation occur before validation?

So validators evaluate the final object that will actually be stored.

---

### Q7. What is the difference between Mutating and Validating Admission?

Mutating Admission can modify objects, while Validating Admission can only allow or reject them.

---

### Q8. Are Admission Controllers Controllers?

No. Admission Controllers execute during API request processing, whereas Controllers continuously reconcile stored resources.

---

### Q9. Can Admission Controllers watch Kubernetes resources?

No. Watching resources is the responsibility of Controllers and Informers.

---

### Q10. What happens if an Admission Controller rejects a request?

The API Server returns an error to the client, and the object is never persisted to etcd.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Pod creation rejected | Admission policy denied the request |
| Default values missing | Mutating Admission Controller not configured or disabled |
| ResourceQuota errors | Namespace quota exceeded |
| Sidecar not injected | Mutating webhook not invoked or namespace excluded |
| Admission latency is high | Slow webhook or overloaded API Server |
| Object accepted unexpectedly | Missing validating policy or webhook |
| API request never reaches Controllers | Admission rejected the request before persistence |
