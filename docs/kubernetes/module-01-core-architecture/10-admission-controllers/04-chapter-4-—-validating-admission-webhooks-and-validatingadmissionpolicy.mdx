# Module 1.10 — Admission Controllers

# Chapter 4 — Validating Admission Webhooks & ValidatingAdmissionPolicy

> **Goal:** Understand how Kubernetes validates API requests using **Validating Admission Webhooks** and the newer **ValidatingAdmissionPolicy (CEL)** framework. By the end of this chapter, you'll understand how Kubernetes enforces security, compliance, governance, and business rules without modifying Kubernetes itself.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. Validating Admission Phase: parallel webhook execution and binary allow/deny decisions
> 2. AdmissionReview response format: `allowed: true/false`, status code, and human-readable message
> 3. ValidatingWebhookConfiguration: rules, object/namespace selectors, matchConditions, and timeouts
> 4. Failure policies (`Fail` vs `Ignore`) and their impact on cluster availability
> 5. Introduction to ValidatingAdmissionPolicy: in-tree CEL-based policy validation (Kubernetes 1.30+ GA)
> 6. Common Expression Language (CEL) syntax for object validation without external webhooks
> 7. ValidatingAdmissionPolicyBinding: scoping CEL policies to namespaces and parameter CRDs
> 8. Performance comparison: Webhook latency (network roundtrip) vs CEL in-process speed ($<0.1$ ms)
> ```

# Real-Life Analogy

Think of Validating Webhooks & CEL like an airport customs passport scanner and luggage X-Ray.

```text
Security Scanner Analogy:

Baggage has passed through auto-tagging (Mutating Webhooks)
Luggage enters the inspection checkpoint (Validating Phase):
  - Check 1 (CEL Policy): Laser scanner checks weight < 50 lbs (Instant in-process check)
  - Check 2 (Validating Webhook): Image sent to off-site specialist (HTTP webhook request)
  - Decision: All checks must approve (allow = true). If ANY check denies -> luggage rejected
  - If off-site link drops:
      - `failurePolicy: Fail` -> Airport halts all departures
      - `failurePolicy: Ignore` -> Security lets bag through with a warning
```

| Security Checkpoint | Validating Admission & CEL |
| :--- | :--- |
| On-site laser weight scanner | `ValidatingAdmissionPolicy` (CEL expression evaluated in-process) |
| Off-site specialist inspection | Validating Admission Webhook (HTTPS request to external pod) |
| Specialist approval ticket | `AdmissionResponse.Allowed: true` |
| Security violation alarm | `AdmissionResponse.Allowed: false` with custom rejection message |
| Network failure policy | `failurePolicy: Fail` (strict) vs `failurePolicy: Ignore` (permissive) |
| Inspection rules binding | `ValidatingAdmissionPolicyBinding` linking CEL rules to namespaces |

> **Important:** `ValidatingAdmissionPolicy` using Common Expression Language (CEL) is a major architectural evolution in Kubernetes. Because CEL expressions are compiled and executed **directly inside the `kube-apiserver` binary**, they eliminate the external network hop, TLS certificate management, and webhook downtime failure modes of traditional validating webhook servers while evaluating complex policies in sub-millisecond time.

# What is a Validating Admission Webhook?

A Validating Admission Webhook is an external HTTPS service that examines an API request and decides:

```text
Allow

or

Reject
```

Unlike a Mutating Webhook,

it **cannot modify** the object.

It only returns a decision.

---

# Mutation vs Validation

```text
Mutating Webhook
  |
  v
Modify Object

----------------------

Validating Webhook
  |
  v
Allow

or

Reject
```

Validation protects the cluster from invalid or non-compliant resources.

Historically,



# What is ValidatingAdmissionPolicy?

ValidatingAdmissionPolicy is a built-in Kubernetes resource that evaluates validation rules using **CEL (Common Expression Language)**.

Unlike webhooks,

it does **not** require an external HTTP service.

---

# Architecture

```text
API Server
  |
  v
CEL Engine
  |
  v
Evaluate Policy
  |
  v
Allow / Reject
```

Everything happens inside the API Server.

---

# Why CEL?

CEL is:

- Safe
- Fast
- Deterministic
- Sandboxed

It allows Kubernetes to evaluate expressions without executing arbitrary code.

# ValidatingAdmissionPolicyBinding

A policy defines **what** to evaluate.

A binding defines **where** the policy applies.

Relationship:

```text
Policy
  |
  v
Binding
  |
  v
Namespaces
  |
  v
Resources
```

This separation allows the same policy to be reused across different scopes.

# Webhooks vs ValidatingAdmissionPolicy

| Validating Webhook | ValidatingAdmissionPolicy |
|-------------------|---------------------------|
| External service | Runs inside API Server |
| HTTPS required | No network calls |
| Any programming language | CEL expressions |
| Operational overhead | Simpler management |
| Maximum flexibility | High performance for declarative rules |

# When to Use Webhooks

Use Validating Webhooks when you need:

- External API lookups
- Database access
- Complex business logic
- Organization-specific integrations
- Cross-system validation

---

# When to Use ValidatingAdmissionPolicy

Use ValidatingAdmissionPolicy when validation depends only on the Kubernetes request itself.

Examples:

- Required labels
- Naming conventions
- Resource limits
- Image prefixes
- Security settings
- Immutable field checks

# Common Misconceptions

### ❌ Misconception 1

Validating Webhooks can modify objects.

**Correct:** They can only allow or reject requests.

---

### ❌ Misconception 2

Validation occurs before mutation.

**Correct:** Mutation always finishes before validation begins.

---

### ❌ Misconception 3

ValidatingAdmissionPolicy replaces every webhook.

**Correct:** It replaces many simple validation webhooks, but complex logic still requires webhooks.

---

### ❌ Misconception 4

CEL can call external APIs.

**Correct:** CEL evaluates expressions locally inside the API Server and cannot perform arbitrary network operations.

---

### ❌ Misconception 5

Every webhook should use Failure Policy = Ignore.

**Correct:** Security-critical validation often requires `Fail`.

---

### ❌ Misconception 6

A rejected request reaches etcd.

**Correct:** Rejected requests are discarded before persistence.

---

### ❌ Misconception 7

Multiple validating webhooks share one decision.

**Correct:** Each webhook evaluates independently, and a rejection from one webhook prevents the request from being admitted.

# Common Interview Questions

### Q1. What is a Validating Admission Webhook?

An external HTTPS service that validates Kubernetes API requests and either allows or rejects them.

---

### Q2. Can a Validating Webhook modify an object?

No. It can only return an allow or deny decision.

---

### Q3. Why does validation happen after mutation?

To ensure validators inspect the final object that will be stored.

---

### Q4. What is ValidatingWebhookConfiguration?

A Kubernetes resource that configures when and how validating webhooks are invoked.

---

### Q5. What is ValidatingAdmissionPolicy?

A built-in Kubernetes validation framework that uses CEL expressions instead of external webhooks.

---

### Q6. What is CEL?

Common Expression Language, a safe expression language used by Kubernetes to evaluate declarative admission policies.

---

### Q7. What is the purpose of ValidatingAdmissionPolicyBinding?

It binds a policy to specific resources, namespaces, or scopes.

---

### Q8. When should you choose a webhook instead of ValidatingAdmissionPolicy?

When validation requires external systems or complex business logic.

---

### Q9. Why is ValidatingAdmissionPolicy generally faster?

Because it runs inside the API Server and avoids network communication.

---

### Q10. What happens when a validating webhook rejects a request?

The API Server returns an error to the client, and the object is never persisted.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Request rejected unexpectedly | Validation policy matched the request |
| Webhook never invoked | Rules, selectors, or match conditions did not match |
| Admission latency high | Slow webhook or network delay |
| Policy not enforced | Missing ValidatingAdmissionPolicyBinding or incorrect webhook configuration |
| Registry policy ignored | Validation rule not matching image field |
| Webhook unavailable | Failure Policy determines allow or reject |
| CEL expression always fails | Invalid or incorrect policy expression |
