# Module 1.10 — Admission Controllers

# Chapter 3 — Mutating Admission Webhooks

> **Goal:** Understand how **Mutating Admission Webhooks** allow Kubernetes to dynamically modify API requests before they are stored in etcd. By the end of this chapter, you'll understand the complete mutation pipeline, AdmissionReview protocol, JSON Patch mechanism, webhook configuration, failure handling, and production patterns used by systems like Istio, Linkerd, Kyverno, and OpenShift.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. What Mutating Webhooks are and how they dynamically alter objects in flight
> 2. The AdmissionReview (v1) request and response protocol
> 3. JSON Patch (RFC 6902): `add`, `replace`, `remove` operations encoded in Base64
> 4. MutatingWebhookConfiguration: rules, clientConfig, failurePolicy, and timeouts
> 5. Namespace and Object selectors: scoping webhooks to specific targets
> 6. Side effects and idempotency: why mutation must be deterministic
> 7. Reinvocation policy (`Never` vs `IfNeeded`): re-running webhooks when downstream webhooks mutate fields
> 8. Production architectures: Istio sidecar injection, Vault agent injection, Kyverno defaulting
> ```

# Real-Life Analogy

Think of Mutating Admission Webhooks like an airport baggage auto-tagging and safety wrap station.

```text
Baggage Prep Station Analogy:

Passenger checks in luggage (Pod manifest submitted to API Server)
Luggage moves down the conveyor belt through automated prep stations (Mutating Webhooks):
  - Station 1 (Istio): Attaches an RFID tracking tag to the handle (Injects envoy sidecar container)
  - Station 2 (Security): Wraps the suitcase in protective tamper-evident film (Adds securityContext)
  - Station 3 (Billing): Sticks a heavy luggage barcode sticker (Adds standard billing labels)
Luggage emerges with modifications applied
Only after all prep stations finish is the luggage sent to X-Ray inspection (Validating phase)
```

| Baggage Prep Station | Mutating Webhook |
| :--- | :--- |
| Unprocessed suitcase | Original API request object (`request.object`) |
| RFID tracking tag attached | Injected sidecar container (Istio / Vault) |
| Tamper-evident film applied | Injected `securityContext` / resource requests |
| Instructions for baggage modification | Base64-encoded JSON Patch (`response.patch`) |
| Prep station offline policy | `failurePolicy: Ignore` or `failurePolicy: Fail` |
| Moving to X-Ray scanner | Passing mutated object to **Validating Admission** phase |

> **Important:** Mutating webhooks **execute strictly before Validating webhooks**. When an object is mutated, the downstream validating admission phase (and schema validation) validates the **mutated version** of the object, not the original YAML submitted by the user. If a mutating webhook introduces invalid fields or violates a security policy, the validating phase will immediately reject the entire request.

# What is a Mutating Admission Webhook?

A Mutating Admission Webhook is an external HTTPS service that receives Kubernetes API requests and returns modifications.

Unlike built-in admission plugins,

it is:

- User-defined
- Deployable
- Configurable
- Extensible

# AdmissionReview API

The API Server communicates with webhooks using the **AdmissionReview** API.

The request contains information about:

- User
- Operation
- Namespace
- Object
- Old Object
- Resource
- UID

The webhook returns an AdmissionReview response.

---

# AdmissionReview Request

Conceptually:

```text
AdmissionReview

+--────── UID

+--────── Resource

+--────── Operation

+--────── UserInfo

+--────── Namespace

+--────── Object
```

The webhook receives the complete request context.

---

# AdmissionReview Response

The webhook responds with:

```text
Allowed?
  |
  v
True

or

False
```

For mutation,

it also returns:

```text
JSON Patch
```

  v

  |
  v

  |

```

# What is JSON Patch?

The webhook does **not** send back the entire modified object.

Instead,

it returns only the changes.

These changes use the JSON Patch format.

---

# Why JSON Patch?

Imagine a Pod with:

```text
300 Fields
```

Webhook wants to add:

```yaml
label:
  team: platform
```

Sending the whole object would waste bandwidth.

Instead,

the webhook returns:

```text
Only The Change
```

---

# Conceptual JSON Patch

```text
Add
  |
  v
/metadata/labels/team
  |
  v
platform
```

The API Server applies the patch to the original object.

---

```text

  |
  v

  |
  v

  |
  v

```

# Namespace Selector

Not every namespace requires mutation.

# Failure Policy

Suppose the webhook is unavailable.

What should Kubernetes do?

Two options exist.

---

# Fail

```text
Webhook Down
  |
  v
Reject Request
```

Use for:

- Security
- Compliance
- Critical policy

---

# Ignore

```text
Webhook Down
  |
  v
Continue Admission
```

Use for:

- Optional mutation
- Best-effort enhancements

Choosing the correct failure policy is a critical production decision.

---

# Timeout

Webhooks should respond quickly.

Example:

```text
API Server
  |
  v
Wait
  |
  v
Webhook
  |
  v
Response
```

If the timeout expires,

the Failure Policy determines what happens next.

---

# Side Effects

Some webhooks modify external systems.

Examples:

- Database writes
- Cloud API calls
- Billing systems

Mutation webhooks should ideally avoid side effects because the same request may be retried.

---

# Why Side Effects Are Dangerous

Suppose:

```text
Webhook
  |
  v
Create Cloud VM
  |
  v
Timeout
  |
  v
Retry
```

Now two VMs may exist.

Admission webhooks should be designed to avoid or tolerate retries safely.

---

# Reinvocation Policy

Imagine:

Webhook A adds:

```text
Container
```

Webhook B modifies:

```text
All Containers
```

Should Webhook B see the newly added container?

Reinvocation Policy controls whether eligible webhooks may run again after earlier mutations.

# Performance Considerations

Unlike built-in admission plugins,

Mutating Webhooks require:

- HTTPS
- Network communication
- TLS validation
- Serialization
- Deserialization

Every webhook increases admission latency.

---

# High Availability

Production webhook deployments should:

```text
Multiple Replicas
  |
  v
Service
  |
  v
Load Balancer
  |
  v
API Server
```

Avoid single points of failure.

# Production Best Practices

✔ Keep mutation logic deterministic.

✔ Make mutations idempotent.

✔ Respond within milliseconds whenever possible.

✔ Minimize network latency.

✔ Avoid external side effects.

✔ Use namespace selectors to reduce unnecessary invocations.

✔ Use object selectors to limit webhook scope.

✔ Choose Failure Policy carefully.

✔ Monitor webhook latency and failures.

✔ Deploy multiple webhook replicas.

# Common Misconceptions

### ❌ Misconception 1

Mutating Webhooks replace built-in admission plugins.

**Correct:** They extend Kubernetes for organization-specific requirements.

---

### ❌ Misconception 2

The webhook returns the entire modified object.

**Correct:** It typically returns a JSON Patch describing only the required changes.

---

### ❌ Misconception 3

Mutation happens after validation.

**Correct:** Mutation always occurs before validation.

---

### ❌ Misconception 4

Only one webhook can modify an object.

**Correct:** Multiple mutating webhooks can execute sequentially.

---

### ❌ Misconception 5

Webhooks should perform long-running work.

**Correct:** Admission webhooks should respond quickly to avoid delaying API requests.

---

### ❌ Misconception 6

Webhook failures are always ignored.

**Correct:** Behavior depends on the configured Failure Policy.

---

### ❌ Misconception 7

Mutating Webhooks should create external resources.

**Correct:** They should avoid side effects because admission requests may be retried.

# Common Interview Questions

### Q1. What is a Mutating Admission Webhook?

An external HTTPS service that modifies Kubernetes API requests before they are persisted.

---

### Q2. When is a Mutating Admission Webhook executed?

After built-in mutating admission plugins and before any validating admission.

---

### Q3. How does the API Server communicate with a webhook?

Using the AdmissionReview API.

---

### Q4. Why does the webhook return a JSON Patch instead of the entire object?

To efficiently describe only the required modifications.

---

### Q5. What is MutatingWebhookConfiguration?

A Kubernetes resource that tells the API Server when and how to invoke a mutating webhook.

---

### Q6. What is the purpose of Namespace Selectors?

To limit webhook execution to specific namespaces.

---

### Q7. What is Failure Policy?

It determines whether API requests should fail or continue if the webhook cannot be reached.

---

### Q8. Why should mutation logic be idempotent?

Because requests may be retried or multiple admission cycles may occur.

---

### Q9. Why are side effects discouraged?

Because admission requests can be retried, potentially causing duplicate external actions.

---

### Q10. Name some real-world uses of Mutating Admission Webhooks.

Istio sidecar injection, Linkerd proxy injection, label injection, image registry rewriting, security defaulting, and secret injection.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Sidecar not injected | Namespace selector or object selector did not match |
| API requests are slow | Webhook latency or timeout |
| Requests rejected unexpectedly | Failure Policy set to `Fail` and webhook unavailable |
| Labels not added | JSON Patch incorrect or webhook not triggered |
| Duplicate mutations | Mutation logic is not idempotent |
| Webhook never called | Rules do not match the request |
| TLS errors | Invalid certificate or CA bundle configuration |
| Webhook loops | Incorrect reinvocation handling or conflicting mutations |
