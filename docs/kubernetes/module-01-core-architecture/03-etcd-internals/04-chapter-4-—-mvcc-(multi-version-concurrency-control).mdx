# Why Should You Learn MVCC?

One of the most common Kubernetes interview questions is:

> **What is `resourceVersion`?**

Or,

> **How does Kubernetes detect update conflicts?**

Or,

> **How do Watches know where to continue after a disconnect?**

The answer starts with:

```text
MVCC
```

Without MVCC:

- Watches would not know what changed.
- Controllers would overwrite each other's updates.
- Kubernetes could not detect stale objects.
- Historical reads would be impossible.
- Optimistic locking would not exist.

MVCC is one of the most important building blocks inside etcd.

---

# Real-Life Analogy

Think of MVCC like a git repository where every commit is permanent and retrievable.

```text
Git Repository Analogy:

Every file change creates a new commit (new revision)
Old commits are never overwritten
You can checkout any historical commit
Two developers can read the same file simultaneously without locking
Merge conflicts detected at commit time (not at read time)
```

| Git | etcd MVCC |
| :--- | :--- |
| Repository | etcd key space |
| File | etcd key |
| Commit hash | Global Revision number |
| File content at commit | Key value at a specific revision |
| `git log` | MVCC revision history |
| Merge conflict | Compare-And-Swap failure |
| `git checkout <commit>` | Historical read at `--rev=<revision>` |

> **Important:** Kubernetes `resourceVersion` is **directly the etcd global revision**, stored as a string. When you read a Pod and see `resourceVersion: "183042"`, that `183042` is the etcd cluster revision at which that Pod was last written. This is why `resourceVersion` is monotonically increasing and cluster-wide.

# What is MVCC?

MVCC stands for:

```text
Multi-Version

Concurrency

Control
```

Instead of replacing data immediately,

MVCC creates:

```text
New Version

for

```

Older versions remain available for a period of time.

# Optimistic Concurrency

Instead of locking,

MVCC assumes conflicts are rare.

Workflow:

```text

v

Remember Revision

v

Modify

v

Write

v

Revision Still Same?

v

Yes

v

Success

------------------

No

v

Conflict
```

This is called:

```text
Optimistic Concurrency Control
```

# Why "Optimistic"?

Because the system optimistically assumes:

```text
Nobody Else

Changed

The Object
```

Most Kubernetes objects are not modified simultaneously.

So this approach is efficient.

# Compare-And-Swap (CAS)

CAS is one of the most common transaction patterns.

Example:

```text

Version == 5

THEN

Update Value

ELSE

Reject
```

No race conditions.



Update succeeds.


Suppose two controllers try to become leader.

Without CAS:


With CAS:

Leader election becomes safe.

# Common Misconceptions

### ❌ Misconception 1

A Revision belongs to one key.

Wrong.

A revision is global across the entire etcd database.

---

### ❌ Misconception 2

Version and Revision are the same.

Wrong.

Revision is global.

Version belongs to a single key.

---

### ❌ Misconception 3

Create Revision changes after updates.

Wrong.

It remains fixed for the lifetime of the key.

---

### ❌ Misconception 4

Historical data is stored forever.

Wrong.

Old revisions are eventually removed during **Compaction**, which we'll study in a later chapter.

---

### ❌ Misconception 5

Optimistic concurrency locks the database.

Wrong.

It avoids locks by detecting conflicts using revisions.

---

### ❌ Misconception 6

`resourceVersion` is simply a timestamp.

Wrong.

It is a version identifier used by Kubernetes for concurrency control and watch semantics. It is not a wall-clock timestamp.

# Common Interview Questions

### Q1. What is MVCC?

MVCC (Multi-Version Concurrency Control) allows etcd to maintain multiple versions of data, enabling historical reads, watches, and optimistic concurrency.

---

### Q2. What is a Global Revision?

A monotonically increasing counter that increments for every successful write in the etcd database.

---

### Q3. What is the difference between Revision and Version?

Revision is global to the database.

Version tracks how many times a particular key has been modified.

---

### Q4. What is Create Revision?

The revision at which the key was first created. It never changes.

---

### Q5. What is Modify Revision?

The revision of the most recent successful update to the key.

---

### Q6. Why are historical reads useful?

They allow clients and watches to observe past database states and recover from temporary disconnections without starting over, as long as the required history has not been compacted.

---

### Q7. What is Optimistic Concurrency Control?

A concurrency model where updates succeed only if the object has not changed since it was read.

---

### Q8. What is Compare-And-Swap (CAS)?

A transactional pattern that updates a value only if a specified condition (such as the expected version or revision) still holds.

---

### Q9. How is `resourceVersion` related to MVCC?

Kubernetes uses version information derived from etcd's MVCC storage to implement optimistic concurrency control and watch continuation.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| HTTP 409 Conflict during update | The object was modified after it was read; retry with the latest version |
| Watch cannot resume | Requested revision has already been compacted |
| Controller repeatedly conflicts | Multiple controllers updating the same object simultaneously |
| Stale reads | Client is using an older object revision than the current state |
| Transaction fails unexpectedly | Compare condition in the transaction evaluated to false |
