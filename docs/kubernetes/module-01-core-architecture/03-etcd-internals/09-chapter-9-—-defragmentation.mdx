# Chapter 9 — Defragmentation

> **Goal:** Understand why etcd databases continue to consume disk space even after compaction, how BoltDB stores data internally using B+ Trees and fixed-size pages, how fragmentation occurs, how online defragmentation reclaims storage, and how defragmentation impacts production performance.
>

>
> ```text

---

> **Important:** Defragmentation is **blocking** on the member being defragmented. The targeted etcd member is unavailable for reads and writes for the entire duration of the defrag operation. In production, defrag must be run as a **rolling operation** — one member at a time — during a planned maintenance window to avoid quorum loss.

> **Why is my etcd database still 20 GB after compaction?**

> **Why didn't compaction reduce disk usage?**

```text
Defragmentation
```

Compaction removes:

```text

```

Defragmentation reclaims:

```text
Disk Space
```

These are two different operations.

# What is Disk Fragmentation?

Disk fragmentation means:

> **The database file contains unused internal space that is no longer storing active data but is still allocated on disk.**

The file size remains unchanged.

Unused pages remain inside the file.

# B+ Tree Overview

BoltDB organizes pages using a:

```text
B+ Tree
```

A B+ Tree is a balanced tree optimized for disk storage.

Unlike a binary tree,

one node can contain many keys.

---

# Simplified B+ Tree

```text
                 Root

           /      |      \

         /        |        \

     Node      Node      Node

     /  \      /  \      /  \

   Leaf Leaf Leaf Leaf Leaf Leaf
```

Actual data resides in leaf pages.

Internal nodes guide searches.

---

# Why Use B+ Trees?

Searching:

```text
Millions

of Keys
```

requires only a few page reads.

Instead of scanning:

```text
Entire Database
```

BoltDB follows:

```text
Root

v

Internal Node

v

Leaf Page
```

Very efficient.


Future writes may reuse them,

# Defragmentation

Defragmentation rewrites the database.

Workflow:

```text

v

v

v

Copy Live Data

v

Discard Empty Pages

v

Replace Old Database
```

Unused pages disappear.

# Online Defragmentation

Modern etcd supports:

```text
Online Defrag
```

Meaning:

The member remains running,

although defragmentation is a resource-intensive maintenance task.

During the operation,

the member rewrites its database to eliminate unused pages.

---

# Online Defrag Workflow

```text
Running Member

v

Pause Internal Writes Briefly

v

Copy Live Pages

v

Rewrite Database

v

Replace File

v

Resume Normal Operation
```

The member remains part of the cluster,

but performance may temporarily decrease.

# Difference Between Compaction and Defragmentation

| Compaction | Defragmentation |
|------------|-----------------|
| Removes old MVCC history | Reclaims physical disk space |
| Logical cleanup | Physical storage rewrite |
| Current data remains | Current data copied into a new compact layout |
| Does not shrink file | Shrinks database file when possible |
| Enables watch cleanup | Improves storage efficiency |

# Performance Effects

Defragmentation is beneficial,

but not free.

During execution:

- Disk I/O increases.
- CPU usage may rise.
- Memory activity increases.
- Request latency may temporarily increase.

For this reason,

production clusters typically schedule defragmentation during maintenance windows or periods of lower activity.

# Production Monitoring

Monitor:

- Database size
- In-use database size
- Free space ratio
- Storage growth
- Disk latency
- Defragmentation duration

---

# Production Best Practices

✔ Run compaction regularly.

✔ Defragment only after sufficient fragmentation has accumulated.

✔ Defragment members one at a time.

✔ Verify cluster health before beginning maintenance.

✔ Monitor disk I/O during defragmentation.

✔ Keep recent snapshots before major maintenance.

✔ Avoid unnecessary defragmentation if the free space ratio is low.

# Common Misconceptions

### ❌ Misconception 1

Compaction frees disk space.

Wrong.

Compaction removes historical MVCC revisions logically.

Defragmentation reclaims physical storage.

---

### ❌ Misconception 2

Free pages disappear automatically.

Wrong.

They remain inside the database file until reused or removed by defragmentation.

---

### ❌ Misconception 3

BoltDB stores data in ordinary files without structure.

Wrong.

BoltDB organizes data using a B+ Tree and fixed-size pages.

---

### ❌ Misconception 4

Defragmentation improves correctness.

Wrong.

Its purpose is storage optimization, not data correctness.

---

### ❌ Misconception 5

Online defragmentation has zero impact.

Wrong.

It can temporarily increase resource usage and latency.

---

### ❌ Misconception 6

You should defragment every day.

Wrong.

Only perform defragmentation when fragmentation justifies the operational cost.

# Common Interview Questions

### Q1. Why doesn't compaction reduce database file size?

Because it removes historical MVCC revisions logically but does not rewrite the BoltDB file.

---

### Q2. What is fragmentation?

Unused pages remain allocated inside the database file after data has been removed.

---

### Q3. What is a BoltDB page?

The basic fixed-size storage unit used by BoltDB to store metadata and user data.

---

### Q4. What is a B+ Tree?

A balanced tree structure optimized for disk-based storage, where internal nodes guide searches and leaf nodes store actual data.

---

### Q5. What is online defragmentation?

A process that rewrites the database while the etcd member remains running, reclaiming unused space.

---

### Q6. Why shouldn't all etcd members be defragmented simultaneously?

Because doing so may temporarily reduce cluster performance and increase operational risk.

---

### Q7. What is space reclamation?

The process of physically removing unused pages so the database file becomes smaller.

---

### Q8. What is the difference between free pages and deleted data?

Deleted historical data creates free pages. Those pages remain allocated until reused or removed by defragmentation.

---

### Q9. Is fragmentation always bad?

No.

Free pages can be reused efficiently. Defragmentation is most valuable when a significant amount of disk space is unused.

---

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Database file remains large after compaction | Defragmentation has not been performed |
| High disk usage despite little active data | Large number of free pages due to fragmentation |
| Increased latency during defragmentation | Expected temporary resource usage during database rewrite |
| Frequent storage growth | High write volume combined with delayed maintenance |
| Database size greatly exceeds in-use size | Significant fragmentation; evaluate whether defragmentation is appropriate |
