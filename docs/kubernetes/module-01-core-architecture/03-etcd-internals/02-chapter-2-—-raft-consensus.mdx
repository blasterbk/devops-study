# Why Should You Learn RAFT?

One of the most common Kubernetes interview questions is:

> **How does etcd ensure every node has exactly the same data?**

Or,

> **Why doesn't Kubernetes lose data when one etcd node crashes?**

Or,

> **How does Kubernetes avoid split-brain?**

The answer is:

```text
RAFT Consensus
```

Without RAFT:

- Multiple nodes could accept conflicting writes.
- Different etcd members could have different databases.
- Kubernetes controllers would see inconsistent cluster state.
- The entire Control Plane could become unreliable.

RAFT is the reason Kubernetes trusts etcd.

---

# Real-Life Analogy

Think of Raft like a committee that must vote before any decision is official.

```text
Committee Voting Analogy:

One chairperson (Leader) proposes decisions
Members (Followers) acknowledge the proposal
Decision is official only after majority votes YES
If chair disappears, members elect a new one
No decision passes without strict majority
```

| Committee | Raft / etcd |
| :--- | :--- |
| Chairperson | Raft Leader |
| Committee members | Raft Followers |
| Candidate for chairperson | Raft Candidate |
| Vote to approve | AppendEntries acknowledgment |
| Majority vote (quorum) | Write commit threshold |
| New chair elected | New Leader election after timeout |

> **Important:** Raft requires a **strict majority quorum** to commit any write. In a 3-member cluster, 2 members must acknowledge before a write is committed. If only 1 member is reachable, writes are rejected entirely — availability is sacrificed to preserve correctness.

# What is Consensus?

Consensus means:

> **All healthy members agree on exactly the same sequence of operations.**

Not merely:

```text
Same Final Data
```

But:

```text
Same Order

v

Same History

v

Same Database
```

Order matters.

# What is RAFT?

RAFT is a distributed consensus algorithm designed to:

- Elect one leader
- Replicate logs
- Maintain consistency
- Recover from failures
- Prevent split-brain

Unlike older algorithms such as Paxos,

RAFT was intentionally designed to be easier to understand and implement.

---

# High-Level Architecture

```text
             RAFT Cluster

        ┌────────┬────────┐

        ▼        ▼        ▼

     Member1  Member2  Member3

          One Leader

         Two Followers
```

At any moment:

```text
Exactly One Leader
```

All writes go through the leader.

Imagine:

Three members all accepting writes independently.

```text
Write A

v

Member 1

-----------------

Write B

v

Member 2

-----------------

Write C

v

Member 3
```

Conflicts become unavoidable.

RAFT solves this by saying:

```text

```

Everyone else forwards requests.

# RAFT Node States

Each member is always in exactly one state.

```text
Follower

v

Candidate

v

Leader
```

Transitions occur automatically.

---

# Followers

Most members are Followers.

Responsibilities:

- Accept replicated logs
- Respond to leader
- Vote during elections
- Reject client writes

Followers are passive.

They never initiate writes.

---

# Follower Workflow

```text
Leader

v

Heartbeat

v

Follower

v

Reset Election Timer
```

As long as heartbeats continue,

the follower remains a follower.

---

# Leader

The Leader is the only member allowed to:

- Accept writes
- Replicate logs
- Send heartbeats
- Coordinate consensus

Every client write begins here.

---

# Leader Responsibilities

```text
Receive Write

v

Append Log

v

Replicate

v

Wait Majority

v

Commit

v

Reply Success
```

Everything flows through the leader.

# Terms

RAFT divides time into logical periods called:

```text
Terms
```

Every election creates a new term.

Example:

```text
Term 1

v

Leader A

----------------

Term 2

v

Leader B

----------------

Term 3

v

Leader C
```

Terms never decrease.

---

# Why Terms Exist

Imagine:

An old leader reconnects after a network issue.

Without terms:

It may continue accepting writes.

With terms:

The old leader sees:

```text
Higher Term Exists

v

Step Down

v

Become Follower
```

Terms prevent stale leaders.

# Random Election Timeout

Why random?

Suppose all followers timeout simultaneously.

```text
Candidate A

Candidate B

Candidate C
```

Nobody wins.

Election repeats forever.

Instead,

timeouts are randomized.

Example:

```text
160 ms

221 ms

295 ms
```

Only one node usually starts first.

# Common Misconceptions

### ❌ Misconception 1

Every etcd member accepts writes.

Wrong.

Only the current leader accepts writes.

---

### ❌ Misconception 2

Heartbeats transfer data.

Wrong.

Heartbeats primarily confirm the leader is still alive and help maintain leadership. Log replication may occur separately or piggyback on heartbeat messages.

---

### ❌ Misconception 3

A write succeeds after reaching the leader.

Wrong.

The write succeeds only after it is replicated to a majority and committed.

---

### ❌ Misconception 4

The oldest server automatically becomes leader.

Wrong.

Leadership is determined through elections and voting, not server age.

---

### ❌ Misconception 5

Split-brain cannot happen because servers communicate.

Wrong.

Network partitions can happen. RAFT prevents split-brain by requiring a majority to elect and maintain a leader.

# Common Interview Questions

### Q1. What problem does RAFT solve?

RAFT provides distributed consensus, ensuring all healthy members agree on the same ordered sequence of operations.

---

### Q2. Why does RAFT use a leader?

A single leader serializes writes, preventing conflicting updates and simplifying consistency.

---

### Q3. What are the three RAFT node states?

- Follower
- Candidate
- Leader

---

### Q4. What is a Term?

A logical election epoch. Each new election increments the term, allowing nodes to identify stale leaders.

---

### Q5. Why are election timeouts randomized?

To reduce the chance that multiple followers become candidates simultaneously, which can lead to repeated split votes.

---

### Q6. What is the purpose of heartbeats?

To let followers know the leader is still alive and prevent unnecessary elections.

---

### Q7. What is the Commit Index?

The Commit Index identifies the highest log entry that has been safely replicated to a majority and can be applied.

---

### Q8. Why is majority consensus required?

It guarantees that committed data survives failures and prevents conflicting leaders from existing simultaneously.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Frequent leader changes | Network instability, high latency, overloaded leader, or election timeout tuning issues |
| Slow writes | Followers slow to acknowledge replication, disk latency, or network delays |
| Cluster becomes read-only for writes | Majority of members unavailable; no leader can safely commit writes |
| Continuous elections | Lost heartbeats, network partitions, or overloaded members |
| Stale leader steps down | Node receives a message with a higher term and transitions back to follower |
