# Why Should You Learn etcd Watches?

One of the most important questions in Kubernetes is:

> **How does Kubernetes know something changed?**

For example:

- A Pod is deleted.
- A Deployment is updated.
- A Node becomes NotReady.
- A Secret changes.
- A ConfigMap is modified.

Who tells:

- Scheduler?
- Controller Manager?
- Operators?
- Informers?
- kube-proxy?

The answer is:

```text
etcd Watches
```

Without Watches:

Every Kubernetes component would need to repeatedly poll the API Server.

That would make Kubernetes extremely inefficient.

---

# Real-Life Analogy

Think of etcd Watches like a radio broadcast station.

```text
Radio Broadcast Analogy:

Station (etcd) broadcasts continuously
Listeners (Kubernetes components) tune in whenever they want
New listeners catch up from any past broadcast (revision-based)
No listener needs to call the station to ask "anything new?"
If signal drops, listener retunes from last heard broadcast
```

| Radio Broadcast | etcd Watches |
| :--- | :--- |
| Radio station | etcd |
| Broadcast signal | Watch event stream |
| Radio listener | kube-apiserver Watch Cache |
| Tune from timestamp | Watch from specific revision |
| Signal lost, retune | Watch reconnect from last revision |
| Station broadcast ID | Revision number per event |

> **Important:** Kubernetes Informers and controllers do **not** watch etcd directly. They watch the **kube-apiserver Watch Cache** — which in turn holds a single Watch stream to etcd. This means etcd only ever serves one Watch stream per resource type, regardless of how many controllers are running.

Imagine:


No unnecessary API requests.

No polling.

Only actual changes are transmitted.

# What is a Watch?

A Watch is a long-lived subscription.

Instead of asking:

```text
What is the current state?
```

You ask:

```text
Notify me

Whenever

Something Changes.
```

The server continuously streams events.

One request.

Many events.

# Watch API

The Watch API allows clients to subscribe to changes for one or more keys or key ranges.

Typical operations include:

- Create Watch
- Cancel Watch
- Receive Events
- Resume Watch

Unlike a traditional REST request,

the Watch API creates a persistent stream.

---

# Watch Request

Conceptually:

```text
Watch

v

Key

v

Starting Revision
```

Example:

```text
Watch

/registry/pods/

Starting Revision = 100
```

Meaning:

```text
Send Every Change

After

Revision 100
```

---

# Watch Response

Suppose:

```text

Pod Created
```

```text

Revision 101
```

Later:

```text
Revision 102

Pod Updated
```

Server sends:

```text

Revision 102
```

Each event is delivered in revision order.

# Revision-Based Watches

Every watch starts at a specific revision.

Example:

```text
Current Revision

500
```

Client requests:

```text
Watch

From Revision 450
```

Server streams:

```text
451

v

452

v

453

v

...

v

500
```

Then continues with new events.

# Why Start From a Revision?

Suppose:

Client disconnects.

Last processed revision:

```text
800
```

Reconnect.

Instead of:

```text
Restart Everything
```

Client requests:

```text
Watch

Revision 801
```

No events are lost, provided the requested history is still available.

# Watch Progress Notifications

Imagine a watch on a quiet cluster.

Nothing changes for hours.

How does the client know:

- The connection is still healthy?
- The watch has not stalled?

The answer is:

```text
Progress Notifications
```

---

# What is a Progress Notification?

A progress notification is **not** a data change.

It simply tells the client:

```text
You Are

Up To Date

Through Revision X
```

No object changed.

The watch is still alive.

---

# Example

Current revision:

```text
1200
```

No writes occur.

Server sends:

```text
Progress

Revision 1200
```

Later:

```text
Progress

Revision 1200
```

Connection remains healthy.

---

# Why Progress Notifications Matter

Without them:

Client cannot distinguish:

```text
No Changes
```

from

```text
Broken Watch
```

Progress notifications eliminate that uncertainty.

# When Recovery Fails

Suppose:

Client disconnects for several hours.

Meanwhile:

Compaction removes:

```text
Revision 900
```

Client requests:

```text
Watch

901
```

Server responds:

```text
Requested Revision

Compacted
```

The client must rebuild its state.

---

```text

v

v

Perform Fresh LIST

v

Receive Latest Objects

v

Start New Watch

v

```

This pattern is fundamental to Kubernetes Informers.

# Production Best Practices

✔ Always resume watches using the last processed revision when possible.

✔ Handle watch termination gracefully by reconnecting.

✔ Be prepared to rebuild state if the requested revision has been compacted.

✔ Keep watch handlers efficient; slow consumers can delay processing.

✔ Use shared Informers rather than creating independent watches for every controller.

✔ Monitor watch latency and reconnect rates in production.

# Common Misconceptions

### ❌ Misconception 1

A watch repeatedly polls the database.

Wrong.

A watch uses a long-lived stream that pushes events as they occur.

---

### ❌ Misconception 2

A watch always starts from the current state.

Wrong.

A watch can start from a specific revision.

---

### ❌ Misconception 3

If a watch disconnects, all history is lost.

Wrong.

A watch can resume from its last processed revision if that revision has not been compacted.

---

### ❌ Misconception 4

Progress notifications indicate object changes.

Wrong.

They simply confirm the watch is active and has caught up through a given revision.

---

### ❌ Misconception 5

Controllers watch etcd directly.

Wrong.

Controllers typically watch the Kubernetes API Server through Informers. The API Server, in turn, maintains watches against etcd.

# Common Interview Questions

### Q1. What is an etcd Watch?

A long-lived subscription that streams changes for specific keys or key ranges as they occur.

---

### Q2. Why are watches more efficient than polling?

Because they keep a persistent connection open and transmit only changes instead of repeatedly transferring the full dataset.

---

### Q3. What is a Watch Stream?

A persistent communication channel over which the server continuously delivers ordered watch events.

---

### Q4. Why are watches revision-based?

Revisions allow clients to resume from a known point and guarantee ordered event delivery.

---

### Q5. What is a Progress Notification?

A message indicating that the watch is current through a particular revision, even if no data has changed.

---

### Q6. What happens if a watch disconnects?

The client reconnects and requests events starting from the last processed revision. If that revision has already been compacted, the client performs a fresh list and starts a new watch.

---

### Q7. How do Kubernetes Informers use watches?

Informers establish watches through the API Server, receive change events, update their local caches, and notify controllers.

---

### Q8. Does every Kubernetes controller create its own etcd watch?

No.

Controllers generally share Informers, and Informers watch resources through the API Server rather than connecting directly to etcd.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Watch unexpectedly closes | Network interruption, server restart, timeout, or cancellation |
| Watch cannot resume | Requested revision has already been compacted |
| Events appear delayed | Slow client processing, API Server load, or network latency |
| High memory usage | Too many active watches or slow consumers causing buffering |
| Controller misses updates | Informer performed a relist after watch expiration or application logic failed to process events correctly |
