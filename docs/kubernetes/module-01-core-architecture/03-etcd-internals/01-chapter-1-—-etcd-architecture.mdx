# Why Should You Learn etcd?

One of the most common Kubernetes interview questions is:

> **Where does Kubernetes store its data?**

The answer is:

```text
etcd
```

But that answer is only the beginning.

Every Kubernetes object ultimately lives inside etcd.

Examples:

- Pods
- Deployments
- Secrets
- ConfigMaps
- Services
- Nodes
- Namespaces
- RBAC
- Certificates
- CRDs
- Leases

Everything eventually becomes an entry inside etcd.

---

# Why etcd Matters

Imagine the Kubernetes API Server suddenly loses all memory.

Can Kubernetes recover?

Yes.

Because the API Server itself is mostly **stateless**.

Its source of truth is:

```text
etcd
```

If etcd disappears,

your cluster loses:

- Desired State
- Current State
- Cluster Configuration
- Secrets
- Certificates
- Scheduling Information

The entire cluster effectively loses its memory.

---

# Real-Life Analogy

Think of etcd like a bank's central vault ledger.

```text
Bank Vault Analogy:

Every branch (Kubernetes component) needs to know account balances
All transactions are recorded in the central ledger (etcd)
Tellers (API Server) verify and record every transaction
Vault is replicated across multiple locations (etcd cluster)
No transaction is confirmed until the majority of vaults agree (Raft)
```

| Bank | Kubernetes / etcd |
| :--- | :--- |
| Central vault ledger | etcd key-value store |
| Bank teller | kube-apiserver |
| Account balance | Kubernetes object (Pod, Deployment, etc.) |
| Ledger replication across vaults | etcd cluster Raft replication |
| Transaction requires majority approval | Raft quorum write commit |
| Branch offices | Kubernetes components (Scheduler, Controllers) |

> **Important:** `kube-apiserver` is the **only** Kubernetes component that directly reads and writes etcd. Schedulers, controllers, kubelets, and all other components communicate exclusively through the API Server — never directly with etcd.

---

# What is etcd?

etcd is a:

```text
Distributed

Consistent

Highly Available

Key-Value Database
```

Developed by CoreOS (now part of Red Hat),

it is specifically designed for:

- Distributed Systems
- Configuration Storage
- Service Discovery
- Leader Election
- Consensus
- Metadata Storage

It is **not** a relational database.

---

# What Makes etcd Special?

Most databases optimize for:

- SQL
- Complex Queries
- Analytics
- Large Transactions

etcd optimizes for:

- Strong Consistency
- Fast Reads
- Reliable Writes
- Fault Tolerance
- Consensus

This makes it perfect for Kubernetes.

---

# Why Kubernetes Uses etcd

Kubernetes needs storage that guarantees:

```text
Every Control Plane component

Always sees

Exactly the same cluster state.
```

If one controller thinks:

```text
Deployment = 5 replicas
```

while another thinks:

```text
Deployment = 3 replicas
```

the cluster becomes inconsistent.

etcd prevents this.

---

# Requirements of Kubernetes Storage

Kubernetes storage must provide:

✓ Strong consistency

✓ High availability

✓ Leader election

✓ Watch support

✓ Atomic transactions

✓ Version history

✓ Distributed consensus

✓ Reliable failure recovery

Very few databases provide all of these.

---

# Why Not MySQL?

MySQL is excellent for applications.

But Kubernetes needs:

```text
Continuous Watches

v

Leader Election

v

Distributed Consensus

v

Linearizable Reads

v

MVCC
```

Traditional relational databases were not designed for this workload.

---

# Why Not Redis?

Redis is extremely fast.

However:

- Primarily in-memory
- No built-in distributed consensus (in the same sense as etcd's RAFT)
- Different consistency guarantees
- Not optimized for Kubernetes-style metadata

# etcd Cluster Architecture

Unlike a traditional database,

etcd is usually deployed as a cluster.

Example:

```text
3 Members
```

Architecture:

```text
           etcd Cluster

      ┌────────────────────┐

      |                    |

      ▼                    ▼

 Member 1              Member 2

      |                    |

      +--────────┬─────────┘

                 ▼

            Member 3
```

Each member stores replicated data.

---

# Why Multiple Members?

Imagine only one database server exists.

```text
Server Crash

v

Cluster Down
```

Now imagine:

```text
3 Members
```

```text
One Member Fails

v

Two Members Continue

v

Cluster Still Works
```

This provides High Availability.

---

# What is a Member?

A **Member** is a single etcd process participating in the cluster.

Each member has:

- Storage Engine
- WAL (Write Ahead Log)
- Snapshot Files
- RAFT State
- Network Connections

Each member maintains a copy of the replicated database.

---

```text
/registry/configmaps/

/registry/nodes/

/registry/services/

/registry/leases/

```

Internally,

---

# Key-Value Example

A Pod:

```yaml
metadata:
  name: nginx
  namespace: default
```

May be stored conceptually as:

```text
Key:

/registry/pods/default/nginx

--------------------------------

Value:

Serialized Pod Object
```

The value is stored in a binary-serialized format, not raw YAML.

# Storage Engine Overview

Internally,

etcd has multiple layers.

```text
Client

v

v

RAFT

v

MVCC

v

Backend

v

BoltDB

v

```

Each layer has a different responsibility.

---

# Layer Responsibilities

### gRPC API

Receives client requests.

---

### RAFT

Ensures every member agrees on writes.

---

### MVCC

Maintains object versions and revision history.

---

### Backend

Provides persistent storage.

---

### BoltDB

Stores data on disk using a B+Tree structure.

# Common Misconceptions

### ❌ Misconception 1

etcd stores YAML files.

Wrong.

Objects are serialized into a compact binary representation before storage.

---

### ❌ Misconception 2

Controllers communicate directly with etcd.

Wrong.

Controllers communicate with the API Server.

Only the API Server normally accesses etcd.

---

### ❌ Misconception 3

Every etcd member independently accepts writes.

Wrong.

Writes are coordinated through the RAFT consensus protocol. (We will study this in the next chapters.)

---

### ❌ Misconception 4

etcd is just another SQL database.

Wrong.

It is a distributed, strongly consistent key-value store optimized for coordination and metadata.

# Common Interview Questions

### Q1. What is etcd?

etcd is a distributed, strongly consistent, highly available key-value database used by Kubernetes as its primary datastore.

---

### Q2. Why does Kubernetes use etcd?

Because it provides strong consistency, distributed consensus, watches, transactions, high availability, and reliable metadata storage.

---

### Q3. What is an etcd member?

An etcd member is a single etcd process participating in the replicated cluster.

---

### Q4. Do Kubernetes components communicate directly with etcd?

Normally, no.

Most Kubernetes components communicate with the API Server, which then communicates with etcd.

---

### Q5. What kind of data does etcd store?

Kubernetes objects such as Pods, Deployments, Services, Secrets, ConfigMaps, Nodes, Leases, and CRDs.

---

### Q6. What is stored inside etcd?

Key-value pairs where the key identifies the resource (for example, `/registry/pods/default/nginx`) and the value contains the serialized object.

---

### Q7. Why are multiple etcd members deployed?

To provide high availability and fault tolerance if one or more members fail.

---

### Q8. What are the major layers inside etcd?

gRPC API, RAFT, MVCC, Backend Storage, and BoltDB.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| API Server cannot start | etcd unavailable or unreachable |
| `kubectl` hangs | API Server waiting for etcd responses |
| Cluster state disappears after restore | Incorrect snapshot restore or mismatched cluster configuration |
| Slow writes | Disk latency, overloaded storage, or consensus delays |
| Slow reads | Heavy load, storage contention, or inefficient request patterns |
