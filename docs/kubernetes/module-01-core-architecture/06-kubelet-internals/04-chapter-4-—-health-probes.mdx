# Module 1.6 — kubelet Internals

# Chapter 4 — Health Probes

> **Goal:** Understand how the kubelet continuously monitors application health using **Readiness**, **Liveness**, and **Startup Probes**. Learn how probe execution works internally, how different probe types are implemented, how probe results influence Kubernetes behavior, and how to design production-grade health checks.
>
> By the end of this chapter, you will understand:
>
> ```text
> 1. The three probe types: Liveness, Readiness, Startup
> 2. Probe mechanisms: HTTP GET, TCP Socket, Exec, gRPC
> 3. Probe parameters: initialDelaySeconds, periodSeconds, failureThreshold
> 4. How kubelet executes probes: ProbeManager goroutines per container
> 5. Readiness probe failure: Pod removed from Service Endpoints (not restarted)
> 6. Liveness probe failure: container restarted (Pod stays on same Node)
> 7. Startup probe: blocks Liveness/Readiness until app finishes initializing
> 8. Common misconfiguration patterns and production best practices
> ```

# Real-Life Analogy

Think of Health Probes like an aircraft pre-flight and in-flight monitoring system.

```text
Aircraft Monitoring Analogy:

Ground crew checks aircraft before takeoff (Startup Probe: is app ready to start?)
Control tower checks if aircraft is ready to receive passengers (Readiness Probe)
Flight monitoring checks if aircraft is still flying normally (Liveness Probe)
If readiness check fails: no new passengers board (removed from Service endpoints)
If liveness check fails: pilot ejects and new aircraft is deployed (container restart)
Startup check must pass before control tower or monitoring take over
```

| Aircraft Monitoring | Health Probes |
| :--- | :--- |
| Ground crew pre-flight check | Startup Probe |
| Ready to board passengers check | Readiness Probe |
| In-flight monitoring | Liveness Probe |
| Passengers not boarding (no new traffic) | Readiness failure: removed from Endpoints |
| Pilot ejects, new aircraft deployed | Liveness failure: container restarted |
| Startup must pass before others begin | Startup probe blocks Liveness + Readiness |

> **Important:** A **Liveness probe failure restarts the container, not the Pod**. The Pod object stays on the same Node with the same IP. Only the container process is killed and restarted by the container runtime. This is why `kubectl get pods` may show a Pod as `Running` with `RESTARTS: 3` — the Pod is alive but its container has restarted three times.

# Why Health Probes Exist

Running does **not** mean healthy.

Consider this application:

```text
Container Started
  |
  v
Application Deadlocked
  |
  v
Process Still Running
```

From Linux's perspective:

```text
Process Exists

✓ Running
```

From the user's perspective:

```text
Website
  |
  v
Timeout
  |
  v
Unavailable
```

The kubelet needs a way to determine whether an application is actually usable.

Health Probes solve this problem.

---

# The Problem Without Health Probes

```text
Container Running
  |
  v
Application Hung
  |
  v
Service Sends Traffic
  |
  v
Every Request Fails
```

Without probes, Kubernetes assumes:

```text
Running Process

=

Healthy Application
```

This assumption is incorrect.

# What Are Health Probes?

A **Health Probe** is a check executed by the kubelet against a container.

Its purpose is to answer one of three questions:

```text
Can I Send Traffic?
  |
  v
Readiness

────────────

Should I Restart It?
  |
  v
Liveness

────────────

Has Startup Finished?
  |
  v
Startup
```

Each probe has a different responsibility.

---

# Probe Architecture

```text
                kubelet

                   |

          Probe Manager

                   |

        Probe Worker Thread

                   |

         Execute Probe

                   |

           Container

                   |

        Success / Failure

                   |

            Update State
```

The kubelet performs every probe locally.

No control plane component executes health probes.

# Important Behavior

Liveness failure causes:

```text
Container Restart
```

It does **not** directly affect Service endpoints.

The temporary removal from Service endpoints usually occurs because the restarted container is not Ready until the Readiness Probe succeeds again.


# Probe Comparison

| Probe | Main Purpose | Failure Result |
|---------|--------------|----------------|
| Readiness | Control traffic | Remove Pod from Service endpoints |
| Liveness | Detect broken containers | Restart the container |
| Startup | Protect slow startup | Delay Readiness and Liveness until startup completes |

# Probe Timing Parameters

Each probe can be configured with timing controls.

Common parameters include:

```text

periodSeconds

timeoutSeconds
```

These determine:

- When probing begins
- How often probes run
- How long kubelet waits for a response
- How many consecutive successes or failures are required before changing state

# Interaction with Services

Readiness directly influences Service routing.

```text
Readiness=True
  |
  v
EndpointSlice Updated
  |
  v
Service Routes Traffic
```

If Readiness becomes False:

```text
Endpoint Removed
  |
  v
Traffic Stops
```

The container continues running.

---

# Relationship with EndpointSlices

```text
Readiness Changes
  |
  v
kubelet Updates Pod Status
  |
  v
EndpointSlice Controller
  |
  v
Update EndpointSlice
  |
  v
Traffic Routing Changes
```

The kubelet does **not** update EndpointSlices directly.

It updates Pod status, and the control plane reconciles EndpointSlices.

---

# Relationship with Restart Policy

Suppose:

```text
Liveness Failure
```

The kubelet decides:

```text
Restart Container
```

The actual restart behavior follows the Pod's `restartPolicy`.

For normal application Pods (such as those created by Deployments), this is typically `Always`.

# Common Misconfigurations

---

## Misconfiguration 1

Using the same endpoint for:

```text
Readiness

+

Liveness
```

Problem:

A temporary dependency failure may unnecessarily restart the application.

Better approach:

```text
Readiness
  |
  v
Dependency Checks

────────────

Liveness
  |
  v
Internal Process Health
```

---

## Misconfiguration 2

Aggressive Timeouts

Example:

```text
timeoutSeconds=1
```

Slow networks or temporary CPU spikes may cause false failures.

---

## Misconfiguration 3

No Startup Probe

Large applications:

```text
Java

.NET

ML Models
```

often require Startup Probes to avoid premature Liveness failures.

---

## Misconfiguration 4

Expensive Exec Probes

Example:

```text
Run Database Query

Every Second
```

This increases CPU usage and may become a bottleneck.

Prefer lightweight checks.

---

## Misconfiguration 5

Checking External Dependencies in Liveness

Example:

```text
Database Down
  |
  v
Liveness Fails
  |
  v
Restart
  |
  v
Database Still Down
  |
  v
Restart Again
```

The restart does not solve the problem.

Dependency availability is usually more appropriate for Readiness.

---

# Production Best Practices

✔ Keep probe endpoints lightweight.

✔ Use Readiness to protect users from partially initialized applications.

✔ Use Liveness only for unrecoverable application failures.

✔ Use Startup Probes for slow-starting workloads.

✔ Avoid expensive Exec Probes whenever possible.

✔ Choose reasonable timeout and failure thresholds based on application behavior.

✔ Monitor probe failures as part of application observability.

✔ Test probe behavior during deployments and failure scenarios.

# Common Misconceptions

### ❌ Misconception 1

Readiness failures restart containers.

**Correct:** Readiness only controls whether traffic is sent to the Pod.

---

### ❌ Misconception 2

Liveness determines traffic routing.

**Correct:** Liveness determines whether the kubelet should restart the container.

---

### ❌ Misconception 3

Startup Probes replace Liveness Probes.

**Correct:** Startup Probes delay the start of Liveness and Readiness checks until initialization is complete.

---

### ❌ Misconception 4

TCP probes verify application correctness.

**Correct:** TCP probes only verify that a TCP connection can be established.

---

### ❌ Misconception 5

The API Server executes health probes.

**Correct:** The kubelet executes all health probes locally on the Node.

---

### ❌ Misconception 6

Readiness directly updates Service objects.

**Correct:** kubelet updates Pod Status, and Kubernetes controllers update EndpointSlices, which Services use for traffic routing.

---

### ❌ Misconception 7

Every failed probe immediately triggers an action.

**Correct:** Actions occur only after the configured failure threshold is reached.

# Common Interview Questions

### Q1. What is the difference between Readiness and Liveness Probes?

Readiness determines whether a Pod should receive traffic, while Liveness determines whether a container should be restarted.

---

### Q2. Why are Startup Probes needed?

They prevent slow-starting applications from being restarted by Liveness Probes before initialization is complete.

---

### Q3. Who executes health probes?

The kubelet.

---

### Q4. Which probe types are supported?

HTTP, TCP, Exec, and gRPC.

---

### Q5. What happens when a Readiness Probe fails?

The Pod is removed from Service endpoints but continues running.

---

### Q6. What happens when a Liveness Probe fails?

The kubelet restarts the container according to the Pod's restart policy.

---

### Q7. Does a TCP probe verify application logic?

No. It only checks whether a TCP connection can be established.

---

### Q8. Why shouldn't external dependency checks usually be used in Liveness Probes?

Because restarting the application does not fix an unavailable external dependency and may create unnecessary restart loops.

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Pod never receives traffic | Readiness Probe failing |
| Container restarts repeatedly | Liveness Probe failing or application crashing |
| Application stuck during startup | Missing or incorrectly configured Startup Probe |
| Frequent false probe failures | Timeout too short or failure threshold too low |
| High CPU usage from probes | Expensive Exec Probes or probe frequency too high |
| Service still routes to unhealthy Pods | Readiness Probe missing or incorrectly implemented |
