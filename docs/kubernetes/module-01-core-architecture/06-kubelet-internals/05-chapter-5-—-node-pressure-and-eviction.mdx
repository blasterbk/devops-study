# Real-Life Analogy

Think of Node Pressure & Eviction like a building fire safety system with priority zones.

```text
Fire Safety Priority Zones Analogy:

Building (Node) has limited fire suppression water (memory/disk)
Fire safety system (Eviction Manager) monitors water pressure continuously
If pressure drops below warning level (soft threshold): issue warning, wait
If pressure drops below critical level (hard threshold): begin evacuation now
Evacuation priority: break room first (BestEffort Pods)
Then open offices (Burstable Pods)
Server room last (Guaranteed Pods: must not be disturbed)
Graceful evacuation: staff get time to save work (terminationGracePeriodSeconds)
```

| Fire Safety System | Node Pressure & Eviction |
| :--- | :--- |
| Building water pressure | Node memory / disk availability |
| Fire safety system | kubelet Eviction Manager |
| Pressure drops below warning | Soft eviction threshold: grace period before eviction |
| Pressure drops critically low | Hard eviction threshold: immediate eviction |
| Break room evacuated first | BestEffort Pods evicted first (no requests/limits) |
| Open offices evacuated next | Burstable Pods evicted next |
| Server room evacuated last | Guaranteed Pods evicted last |
| Staff save work before leaving | `terminationGracePeriodSeconds` |

> **Important:** Pod eviction order is determined by **QoS class**: `BestEffort` Pods (no requests/limits) are evicted first, then `Burstable` (requests != limits), and finally `Guaranteed` (requests == limits) Pods are evicted last. Within the same QoS class, Pods consuming the **most resources above their request** are evicted first. Setting `resources.requests` and `limits` on all containers is the most effective way to protect your workloads from eviction.

# Why Node Pressure Exists

A Kubernetes Node has finite resources.

```text
CPU

Memory

Disk

PIDs
```

If these resources become exhausted, the entire Node may fail.

Consider this situation:

```text
Node Memory

64 GB
  |
  v
Applications Allocate Memory
  |
  v
63 GB
  |
  v
63.8 GB
  |
  v
63.95 GB
  |
  v
64 GB
```

Eventually:

```text
Linux
  |
  v
Out Of Memory
  |
  v
OOM Killer
  |
  v
Random Processes Killed
```

This may include:

- kubelet
- container runtime
- system services
- application containers

Instead of allowing the operating system to fail unpredictably, Kubernetes proactively evicts Pods.

# What is Node Pressure?

**Node Pressure** occurs when a Node experiences resource shortages severe enough that kubelet must take action.

Examples include:

```text
Memory Pressure

Disk Pressure

PID Pressure
```

These conditions indicate that the Node cannot safely continue operating without intervention.

# Why Doesn't Linux Handle Everything?

Linux has mechanisms like:

```text
OOM Killer
```

However, the Linux kernel:

- Does not understand Kubernetes workloads.
- Does not understand Pod priorities.
- Does not understand QoS classes.

Linux simply kills processes.

Example:

```text
Random Process
  |
  v
Killed
  |
  v
Critical Application Lost
```

Kubernetes provides smarter workload-aware decisions.

# Types of Node Pressure

Kubernetes currently recognizes several major pressure conditions.

---

## Memory Pressure

Occurs when available memory becomes critically low.

```text
RAM
  |
  v
Almost Full
  |
  v
MemoryPressure=True
```

Memory is the most common cause of Pod evictions.

---

## Disk Pressure

Occurs when storage becomes critically full.

Examples:

```text
Container Images

Logs

Volumes

EmptyDir

Writable Layers
```

If storage fills completely:

```text
New Pods Cannot Start

Logs Cannot Be Written

Images Cannot Be Pulled
```

---

## PID Pressure

Linux limits the number of processes (PIDs).

Example:

```text
Maximum PIDs

32768
  |
  v
32760 Used
  |
  v
32767 Used
  |
  v
No New Processes
```

Containers can no longer create processes.

# Pod Selection for Eviction

Not every Pod has equal importance.

The Eviction Manager evaluates several factors before selecting Pods.

---

# Primary Selection Criteria

Generally, the kubelet prefers to evict Pods that:

- Exceed their resource requests
- Have lower QoS
- Have lower priority
- Help relieve the current resource pressure

The goal is to free sufficient resources while minimizing impact on critical workloads.

---

# Resource Requests Matter

Consider two Pods.

Pod A:

```text
Request

1 GB

Usage

900 MB
```

Pod B:

```text
Request

1 GB

Usage

3 GB
```

Pod B is consuming significantly more memory than requested and is more likely to be selected.

---

# Pod Priority

Higher-priority Pods receive stronger protection.

Example:

```text
Critical DNS

Priority

1,000,000

────────────

Test Application

Priority

0
```

The test application is a more likely eviction candidate.

---

# QoS Classes

Every Pod belongs to one of three Quality of Service (QoS) classes.

```text
Guaranteed

Burstable

BestEffort
```

QoS influences eviction order.

---

# Guaranteed

Requirements:

```text
Requests

=

Limits

For Every Container
```

Example:

```yaml
requests:

  memory: 2Gi

limits:

  memory: 2Gi
```

These Pods receive the strongest protection.

---

# Burstable

Requests are specified,

but requests and limits differ.

Example:

```yaml
requests:

  memory: 1Gi

limits:

  memory: 4Gi
```

Burstable Pods receive medium protection.

---

# BestEffort

No CPU or memory requests or limits are defined.

Example:

```yaml
resources: {}
```

These Pods receive the lowest protection.

---

# QoS Eviction Order

Under memory pressure, Kubernetes generally prefers this order:

```text
BestEffort
  |
  v
Burstable
  |
  v
Guaranteed
```

This is a **general priority**, not an absolute rule. Other factors such as actual resource usage, requests, and Pod Priority are also considered.

---


Pods:

```text

4 GB

────────────

Burstable

10 GB

────────────

Guaranteed

20 GB
```

The BestEffort Pod is generally the first eviction candidate.

# Production Best Practices

✔ Always configure CPU and memory requests.

✔ Avoid BestEffort Pods for production workloads.

✔ Set realistic resource limits.

✔ Monitor Node Pressure conditions.

✔ Configure appropriate eviction thresholds.

✔ Use meaningful Pod PriorityClasses for critical services.

✔ Implement graceful application shutdown using SIGTERM.

✔ Use `preStop` hooks only when necessary and keep them fast.

✔ Monitor memory leaks before they trigger evictions.

# Common Misconceptions

### ❌ Misconception 1

Linux OOM Killer performs Kubernetes evictions.

**Correct:** Kubernetes attempts to evict Pods before the Linux OOM Killer must terminate processes.

---

### ❌ Misconception 2

Guaranteed Pods can never be evicted.

**Correct:** Guaranteed Pods have the strongest protection but can still be evicted if necessary to preserve Node stability.

---

### ❌ Misconception 3

Readiness failures trigger eviction.

**Correct:** Readiness only affects traffic routing. Evictions occur because of Node pressure.

---

### ❌ Misconception 4

BestEffort Pods are always evicted first.

**Correct:** BestEffort Pods are generally preferred candidates, but the Eviction Manager also considers actual resource usage, resource requests, and Pod Priority.

---

### ❌ Misconception 5

Eviction immediately kills containers.

**Correct:** The kubelet first performs graceful termination using SIGTERM and the configured grace period.

---

### ❌ Misconception 6

Node shutdown always kills Pods immediately.

**Correct:** With Graceful Node Shutdown enabled, kubelet coordinates orderly Pod termination before the operating system powers off.

# Common Interview Questions

### Q1. What is Node Pressure?

A condition where a Node experiences resource shortages such as low memory, disk space, or available PIDs.

---

### Q2. What is the purpose of the Eviction Manager?

To monitor Node resources, detect pressure conditions, select Pods for eviction, and protect overall Node stability.

---

### Q3. What are the major Node pressure conditions?

MemoryPressure, DiskPressure, and PIDPressure.

---

### Q4. What is the difference between hard and soft eviction thresholds?

Hard thresholds trigger immediate eviction, while soft thresholds allow a grace period before eviction if the condition persists.

---

### Q5. Which QoS class receives the highest protection?

Guaranteed.

---

### Q6. What generally happens first during memory pressure?

BestEffort Pods are usually preferred for eviction before Burstable and Guaranteed Pods, assuming other factors are comparable.

---

### Q7. Does eviction delete Pods immediately?

No. The kubelet performs graceful termination before forcefully killing containers if required.

---

### Q8. What is Graceful Node Shutdown?

A kubelet feature that gracefully terminates Pods when the operating system initiates a shutdown.

---

# Troubleshooting Guide

| Problem | Likely Cause |
|----------|--------------|
| Pods frequently evicted | Memory, disk, or PID pressure on the Node |
| Node reports MemoryPressure | Memory usage exceeded configured thresholds |
| DiskPressure remains True | Logs, images, or writable layers consuming excessive storage |
| Critical application evicted | Missing PriorityClass, inappropriate QoS, or severe Node pressure |
| Applications terminate abruptly | `terminationGracePeriodSeconds` too short or application ignores SIGTERM |
| Node becomes unstable before evictions occur | Eviction thresholds configured too aggressively or kubelet unable to reclaim resources quickly |
