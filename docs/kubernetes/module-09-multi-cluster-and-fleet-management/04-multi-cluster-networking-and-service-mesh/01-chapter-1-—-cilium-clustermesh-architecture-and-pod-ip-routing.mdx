# Chapter 1 — Cilium ClusterMesh Architecture & Pod IP Routing

> **Goal:** Master high-performance, kernel-level cross-cluster networking and service failover using **Cilium ClusterMesh** — understanding how extended Berkeley Packet Filter (**eBPF**) establishes direct Pod-to-Pod routing across independent Kubernetes clusters without intermediate Layer 7 proxies, enforcing **Non-Overlapping Pod CIDR** topology designs, synchronizing cross-cluster security identities via `kvstoremesh`, and configuring resilient **Global Services** (`io.cilium/global-service`).
>
> By the end of this chapter, you will understand:
> 1. The performance and architectural advantages of eBPF-native cross-cluster routing
> 2. Why non-overlapping Pod and Service CIDR allocations are mandatory in ClusterMesh
> 3. How `kvstoremesh` synchronizes security identities and endpoint IPs across clusters
> 4. How to author Global Services with automatic cross-cluster failover and local affinity
> 5. How Cilium enforces unified, cross-cluster `CiliumNetworkPolicies`
> 6. How to verify ClusterMesh connectivity and endpoint synchronization using the `cilium` CLI

## Real-Life Analogy

Think of Cilium ClusterMesh as **building a high-speed underground maglev tunnel connecting the subway networks of two neighboring metropolitan cities**:

- **The Traditional Gateway Approach (The Slow Border Checkpoint - Istio East-West Gateways):** City A (**Cluster 1**) and City B (**Cluster 2**) each have their own internal subways (**Pods**). When a passenger in City A wants to visit City B, they must exit their train, walk through an airport terminal, pass through 3 customs security lines (**Layer 7 Ingress Gateway $\to$ Proxy $\to$ mTLS Re-Encryption**), board a second train, and repeat the process (**High CPU Overhead & 15ms+ Latency**).
- **The Cilium ClusterMesh Solution (The Direct Maglev Track - eBPF):** Cilium digs a direct high-speed subway tunnel between City A and City B (**Direct eBPF Kernel Datapath**).
- **The Non-Overlapping Station Numbers (Unique Pod CIDRs):** Stations in City A are numbered `100–199` (**Pod CIDR: `10.244.0.0/16`**), and stations in City B are numbered `200–299` (**Pod CIDR: `10.245.0.0/16`**). A train in City A can drive directly to Station 242 in City B in **0.5 milliseconds** without stopping at any gates.
- **The Global Service Emergency Backup (`service.cilium.io/global-service`):** If the hospital in City A is flooded (**All local pods crash**), ambulances automatically reroute through the maglev tunnel directly to the hospital in City B (**Instant Cross-Cluster Failover**).

## ClusterMesh Prerequisites & CIDR Requirements

> [!CRITICAL]
> **The Golden Rule of ClusterMesh:** Direct Pod-to-Pod routing requires that **every cluster in the mesh possess globally unique, non-overlapping Pod and Service CIDR blocks**. Overlapping CIDRs require NAT translation (such as Submariner Globalnet).

## Complete Production `Global Service` Manifest

Deploy this identical Service manifest to **both Cluster 01 and Cluster 02**:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payment-backend-svc
  namespace: production
  annotations:
    # 1. Enables cross-cluster service discovery & load balancing!
    service.cilium.io/global-service: "true"

    # 2. Controls shared endpoint aggregation across clusters
    service.cilium.io/shared-service: "true"

    # 3. Local Affinity: Prefer local pods; route cross-cluster ONLY during failover!
    service.cilium.io/affinity: "local"
spec:
  type: ClusterIP
  selector:
    app: payment-backend
  ports:
  - name: http
    port: 8080
    targetPort: 8080
```

## Cross-Cluster Security Policies (`CiliumNetworkPolicy`)

ClusterMesh synchronizes identity security IDs (`cilium-identity`) across clusters, enabling cross-cluster firewall rules:

```yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-us-east-frontend-to-payment
  namespace: production
spec:
  endpointSelector:
    matchLabels:
      app: payment-backend
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: frontend
        # Restricts ingress strictly to frontend pods originating from Cluster 01!
        io.cilium.k8s.policy.cluster: cluster-us-east
    toPorts:
    - ports:
      - port: "8080"
        protocol: TCP
```

## Common Interview Questions

**Q1: How does Cilium ClusterMesh achieve direct Pod-to-Pod cross-cluster routing without Layer 7 proxies?**

Cilium operates at the **Linux kernel layer using extended Berkeley Packet Filter (eBPF)**. In ClusterMesh, the Cilium daemon on each node synchronizes the global BPF routing and endpoint maps (`cilium_endpoints`). When a pod in Cluster A sends a TCP packet to a Pod IP in Cluster B, the local node's eBPF datapath intercepts the socket syscall, encapsulates the packet (or routes it natively over direct VPC peering), and delivers it straight to the destination node's network interface without passing through any intermediate Envoy gateways or reverse proxies.

**Q2: What is the mandatory network CIDR requirement for deploying Cilium ClusterMesh?**

ClusterMesh requires **strictly Non-Overlapping Pod and Service CIDRs** across all member clusters (e.g. Cluster 1 uses `10.244.0.0/16`, Cluster 2 uses `10.245.0.0/16`). Because routing occurs directly at Layer 3/4 by Pod IP, if two clusters share overlapping subnets (e.g. both using `10.244.0.0/16`), the kernel cannot determine which physical node owns the target IP, resulting in routing collisions.

**Q3: How does `service.cilium.io/affinity: "local"` optimize performance in Global Services?**

When a Service is annotated with `service.cilium.io/global-service: "true"` and `service.cilium.io/affinity: "local"`, Cilium's eBPF load-balancing logic prioritizes **local in-cluster pods**. As long as at least one healthy pod exists in the local cluster, 100% of traffic stays local (avoiding cross-region WAN latency). If all local pods fail or crash, Cilium automatically fails over and routes requests to healthy backend pods in remote clusters.

**Q4: How does `kvstoremesh` synchronize state between multiple clusters in Cilium?**

`kvstoremesh` is a lightweight caching proxy deployed in each cluster that connects to the remote `etcd` or `cilium-etcd` instances of peer clusters. It watches and replicates identity security IDs (`cilium-identity`), node IPs, and global service endpoint registrations in real time, allowing each local cluster's eBPF maps to stay synchronized with minimal CPU and memory overhead.

**Q5: How does cross-cluster security policy enforcement work in Cilium ClusterMesh?**

When a packet crosses cluster boundaries, the source cluster's Cilium agent encodes the pod's numerical **Security Identity ID** into the packet's network encapsulation header (VXLAN/Geneve) or attaches it via eBPF metadata. The destination node's eBPF program decodes the security identity and evaluates local `CiliumNetworkPolicies` (matching labels like `io.cilium.k8s.policy.cluster: cluster-us-east`), enforcing zero-trust micro-segmentation across clusters at line rate.
