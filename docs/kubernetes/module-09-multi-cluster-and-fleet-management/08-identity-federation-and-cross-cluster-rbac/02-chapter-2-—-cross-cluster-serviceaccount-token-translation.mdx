# Chapter 2 — Cross-Cluster ServiceAccount Token Translation

> **Goal:** Master secure, secretless cross-cluster workload authentication and zero-trust service federation using **Projected ServiceAccount Tokens** and **CNCF SPIFFE/SPIRE** — understanding how Kubernetes exposes public **OIDC JWKS Discovery Endpoints** to allow foreign clusters to cryptographically verify local pod identities, authoring audience-bound and time-bound token projections (`TokenRequest`), and establishing cross-cluster cryptographic trust bundles using **SPIFFE IDs** and **X.509 SVIDs**.
>
> By the end of this chapter, you will understand:
> 1. Why sharing static Kubernetes Secret tokens across clusters violates zero-trust principles
> 2. How the `TokenRequest` API issues short-lived, audience-scoped projected tokens
> 3. How Cluster B verifies Cluster A's tokens via Cluster A's public OIDC discovery endpoint
> 4. The architecture of CNCF SPIFFE (Specification) and SPIRE (Runtime Implementation)
> 5. How SPIRE Server and Agent federate trust bundles for cross-cluster mutual TLS
> 6. How to author production Projected Token Pod specs and SPIFFE Workload Entries

## Real-Life Analogy

Think of cross-cluster workload identity as **an employee from a branch office visiting a foreign corporate office building with an internationally verifiable digital passport**:

- **The Static Secret Anti-Pattern (The Forged Paper Letter):** A pod in Cluster A (**The visiting worker**) wants to read a database in Cluster B (**The foreign branch**). In the past, engineers generated a permanent static service account token in Cluster B, copied the base64 string, and pasted it into a Secret in Cluster A (**Hardcoded Shared Secret**). If the token is leaked or stolen, the attacker has permanent access, and rotating it requires manual downtime across both clusters.
- **The Kubernetes OIDC Discovery Model (The Real-Time Digital Passport Verification):**
  - **The Digital Passport (`Projected ServiceAccount Token`):** The pod in Cluster A holds a short-lived digital token signed by Cluster A's private key, stamped specifically for Cluster B (**`aud: "https://cluster-b.api.internal"`**).
  - **The Public Passport Verification Website (`JWKS Discovery`):** Cluster B receives the token. It does not need to call Cluster A's admin. It opens Cluster A's public key registry (**`/.well-known/openid-configuration` & `/openid/v1/jwks`**), cryptographically verifies the mathematical signature, and grants access immediately!
- **The Global Diplomatic Trust Bundle (SPIFFE / SPIRE):** Every workload across 50 clusters receives a globally unique universal identity (**SPIFFE ID: `spiffe://enterprise.org/ns/prod/sa/payment-api`**). Even if clusters run on completely different clouds, workloads authenticate over mutual TLS automatically without any shared passwords!

## 1. Projected Token Pod Specification (Cluster A)

Configure a pod to project a short-lived token tailored specifically for cross-cluster consumption:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-processor-pod
  namespace: production
spec:
  serviceAccountName: payment-sa
  containers:
  - name: processor
    image: ghcr.io/enterprise-org/payment-processor:v1.2.0
    volumeMounts:
    - name: cross-cluster-token
      mountPath: /var/run/secrets/tokens
      readOnly: true
  volumes:
  - name: cross-cluster-token
    projected:
      sources:
      - serviceAccountToken:
          path: cluster-b-token
          # 1. Binds token strictly to Cluster B API / Vault audience!
          audience: "https://cluster-b.k8s.enterprise.com"
          # 2. Ephemeral 1-Hour Time-to-Live!
          expirationSeconds: 3600
```

## 2. SPIFFE / SPIRE Universal Workload Federation

For heterogeneous environments (hybrid cloud, VMs, Kubernetes), **CNCF SPIFFE/SPIRE** provides universal cryptographic identity:

```yaml
apiVersion: spire.spiffe.io/v1alpha1
kind: ClusterSPIFFEID
metadata:
  name: payment-cross-cluster-id
spec:
  # 1. Universal SPIFFE ID Syntax
  spiffeIDTemplate: "spiffe://enterprise.org/ns/{{ .PodMeta.Namespace }}/sa/{{ .PodSpec.ServiceAccountName }}"
  podSelector:
    matchLabels:
      app: payment-processor
  # 2. Federated Trust Domain (Trusts workloads from secondary cloud!)
  federatesWith:
    - "gcp-cloud.enterprise.org"
```

## How Cluster B Validates Tokens via OIDC Discovery

Kubernetes exposes standard public OIDC discovery endpoints natively:

```bash
# 1. Fetch Cluster A's OIDC Discovery Document
curl -k https://cluster-a.k8s.internal:6443/.well-known/openid-configuration

# Returns:
# {
#   "issuer": "https://cluster-a.k8s.internal:6443",
#   "jwks_uri": "https://cluster-a.k8s.internal:6443/openid/v1/jwks",
#   "response_types_supported": ["id_token"],
#   "subject_types_supported": ["public"],
#   "id_token_signing_alg_values_supported": ["RS256"]
# }

# 2. Fetch Cluster A's Public Verification Keys (JWKS)
curl -k https://cluster-a.k8s.internal:6443/openid/v1/jwks
```

## Common Interview Questions

**Q1: What are Kubernetes Projected ServiceAccount Tokens, and why did they replace legacy secret-based tokens?**

Legacy Kubernetes ServiceAccount tokens were stored as permanent, non-expiring `Secret` objects in `etcd`. If stolen, they provided indefinite API access. Starting in Kubernetes 1.22, **Projected ServiceAccount Tokens** (powered by the `TokenRequest` API) replaced legacy secrets. Projected tokens are: (1) **Time-Bound** (expire in 1 hour); (2) **Audience-Bound** (contain `aud` claims restricting their use to specific target services); and (3) **Ephemeral** (injected directly into container memory via tmpfs volumes and dynamically rotated by Kubelet without pod restarts).

**Q2: How does a target cluster (Cluster B) authenticate a projected token issued by an origin cluster (Cluster A)?**

When the pod in Cluster A sends its projected token to Cluster B's API server:
1. Cluster B inspects the JWT's `iss` (Issuer) claim, identifying Cluster A as the authority.
2. Cluster B fetches Cluster A's public JSON Web Key Set from `https://cluster-a:6443/openid/v1/jwks`.
3. Cluster B mathematically verifies the signature using Cluster A's public key.
4. Cluster B checks that the `aud` (Audience) matches Cluster B and that the token is not expired, authenticating the caller without contacting Cluster A's control plane.

**Q3: What is the difference between SPIFFE and SPIRE?**

- **`SPIFFE` (Secure Production Identity Framework for Everyone)**: An open standard specification that defines: (1) A universal naming standard for workload identities (**SPIFFE ID**: `spiffe://<trust-domain>/ns/<ns>/sa/<sa>`); and (2) A verifiable cryptographic identity document (**SVID**: X.509 certificate or JWT).
- **`SPIRE` (SPIFFE Runtime Engine)**: The production-ready reference implementation of the SPIFFE standard. It consists of `spire-server` and `spire-agent`, which attest workload attributes and dynamically issue short-lived X.509 SVIDs directly to containers via local Unix domain sockets.

**Q4: How does SPIFFE/SPIRE establish trust between two completely different cloud providers (e.g. AWS and GCP)?**

SPIFFE uses **Federated Trust Bundles**. The SPIRE Server in AWS and the SPIRE Server in GCP exchange their respective Root Certificate Authority (CA) public keys via a secure OIDC / HTTPS bundle endpoint. When a pod in AWS connects to a pod in GCP over mutual TLS, both sides present their X.509 SVID certificates. Because each side possesses the other's public CA bundle in its trust store, the TLS handshake succeeds with mutual cryptographic verification.

**Q5: What is the security consequence of omitting the `audience` field when requesting a projected token?**

If the `audience` field is omitted, the token defaults to the local cluster's API server audience (`https://kubernetes.default.svc`). If an application sends this default token to a third-party microservice or external database, a compromised third-party service could **replay that token against the Kubernetes API server**, impersonating the calling pod and gaining unauthorized cluster access. Specifying a strict target audience (e.g. `aud: "https://vault.corp"`) ensures that only Vault will accept the token, blocking token replay attacks.
