## Real-Life Analogy

Think of Grafana Mimir as **a massive national post office sorting distribution facility built to handle 1 billion letters per day**:

- **The Thanos Approach (The Visiting Inspector - Pull Model):** An inspector flies to 50 regional post offices every time a customer asks a question, reading local notebooks and checking the filing cabinets (**Thanos Querier connecting out to 50 Sidecars**).
- **The Mimir Approach (The 24/7 High-Speed Conveyor Belt - Push Model):** Regional post offices do not keep local historical archives. As soon as a letter is stamped (**Prometheus collects a metric**), it shoots down a high-speed pneumatic tube (**Prometheus `remote_write`**) straight into the national processing hub (**Mimir**).
- **The National Sorting Machine (The `Distributor`):** The distributor reads the zip code on the envelope, hashes the address (**Consistent Hash Ring**), and fans out 3 identical copies to 3 sorting clerks (**`Ingester` replication factor: 3**) so no letters are ever lost.
- **The Multi-Company Mailbox Divider (`X-Scope-OrgID`):** Amazon, Apple, and Netflix all send mail through the same building, but each company's letters are locked in private, cryptographically segregated vaults (**Multi-Tenancy**).
- **The Fast Reading Supercomputer (`Query-Frontend`):** When the CEO asks: *"Show me the mail volume for the last 365 days,"* the supercomputer splits the 365-day request into 365 parallel 1-day micro-queries, executes them simultaneously across 50 worker nodes, and displays the full graph on the screen in **0.4 seconds**!

## 1. Configuring Prometheus `remote_write` for Mimir

Configure local Prometheus instances to stream metrics to the central Mimir cluster:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: Prometheus
metadata:
  name: k8s-prometheus
  namespace: monitoring
spec:
  # 1. Attach Cluster Identifier Labels
  externalLabels:
    cluster: "prod-us-east-01"
    environment: "production"
    cloud: "aws"
  
  # 2. Remote Write Pipeline to Central Mimir Hub
  remoteWrite:
    - url: "https://mimir.observability.enterprise.com/api/v1/push"
      remoteTimeout: 30s
      headers:
        # Multi-Tenant Header: Isolates metrics to this specific business tenant!
        X-Scope-OrgID: "enterprise-production"
      writeRelabelConfigs:
        # Drops noisy high-cardinality container metric bloat before transmission!
        - sourceLabels: [__name__]
          regex: "container_tasks_state|go_gc_.*"
          action: drop
      queueConfig:
        capacity: 10000
        maxShards: 50
        maxSamplesPerSend: 2000
        batchSendDeadline: 5s
```

## 2. Production Mimir Architecture Configuration (`mimir.yaml`)

```yaml
# mimir.yaml (Central Mimir Gateway)
multitenancy_enabled: true             # Enforces X-Scope-OrgID validation

# 1. Distributor Ingestion Ring
distributor:
  ring:
    instance_sync_period: 15s
  ha_tracker:
    enable_ha_tracker: true            # Deduplicates redundant Prometheus HA pairs!

# 2. Ingester In-Memory TSDB Settings
ingester:
  ring:
    replication_factor: 3              # 3x Replication for zero data loss!
  final_sleep: 0s

# 3. Query Frontend Acceleration
query_frontend:
  split_queries_by_interval: 24h       # Splits a 30-day query into 30 parallel 1-day jobs!
  cache_results: true
  results_cache:
    backend: memcached
    memcached_client:
      host: memcached.observability.svc:11211

# 4. Long-Term Storage
common:
  storage:
    backend: s3
    s3:
      bucket_name: enterprise-mimir-metrics
      endpoint: s3.us-east-1.amazonaws.com
```

## Common Interview Questions

**Q1: What is Grafana Mimir, and why was it created as a successor to Cortex?**

Grafana Mimir is an open-source, horizontally scalable, multi-tenant time series database (TSDB) for Prometheus metrics. Created by Grafana Labs (forked and modernized from CNCF Cortex), Mimir was engineered to eliminate horizontal scaling bottlenecks. It allows organizations to scale metric ingestion beyond **1 billion active series**, providing blazing-fast PromQL query execution over multi-year time ranges using distributed query sharding and multi-layer caching.

**Q2: How does the `X-Scope-OrgID` HTTP header enforce hard multi-tenancy in Mimir?**

In Mimir, multi-tenancy is enforced natively at the API gateway layer. Every incoming HTTP `remote_write` push and PromQL read request **must include the `X-Scope-OrgID` header** (e.g. `X-Scope-OrgID: team-billing`). Mimir physically isolates metric storage chunks in S3 under directory prefixes corresponding to the tenant ID (`s3://bucket/<tenant-id>/...`). A query executed by Tenant A can never read, see, or touch time series belonging to Tenant B.

**Q3: How does the `query-frontend` in Mimir accelerate long-range PromQL queries?**

When a user opens a Grafana dashboard requesting a 90-day time graph:
1. **Query Splitting**: The `query-frontend` intercepts the request and splits the single 90-day query into **90 separate 1-day sub-queries**.
2. **Parallel Dispatch**: It dispatches all 90 sub-queries in parallel across a pool of stateless Querier workers.
3. **Caching**: It caches the static historical days in Memcached / Redis (since past metric data never changes).
4. **Stitching**: It merges the results into a single array, returning the response in under 500 milliseconds.

**Q4: How does Mimir handle High-Availability (HA) Prometheus deduplication?**

When running HA Prometheus pairs (e.g. `prometheus-0` and `prometheus-1` scraping the same cluster), both push identical samples to Mimir. Mimir's **HA Tracker** in the Distributor inspects incoming samples for `cluster` and `__replica__` labels. It dynamically elects one replica as the "active" source and discards samples from the standby replica. If the active replica stops pushing data for 30 seconds, Mimir automatically switches to the standby replica with zero data loss.

**Q5: What are the trade-offs of using Prometheus `remote_write` compared to Thanos Sidecar?**

- **`remote_write` (Mimir)**: Pushes metrics continuously over the network. Requires continuous outbound network bandwidth and RAM buffers in the local cluster, but provides immediate centralization and hard multi-tenant isolation.
- **Thanos Sidecar**: Zero continuous stream overhead; writes locally and uploads 2-hour blocks in batches to S3. However, running ad-hoc global queries requires the central Querier to open live gRPC connections into every spoke cluster, which is difficult across strict enterprise firewalls.
