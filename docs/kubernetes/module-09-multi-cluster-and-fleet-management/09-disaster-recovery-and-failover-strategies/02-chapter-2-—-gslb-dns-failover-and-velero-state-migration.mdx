> 1. How GSLB (Cloudflare, AWS Route53, K8gb) routes global traffic based on real-time endpoint health
> 2. How DNS TTLs, active health checks, and Anycast IPs coordinate sub-30-second automated failovers

## Real-Life Analogy

Think of GSLB DNS Failover and Velero State Migration as **an intelligent airport air traffic control tower combined with a high-speed disaster relocation convoy**:

- **The Global Air Traffic Controller (GSLB - Global Server Load Balancing):** Airplanes (**Global User HTTP Requests**) fly towards the destination city.
  - The control tower (**Cloudflare / Route53 GSLB**) constantly monitors the runway lights at Airport A in Virginia (**Primary Cluster Health Probe `/healthz`**).
  - If a blizzard covers the runway in Virginia (**Regional Datacenter Outage**), the control tower immediately radios all incoming planes: *"Reroute to Airport B in Ohio (**Standby Cluster LoadBalancer IP**)."*
  - The planes land safely in Ohio in **under 30 seconds** without a single passenger noticing (**Automated DNS Failover**).
- **The Armored Relocation Convoy (Velero State Migration):** In the background, what about the physical luggage, passenger manifests, and cargo stored in Airport A (**Stateful Persistent Volumes and Kubernetes Objects**)?
  - Every 1 hour, Velero takes high-resolution digital scans of all cargo boxes (**CSI VolumeSnapshots**) and saves them into an indestructible bomb-proof vault in the mountains (**Amazon S3 Object Storage**).
  - If Airport A is completely vaporized by an earthquake, Velero drives to a brand-new airport in Europe, downloads the cargo scans from the vault, and 3D-prints the exact identical luggage and buildings (**`velero restore create`**) in **15 minutes**!

## 1. Velero Automated Disaster Backup Schedule (`Schedule` CRD)

Configure automated hourly backups capturing both Kubernetes API objects and persistent storage:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: payment-production-hourly-backup
  namespace: velero
spec:
  schedule: "0 * * * *"                # Cron expression: Runs every hour at minute 0!
  template:
    includedNamespaces:
      - payment-production
      - database-production
    includedResources:
      - "*"
    includeClusterResources: true
    snapshotVolumes: true              # Triggers cloud CSI VolumeSnapshots for all PVCs!
    storageLocation: default           # Points to S3 BackupStorageLocation
    volumeSnapshotLocations:
      - aws-us-east-1                  # Points to AWS EBS VolumeSnapshotLocation
    ttl: 720h0m0s                      # Retains backups in S3 for 30 days
```

## 2. Velero Disaster Recovery Re-Hydration (`Restore` CRD)

To restore the stateful application into a brand new disaster recovery cluster in another region:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: payment-emergency-restore-001
  namespace: velero
spec:
  backupName: payment-production-hourly-backup-20260818120000
  includedNamespaces:
    - payment-production
    - database-production
  restorePVs: true                     # Recreates PVs and restores data from EBS snapshots!
  preserveNodePorts: true
```

## Velero Command-Line Operations

```bash
# 1. Manually trigger an immediate backup of the production namespace
velero backup create payment-prod-manual-backup --include-namespaces payment-production

# 2. Inspect backup status and volume snapshot logs
velero backup describe payment-prod-manual-backup --details

# 3. Restore the application in the secondary disaster recovery cluster
velero restore create --from-backup payment-prod-manual-backup

# 4. Monitor real-time restore progress
velero restore get
```

## Common Interview Questions

**Q1: How does Global Server Load Balancing (GSLB) coordinate automated multi-cluster disaster failover?**

GSLB systems (such as Cloudflare Load Balancing, AWS Route53, or open-source K8gb) operate at the **global DNS layer**. GSLB health probers continuously send synthetic HTTP/TCP probes to each regional cluster's ingress load balancer IP (testing `/healthz` or `/livez`). When a primary cluster fails health probes for a specified threshold (e.g. 3 consecutive probes over 30 seconds), the GSLB dynamically updates the DNS A/AAAA records for the global domain (`api.enterprise.com`), pointing client traffic to the healthy standby cluster's IP address.

**Q2: What is the significance of DNS Time-To-Live (TTL) during a GSLB failover?**

The DNS TTL dictates **how many seconds downstream DNS resolvers (ISPs, corporate DNS servers, client browsers) cache the DNS response before querying the authoritative GSLB nameserver again**. If a service uses a standard 1-day TTL (`86400s`), clients will continue attempting to connect to the dead cluster for 24 hours after an outage occurs. Setting a low TTL of **15 to 30 seconds** ensures that $> 99\%$ of global traffic converges onto the new standby cluster within 30 seconds of failover.

**Q3: How does Velero capture persistent volume storage data across different cloud providers?**

Velero supports two primary storage backup mechanisms:
1. **CSI VolumeSnapshots (Native Cloud Snapshots)**: Velero integrates with the Kubernetes Container Storage Interface (CSI) to trigger point-to-point block-level snapshots of cloud disk volumes (AWS EBS, GCP Persistent Disks, Azure Managed Disks).
2. **Kopia / Restic (File-Level Backup)**: For bare-metal or on-premises storage (Ceph, NFS, local disks), Velero runs an in-pod data mover daemon that reads files directly from the mounted filesystem and streams deduplicated, encrypted file blocks into S3/GCS object storage.

**Q4: How do you migrate a stateful Kubernetes application from AWS EKS to Google Cloud GKE using Velero?**

1. In the source AWS EKS cluster, create a Velero backup using file-level backup (`--default-volumes-to-fs-backup`) to bypass AWS-specific EBS snapshots.
2. Velero uploads the Kubernetes manifests and persistent volume data files into a shared S3 / Google Cloud Storage bucket.
3. In the destination GCP GKE cluster, install Velero pointed at the same storage bucket.
4. Run `velero restore create --from-backup <name>`. Velero creates new GKE persistent volumes, restores the files from object storage, and brings up the application pods in GCP seamlessly.

**Q5: What are Velero `RestoreItemActions` and why are they needed during cross-cloud migration?**

Different cloud providers and Kubernetes distributions have different StorageClasses and API versions (e.g. AWS uses `gp3`, GCP uses `standard-rwo`). Velero **`RestoreItemActions`** (plugins or ConfigMaps) allow modifying resource YAML on-the-fly during restore. Administrators can configure a `change-storage-class-config` ConfigMap to automatically translate `storageClassName: gp3` to `storageClassName: standard-rwo` during the restore process without manual manifest editing.
