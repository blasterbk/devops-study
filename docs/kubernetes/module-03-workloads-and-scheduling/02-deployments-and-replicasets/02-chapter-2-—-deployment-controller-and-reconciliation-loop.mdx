# Chapter 2 — Deployment Controller & Reconciliation Loop

> **Goal:** Master the inner workings of the Kubernetes Deployment controller — understanding how it manages multiple child ReplicaSets, calculates `maxSurge` and `maxUnavailable` quotas during rolling updates, injects `pod-template-hash` labels, enforces `progressDeadlineSeconds`, and recovers from stalled rollouts.
>
> By the end of this chapter, you will understand:
> 1. The hierarchical relationship: `Deployment → ReplicaSet → Pod`
> 2. How the Deployment controller orchestrates rolling updates without touching Pods directly
> 3. The exact mathematical formulas governing `maxSurge` and `maxUnavailable`
> 4. How `pod-template-hash` ensures Pods are associated with the correct revision
> 5. How `progressDeadlineSeconds` detects stalled rollouts in CI/CD pipelines
> 6. How to diagnose rollout failures using `kubectl rollout status` and Deployment conditions

## Real-Life Analogy

Think of a Deployment as the **CEO of a passenger railway company**:

- The **CEO (Deployment Controller)** does not personally build train cars (Pods). Instead, when introducing a new high-speed bullet train (Version 2.0), the CEO hires a **Contractor (ReplicaSet V2)** while the **Old Contractor (ReplicaSet V1)** is still operating the older diesel trains.
- **Rollout Strategy (`maxSurge` and `maxUnavailable`):**
  - The railway policy states: *"We normally run 10 trains (`replicas: 10`). During an upgrade, we can afford to have at most 2 extra trains on the tracks (`maxSurge: 2`), and at most 1 train taken out of service for track upgrades (`maxUnavailable: 1`)."*
  - The CEO orders Contractor V2 to build 2 bullet trains (Total active = 11). Once they pass safety tests (`Ready`), the CEO orders Contractor V1 to decommission 2 diesel trains.
- This phased handoff continues smoothly until Contractor V2 is running all 10 trains and Contractor V1 is scaled down to 0.

## Hierarchical Separation of Concerns

A core design principle of Kubernetes is **layered abstraction**:

```text
 ┌────────────────────┬───────────────────────────────────────────────────────────────────────┐
 │ Component          │ Primary Responsibility                                                │
 │────────────────────┼───────────────────────────────────────────────────────────────────────┤
 │ **Deployment**     │ Manages **Declarative State & Rollouts**. Creates, scales, and prunes │
 │                    │ child ReplicaSets. Never creates Pods directly.                       │
 │────────────────────┼───────────────────────────────────────────────────────────────────────┤
 │ **ReplicaSet**     │ Manages **Pod Scale & Self-Healing**. Reconciles pod count to match   │
 │                    │ its current `.spec.replicas`.                                         │
 │────────────────────┼───────────────────────────────────────────────────────────────────────┤
 │ **Pod**            │ Represents the **Actual Runtime Workload** (containers, volumes, IP). │
 └────────────────────┴───────────────────────────────────────────────────────────────────────┘
```

## The Rolling Update Algorithm: `maxSurge` & `maxUnavailable`

During a `RollingUpdate`, the Deployment controller dynamically scales child ReplicaSets while adhering to strict upper and lower capacity boundaries:

```text
 ┌──────────────────────┬──────────────────────────────────────────┬──────────────────────────────────────────┐
 │ Setting              │ Definition                               │ Formula & Default                        │
 │──────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────┤
 │ **`maxSurge`**       │ Maximum number of Pods that can be       │ Default: `25%` (rounded UP to integer).  │
 │                      │ created **ABOVE** desired `replicas`.    │ $\text{Max Pods} = \text{replicas} + \text{maxSurge}$   │
 │──────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────┤
 │ **`maxUnavailable`** │ Maximum number of Pods that can be       │ Default: `25%` (rounded DOWN to integer).│
 │                      │ unavailable **BELOW** desired `replicas`.│ $\text{Min Ready} = \text{replicas} - \text{maxUnavailable}$ │
 └──────────────────────┴──────────────────────────────────────────┴──────────────────────────────────────────┘
```

### Mathematical Example: `replicas: 4`, `maxSurge: 1`, `maxUnavailable: 0`
- **Max Pods allowed at any time:** $4 + 1 = 5$
- **Min Ready Pods required at all times:** $4 - 0 = 4$
- **Step 1:** Controller creates New RS and scales it to `1` (Total = 5: 4 Old, 1 New).
- **Step 2:** New Pod becomes `Ready`. Controller scales Old RS down to `3` (Total = 4: 3 Old, 1 New).
- **Step 3:** Controller scales New RS to `2` (Total = 5).
- **Step 4:** New Pod becomes `Ready`. Old RS scales to `2`...
- **Result:** **Zero downtime** with 100% service capacity guaranteed at all times!

## The `pod-template-hash` Mechanism

How does a Deployment prevent label collision when old and new Pods share the same user labels (e.g. `app: web`)?

1. When you create or update a Deployment, the controller hashes the entire `.spec.template` contents using FNV-32a.
2. It generates a short hash string (e.g., `7b8f94d86`).
3. The controller appends this hash to:
   - The child ReplicaSet name: `web-app-7b8f94d86`
   - The ReplicaSet selector: `pod-template-hash: 7b8f94d86`
   - The Pod template labels: `pod-template-hash: 7b8f94d86`
4. This ensures each ReplicaSet only counts and manages Pods that match its exact template specification.

## Rollout Stalling & `progressDeadlineSeconds`

If a new container image fails to pull or crashes on boot, the rolling update cannot complete. `progressDeadlineSeconds` (default: **600 seconds / 10 minutes**) specifies the maximum time Kubernetes will wait for a rollout to make progress.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: resilient-service
spec:
  replicas: 5
  progressDeadlineSeconds: 120    # Fail fast after 2 minutes of no progress
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
```

### What Happens When Progress Fails?
1. The Deployment status condition `Progressing` transitions to `False`:
   ```yaml
   conditions:
   - type: Progressing
     status: "False"
     reason: ProgressDeadlineExceeded
     message: ReplicaSet "resilient-service-5c9a" has timed out progressing.
   ```
2. The controller **halts the rollout** (does not scale down remaining old Pods).
3. The cluster continues serving traffic from the healthy older revision.
4. CI/CD pipelines monitoring `kubectl rollout status` receive a non-zero exit code and fail the build.

## Pausing and Resuming Deployments

You can **pause** a Deployment to batch multiple changes (e.g., updating images, CPU limits, and environment variables) without triggering multiple rolling updates:

```bash
# 1. Pause the Deployment
kubectl rollout pause deployment/web-app

# 2. Make multiple mutations (none of these trigger a rollout yet)
kubectl set image deployment/web-app web=nginx:1.25
kubectl set resources deployment/web-app -c=web --limits=cpu=500m,memory=512Mi
kubectl set env deployment/web-app FEATURE_FLAG=true

# 3. Resume the Deployment (triggers a single clean rollout with all changes applied)
kubectl rollout resume deployment/web-app
```

## Complete Production Deployment Manifest

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: production-payment-api
  namespace: finance
  labels:
    app: payment-api
    tier: backend
spec:
  replicas: 4
  revisionHistoryLimit: 10
  progressDeadlineSeconds: 180

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%          # 1 extra Pod allowed
      maxUnavailable: 0      # Never drop below 4 ready replicas

  selector:
    matchLabels:
      app: payment-api
      tier: backend

  template:
    metadata:
      labels:
        app: payment-api
        tier: backend
    spec:
      terminationGracePeriodSeconds: 45
      containers:
      - name: api
        image: payment-api:v2.1.0
        imagePullPolicy: IfNotPresent
        ports:
        - name: http
          containerPort: 8080

        # Readiness probe is CRITICAL for maxUnavailable calculations
        readinessProbe:
          httpGet:
            path: /health/ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 3
          successThreshold: 1
          failureThreshold: 2

        livenessProbe:
          httpGet:
            path: /health/live
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 10

        resources:
          requests:
            cpu: "250m"
            memory: "256Mi"
          limits:
            cpu: "1000m"
            memory: "512Mi"
```

## Hands-On Lab: Observing Rolling Updates & Stall Timeouts

```bash
# Step 1: Create lab namespace
kubectl create namespace deploy-lab

# Step 2: Deploy base application (Version 1)
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: rolling-demo
  namespace: deploy-lab
spec:
  replicas: 4
  progressDeadlineSeconds: 30
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: rolling-demo
  template:
    metadata:
      labels:
        app: rolling-demo
    spec:
      containers:
      - name: web
        image: nginx:1.24-alpine
EOF

# Step 3: Wait for V1 deployment to finish
kubectl rollout status deployment/rolling-demo -n deploy-lab

# Step 4: Inspect the generated ReplicaSet and hash label
kubectl get rs -n deploy-lab -l app=rolling-demo --show-labels

# Step 5: Trigger a rolling update to Version 2 and watch ReplicaSets in real-time
kubectl set image deployment/rolling-demo web=nginx:1.25-alpine -n deploy-lab

# In another terminal or immediately:
kubectl get rs -n deploy-lab -w

# Step 6: Trigger a BAD rollout (broken image) to test progressDeadlineSeconds
kubectl set image deployment/rolling-demo web=nginx:invalid-tag-does-not-exist -n deploy-lab

# Step 7: Observe rollout status timing out after 30 seconds
kubectl rollout status deployment/rolling-demo -n deploy-lab --timeout=45s

# Step 8: Inspect Deployment conditions to see ProgressDeadlineExceeded
kubectl describe deployment rolling-demo -n deploy-lab | grep -A 5 "Conditions:"

# Step 9: Roll back the bad update
kubectl rollout undo deployment/rolling-demo -n deploy-lab
kubectl rollout status deployment/rolling-demo -n deploy-lab

# Step 10: Clean up
kubectl delete namespace deploy-lab
```

## Common Interview Questions

**Q1: How does the Deployment controller orchestrate a zero-downtime rolling update?**

The Deployment controller does not interact with Pods directly. Instead, when `.spec.template` is updated, it creates a new child ReplicaSet. It gradually scales up the new ReplicaSet and scales down the old ReplicaSet in discrete steps dictated by `maxSurge` and `maxUnavailable`. A new Pod is not considered operational until it passes its readiness probes; only then does the controller scale down old Pods, ensuring continuous traffic handling capacity throughout the rollout.

**Q2: What is the exact behavior of `maxSurge: 1` and `maxUnavailable: 0` on a 4-replica Deployment?**

`maxSurge: 1` permits the cluster to run at most 5 total Pods ($4 + 1$) during the rollout. `maxUnavailable: 0` requires that at least 4 healthy Pods remain `Ready` at all times. The controller will start by scaling the new ReplicaSet to 1 (5 total pods). Once that new Pod passes readiness probes, it scales the old ReplicaSet down to 3 (4 total pods). It repeats this one-by-one progression until all 4 replicas belong to the new ReplicaSet, guaranteeing zero loss of capacity.

**Q3: What is the `pod-template-hash` label, and why does Kubernetes generate it automatically?**

The `pod-template-hash` is a 32-bit hash string automatically computed from the Pod template specification (`spec.template`) and injected into both the child ReplicaSet and all its Pods. It uniquely distinguishes Pods created by different revisions of the same Deployment. This prevents the Deployment's parent selector (e.g. `app: web`) from accidentally adopting or scaling Pods from different revisions or other controllers.

**Q4: What does `progressDeadlineSeconds` control, and what happens when it expires?**

`progressDeadlineSeconds` specifies the maximum time (in seconds) the Deployment controller will wait for a rollout to make forward progress before marking it as stalled. If tasks like container image pulling, readiness probes, or node scheduling fail to progress within this window, the controller sets the Deployment's `Progressing` condition to `False` with the reason `ProgressDeadlineExceeded`. The rollout stops progressing, leaving existing healthy Pods online, and CI/CD pipelines receive a failure code.

**Q5: Why would an operator use `kubectl rollout pause` on a Deployment?**

`kubectl rollout pause` halts active rollout reconciliation on a Deployment. It is used when applying multiple configuration changes sequentially (such as updating resource requests, environment variables, configmaps, and container image tags). Pausing prevents the controller from creating intermediate ReplicaSets and triggering unnecessary rolling updates for each edit. Once all changes are applied, running `kubectl rollout resume` executes a single, clean rollout.
