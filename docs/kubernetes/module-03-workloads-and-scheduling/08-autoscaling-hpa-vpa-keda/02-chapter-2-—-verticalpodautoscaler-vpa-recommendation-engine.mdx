# Chapter 2 — VerticalPodAutoscaler (VPA) Recommendation Engine

> **Goal:** Master the architecture and operations of the Kubernetes VerticalPodAutoscaler (VPA) — understanding the three decoupled components (Recommender, Updater, Admission Controller), evaluating update modes (`Off`, `Initial`, `Auto`), bounding recommendations with `ResourcePolicy`, resolving HPA vs VPA feedback conflicts, and utilizing in-place pod resizing without evictions.
>
> By the end of this chapter, you will understand:
> 1. The structural separation of concerns: Recommender vs Updater vs Admission Controller
> 2. How the Recommender computes percentiles (Target, LowerBound, UpperBound, UncappedTarget)
> 3. The 4 VPA update modes: `Off` (advisory), `Initial` (on boot), `Recreate` (evict & replace), `Auto`
> 4. How `resourcePolicy.minAllowed` and `maxAllowed` protect against runaway cloud costs
> 5. Why HPA and VPA must NEVER scale on the same resource metric simultaneously
> 6. How In-Place Pod Resizing (Kubernetes 1.29+ beta) resizes CPU and memory without container restarts

## Real-Life Analogy

Think of VPA as a **personal tailor for growing children**:

- **Horizontal Scaling (HPA):** If one child can't carry a heavy wooden log, you hire 3 more children (adding more Pods).
- **Vertical Scaling (VPA):** The child is outgrowing their jacket. Instead of getting 3 more children, the tailor measures the child's actual arm length and shoulders (resource utilization) and tailors a **larger jacket (allocating more CPU and RAM to the same container)**.
- **The Three Tailor Roles:**
  - **The Recommender:** Measures the child every month and writes down recommended clothing sizes (`updateMode: Off`).
  - **The Admission Controller:** When the child is born or bought new clothes, it ensures they put on the correctly sized jacket right from day one (`updateMode: Initial`).
  - **The Updater:** When the jacket is too tight, it takes the old jacket off and gives them a larger one, even if it disrupts playtime (`updateMode: Auto / Recreate`).

## The 3 Decoupled VPA Components

Unlike the monolithic HPA controller, VPA consists of three modular microservices:

```text
 ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────┐
 │ Component                    │ Core Functionality                                                  │
 │──────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
 │ **`vpa-recommender`**        │ Analyzes historical CPU and memory utilization, computes statistical│
 │                              │ percentiles, and updates the VPA object's `.status.recommendation`. │
 │──────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
 │ **`vpa-admission-controller`**│ Mutating admission webhook that intercepts Pod creation requests and│
 │                              │ injects the latest recommended `requests` into the Pod manifest.    │
 │──────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
 │ **`vpa-updater`**            │ Periodically evaluates running Pods; if resource limits diverge     │
 │                              │ significantly from recommendations, it forcefully evicts the Pod.   │
 └──────────────────────────────┴─────────────────────────────────────────────────────────────────────┘
```

## The 4 VPA Update Modes

Configured under `.spec.updatePolicy.updateMode`:

```text
 ┌──────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
 │ Mode                 │ Operational Behavior & Best Use Cases                                       │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`Off`** (Advisory) │ **Recommendation Only (Zero Disruptions).**                                 │
 │                      │ Computes metrics and populates status, but NEVER evicts or mutates Pods.    │
 │                      │ *Best for:* Production capacity planning and observability baselines.       │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`Initial`**        │ **Assign on Creation Only.**                                                │
 │                      │ Mutates requests when a Pod is spawned. Never evicts running Pods.          │
 │                      │ *Best for:* Stateful workloads or batch Jobs that cannot tolerate eviction. │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`Recreate`**       │ **Evict & Replace.**                                                        │
 │                      │ Evicts running Pods whose resources diverge from targets so they can be     │
 │                      │ recreated with updated sizes by their parent controller.                    │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`Auto`**           │ **Full Automated Lifecycle.**                                               │
 │                      │ Currently an alias for `Recreate` (will switch to in-place resize in future)│
 └──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## Understanding VPA Recommendation Values

Running `kubectl describe vpa <name>` reveals four distinct recommendation thresholds:

```yaml
status:
  recommendation:
    containerRecommendations:
    - containerName: web-app
      # 1. Target: The ideal recommended resource allocation (used by Admission/Updater)
      target:
        cpu: "350m"
        memory: "512Mi"
      # 2. LowerBound: Minimum allocation before Updater considers the Pod under-provisioned
      lowerBound:
        cpu: "200m"
        memory: "384Mi"
      # 3. UpperBound: Maximum allocation before Updater considers the Pod over-provisioned
      upperBound:
        cpu: "800m"
        memory: "1024Mi"
      # 4. UncappedTarget: The raw recommendation ignoring minAllowed/maxAllowed policies
      uncappedTarget:
        cpu: "1200m"
        memory: "2048Mi"
```

## Restricting VPA with `ResourcePolicy`

To prevent a memory leak bug from tricking VPA into requesting an entire 64GB node, always configure `minAllowed` and `maxAllowed` boundaries:

```yaml
spec:
  resourcePolicy:
    containerPolicies:
    - containerName: web-app
      mode: Auto
      minAllowed:
        cpu: "100m"
        memory: "128Mi"
      maxAllowed:
        cpu: "2000m"
        memory: "4Gi"
      controlledResources: ["cpu", "memory"]
```

## The HPA vs VPA Conflict (The Deadly Loop)

> [!CAUTION]
> **Never configure HPA and VPA to scale on CPU or Memory simultaneously on the same Deployment!**

```text
 The Fatal HPA + VPA Race Condition:

 1. Traffic increases ──► CPU usage spikes across Pods.
 2. HPA reacts: "CPU is high! Scale out from 3 to 10 replicas!"
 3. VPA reacts: "CPU is high! Resize Pods from 500m to 2000m CPU!"
 4. Result: 10 massive Pods created (20 Cores total), causing massive over-provisioning!
 5. Traffic subsides: HPA scales down while VPA scales down, causing violent flapping and evictions!
```

### The Solution:
- Use **VPA for CPU/Memory** and **HPA for Custom/External Metrics** (e.g. HTTP Requests/sec or SQS queue depth).
- Or use **VPA in `updateMode: Off`** for sizing recommendations and let HPA drive autoscaling.

## Modern Evolution: In-Place Pod Resizing (Kubernetes 1.29+ Beta)

Historically, resizing a container required killing the Pod. In-Place Pod Resizing (`InPlacePodVerticalScaling` feature gate) mutates cgroup limits **without restarting containers**:

```yaml
spec:
  containers:
  - name: db
    image: postgres:15
    resources:
      requests:
        cpu: "1"
        memory: "2Gi"
    # Configures in-place resize behavior per resource
    resizePolicy:
    - resourceName: cpu
      restartPolicy: NotRequired     # <--- Resizes CPU online without restart!
    - resourceName: memory
      restartPolicy: RestartContainer # Memory might require app restart
```

## Complete Production VPA Manifest

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: api-vpa-recommender
  namespace: production
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: customer-api

  updatePolicy:
    updateMode: "Off"    # Production safety: Recommendation-only mode

  resourcePolicy:
    containerPolicies:
    - containerName: '*'
      minAllowed:
        cpu: "100m"
        memory: "256Mi"
      maxAllowed:
        cpu: "4000m"
        memory: "8Gi"
      controlledResources: ["cpu", "memory"]
```

## Hands-On Lab: Deploying VPA in Recommendation Mode

```bash
# Step 1: Create lab namespace
kubectl create namespace vpa-lab

# Step 2: Deploy a sample application with arbitrary initial resources
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vpa-demo-app
  namespace: vpa-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: vpa-demo
  template:
    metadata:
      labels:
        app: vpa-demo
    spec:
      containers:
      - name: web
        image: python:3.11-slim
        command: ["python", "-c", "import time, math; [math.sqrt(i) for i in range(10000000)]; time.sleep(3600)"]
        resources:
          requests:
            cpu: "50m"
            memory: "64Mi"
EOF

# Step 3: Apply a VPA targeting the Deployment in "Off" mode
cat <<EOF | kubectl apply -f -
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: demo-vpa
  namespace: vpa-lab
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: vpa-demo-app
  updatePolicy:
    updateMode: "Off"
EOF

# Step 4: Wait for VPA recommender to gather metrics and inspect recommendations
sleep 15
kubectl describe vpa demo-vpa -n vpa-lab

# Step 5: Clean up lab
kubectl delete namespace vpa-lab
```

## Common Interview Questions

**Q1: What are the three core components of the VerticalPodAutoscaler (VPA)?**

VPA consists of three decoupled components:
1. `vpa-recommender`: Collects current and historical resource usage metrics from `metrics-server` or Prometheus, computes statistical percentiles, and updates the VPA object's recommended targets.
2. `vpa-updater`: Periodically inspects running Pods and issues eviction requests for Pods whose allocated resources diverge significantly from the Recommender's target values.
3. `vpa-admission-controller`: A mutating admission webhook that intercepts new Pod creation requests and rewrites container `resources.requests` and `limits` with the latest VPA recommendations.

**Q2: What is the difference between VPA update modes `Off`, `Initial`, and `Auto`?**

- `Off`: Generates CPU and memory sizing recommendations in the VPA status for advisory analysis, but never mutates manifests or evicts running Pods.
- `Initial`: Assigns recommended resource requests only at Pod creation time (via the admission webhook); running Pods are never evicted.
- `Auto`: Full automated lifecycle management; evicts running Pods when their resource allocations become suboptimal so they can be recreated with updated sizes by their parent controller.

**Q3: Why can't HPA and VPA scale on CPU or Memory simultaneously for the same workload?**

HPA scales the number of Pod replicas horizontally based on CPU/memory utilization, while VPA scales the individual Pod's CPU/memory requests vertically. If traffic increases, both controllers react simultaneously: HPA spawns additional Pods while VPA increases container size. When traffic recedes, both controllers downscale concurrently. This creates an uncoordinated positive feedback loop resulting in severe resource thrashing, continuous pod evictions, and unpredictable capacity exhaustion.

**Q4: What is In-Place Pod Resizing, and how does it improve upon traditional VPA?**

Traditional VPA (in `Recreate` or `Auto` mode) must evict and recreate the entire Pod to adjust CPU and memory allocations, causing brief service interruptions and requiring surplus cluster capacity. In-Place Pod Resizing allows the Kubelet to dynamically modify container cgroup allocations (`cpu.cfs_quota_us` and `memory.max`) in-place without terminating the container process or rescheduling the Pod, enabling seamless zero-downtime vertical autoscaling.

**Q5: What is the role of `ResourcePolicy` in a VPA manifest?**

`ResourcePolicy` defines operational safety guardrails for the VPA. It allows administrators to set `minAllowed` (preventing VPA from scaling down below baseline operational floors) and `maxAllowed` (preventing VPA from requesting exorbitant resources due to application memory leaks), as well as selecting which specific containers and resources (`cpu`, `memory`) VPA is authorized to control.
