# Chapter 3 — Pod RestartPolicy vs Job BackoffLimit

> **Goal:** Master the failure handling, retry mechanics, and policy engines of Kubernetes Jobs — understanding the operational difference between `restartPolicy: Never` and `restartPolicy: OnFailure`, tracing the exponential backoff retry curve, avoiding etcd pod sprawl, and implementing modern `podFailurePolicy` rules to handle spot instance preemptions vs unrecoverable application errors.
>
> By the end of this chapter, you will understand:
> 1. Why `restartPolicy: Always` is strictly forbidden in Job specifications
> 2. How `restartPolicy: Never` creates a new Pod vs how `OnFailure` restarts containers in-place
> 3. The exponential backoff algorithm governing Job retry delays (10s to 360s)
> 4. How `backoffLimit` defines the cluster's failure budget before marking a Job `Failed`
> 5. How to write `podFailurePolicy` rules to fail fast on fatal exit codes and ignore spot evictions
> 6. How to diagnose failing batch jobs using `kubectl get job` and container exit codes

## Real-Life Analogy

Think of a Job retry policy as **troubleshooting a faulty lawnmower engine**:

- **`restartPolicy: OnFailure` (Pulling the Starter Cord on the Same Mower):** The engine sputters and stalls (container exits non-zero). You don't throw the lawnmower in the dump; you stay standing in the exact same yard (same Pod, same IP, same node), wait a moment, and pull the starter cord again.
- **`restartPolicy: Never` (Throwing the Mower Away and Buying a New One):** The engine stalls. You immediately mark that lawnmower as dead (`Pod: Failed`), leave it sitting on the lawn, and order a brand new lawnmower delivered to a potentially different yard (`New Pod created on Node B`).
- **`podFailurePolicy` (The Smart Mechanic's Rules):**
  - If the spark plug fails (`Exit Code 1`): Retry up to 6 times (`action: Count`).
  - If the engine block is cracked in half (`Exit Code 42 - Unrecoverable Config Error`): Stop pulling the cord immediately! Do not waste time retrying (`action: FailJob`).
  - If someone steals the mower off the lawn (Spot VM preemption / Node shutdown): Don't blame the engine! Order a replacement without counting it as a failure (`action: Ignore`).

## `restartPolicy: Never` vs `OnFailure`

The table below contrasts the two valid restart policies for batch workloads:

```text
 ┌───────────────────────────┬─────────────────────────────────┬─────────────────────────────────┐
 │ Dimension                 │ `restartPolicy: OnFailure`      │ `restartPolicy: Never`          │
 │───────────────────────────┼─────────────────────────────────┼─────────────────────────────────┤
 │ **Container Supervisor**  │ Local `kubelet` daemon on node  │ `kube-controller-manager` (Job) │
 │ **Pod Lifecycle**         │ Same Pod stays alive; restarts  │ Pod transitions to `Failed`; a  │
 │                           │ container locally inside cgroup │ brand new Pod is scheduled      │
 │ **Node Placement**        │ Bound to original node          │ May schedule on different node  │
 │ **Storage Volumes**       │ Local `emptyDir` data retained  │ Fresh `emptyDir` volume created │
 │ **Pod Artifact Sprawl**   │ Minimal (Only 1 Pod object)     │ High (Creates $N$ Failed Pods)  │
 │ **Best For**              │ In-memory caching, transient    │ Node-specific hardware faults,  │
 │                           │ network glitches                │ clean environment guarantees    │
 └───────────────────────────┴─────────────────────────────────┴─────────────────────────────────┘
```

> [!IMPORTANT]
> **Why is `restartPolicy: Always` prohibited?**
> A Job's purpose is to run until `.spec.completions` successful terminations occur. If `restartPolicy: Always` were permitted, a container that exited with code `0` (success) would be immediately restarted by the Kubelet, preventing the Job from ever reaching a terminal `Complete` state.

## Exponential Backoff Delay & `backoffLimit`

When a Job's Pod fails, the Job controller does not immediately launch a replacement. It enforces an **exponential backoff delay** to avoid overloading the cluster or external databases:

$$\text{Delay} = 10\text{s} \times 2^{(\text{retry count} - 1)}$$

```text
 Retry Progression (Default backoffLimit: 6):
 - Failure 1: Wait 10 seconds before starting Pod 2
 - Failure 2: Wait 20 seconds before starting Pod 3
 - Failure 3: Wait 40 seconds before starting Pod 4
 - Failure 4: Wait 80 seconds before starting Pod 5
 - Failure 5: Wait 160 seconds before starting Pod 6
 - Failure 6: Wait 320 seconds before starting Pod 7
 - Failure 7: backoffLimit (6) EXCEEDED ──► Job marked FAILED!
```

*Note: The exponential backoff delay is capped at a maximum of **6 minutes (360 seconds)**.*

## Advanced Error Handling: `podFailurePolicy` (Kubernetes 1.26+ GA)

Standard `backoffLimit` treats all errors identically. A missing configuration file (fatal) and a node hardware reboot (transient) both burn the same retry budget.

`podFailurePolicy` provides declarative error-handling rules:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: smart-data-job
spec:
  backoffLimit: 6
  podFailurePolicy:
    rules:
    # Rule 1: Fatal Application Error -> FAIL IMMEDIATELY (Do not retry!)
    - action: FailJob
      onExitCodes:
        containerName: main-worker
        operator: In
        values: [42, 100]    # 42 = Invalid Input, 100 = Auth Failed

    # Rule 2: Cloud Spot VM Interruption -> IGNORE (Do not count against backoffLimit!)
    - action: Ignore
      onPodConditions:
      - type: DisruptionTarget
        status: "True"

    # Rule 3: General Failures -> COUNT against backoffLimit
    - action: Count
      onExitCodes:
        operator: NotIn
        values: [0]
```

```text
 Actions Supported in podFailurePolicy:
 1. `FailJob`: Marks the Job as Failed immediately and terminates all other running pods.
 2. `Ignore`: Does NOT increment the failure counter (ideal for spot node evictions).
 3. `Count`: Standard failure handling; increments failure count toward `backoffLimit`.
```

## Complete Production Job Manifest with `podFailurePolicy`

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: financial-settlement
  namespace: batch-finance
  labels:
    tier: batch
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 5
  activeDeadlineSeconds: 1200
  ttlSecondsAfterFinished: 300

  # Fine-grained error evaluation
  podFailurePolicy:
    rules:
    - action: FailJob
      onExitCodes:
        containerName: processor
        operator: In
        values: [2, 3]    # 2 = Bad Schema, 3 = Corrupt Transaction Log
    - action: Ignore
      onPodConditions:
      - type: DisruptionTarget
        status: "True"

  template:
    metadata:
      labels:
        tier: batch
    spec:
      restartPolicy: Never
      containers:
      - name: processor
        image: python:3.11-alpine
        command:
        - "python"
        - "-c"
        - |
          import sys, time
          print("Checking database credentials...")
          time.sleep(2)
          # Simulate unrecoverable config error
          print("FATAL: Configuration schema invalid! Exiting with code 2")
          sys.exit(2)
```

## Hands-On Lab: Observing Pod Retries & podFailurePolicy Fast-Fail

```bash
# Step 1: Create lab namespace
kubectl create namespace retry-lab

# Step 2: Deploy a Job with restartPolicy: Never and observe multiple Failed Pods
cat <<EOF | kubectl apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: retry-demo
  namespace: retry-lab
spec:
  backoffLimit: 2
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: failing-app
        image: alpine:latest
        command: ["sh", "-c", "echo 'Failing on purpose'; exit 1"]
EOF

# Step 3: Watch Pods being spawned and failed
sleep 15
kubectl get pods -n retry-lab
# Notice: You see multiple Pods in 'Error' state (one for each retry attempt)!

# Step 4: Deploy a Job with podFailurePolicy: FailJob to test fast-failure
cat <<EOF | kubectl apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: fast-fail-demo
  namespace: retry-lab
spec:
  backoffLimit: 10
  podFailurePolicy:
    rules:
    - action: FailJob
      onExitCodes:
        operator: In
        values: [42]
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: alpine:latest
        command: ["sh", "-c", "echo 'Fatal error encountered'; exit 42"]
EOF

# Step 5: Verify Job fails IMMEDIATELY without attempting 10 retries
sleep 5
kubectl get job fast-fail-demo -n retry-lab -o yaml | grep -A 5 "conditions:"
# Notice: Status is Failed, Reason: PodFailurePolicy, without wasting any retries!

# Step 6: Clean up lab
kubectl delete namespace retry-lab
```

## Common Interview Questions

**Q1: What is the operational difference between `restartPolicy: Never` and `restartPolicy: OnFailure` in a Kubernetes Job?**

With `restartPolicy: OnFailure`, when a container process exits non-zero, the local `kubelet` on the worker node restarts the container inside the **same Pod sandbox**. The Pod remains on the same node, preserves its IP address, and retains any data in `emptyDir` volumes. With `restartPolicy: Never`, the failing Pod is permanently marked as `Failed`, and the `kube-controller-manager` Job controller creates an entirely **new Pod object**, which may be scheduled on a different worker node with clean volumes.

**Q2: How does Kubernetes calculate retry delays when a Job Pod fails?**

Kubernetes applies an exponential backoff delay algorithm: $\text{Delay} = 10\text{s} \times 2^{(\text{retry} - 1)}$. The first retry waits 10 seconds, the second waits 20s, followed by 40s, 80s, 160s, and 320s, with a maximum upper ceiling capped at 6 minutes (360 seconds). This prevents failing batch jobs from spamming API server logs or overwhelming external dependencies during cascading database outages.

**Q3: What problem does `podFailurePolicy` solve in Kubernetes batch processing?**

Standard `backoffLimit` treats all Pod terminations identically, burning the failure budget whether caused by a fatal application bug (e.g. invalid credentials) or an infrastructure event (e.g. Spot VM preemption). `podFailurePolicy` introduces fine-grained rules based on container exit codes or Pod conditions: (1) `action: FailJob` fails the Job immediately on fatal application exit codes without wasting retry attempts; (2) `action: Ignore` disregards terminations caused by node preemptions (`DisruptionTarget`) so they don't count toward `backoffLimit`.

**Q4: Why is `restartPolicy: Always` rejected by the Kubernetes API server for Job resources?**

A Job's fundamental contract is to run workloads to completion. When a container process exits with code `0` (success), `restartPolicy: Always` would instruct the Kubelet to immediately restart the container. This creates an infinite loop where the container repeatedly executes and terminates, preventing the Job controller from ever recognizing that the task has finished and leaving the Job stuck running forever.

**Q5: What happens when a Job reaches its `backoffLimit` threshold?**

When the cumulative number of failed Pods reaches `.spec.backoffLimit` (default: 6), the Job controller halts the creation of new Pods, sends termination signals (`SIGTERM`/`SIGKILL`) to any currently running workers, and updates the Job's `.status.conditions` to `type: Failed, status: True, reason: BackoffLimitExceeded`.
