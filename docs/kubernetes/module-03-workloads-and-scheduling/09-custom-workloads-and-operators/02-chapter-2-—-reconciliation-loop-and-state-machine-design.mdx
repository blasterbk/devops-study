# Chapter 2 — Reconciliation Loop & State Machine Design

> **Goal:** Master the core software engineering principles of Kubernetes controllers — designing level-triggered idempotent reconciliation loops (`Observe → Compare → Act`), implementing `Finalizers` to safely tear down external cloud assets, setting `OwnerReferences` for automated garbage collection, tuning event predicates to eliminate CPU reconcile storms, and configuring High-Availability Leader Election.
>
> By the end of this chapter, you will understand:
> 1. The 4-step level-triggered reconciliation loop: Observe, Compare, Act, Requeue
> 2. Why idempotency is mandatory for Kubernetes controllers
> 3. How `ctrl.Result` controls immediate backoff requeues vs delayed polling
> 4. How Finalizers block API deletion to execute external cloud cleanup
> 5. When to use `OwnerReferences` (in-cluster) vs `Finalizers` (out-of-cluster)
> 6. How leader election guarantees active-passive HA in multi-replica controller deployments

## Real-Life Analogy

Think of a reconciliation loop as an **automated building climate control system (Smart Thermostat)**:

- **Level-Triggered State (Observe):** The thermostat does not care *how many times* you opened the front door (edge events). Every 10 seconds, it simply reads the actual current temperature in the room: *"It is 78°F."*
- **The Desired Spec (Compare):** It reads the target temperature set by the homeowner: *"The desired temperature is 70°F."* It computes the diff: $\Delta = 78 - 70 = +8^\circ\text{F}$.
- **Idempotent Action (Act):** The thermostat turns on the air conditioning compressor. If the control loop runs 50 times while the room is cooling, running the loop 50 times simply leaves the AC on; it does not accidentally turn on 50 separate air conditioners (Idempotency).
- **The Finalizer (The Safe Shutdown Checklist):** When the homeowner unplugs and sells the thermostat (Object Deletion), the system does **not** instantly vanish. It holds open a **Finalizer Lock** to safely pump refrigerant back into the storage tank and close the gas intake valve. Once the external cleanup finishes, it releases the lock and powers off completely.

## The Principle of Idempotency

In distributed systems, network packets are dropped, API calls are retried, and events arrive out of order.

```text
 Definition of Idempotency:
 A reconciliation loop is idempotent if running `Reconcile()` once produces the exact same 
 system state as running `Reconcile()` 100 times in rapid succession.
```

### Key Idempotency Rules:
1. **Never Assume State:** Never assume a resource was created just because you issued a creation command in a previous loop iteration; always check cache first.
2. **Use Server-Side Apply (SSA) or Structured Patching:** Prefer `r.Patch()` over blind `r.Update()` to avoid overwriting fields modified by other controllers.
3. **Handle Not-Found Errors Gracefully:** If fetching the object returns `NotFound`, return `ctrl.Result{}, nil` immediately to halt reconciliation.

## Mastering `ctrl.Result` Return Flow

The return value of `Reconcile(ctx, req)` dictates how the controller runtime schedules the next evaluation:

```text
 ┌──────────────────────────────────────┬─────────────────────────────────────────────────────────────────────┐
 │ Return Statement                     │ Controller Runtime Behavior                                         │
 │──────────────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
 │ `return ctrl.Result{}, nil`          │ **Success.** Reconciliation complete. Controller sleeps until the   │
 │                                      │ next watch event occurs on the parent or owned child resources.     │
 │──────────────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
 │ `return ctrl.Result{RequeueAfter: d},│ **Periodic Polling.** Re-runs the loop after duration `d` (e.g. 5m) │
 │  nil`                                │ to poll external APIs or verify long-running background tasks.      │
 │──────────────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
 │ `return ctrl.Result{}, err`          │ **Transient Failure.** Triggers an immediate requeue with           │
 │                                      │ exponential rate-limiting backoff (prevents API spam).              │
 │──────────────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
 │ `return ctrl.Result{Requeue: true},  │ **Immediate Requeue.** Pushes the request immediately back to the   │
 │  nil`                                │ head of the workqueue. (Use sparingly).                             │
 └──────────────────────────────────────┴─────────────────────────────────────────────────────────────────────┘
```

## Finalizers vs OwnerReferences

When an object is deleted from Kubernetes, how do you clean up its associated assets?

```text
 ┌───────────────────────────┬─────────────────────────────────┬─────────────────────────────────┐
 │ Dimension                 │ `OwnerReferences`               │ `Finalizers`                    │
 │───────────────────────────┼─────────────────────────────────┼─────────────────────────────────┤
 │ **Target Assets**         │ **In-Cluster Resources**        │ **External Out-of-Cluster**     │
 │                           │ (Child Pods, PVCs, Services)    │ (AWS S3, Cloud SQL, DNS Records)│
 │ **Execution Mechanism**   │ Automated Garbage Collector     │ Custom Go cleanup logic written │
 │                           │ inside API server               │ in your controller              │
 │ **Deletes from etcd**     │ Immediately                     │ BLOCKED until finalizer removed │
 │ **Helper Function**       │ `controllerutil.SetController-  │ `controllerutil.AddFinalizer` / │
 │                           │  Reference`                     │ `controllerutil.RemoveFinalizer`│
 └───────────────────────────┴─────────────────────────────────┴─────────────────────────────────┘
```

## The Complete Finalizer Lifecycle Pattern

```go
const myFinalizerName = "storage.example.com/cleanup-s3-bucket"

func (r *BucketReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var bucket storagev1.CloudBucket
    if err := r.Get(ctx, req.NamespacedName, &bucket); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    // 1. Check if the object is under deletion
    if bucket.ObjectMeta.DeletionTimestamp.IsZero() {
        // Object is NOT being deleted -> Ensure our finalizer is registered
        if !controllerutil.ContainsFinalizer(&bucket, myFinalizerName) {
            controllerutil.AddFinalizer(&bucket, myFinalizerName)
            if err := r.Update(ctx, &bucket); err != nil {
                return ctrl.Result{}, err
            }
        }
    } else {
        // 2. Object IS being deleted -> Run external cleanup!
        if controllerutil.ContainsFinalizer(&bucket, myFinalizerName) {
            // Call AWS / Cloud Provider API to delete external S3 bucket
            if err := r.deleteExternalS3Bucket(&bucket); err != nil {
                // Return error to retry cleanup on failure!
                return ctrl.Result{}, err
            }

            // Cleanup succeeded -> Remove finalizer to allow etcd deletion
            controllerutil.RemoveFinalizer(&bucket, myFinalizerName)
            if err := r.Update(ctx, &bucket); err != nil {
                return ctrl.Result{}, err
            }
        }
        // Stop reconciliation as object will be removed
        return ctrl.Result{}, nil
    }

    // 3. Normal Active Reconciliation Logic Here...
    return ctrl.Result{}, nil
}
```

## Leader Election for Controller High Availability

When running multiple replicas of your custom operator pod (`replicas: 3`) for high availability:
- **Leader Election** ensures that **only one active leader** executes `Reconcile()` loops.
- The other 2 replicas sit in a standby hot-spare state, maintaining their informer caches.
- If the active leader pod crashes, a standby replica immediately acquires the lease within 10 seconds via a Kubernetes `Lease` object in `coordination.k8s.io`.

```go
func main() {
    mgr, err := ctrl.NewManager(ctrl.GetConfigOrDie(), ctrl.Options{
        Scheme:                 scheme,
        LeaderElection:         true,                  // Enable HA Leader Election!
        LeaderElectionID:       "my-operator-lock",    // Name of the Lease resource
        LeaderElectionNamespace: "kube-system",
    })
}
```

## Hands-On Lab: Observing Finalizer Deletion Blocking

```bash
# Step 1: Create lab namespace
kubectl create namespace finalizer-lab

# Step 2: Create a raw ConfigMap with a manual Finalizer attached
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: protected-config
  namespace: finalizer-lab
  finalizers:
  - example.com/database-backup-guard
data:
  database_url: "postgres://db.prod:5432"
EOF

# Step 3: Attempt to delete the ConfigMap (Run in background or notice it BLOCKS)
kubectl delete cm protected-config -n finalizer-lab --wait=false

# Step 4: Inspect the ConfigMap status
kubectl get cm protected-config -n finalizer-lab -o yaml
# Observe: metadata.deletionTimestamp is SET, but the object is NOT DELETED!

# Step 5: Simulate the controller finishing external cleanup and removing the finalizer
kubectl patch cm protected-config -n finalizer-lab -p '{"metadata":{"finalizers":[]}}' --type=merge

# Step 6: Verify the ConfigMap is now instantly deleted!
kubectl get cm protected-config -n finalizer-lab

# Step 7: Clean up lab
kubectl delete namespace finalizer-lab
```

## Common Interview Questions

**Q1: What are the four fundamental steps of a Kubernetes reconciliation loop?**

The four steps are: (1) **Observe**: Query the in-memory Informer cache to retrieve the current state of the Custom Resource and all related child resources; (2) **Compare**: Compute the delta between the declared desired state (`.spec`) and the observed actual state; (3) **Act**: Execute API calls (Create, Patch, Delete) to bring the cluster state into alignment with the spec, and update `.status`; (4) **Requeue**: Return `ctrl.Result` to either sleep until the next event, trigger an exponential backoff on error, or schedule a delayed poll.

**Q2: What is a Finalizer in Kubernetes, and how does it prevent data loss?**

A Finalizer is a key in `.metadata.finalizers[]` that alerts the Kubernetes API server that an asynchronous pre-deletion cleanup routine must execute before the object can be removed from `etcd`. When a user deletes an object with a finalizer, the API server sets `.metadata.deletionTimestamp` but **blocks deletion**. The controller detects the timestamp, tears down external infrastructure (e.g. cloud storage buckets, load balancers, DNS records), and removes the finalizer string, allowing the API server to finalize object deletion.

**Q3: When should you use `OwnerReferences` versus `Finalizers` for resource cleanup?**

Use **`OwnerReferences`** for dependent Kubernetes resources that live **inside the same cluster and namespace** (such as child Pods, ConfigMaps, Secrets, or Services created by the parent). The built-in Kubernetes garbage collector automatically cascades deletion to child objects. Use **`Finalizers`** when managing **out-of-cluster external resources** (such as cloud AWS S3 buckets, GCP CloudSQL databases, external DNS records, or Vault tokens) that require custom Go API client calls to tear down cleanly before the custom resource is destroyed.

**Q4: Why must a Kubernetes controller's `Reconcile()` function be strictly idempotent?**

Reconciliation is **level-triggered**, meaning events indicate that the *state has changed*, but do not guarantee a 1:1 mapping with specific user actions. Events can be duplicated, delayed, or batched during network latency or controller restarts. If `Reconcile()` is not idempotent, executing the loop multiple times could provision duplicate cloud resources, overwrite valid status updates, or cause infinite reconciliation loops.

**Q5: How does Leader Election work in multi-replica Kubernetes operator deployments?**

Leader election prevents split-brain race conditions by ensuring only one operator replica reconciles resources at a time. The controller runtime uses the `coordination.k8s.io/v1` `Lease` API. All operator replicas attempt to acquire and renew a shared `Lease` object every few seconds. The replica that holds the lease becomes the active Leader and runs reconcilers; standby replicas keep their informer caches warm. If the leader fails to renew the lease due to a crash, a standby replica takes over within seconds.
