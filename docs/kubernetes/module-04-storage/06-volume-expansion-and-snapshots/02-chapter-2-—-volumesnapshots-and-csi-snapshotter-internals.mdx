> By the end of this chapter, you will understand:
> 1. The 3 core Snapshot CRDs: `VolumeSnapshotClass`, `VolumeSnapshot`, and `VolumeSnapshotContent`
> 2. How `snapshot-controller` and `csi-snapshotter` coordinate with cloud storage APIs

> 5. The architectural difference between Crash-Consistent and Application-Consistent snapshots

## Real-Life Analogy

Think of VolumeSnapshots as **taking a high-resolution photograph of a busy architectural construction site**:

- **The Construction Site (Active PersistentVolume):** Thousands of bricks and concrete beams are being placed every minute (Active database write transactions).
- **The Snapshot Command (`VolumeSnapshot`):** The project manager pushes a button on their camera: *"Capture the state of the building at exactly 2:00 PM."*
- **The Photo Negative (`VolumeSnapshotContent`):** The camera produces an immutable high-resolution digital negative stored in the secure corporate cloud archive (AWS EBS Snapshot / GCP Snapshot).
- **Building a Duplicate Clone (`dataSource: VolumeSnapshot`):** A client wants to test an earthquake simulation. Instead of demolishing the real building, they hand the 2:00 PM digital negative to a 3D building printer (`PVC creation`). The printer creates an exact physical replica of the building in 30 seconds (**Instant Test Database**).
- **Crash-Consistent vs Application-Consistent:**
  - *Crash-Consistent:* Snapping a photo while a worker is mid-air dropping a brick. When you clone the building, you find a half-dropped brick on the floor that needs cleanup.
  - *Application-Consistent:* Yelling *"Freeze!"* over the megaphone (`FLUSH TABLES;`), waiting for all workers to set down their tools, snapping the crystal-clear photo, and yelling *"Resume!"*.

## The 3 Snapshot Custom Resource Definitions (CRDs)

Managed under the `snapshot.storage.k8s.io/v1` API group:

```text
 ┌──────────────────────────────┬─────────┬───────────────────────────────────────────────────────────┐
 │ Custom Resource              │ Scope   │ Operational Responsibility                                │
 │──────────────────────────────┼─────────┼───────────────────────────────────────────────────────────┤
 │ **`VolumeSnapshotClass`**    │ Cluster │ Defines storage driver, parameters, and deletion policies │
 │                              │         │ (`deletionPolicy: Delete` vs `Retain`).                   │
 │──────────────────────────────┼─────────┼───────────────────────────────────────────────────────────┤
 │ **`VolumeSnapshot`**         │ Namespace│ Developer request specifying the source PVC to snapshot.  │
 │──────────────────────────────┼─────────┼───────────────────────────────────────────────────────────┤
 │ **`VolumeSnapshotContent`**  │ Cluster │ The actual snapshot artifact containing the cloud provider│
 │                              │         │ snapshot ID (`snapshotHandle: snap-0123456789`).          │
 └──────────────────────────────┴─────────┴───────────────────────────────────────────────────────────┘
```

## Restoring a New PVC from a `VolumeSnapshot`

To spin up a new database replica, staging environment, or disaster recovery instance:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: staging-db-restored-pvc
  namespace: database
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: ebs-gp3-sc
  # 1. Point dataSource to the VolumeSnapshot
  dataSource:
    name: prod-backup-20260818
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  resources:
    requests:
      storage: 100Gi    # Can be equal to or larger than original snapshot size!
```

## Direct PVC-to-PVC Volume Cloning

Kubernetes also supports **Volume Cloning** without requiring an intermediate `VolumeSnapshot` object. This is natively supported by cloud CSI drivers:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: instant-clone-pvc
  namespace: database
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: ebs-gp3-sc
  # 2. Point dataSource directly to an existing PersistentVolumeClaim!
  dataSource:
    name: production-db-pvc
    kind: PersistentVolumeClaim
  resources:
    requests:
      storage: 100Gi
```

```text
 Volume Cloning Mechanics:
 - The CSI driver provisions a brand-new cloud volume initialized with an exact copy of the source disk.
 - The clone is independent: writes to the clone do not affect the original source volume.
```

## Crash-Consistent vs Application-Consistent Snapshots

```text
 ┌───────────────────────────┬─────────────────────────────────┬─────────────────────────────────┐
 │ Feature                   │ Crash-Consistent Snapshot       │ Application-Consistent Snapshot │
 │───────────────────────────┼─────────────────────────────────┼─────────────────────────────────┤
 │ **Capture Method**        │ Snapshot triggered immediately  │ Database paused (`fsync`/lock), │
 │                           │ while app is actively writing.  │ snapshot taken, database resumed│
 │ **In-Memory Buffers**     │ Dirty pages in RAM are NOT saved│ In-memory write buffers FLUSHED │
 │                           │ to the snapshot!                │ cleanly to disk before snapshot.│
 │ **Recovery Process**      │ Database runs crash recovery &  │ Database starts instantly with  │
 │                           │ WAL log replay on boot.         │ zero crash recovery needed.     │
 │ **Tooling Required**      │ Standard CSI Snapshotter        │ Pre/Post Snapshot Hooks (Velero)│
 └───────────────────────────┴─────────────────────────────────┴─────────────────────────────────┘
```

## Complete Production Snapshot & Class Manifests

```yaml
# 1. Cluster-Scoped VolumeSnapshotClass
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: aws-ebs-snapclass
driver: ebs.csi.aws.com
deletionPolicy: Delete
parameters:
  tagSpecification_1: "Department=Engineering"
---
# 2. Point-in-Time VolumeSnapshot Request
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: daily-db-snapshot
  namespace: database
spec:
  volumeSnapshotClassName: aws-ebs-snapclass
  source:
    persistentVolumeClaimName: production-postgres-pvc
```

## Hands-On Lab: Taking a Snapshot & Restoring a Cloned PVC

```bash
# Step 1: Create lab namespace
kubectl create namespace snapshot-lab

# Step 2: Verify VolumeSnapshot CRDs are installed in cluster
kubectl get crd | grep snapshot.storage.k8s.io || echo "Install external snapshotter CRDs if missing"

# Step 3: Create a mock VolumeSnapshotClass
cat <<EOF | kubectl apply -f -
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: lab-snapclass
driver: hostpath.csi.k8s.io    # Or ebs.csi.aws.com in cloud
deletionPolicy: Delete
EOF

# Step 4: Create a source PVC and populate with test data
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: source-data-pvc
  namespace: snapshot-lab
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: data-writer-pod
  namespace: snapshot-lab
spec:
  volumes:
  - name: storage
    persistentVolumeClaim:
      claimName: source-data-pvc
  containers:
  - name: writer
    image: alpine:latest
    command: ["sh", "-c", "echo 'CRITICAL DATABASE TRANSACTION 2026' > /data/backup.txt; sleep 3600"]
    volumeMounts:
    - name: storage
      mountPath: /data
EOF

# Step 5: Wait for Pod to become Ready and data to be written
kubectl wait --for=condition=Ready pod/data-writer-pod -n snapshot-lab --timeout=30s

# Step 6: Trigger a VolumeSnapshot
cat <<EOF | kubectl apply -f -
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: lab-backup-snap
  namespace: snapshot-lab
spec:
  volumeSnapshotClassName: lab-snapclass
  source:
    persistentVolumeClaimName: source-data-pvc
EOF

# Step 7: Inspect VolumeSnapshot and VolumeSnapshotContent status
sleep 3
kubectl get volumesnapshot -n snapshot-lab
kubectl get volumesnapshotcontent

# Step 8: Clean up lab
kubectl delete namespace snapshot-lab
kubectl delete volumesnapshotclass lab-snapclass
```

## Common Interview Questions

**Q1: What are the three Custom Resource Definitions (CRDs) that comprise the Kubernetes Snapshot API?**

The three Snapshot CRDs are:
1. `VolumeSnapshotClass` (Cluster-Scoped): Defines the CSI storage driver, parameters, and deletion policy (`Delete` or `Retain`) for snapshots.
2. `VolumeSnapshot` (Namespace-Scoped): A user request pointing to a specific source `PersistentVolumeClaim` to capture a point-in-time snapshot.
3. `VolumeSnapshotContent` (Cluster-Scoped): Created automatically by the snapshot controller, representing the actual point-in-time snapshot asset in the cloud (holding `status.snapshotHandle`).

**Q2: How do `snapshot-controller` and the `csi-snapshotter` sidecar collaborate?**

- `snapshot-controller`: A centralized Kubernetes controller that watches `VolumeSnapshot` and `VolumeSnapshotContent` objects, binds them together, and tracks their readiness status.
- `csi-snapshotter`: A sidecar container running inside the vendor's CSI Controller pod. It intercepts `VolumeSnapshot` requests referencing its driver and issues the standard CSI gRPC `CreateSnapshot()` call to the cloud provider API.

**Q3: How do you restore a new PersistentVolumeClaim from a `VolumeSnapshot`?**

To restore a volume: Create a new `PersistentVolumeClaim` manifest and configure `.spec.dataSource` with `kind: VolumeSnapshot`, `apiGroup: snapshot.storage.k8s.io`, and `name: <snapshot-name>`. When submitted, the `csi-provisioner` sidecar instructs the cloud API to create a new storage volume initialized with the data from that snapshot handle.

**Q4: What is the difference between restoring from a `VolumeSnapshot` and direct PVC Volume Cloning?**

- **Restoring from VolumeSnapshot**: Creates a PVC from an existing, immutable snapshot archive; ideal for scheduled backups, disaster recovery, and long-term historical restores.
- **Volume Cloning (`dataSource: kind: PersistentVolumeClaim`)**: Directly duplicates a running source PVC to a new target PVC in one step without generating a snapshot artifact; ideal for instant ephemeral dev/test staging environments.

**Q5: What is the difference between Crash-Consistent and Application-Consistent snapshots?**

- **Crash-Consistent**: A snapshot taken while the application is running without flushing in-memory caches. Upon restore, the database is in the state it would be after an abrupt power loss, requiring WAL log replay and crash recovery.
- **Application-Consistent**: Uses pre-freeze and post-thaw hooks (such as `fsync` and database read locks) to flush all dirty memory buffers to disk before snapshotting, guaranteeing zero transaction loss and immediate clean startup upon restore.
