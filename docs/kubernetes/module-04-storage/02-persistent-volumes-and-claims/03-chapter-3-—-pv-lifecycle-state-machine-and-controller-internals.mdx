# Chapter 3 — PV Lifecycle State Machine & Controller Internals

> **Goal:** Master the internal control loops and state machine governing Kubernetes PersistentVolumes — understanding the 4-phase PV state machine (`Available` $\to$ `Bound` $\to$ `Released` $\to$ `Failed`), tracing the `syncClaim` and `syncVolume` reconciliation loops in `kube-controller-manager`, analyzing bidirectional `claimRef` pointers, and understanding how storage protection finalizers prevent active volume deletion.
>
> By the end of this chapter, you will understand:
> 1. The 4 states of the PersistentVolume lifecycle state machine
> 2. The internal reconciliation logic of `pv-controller` in `kube-controller-manager`
> 3. How bidirectional `claimRef` and `volumeName` pointers lock volume bindings
> 4. How `kubernetes.io/pvc-protection` and `kubernetes.io/pv-protection` finalizers operate
> 5. What triggers a PV to enter the `Failed` state and how to recover it
> 6. How to troubleshoot stuck `Terminating` PVCs safely in production

## Real-Life Analogy

Think of the PV controller and its state machine as an **automated airport baggage carousel management system**:

- **`Available` (Empty Luggage Cart):** A luggage cart sits parked in the staging rack, ready for anyone with a valid boarding pass.
- **`Bound` (Locked Cart with Luggage Tag):** Passenger #452 checks in a heavy suitcase (PVC created). The automated system assigns Cart #12 (`claimRef`) to Passenger #452 and prints Cart #12 on the passenger's luggage receipt (`volumeName`). The cart is locked to that passenger.
- **`pvc-protection` Finalizer (The Active Conveyor Belt Lock):** Passenger #452 tries to cancel their flight while the suitcase is physically moving inside the airplane cargo hold (Pod running). The system blocks cancellation (`Terminating` state) until the baggage handlers safely remove the suitcase from the airplane.
- **`Released` (Unclaimed Baggage):** The passenger leaves the airport without taking their bag. The cart remains locked in the unclaimed baggage office until an airline manager reviews the tag.
- **`Failed` (Jammed Wheel / Damaged Cart):** The automated cleaning arm tries to sanitize the cart, but a wheel breaks off. The cart flashes a red warning light (`Failed`) and requires a human mechanic to inspect and repair it.

## The 4 PV Lifecycle States

```text
 ┌──────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
 │ Lifecycle State      │ Status Definition & Operational Characteristics                             │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`Available`**      │ A free cluster storage asset. Ready to be matched and bound to any incoming │
 │                      │ qualifying PersistentVolumeClaim.                                           │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`Bound`**          │ The volume is exclusively paired with a specific claim. Locked via          │
 │                      │ bidirectional `claimRef` and `volumeName` metadata.                         │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`Released`**       │ The bound PVC has been deleted, but the physical storage has not yet been   │
 │                      │ reclaimed by the cluster (`persistentVolumeReclaimPolicy: Retain`).         │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **`Failed`**         │ The automated background volume deletion or scrubbing routine failed (e.g.  │
 │                      │ cloud API timeout or disk detach error). Requires admin intervention.       │
 │──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## The `pv-controller` Reconciliation Internals

The `pv-controller` running inside `kube-controller-manager` operates two synchronized control loops:

```text
 ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────┐
 │ Control Loop                 │ Core Responsibility                                                 │
 │──────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
 │ **1. `syncClaim` Loop**      │ - Watches PersistentVolumeClaim events.                             │
 │                              │ - If PVC is `Unbound`: Finds matching `Available` PV and binds it.  │
 │                              │ - If no matching PV: Triggers dynamic provisioning via StorageClass.│
 │──────────────────────────────┼─────────────────────────────────────────────────────────────────────┤
 │ **2. `syncVolume` Loop**     │ - Watches PersistentVolume events.                                  │
 │                              │ - If PV is `Bound`: Checks if referenced PVC still exists in etcd.  │
 │                              │ - If PVC was deleted: Executes `persistentVolumeReclaimPolicy`.     │
 └──────────────────────────────┴─────────────────────────────────────────────────────────────────────┘
```

## Bidirectional `claimRef` Pointer Locking

Binding is locked by writing mutual cross-references:

```yaml
# 1. On the PersistentVolume:
spec:
  claimRef:
    apiVersion: v1
    kind: PersistentVolumeClaim
    name: database-pvc
    namespace: production
    uid: a9b4c2e1-4567-89ab-cdef-0123456789ab
---
# 2. On the PersistentVolumeClaim:
spec:
  volumeName: pv-ebs-production-01
```

> [!IMPORTANT]
> The presence of the **`uid`** inside `claimRef` is critical. If a user deletes `database-pvc` and immediately creates a new PVC with the *exact same name* (`database-pvc`), the PV will **not** accidentally bind to the new claim because the new PVC has a different `uid`!

## Storage Protection Finalizers

To prevent accidental data corruption, Kubernetes injects storage protection finalizers:

```text
 ┌──────────────────────────────────────┬─────────────────────────────────────────────────────────────┐
 │ Finalizer Key                        │ Protection Mechanism                                        │
 │──────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
 │ **`kubernetes.io/pvc-protection`**   │ Attached to every active PVC. If a user runs `kubectl delete│
 │                                      │ pvc`, the PVC enters `Terminating` but is NOT deleted as    │
 │                                      │ long as an active Pod is mounting the volume.               │
 │──────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
 │ **`kubernetes.io/pv-protection`**    │ Attached to every active PV. Prevents deleting a PV while it│
 │                                      │ is currently bound to an active claim.                      │
 └──────────────────────────────────────┴─────────────────────────────────────────────────────────────┘
```

```text
 The Zero-Data-Loss Termination Flow:
 1. User runs: `kubectl delete pvc db-storage-pvc`
 2. API Server adds `metadata.deletionTimestamp` (Status: Terminating).
 3. `pvc-protection` finalizer BLOCKS deletion because `Pod: postgres-0` is running.
 4. Once `postgres-0` is terminated, Kubelet unmounts volume and releases hold.
 5. `pvc-protection` finalizer is removed, and the PVC is safely deleted from etcd.
```

## Troubleshooting `Failed` PersistentVolumes

A PV enters the `Failed` state when automated deletion fails (e.g., cloud credentials expired or disk is locked by another AWS EC2 instance).

```text
 Administrator Recovery Protocol for Failed PVs:

 1. Inspect Controller Logs:
    `kubectl describe pv <pv-name>` -> Check Message and Reason fields.

 2. Manually Resolve Cloud Lock:
    Log into AWS / GCP / Azure Console and detach the volume from any stale VM instances.

 3. Reset PV Status:
    Edit the PV status subresource or recreate the PV manifest with status: Available.
```

## Hands-On Lab: Observing Storage Protection Finalizers

```bash
# Step 1: Create lab namespace
kubectl create namespace finalizer-storage-lab

# Step 2: Create a local PV and matching PVC
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: PersistentVolume
metadata:
  name: protected-pv
spec:
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  storageClassName: manual-protected
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /tmp/protected-data
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: protected-pvc
  namespace: finalizer-storage-lab
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: manual-protected
  resources:
    requests:
      storage: 500Mi
EOF

# Step 3: Launch a Pod actively consuming the PVC
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: active-pod
  namespace: finalizer-storage-lab
spec:
  volumes:
  - name: storage
    persistentVolumeClaim:
      claimName: protected-pvc
  containers:
  - name: app
    image: alpine:latest
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: storage
      mountPath: /mnt/data
EOF

# Step 4: Wait for Pod to enter Running state
kubectl wait --for=condition=Ready pod/active-pod -n finalizer-storage-lab --timeout=30s

# Step 5: Attempt to delete the PVC while the Pod is actively running
kubectl delete pvc protected-pvc -n finalizer-storage-lab --wait=false

# Step 6: Observe that the PVC is stuck in "Terminating" (Protected by finalizer!)
kubectl get pvc -n finalizer-storage-lab
# Notice: STATUS is Terminating, but data is NOT deleted!

# Step 7: Delete the Pod to release the volume mount
kubectl delete pod active-pod -n finalizer-storage-lab

# Step 8: Observe the PVC is now automatically and safely deleted!
sleep 2
kubectl get pvc -n finalizer-storage-lab

# Step 9: Clean up lab
kubectl delete namespace finalizer-storage-lab
kubectl delete pv protected-pv
```

## Common Interview Questions

**Q1: What are the four states of the PersistentVolume lifecycle state machine?**

The four states are:
1. `Available`: A free, healthy volume that is ready to be bound to any matching claim.
2. `Bound`: The volume is exclusively locked and attached to a specific PersistentVolumeClaim.
3. `Released`: The bound PVC was deleted, but the physical storage has not yet been scrubbed or re-allocated (`persistentVolumeReclaimPolicy: Retain`).
4. `Failed`: The automated volume reclamation or deletion process encountered an error, requiring administrator intervention.

**Q2: What is the purpose of `kubernetes.io/pvc-protection`, and what happens if you delete an in-use PVC?**

`kubernetes.io/pvc-protection` is a built-in finalizer attached to every active PVC. When an operator runs `kubectl delete pvc <name>` on a PVC that is actively mounted by a running Pod, the API server sets `metadata.deletionTimestamp` and marks the PVC status as `Terminating`. However, the finalizer **blocks deletion from `etcd`** until all referencing Pods are terminated and Kubelet cleanly unmounts the volume, preventing in-flight data corruption.

**Q3: Why does `claimRef` on a PersistentVolume contain both the name and the `uid` of the claim?**

Storing the unique UUID (`uid`) in addition to the name ensures cryptographic binding identity. If a claim named `mysql-pvc` is deleted and an attacker or automated script immediately recreates a new claim with the identical name `mysql-pvc`, the new claim will have a different `uid`. The `pv-controller` verifies the `uid` and refuses to bind the existing PV to the new claim, preventing unauthorized access to sensitive leftover database data.

**Q4: How do the `syncClaim` and `syncVolume` loops collaborate in the `pv-controller`?**

`syncClaim` and `syncVolume` operate concurrently inside `kube-controller-manager`:
- `syncClaim` watches for new or modified PVCs, searches the in-memory cache for available matching PVs, establishes bindings, or triggers dynamic provisioning if a StorageClass is referenced.
- `syncVolume` watches PVs, verifies whether bound PVCs are still active, and triggers the configured reclaim policy (`Retain` or `Delete`) when a bound PVC disappears from `etcd`.

**Q5: How can an administrator recover a PersistentVolume that has entered the `Failed` status?**

A PV enters `Failed` status when automated cloud deletion or volume cleanup fails. To recover it: (1) Run `kubectl describe pv <name>` to inspect controller error messages; (2) Fix the underlying cloud storage state (e.g. manually detach the EBS volume or unlock cloud API permissions); (3) Manually clear any corrupted metadata or recreate the PV manifest in the `Available` state to restore it to the cluster's usable capacity pool.
