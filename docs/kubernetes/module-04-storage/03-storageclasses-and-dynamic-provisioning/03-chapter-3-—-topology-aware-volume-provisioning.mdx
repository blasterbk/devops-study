# Chapter 3 — Topology-Aware Volume Provisioning

> **Goal:** Master topology-aware volume provisioning and local storage architectures in Kubernetes — understanding how `allowedTopologies` constrains dynamic provisioning to specific availability zones or on-premise racks, how Local Persistent Volumes (Local PVs) provide ultra-low-latency NVMe performance while preserving scheduler awareness, and how to balance multi-zone cloud egress costs.
>
> By the end of this chapter, you will understand:
> 1. How `allowedTopologies` in a `StorageClass` restricts volume placement to specific zones
> 2. How the CSI external-provisioner evaluates zone match expressions
> 3. The structural difference between insecure `hostPath` mounts and scheduler-aware Local Persistent Volumes
> 4. Why distributed databases (Cassandra, Elasticsearch, Kafka, ScyllaDB) prefer Local PVs over cloud SANs
> 5. How node hardware failures impact Local Persistent Volumes and data recovery patterns
> 6. How to combine Topology-Aware Storage with Pod Anti-Affinity

## Real-Life Analogy

Think of topology-aware storage as **booking hotel rooms and renting storage lockers in specific neighborhood branches**:

- **Unrestricted Cloud Storage (Random Locker):** You rent a locker in a citywide storage franchise (`StorageClass`). The franchise gives you a locker in **District East**, but your office is in **District West**. Every time your staff needs a file, they must drive across town through heavy traffic, paying bridge tolls (**Cross-AZ Data Transfer Fees & Network Latency**).
- **`allowedTopologies` (Restricted District Booking):** You specify in your corporate policy: *"Only rent storage lockers located in District North or District West (`allowedTopologies: [us-east-1a, us-east-1b]`)."* The automated system will never provision a locker in District South.
- **Local Persistent Volume (A Heavy Safe Bolted to the Floor of Room 204):** Instead of an off-site locker, you install a 500-pound steel safe physically bolted inside Room 204 (`Local PV`). Access is instantaneous (Direct NVMe speed / zero network hop). However, if Room 204 catches fire (hardware crash), you cannot wheel the safe to Room 205; you must rely on your backup safe in a different building (Database-level application replication).

## Restricting Provisioning with `allowedTopologies`

By default, a dynamic `StorageClass` will provision volumes across any zone where worker nodes exist.

To restrict volume creation to specific Availability Zones (e.g. to isolate workloads to cheaper zones, avoid high cross-AZ latency, or comply with regional data sovereignty):

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: restricted-zone-sc
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true

# Restrict provisioning strictly to us-east-1a and us-east-1b
allowedTopologies:
- matchLabelExpressions:
  - key: topology.kubernetes.io/zone
    values:
    - us-east-1a
    - us-east-1b
```

```text
 Evaluation Rules for allowedTopologies:
 1. Multiple `allowedTopologies` list items are evaluated with OR logic.
 2. Multiple `matchLabelExpressions` within the same item are evaluated with AND logic.
 3. If a Pod is scheduled onto a node in `us-east-1c`, the CSI provisioner will REJECT volume 
    creation, and the scheduler will rebalance the Pod to an allowed zone.
```

## Local Persistent Volumes (Local PVs) vs `hostPath`

A **Local Persistent Volume** represents a dedicated local disk (e.g. direct-attached PCIe NVMe SSD) mounted directly on a single worker node.

```text
 ┌───────────────────────────┬─────────────────────────────────┬─────────────────────────────────┐
 │ Dimension                 │ `hostPath` Volume               │ Local Persistent Volume (PV)    │
 │───────────────────────────┼─────────────────────────────────┼─────────────────────────────────┤
 │ **Scheduler Awareness**   │ NONE. Scheduler does not know   │ **FULL.** PV declares mandatory │
 │                           │ if host directory exists.       │ `nodeAffinity` to specific node.│
 │ **Portability Safety**    │ If Pod reschedules to Node B,   │ Scheduler GUARANTEES Pod will   │
 │                           │ it mounts an empty new dir!     │ ONLY schedule on the same node. │
 │ **Quota & Capacity**      │ No capacity tracking            │ Managed via standard PVC quota  │
 │ **Security**              │ Critical breakout risk          │ Secure & isolated mount point   │
 └───────────────────────────┴─────────────────────────────────┴─────────────────────────────────┘
```

## Local PV Node Affinity Contract

Every Local PersistentVolume **must** declare `.spec.nodeAffinity` defining the exact host node where the physical disk resides:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: local-nvme-pv-01
spec:
  capacity:
    storage: 500Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: local-nvme
  local:
    path: /mnt/disks/nvme0n1       # Physical mount path on node OS

  # The Scheduler Contract: Pods using this PV CAN ONLY schedule on worker-01!
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values:
          - worker-01
```

## High-Performance Database Architecture: Why Local PVs?

For high-throughput distributed databases (Cassandra, ScyllaDB, Elasticsearch, Kafka, ClickHouse):

```text
 Network Cloud Disk (EBS/PD) vs Local NVMe SSD:
 - Cloud Block Storage (EBS gp3): ~1-3ms latency, capped at 16,000 IOPS, network shared.
 - Local Direct PCIe NVMe: ~10-50 microseconds latency, 500,000+ IOPS, dedicated hardware!
```

### The Trade-Off & Failure Domain Strategy:
- **The Risk:** If `worker-01` has a motherboard failure, the local NVMe disk goes offline with it.
- **The Solution:** The database handles replication at the application layer across 3 separate nodes across 3 separate zones! If Node 1 dies, Cassandra or Kafka serves data from Node 2 and Node 3 while a replacement Pod bootstraps on a new node.

## Complete Production Topology-Aware Manifest

```yaml
# 1. StorageClass for Local NVMe Storage
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-local-nvme
provisioner: kubernetes.io/no-provisioner    # Local PVs do not use dynamic CSI
volumeBindingMode: WaitForFirstConsumer      # Mandatory for Local PV!
reclaimPolicy: Retain
---
# 2. Local Persistent Volume on Worker Node 1
apiVersion: v1
kind: PersistentVolume
metadata:
  name: cassandra-data-pv-0
spec:
  capacity:
    storage: 1Ti
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-local-nvme
  local:
    path: /mnt/fast-storage/disk0
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values: ["node-us-east-1a-01"]
---
# 3. PVC Claiming the Local NVMe Storage
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: cassandra-storage-claim
  namespace: database
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-local-nvme
  resources:
    requests:
      storage: 1Ti
```

## Hands-On Lab: Deploying a Local Persistent Volume with Node Affinity

```bash
# Step 1: Create lab namespace
kubectl create namespace topology-lab

# Step 2: Identify a worker node to host local storage
LOCAL_NODE=$(kubectl get nodes --no-headers | head -n 1 | awk '{print $1}')
echo "Binding local storage to node: $LOCAL_NODE"

# Step 3: Create Local StorageClass and PersistentVolume
cat <<EOF | kubectl apply -f -
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: lab-local-sc
provisioner: kubernetes.io/no-provisioner
volumeBindingMode: WaitForFirstConsumer
---
apiVersion: v1
kind: PersistentVolume
metadata:
  name: lab-nvme-pv
spec:
  capacity:
    storage: 2Gi
  accessModes:
    - ReadWriteOnce
  storageClassName: lab-local-sc
  persistentVolumeReclaimPolicy: Retain
  local:
    path: /tmp/nvme-disk
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values: ["$LOCAL_NODE"]
EOF

# Step 4: Create a PVC requesting the local storage
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: local-pvc
  namespace: topology-lab
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: lab-local-sc
  resources:
    requests:
      storage: 1Gi
EOF

# Step 5: Deploy a Pod consuming the Local PVC
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: local-db-pod
  namespace: topology-lab
spec:
  volumes:
  - name: db-data
    persistentVolumeClaim:
      claimName: local-pvc
  containers:
  - name: engine
    image: alpine:latest
    command: ["sh", "-c", "echo 'High IOPS Transaction Log' > /data/tx.log; sleep 3600"]
    volumeMounts:
    - name: db-data
      mountPath: /data
EOF

# Step 6: Verify the scheduler placed the Pod on the EXACT node defined in nodeAffinity!
sleep 3
SCHEDULED_NODE=$(kubectl get pod local-db-pod -n topology-lab -o jsonpath='{.spec.nodeName}')
echo "Pod placed on: $SCHEDULED_NODE (Target was: $LOCAL_NODE)"
if [ "$SCHEDULED_NODE" = "$LOCAL_NODE" ]; then echo "SUCCESS: Scheduler strictly respected Local PV nodeAffinity!"; fi

# Step 7: Clean up lab
kubectl delete namespace topology-lab
kubectl delete pv lab-nvme-pv
kubectl delete storageclass lab-local-sc
```

## Common Interview Questions

**Q1: What is `allowedTopologies` in a StorageClass, and when should it be used?**

`allowedTopologies` restricts dynamic volume provisioning to a specific subset of failure domains (such as cloud Availability Zones or on-premise racks). It is used when: (1) Storage assets should only be created in specific zones to optimize compute costs or latency; (2) Certain zones lack physical storage hardware (e.g. bare-metal SAN attachments); or (3) Complying with regulatory data residency requirements that mandate data remain in specific geographical regions.

**Q2: How does a Local Persistent Volume (Local PV) differ from a `hostPath` volume?**

While both mount directories from the local node OS, a `hostPath` volume has **zero scheduler awareness**; if a Pod is rescheduled, the scheduler may place it on a different node where the directory is empty, causing data loss. A Local Persistent Volume declares explicit `.spec.nodeAffinity` locking the volume to a specific host. The `kube-scheduler` guarantees that any Pod mounting that Local PV will **only schedule on the exact node** hosting that physical drive.

**Q3: Why do high-performance distributed databases (Cassandra, Kafka, ClickHouse) prefer Local PVs over cloud block storage?**

Cloud block storage (like AWS EBS or Azure Managed Disks) connects over an internal network hypervisor fabric, introducing 1–3 milliseconds of network latency and strict IOPS/throughput throttling caps. Local NVMe SSDs connect directly to the server's PCIe bus, delivering sub-millisecond latencies and hundreds of thousands of IOPS. Because modern distributed databases already manage multi-node replication and fault tolerance at the software layer, they benefit greatly from local raw speed.

**Q4: What happens to a Local PV if its host worker node experiences a permanent hardware failure?**

Because the data resides physically on that specific node's local disk, a permanent node hardware failure results in the Local PV becoming unavailable. The Pod cannot be rescheduled to other nodes because its bound PVC is locked to the dead node via `nodeAffinity`. To recover, the application must handle failover using application-level replication (e.g. promoting another database replica) or delete the PVC to provision a fresh local disk on a new node and backfill data from the cluster.

**Q5: Why must a StorageClass for Local Persistent Volumes use `volumeBindingMode: WaitForFirstConsumer`?**

Local Persistent Volumes are physically bound to one specific node. If `volumeBindingMode: Immediate` were used, the `pv-controller` would bind a developer's PVC to an arbitrary Local PV on Node A immediately upon creation. Later, when the Pod is evaluated, the scheduler might need to place the Pod on Node B due to CPU/memory constraints or pod anti-affinity, resulting in an unresolvable scheduling deadlock.
