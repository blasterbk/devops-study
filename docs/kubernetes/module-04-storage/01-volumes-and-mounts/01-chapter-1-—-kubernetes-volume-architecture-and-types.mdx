# Chapter 1 — Kubernetes Volume Architecture & Types

> 1. The structural difference between ephemeral container writable layers and Kubernetes volumes
> 2. How the Linux kernel's mount namespace (`mntns`) and bind-mounts isolate storage per container

> 4. The 3-phase volume lifecycle: Attach (Controller), Format/Stage (Kubelet), Mount/Publish (CRI)
> 5. The full taxonomy of Kubernetes volume types: Ephemeral, Config, Persistent, and Projected

## Real-Life Analogy

Think of a container and its volumes as a **laptop computer and external USB thumb drives**:

- **Container Writable Layer (The Laptop's Internal Scratch Disk):** When you boot up a fresh laptop, you can download files to the desktop. But this laptop is an ephemeral rental: the moment you turn it off (container crash or restart), the rental company completely wipes the hard drive back to factory settings. Any unsaved business data is lost forever.
- **Kubernetes Volumes (Plug-in External Hard Drives):** To keep your financial database safe, you plug in an external USB hard drive (`spec.volumes`). The files reside safely on the external drive.
- **Decoupled Mount Point (`mountPath: /data`):** On your laptop, the external drive appears as a normal local folder (`/data`). You can unplug the drive from Laptop A and plug it into Laptop B (Pod rescheduling), and all database records are instantly accessible without reformatting.
- **Read-Only Volume (`readOnly: true`):** A read-only SD card with the write-protect switch enabled. Your application can read system configurations or TLS certificates, but malicious code or bugs cannot overwrite the data.

## Container RootFS vs Kubernetes Volumes

Every container running inside a Pod consists of an **OverlayFS** union mount:

```text
 ┌───────────────────────────┬─────────────────────────────────┬─────────────────────────────────┐
 │ Layer Type                │ Persistence & Lifecycle         │ Performance & Use Case          │
 │───────────────────────────┼─────────────────────────────────┼─────────────────────────────────┤
 │ **Image Layer**           │ Immutable & Read-Only. Shared   │ High-speed cached reads.        │
 │ (e.g. `python:3.11-slim`) │ across all containers on node.  │ Contains binaries and runtime.  │
 │───────────────────────────┼─────────────────────────────────┼─────────────────────────────────┤
 │ **Container Writable**    │ Ephemeral. Created on container │ Copy-On-Write (CoW) overhead.   │
 │ **Layer**                 │ boot; WIPED on container exit.  │ Temp scratch files only.        │
 │───────────────────────────┼─────────────────────────────────┼─────────────────────────────────┤
 │ **Kubernetes Volume**     │ Decoupled from container.       │ Direct native I/O (ext4/XFS).   │
 │ (`mountPath: /data`)      │ Survives container crashes.     │ Databases, logs, certificates.  │
 └───────────────────────────┴─────────────────────────────────┴─────────────────────────────────┘
```

### How Mount Namespaces (`mntns`) Isolate Storage
When Kubelet instructs the container runtime (containerd or CRI-O) to spawn a container:
1. It creates a dedicated Linux **mount namespace (`mntns`)** for the container process.
2. It pivots the root filesystem to the container's OverlayFS root.
3. It performs a kernel **bind-mount** (`mount --bind <host-staging-dir> <container-mount-path>`).
4. Any writes inside `/var/data` bypass the container's Copy-On-Write storage driver entirely, writing directly to the underlying block device or network share with zero containerization performance penalty.

## In-Tree Storage Plugins vs Out-of-Tree CSI

Historically, Kubernetes included storage drivers directly inside the core `kubernetes/kubernetes` codebase. This proved unsustainable:

```text
 The Legacy In-Tree Storage Problem:
 - Adding a new vendor storage driver required modifying core Kubernetes source code.
 - A minor bug in an AWS EBS or Ceph storage plugin could crash the entire `kube-controller-manager`!
 - Storage vendors were forced to align release cycles with Kubernetes quarterly releases.
```

### The CSI Solution (Kubernetes 1.13+ / 1.25+ CSIMigration GA):
- Storage drivers were completely extracted out of core Kubernetes into the **Container Storage Interface (CSI)** specification.
- Storage vendors now build and maintain independent container images deployed via Helm or Operators.
- The Kubernetes control plane communicates with CSI plugins via lightweight **gRPC over Unix Domain Sockets** (`/var/lib/kubelet/csi-plugins/.../csi.sock`).

## The 3-Phase Volume Lifecycle

Attaching and mounting storage to a Pod involves three distinct control loops:

```text
               The 3-Phase Volume Lifecycle Timeline

 1. ATTACH (Controller Layer)
    - Managed by: `AttachDetachController` inside `kube-controller-manager`
    - Action: Calls cloud API (e.g. AWS `AttachVolume`) to attach disk to VM instance.
    - Status: Block device appears on host OS (e.g. `/dev/xvdf`).

 2. STAGE / FORMAT (Node Kubelet Layer)
    - Managed by: `VolumeManager` inside `kubelet`
    - Action: Calls CSI `NodeStageVolume`. Formats disk with filesystem (`mkfs.ext4`)
      and mounts to global staging path:
      `/var/lib/kubelet/plugins/kubernetes.io/csi/volume-123/globalmount`

 3. PUBLISH / MOUNT (Container CRI Layer)
    - Managed by: `kubelet` & Container Runtime (containerd)
    - Action: Calls CSI `NodePublishVolume`. Creates container `mntns` bind-mount
      from global staging path into container `/var/data`.
```

## Taxonomy of Kubernetes Volume Types

```text
 ┌──────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
 │ Category             │ Volume Types & Core Characteristics                                         │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **1. Ephemeral**     │ `emptyDir`, `configMap`, `secret`, `downwardAPI`, `projected`.              │
 │                      │ Lifetime is strictly bound to the Pod. Deleted when Pod is deleted.         │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **2. Node-Local**    │ `hostPath`, `local`.                                                        │
 │                      │ Directly mounts files or disks from the host worker node filesystem.        │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **3. Persistent**    │ `persistentVolumeClaim` (backed by AWS EBS, Azure Disk, GCE PD, Ceph RBD).  │
 │                      │ Decoupled from Pod and Node lifecycle; persists indefinitely.               │
 │──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
 │ **4. Network Shared**│ `nfs`, `glusterfs`, `cifs`, AWS EFS, GCP Filestore.                         │
 │                      │ Supports multi-pod concurrent read/write access (`ReadWriteMany`).          │
 └──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## Complete Multi-Volume Pod Manifest

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: multi-volume-enterprise-pod
  namespace: default
  labels:
    app: secure-processor
spec:
  # Volumes declared at Pod level
  volumes:
  # 1. Ephemeral scratch storage
  - name: scratch-space
    emptyDir:
      sizeLimit: 500Mi

  # 2. ConfigMap mounted as directory of files
  - name: app-config
    configMap:
      name: engine-config
      defaultMode: 0644

  # 3. Persistent Volume Claim for database storage
  - name: database-storage
    persistentVolumeClaim:
      claimName: postgres-data-pvc

  containers:
  - name: processing-engine
    image: postgres:15-alpine
    ports:
    - containerPort: 5432

    # Volume mounts inside container filesystem
    volumeMounts:
    # Mounted read-write for active database transactions
    - name: database-storage
      mountPath: /var/lib/postgresql/data

    # Mounted read-only for immutable application configuration
    - name: app-config
      mountPath: /etc/engine/config
      readOnly: true

    # Mounted for temporary scratch calculations
    - name: scratch-space
      mountPath: /tmp/scratch

    resources:
      requests:
        cpu: "250m"
        memory: "512Mi"
      limits:
        cpu: "1000m"
        memory: "1Gi"
```

## Hands-On Lab: Inspecting Linux Mount Namespaces & Storage Decoupling

```bash
# Step 1: Create lab namespace
kubectl create namespace volume-lab

# Step 2: Deploy a Pod with both ephemeral emptyDir and ConfigMap volumes
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: lab-config
  namespace: volume-lab
data:
  app.properties: |
    environment=production
    log_level=debug
---
apiVersion: v1
kind: Pod
metadata:
  name: storage-inspector
  namespace: volume-lab
spec:
  volumes:
  - name: scratch-vol
    emptyDir: {}
  - name: config-vol
    configMap:
      name: lab-config
  containers:
  - name: inspector
    image: alpine:latest
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: scratch-vol
      mountPath: /mnt/scratch
    - name: config-vol
      mountPath: /mnt/config
      readOnly: true
EOF

# Step 3: Wait for Pod to enter Running state
kubectl wait --for=condition=Ready pod/storage-inspector -n volume-lab --timeout=30s

# Step 4: Verify volume mounts inside the container namespace
kubectl exec -n volume-lab storage-inspector -- mount | grep /mnt

# Step 5: Write data to the scratch volume
kubectl exec -n volume-lab storage-inspector -- sh -c "echo 'Persisted in emptyDir' > /mnt/scratch/data.txt"
kubectl exec -n volume-lab storage-inspector -- cat /mnt/scratch/data.txt

# Step 6: Test Read-Only enforcement on ConfigMap volume
kubectl exec -n volume-lab storage-inspector -- sh -c "echo 'corrupt' > /mnt/config/app.properties" 2>&1 || echo "SUCCESS: Read-only filesystem prevented unauthorized write!"

# Step 7: Inspect container rootfs isolation (Writing outside volume is ephemeral)
kubectl exec -n volume-lab storage-inspector -- sh -c "echo 'temp' > /tmp/rootfs_file.txt"

# Step 8: Clean up lab
kubectl delete namespace volume-lab
```

## Common Interview Questions

**Q1: What is the fundamental difference between a container's root filesystem and a Kubernetes volume?**

A container's root filesystem is an ephemeral OverlayFS layer backed by the container runtime's Copy-On-Write (CoW) storage driver; any files written directly to rootfs are permanently destroyed when the container process terminates or restarts. A Kubernetes volume is an independent storage abstraction mounted into the container's Linux mount namespace (`mntns`) via kernel bind-mounts; its lifecycle is decoupled from container restarts, allowing data to persist across application crashes and updates.

**Q2: What is the Container Storage Interface (CSI), and why did Kubernetes migrate away from in-tree volume plugins?**

The Container Storage Interface (CSI) is an industry-standard specification allowing storage vendors to develop out-of-tree storage plugins that work seamlessly across container orchestrators. In-tree volume drivers were embedded directly inside the `kubernetes/kubernetes` binary repository. This created severe maintenance problems: storage bugs could crash control-plane components, security vulnerabilities required full Kubernetes cluster upgrades to patch, and third-party vendors were constrained by Kubernetes core release cycles.

**Q3: What are the three phases of mounting a block storage volume in Kubernetes?**

The three phases are:
1. **Attach (`ControllerPublishVolume`):** The `AttachDetachController` in `kube-controller-manager` calls the cloud provider API to attach the virtual disk to the target worker node VM.
2. **Stage (`NodeStageVolume`):** The `kubelet` on the node formats the raw block device with a filesystem (e.g. ext4 or XFS) and mounts it to a global host directory.
3. **Publish (`NodePublishVolume`):** The `kubelet` and container runtime bind-mount the global directory into the container's private mount namespace at the declared `mountPath`.

**Q4: How does `readOnly: true` protect volume mounts in a Pod?**

When `readOnly: true` is specified in `volumeMounts`, Kubelet passes the `MS_RDONLY` flag to the Linux kernel `mount()` syscall during the bind-mount operation. The kernel enforces read-only access at the Virtual File System (VFS) layer. Any write attempt by container processes returns `Read-only file system` (`EROFS`), protecting sensitive configuration files, TLS certificates, and secrets from accidental mutation or tampering.

**Q5: What happens if two containers in the same Pod mount the same volume?**

Storage volumes are declared at the Pod level (`spec.volumes`) and can be mounted simultaneously by multiple containers in that Pod. Both containers share the same underlying storage namespace and can read and write to the same files in real time. This is the foundation of the Sidecar pattern (e.g. a main web application writing logs to a shared `emptyDir` volume while a Fluent Bit sidecar container tails and ships those logs).
