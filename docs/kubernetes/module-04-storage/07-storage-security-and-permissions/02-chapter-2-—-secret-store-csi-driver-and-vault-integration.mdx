# Chapter 2 — Secret Store CSI Driver & Vault Integration

> **Goal:** Master external secrets management in Kubernetes using the Secrets Store CSI Driver — understanding how `SecretProviderClass` Custom Resources retrieve credentials from HashiCorp Vault, AWS Secrets Manager, and Azure Key Vault, mounting secrets directly into container memory (`tmpfs`) without persisting plaintext credentials in `etcd`, configuring live secret auto-rotation, and synchronizing external credentials into native Kubernetes Secret objects.
>
> By the end of this chapter, you will understand:
> 1. The security vulnerabilities of native Kubernetes Secrets (plain base64 in `etcd`)
> 2. How the Secrets Store CSI Driver fetches secrets at Pod boot via CSI Ephemeral Inline Volumes
> 3. How to configure `SecretProviderClass` for HashiCorp Vault and AWS Secrets Manager
> 4. How live secret auto-rotation refreshes credentials on disk without restarting Pods
> 5. How `secretObjects` synchronizes external credentials into native Kubernetes `Secret` resources
> 6. How to troubleshoot IAM authentication failures between CSI drivers and cloud vaults

## Real-Life Analogy

Think of the Secrets Store CSI Driver as a **biometric pneumatic dispatch tube connecting directly to a Swiss bank vault**:

- **Native Kubernetes Secrets (Sticky Notes in the Office Drawer):** Storing database passwords in native Kubernetes Secrets is like writing your credit card PIN on a sticky note and storing it in the office drawer (`etcd`). Even if the note is encoded in base64, anyone who opens the drawer can read the PIN in 1 second.
- **The Swiss Bank Vault (HashiCorp Vault / AWS Secrets Manager):** An external, enterprise-grade vault protected by encryption hardware (HSM), automated password rotation, and detailed audit trails.
- **Secrets Store CSI Driver (The Pneumatic Tube):** When an employee (Pod) sits down at their desk, the system authenticates the employee's ID badge (Kubernetes ServiceAccount). The vault opens a pneumatic tube (`CSI Inline Volume`) and drops the temporary key directly onto the employee's desk in **temporary RAM (`tmpfs`)**.
- **The Automatic Key Shredder (Zero Disk Persistence):** The password is never written to the building's physical hard drives or etcd. When the employee leaves for the day (Pod deleted), the key vanishes into thin air.
- **Auto-Rotation (The 30-Minute Key Refresh):** Every 30 minutes, the bank automatically shoots a brand-new key down the tube, replacing the old key on the desk without making the employee leave their seat.

## The `SecretProviderClass` Custom Resource

The `SecretProviderClass` defines where the secrets reside and which cloud provider plugin to invoke:

```yaml
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: vault-db-credentials
  namespace: production
spec:
  provider: vault
  parameters:
    vaultAddress: "https://vault.internal.company.com:8200"
    roleName: "payments-app-role"
    objects: |
      - objectName: "db-password"
        secretPath: "secret/data/production/database"
        secretKey: "password"
      - objectName: "api-key"
        secretPath: "secret/data/production/stripe"
        secretKey: "token"
```

## Mounting External Secrets in a Pod

Pods consume the `SecretProviderClass` via a **CSI Ephemeral Inline Volume**:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-processor
  namespace: production
spec:
  replicas: 2
  selector:
    matchLabels:
      app: payment-processor
  template:
    metadata:
      labels:
        app: payment-processor
    spec:
      serviceAccountName: payments-sa    # IAM / Vault Role Authenticator
      containers:
      - name: app
        image: payment-service:v2.1
        volumeMounts:
        - name: vault-secrets-mount
          mountPath: /etc/secrets
          readOnly: true

      volumes:
      - name: vault-secrets-mount
        csi:
          driver: secrets-store.csi.k8s.io
          readOnly: true
          volumeAttributes:
            secretProviderClass: vault-db-credentials
```

## Live Auto-Rotation & Syncing as Kubernetes Secrets

### 1. Live Secret Auto-Rotation:
When the driver is installed with `--enable-secret-rotation=true`, the CSI driver periodically polls the external vault (default: every 2 minutes). When a secret changes in HashiCorp Vault or AWS, the driver updates the file at `/etc/secrets/db-password` in-place inside the running container!

### 2. Syncing to Kubernetes Secret Objects (`secretObjects`):
If your application requires secrets to be injected as **Environment Variables** (`env.valueFrom.secretKeyRef`), the driver can create a synchronized native Secret:

```yaml
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: aws-secrets-sync
spec:
  provider: aws
  secretObjects:
  # Creates a native K8s Secret synchronized with external vault!
  - secretName: synced-database-secret
    type: Opaque
    data:
    - objectName: "db-password"
      key: DB_PASSWORD
```

## Common Interview Questions

**Q1: What is the Secrets Store CSI Driver, and why is it preferred over native Kubernetes Secrets?**

The Secrets Store CSI Driver is a CNCF subproject that allows Kubernetes to mount secrets, keys, and certificates from enterprise external secret stores (such as HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, and GCP Secret Manager) directly into Pods as files. It is preferred because: (1) Secrets are **never persisted as plaintext base64 in `etcd`**; (2) Secrets reside only in volatile container memory (`tmpfs`); and (3) It centralizes audit logging and lifecycle rotation in enterprise security vaults.

**Q2: What is the role of the `SecretProviderClass` Custom Resource?**

`SecretProviderClass` is a namespace-scoped CRD that acts as the configuration blueprint for external secret retrieval. It specifies: (1) The cloud/vault provider plugin (`vault`, `aws`, `azure`, `gcp`); (2) The external vault endpoint URL and authentication role; (3) The exact paths and keys of the secrets to fetch; and (4) Optional `secretObjects` mappings to synchronize external secrets into native Kubernetes Secret objects.

**Q3: How does Secret Auto-Rotation work in the Secrets Store CSI Driver?**

When the driver is launched with `--enable-secret-rotation=true`, the CSI Node DaemonSet runs a background polling reconciler (by default, every 120 seconds). It queries the external vault for the latest secret version. If a key has been rotated in HashiCorp Vault or AWS, the CSI driver automatically rewrites the mounted file inside the container's `tmpfs` filesystem in-place, allowing applications supporting hot-reload to adopt new credentials without container restarts.

**Q4: Can secrets retrieved by the Secrets Store CSI Driver be consumed as container environment variables?**

Yes, but with one caveat: The driver mounts secrets as files by default. To consume them as environment variables, the `SecretProviderClass` must define `.spec.secretObjects`. Crucially, because the CSI driver runs at Pod mount time, the Pod **must mount the CSI volume** first; once mounted, the CSI driver automatically creates the synchronized Kubernetes `Secret` object in `etcd`, which other containers can reference via `env.valueFrom.secretKeyRef`.

**Q5: How does the Secrets Store CSI Driver authenticate to cloud secret managers without hardcoding passwords?**

The driver authenticates using modern **Workload Identity Federation**:
- On AWS: Uses **IAM Roles for Service Accounts (IRSA)** via Projected Bound ServiceAccount Tokens.
- On Azure: Uses **Azure Workload Identity**.
- On GCP: Uses **GKE Workload Identity**.
- On HashiCorp Vault: Uses the **Vault Kubernetes Authentication Method**, which verifies the Pod's local JWT token with the Kubernetes TokenReview API.
